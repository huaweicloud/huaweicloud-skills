# Lifecycle Rule JSON Format

The obsutil `lifecycle` command reads and writes a JSON document that mirrors the OBS `GET/PUT /{bucket}?lifecycle` REST payload. This file documents the schema, worked examples, and best-practice
guidance used by the analyzer script.

## Schema

```json
{
  "Rules": [
    {
      "ID": "string",
      "Prefix": "string",
      "Status": "Enabled | Disabled",
      "Transitions": [
        {
          "Date": "RFC3339 date",
          "Days": "integer (days after last modified)",
          "StorageClass": "WARM | COLD | DEEP_ARCHIVE"
        }
      ],
      "Expiration": {
        "Date": "RFC3339 date",
        "Days": "integer (days after last modified)",
        "ExpiredObjectDeleteMarker": "true | false | ''"
      },
      "NoncurrentVersionTransitions": [
        {
          "NoncurrentDays": "integer",
          "StorageClass": "WARM | COLD | DEEP_ARCHIVE"
        }
      ],
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": "integer"
      },
      "AbortIncompleteMultipartUpload": {
        "DaysAfterInitiation": "integer"
      },
      "Filter": {
        "Prefix": "string",
        "Tags": [
          {"Key": "string", "Value": "string"}
        ]
      }
    }
  ]
}
```

### Field semantics

| Field | Meaning | Notes |
|-------|---------|-------|
| `ID` | Unique rule identifier | 1-255 chars; must be unique within the bucket |
| `Prefix` | Object key prefix the rule applies to | Empty string = whole bucket. Deprecated in favor of `Filter.Prefix` but still honored. **Echo quirk:** `obsutil lifecycle -method=get` returns BOTH rule-level `Prefix` (authoritative, e.g. `data/`) and `Filter.Prefix` which may be an empty string `""` even when a prefix is configured — treat an empty `Filter.Prefix` as "no filter prefix", never as "prefix is empty" |
| `Status` | Rule toggle | `Enabled` — active; `Disabled` — configured but inactive |
| `Transitions` | Storage-class transition actions | `WARM` = Infrequent Access, `COLD` = Archive, `DEEP_ARCHIVE` = Deep Archive |
| `Expiration` | Delete (expire) objects | `Days` = days after last modification; or fixed `Date` |
| `NoncurrentVersionExpiration` | Expire non-current versions | Requires bucket versioning enabled |
| `AbortIncompleteMultipartUpload` | Abort incomplete multipart uploads | `DaysAfterInitiation` = days after upload start |
| `Filter` | Prefix + tag filters (newer style) | `Tags` can only be used when `Filter.Prefix` is also present |

### Constraints (API-enforced)

1. **One action per rule type allowed** — a rule may contain at most one `Expiration`, one `Transition` per storage class, etc. Use multiple rules instead.
2. **Prefix + Tags**: a tag filter requires `Filter.Prefix` (may be empty string `""`).
3. **At least one action** — a rule must contain at least one of `Transitions`/`Expiration`/`NoncurrentVersion*`/`AbortIncompleteMultipartUpload`.
4. **PUT replaces the whole config** — obsutil `-method=put` overwrites the bucket's entire lifecycle configuration. Always merge with existing rules first.
5. `Date` and `Days` are mutually exclusive within one action; `Date` must be in RFC3339 (e.g. `2026-12-31T00:00:00Z`).

## Examples

### 1. Expire logs after 30 days (prefix `logs/`)

```json
{
  "Rules": [
    {
      "ID": "expire-logs-30d",
      "Prefix": "logs/",
      "Status": "Enabled",
      "Expiration": {"Days": 30}
    }
  ]
}
```

### 2. Transition to Archive after 90 days, expire after 365 days (whole bucket)

```json
{
  "Rules": [
    {
      "ID": "archive-90-expire-365",
      "Prefix": "",
      "Status": "Enabled",
      "Transitions": [
        {"Days": 90, "StorageClass": "COLD"}
      ],
      "Expiration": {"Days": 365}
    }
  ]
}
```

### 3. Tag-filtered rule (via Filter; same rule as created by the analyzer `create-rule`)

```json
{
  "Rules": [
    {
      "ID": "tag-rule",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "",
        "Tags": [{"Key": "env", "Value": "dev"}]
      },
      "Expiration": {"Days": 7}
    }
  ]
}
```

### 4. Noncurrent-version + multipart cleanup (versioned bucket)

```json
{
  "Rules": [
    {
      "ID": "version-cleanup",
      "Prefix": "",
      "Status": "Enabled",
      "NoncurrentVersionExpiration": {"NoncurrentDays": 30},
      "AbortIncompleteMultipartUpload": {"DaysAfterInitiation": 7}
    }
  ]
}
```

## Console ↔ JSON equivalence

Each lifecycle rule in the OBS console maps to one object in `Rules[]`:

```
Console: Prefix=logs/, Action=Expire after 30 days, Status=Enabled
   └─> {"ID": "<auto-generated>", "Prefix": "logs/", "Status": "Enabled", "Expiration": {"Days": 30}}
```

```json
{
  "standard": 0.099,
  "warm": 0.06,
  "cold": 0.03,
  "deep_archive": 0.014
}
```

Prices are USD/GB/month approximations for guidance only — actual billing comes from BSS pricing and varies by region. Override with `--price-file /path/to/prices.json` (same keys).

## Best practices

- Start with a **preview (dry-run)** before creating/updating/deleting any rule (`huawei_preview_obs_lifecycle`).
- Use **unique, descriptive rule IDs** (`logs-expire-30d` instead of `rule1`) so diagnosis and updates are traceable.
- Combine transition + expiration in one rule to avoid extra transitions (each transition action incurs a data-retrieval/transition charge).
- For versioned buckets, handle non-current versions explicitly, otherwise old versions accumulate forever.
- Do not create overlapping prefix rules with conflicting actions — the **first matching rule** wins; overlapping rules are a top cause of "lifecycle not working" reports.
