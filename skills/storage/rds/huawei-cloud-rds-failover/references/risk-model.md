# RDS 主备倒换 — 风险模型（阈值业务含义）

本文件描述 `scripts/risk.py` 中 **风险检测 / 风险评估 / 风险预警** 的阈值业务依据。
prepare 阶段自动执行检测与评估。

> 📌 **阈值单一事实来源**：所有阈值的权威定义在 `scripts/risk.py` 的 `THRESH` 常量中。
> 本文件仅描述各阈值的**业务含义与设定依据**，不重复维护阈值数值——调整阈值时只需修改 `risk.py` 的 `THRESH`，
> 本文件的业务依据无需同步更新。如需查看当前阈值数值，请直接阅读 `THRESH` 常量或运行 `python3 -c "from risk import THRESH; import json; print(json.dumps(THRESH, indent=2))"`。

## 四级分级定义

| 等级 | 含义 | 对流程的影响 |
|------|------|-------------|
| 🟢 提示（info） | 正常，无风险信号 | 不产生预警，不阻止 |
| ⚪ 未知（unknown） | 数据缺失（无权限 / 超时 / CES 无数据 / 引擎不支持） | 总体等级升为"中"，提示人工确认；**不自动放行** |
| 🟠 预警（warning） | 存在风险信号，建议处理或确认 | 总体等级升为"中"，控制台/报告预警；不自动阻止 |
| 🔴 严重（critical） | 极可能影响倒换成败或数据安全 | 总体等级升为"阻止"，execute 默认拒绝（需 `--force`） |

**总体等级规则**：任一严重项 → `blocked`（阻止执行）；否则任一预警项或未知项 → `medium`；否则 → `low`。

**数据缺失规则（fail-safe 设计）**：
- **引擎不支持**（如 `ShowReplicationStatus` 对某些引擎不可用）→ 降级为"未知（unknown）"，附说明，不阻止但提示人工确认。
- **无权限 / 超时 / CES 无数据** → 标记为"未知（unknown）"，**不降级为提示**，不自动放行。
  外部数据在边界处视为不可信，缺失不等于安全。未知项会使总体风险升至"中"，需人工确认后再执行。
- **绝不因数据缺失误判为严重**——数据缺失不会被凭空升级为 critical。

## 阈值业务依据

> 以下仅描述各检测项的阈值设定依据。具体数值请查阅 `risk.py` 的 `THRESH` 常量。

### 复制延迟（warn / crit）
华为云可靠性优先（`switch_strategy=reliability`）切主时会等待主备复制追平，
官方联动基线约为 5s 以内；延迟超过预警值说明倒换窗口被拉长，超过严重值则极可能超时或触发降级切换。

### CPU / 内存（70/80 预警，90 严重）
倒换窗口所有存量连接被断开、事务回滚，业务会集中重连；高负载下恢复期性能不足，
中断影响被放大。90% 以上持续占用属于"倒换大概率出问题"的信号。

### 存储 / 磁盘（80/95）
倒换期间要写错误日志、慢日志、binlog 追赶，磁盘接近写满时这些动作会失败；
95% 以上属写满临界，倒换/恢复可能直接失败。

### 连接数（70%/90%）
倒换瞬间旧连接全部失效，应用连接池会瞬间发起重连——连接数已接近 max_connections 时，
重连风暴会压垮新主库。此为倒换演练最常见的"雪崩"源头。

### 备份新鲜度（48h / 保留周期）
主备倒换本身不损坏数据（半同步下已提交数据 RPO≈0），备份是异常场景的恢复兜底。
超过保留周期（`backup_strategy.keep_days`，按 ≤7 天截断）仍无成功备份按严重处理。

### 错误日志（10 / 50 条·24h）
部分 `Got an error reading communication packets` 类 ERROR 属客户端断开常见噪音，
少量（≤10）不构成风险；持续大量 ERROR 说明实例存在系统性异常。
此阈值区间较宽，避免把常规噪音升级为预警。

### 复制模式 / 切换策略
- `async`：存在未复制数据丢失窗口（RPO>0），倒换可能丢少量数据 → 预警
- `availability`：切主不强制等待数据追平，极端情况下丢数据 → 预警
- `reliability`：切主等待复制追平，优先数据一致性 → 提示

### MySQL 持久化参数（仅提示，不阻止）
- `innodb_flush_log_at_trx_commit ≠ 1`：崩溃/强制切换时最多丢约 1s 已提交事务 redo
- `sync_binlog ≠ 1`：binlog 批量落盘，故障时丢部分 binlog 记录
二者影响**恢复精度**，不影响主备复制链路，故仅作提示供用户评估 RPO 要求。

## execute 前的两道动态防线

prepare 的风险评估是**快照**（生成时刻的现场），若 prepare 后隔数小时才 execute，负载/复制延迟可能已变化。
因此 execute 实际执行前还有两道动态防线：

1. **实例一致性校验**：`risk_assessment.json` 的 region/instance_id 与当前 `config.json` 不一致 → 默认阻止。
   防止"prepare 了实例 A、config 改成 B、拿 A 的评估放行 B 的倒换"这类张冠李戴。
2. **执行前实时复核**（`risk.realtime_safety_check`）：调用 StartFailover 前立即查询
   主备复制状态（ShowReplicationStatus）与近 5 分钟复制延迟（CES rds073），
   严重异常时默认阻止（需 `--force`）。阈值与 prepare 阶段一致。

## 为什么用"阻止 + --force"而非一律放行

倒换演练的目的是验证高可用，而不是制造故障。当检测到复制异常、磁盘写满、无备份等
"倒换时必然出问题"的信号时，演练大概率演变成真实故障。
因此默认拒绝执行，把最终决定权交还人工：`execute --yes --force` 表示
"我已评估风险并接受"，这是有意识的选择，而不是默认路径。

## 扩展与维护

- 新增检测项：在 `risk.py` 的 `detect_*` 系列函数加探测逻辑 → 在 `assess_risks` 加一条 `_item(...)` → 在本文件补一行业务依据。
- 阈值调整：直接改 `risk.py` 的 `THRESH` 常量（单一事实来源），本文件无需同步数值。
- 引擎差异：`ShowReplicationStatus` 并非所有引擎都支持（MySQL/PostgreSQL 可用）；不支持时自动降级为"未知"，不影响流程。
