# Common DWS Planning Scenario Examples (v2.2.0 Single Plan + Daily Growth Analysis)

> 6 common scenarios (Scenario A-F). From v2.2.0 onwards, each scenario outputs only **one plan**:
> The minimum spec that meets the requirement (minimum compute surplus; when surplus difference ≤0.5% is considered a tie, the one with fewer nodes is chosen), and candidate combinations are shown for comparison.
> Scenario B/D include growth reservation and scale-out cadence examples with **daily incremental data volume + data retention period**.
> The following numbers are generated by `scripts/generate_dws_report.py` (v2.2.0).
> **Metric (v2.2.0)**: DWS Serverless/whole-machine sales, node price already includes system disk/management/license — all plans
> have **no "system disk" row**; total = node + data disk/cache (+ storage-compute separated OBS).

## Scenario A: Migration Scenario — Competitor 1:4 (Small-to-medium, few point queries)

| Item | Value |
|----|----|
| Scenario | Migration scenario (from Greenplum) |
| Competitor CPU/Memory | 96 cores / 384GB → Memory ratio 1:4 |
| Data volume loaded into warehouse | 5 TB (5120 GB) |
| Query characteristics | Reporting-oriented, few point queries (no index) |
| Architecture mode | Storage-compute integrated (<20TB, recommended) |
| Deployment region | North China-Beijing 4 |
| Daily incremental data volume | Not provided (no growth forecast) |

**CPU calculation:**
```
Target vCPU = competitor cores = 96 (equivalent match, no ≥96 hard minimum)
Memory ratio = competitor 1:4
```

**Minimum spec selection (candidate comparison, sorted by compute surplus ascending):**
```
dwsx2.h.8xlarge.4.c7n   32 cores   3 nodes  96 cores (surplus 0)   per-node 2500GB   ← optimal
dwsx2.h.4xlarge.4.c7n   16 cores   6 nodes  96 cores (surplus 0)   per-node 1300GB   (near tie, take fewer nodes)
dwsx2.h.16xlarge.4.c7n  64 cores   3 nodes 192 cores (surplus 96)  per-node 2500GB
dwsk2.h.24xlarge        96 cores   3 nodes 288 cores (surplus 192) per-node 2500GB
dwsk2.h.32xlarge       128 cores   3 nodes 384 cores (surplus 288) per-node 2500GB
→ dwsx2.h.8xlarge.4.c7n (32 cores/128GB) × 3 = 96 vCPU / 384GB
```

**Storage (storage-compute integrated, high watermark 70%, no index):**
```
Effective storage = 5120 / 0.7 = 7314 GB
Per node = ceil(7314/3) = 2438 → 2500 GB (round up to 100GB)
```

## Scenario B: Migration Scenario — Competitor 1:8 (Medium) + Daily Growth Analysis

| Item | Value |
|----|----|
| Scenario | Migration scenario (Teradata migration) |
| Competitor CPU/Memory | 128 cores / 1024GB → Memory ratio 1:8 |
| Data volume loaded into warehouse | 10 TB |
| Query characteristics | Frequent point queries (+30% index) |
| Architecture mode | Storage-compute integrated |
| Deployment region | East China-Shanghai 1 |
| Daily incremental data volume | 80 GB/day |
| Data retention period | 12 months (planning cycle, customer specified) |

**CPU:** V=128 (competitor equivalent), Ratio=1:8

**Minimum spec selection:**
```
dwsx2.4xlarge.m7    16 cores   8 nodes  128 cores (surplus 0)  per-node 2400GB   ← optimal
dwsx2.8xlarge.m7n   32 cores   4 nodes  128 cores (surplus 0)  per-node 4800GB   (near tie, take fewer nodes)
dwsx2.24xlarge.m7   96 cores   3 nodes 288 cores (surplus 160) per-node 6400GB
dwsx2.16xlarge.m7n  64 cores   3 nodes 192 cores (surplus 64)  per-node 6400GB
→ dwsx2.4xlarge.m7 (16 cores/128GB) × 8 = 128 vCPU / 1024GB
  (16-core tier has minimum surplus; if preferring fewer nodes, can choose 32 cores × 4)
```

**Storage (70% high watermark + 30% index):**
```
Effective = 10240/0.7 = 14629 GB; with index = 14629×1.3 = 19017 GB
Per node (8 nodes) = ceil(19017/8) = 2377 → 2400 GB
```

**Growth reservation and scale-out recommendation (daily 80GB/day × 12 months retention):**
```
Planning period new = 80×30×12 = 28,800 GB; end-of-period total data ≈ 38.12 TB
Initial configured capacity 19,200 GB, initial data occupancy about 69% (≈ high watermark 70% metric)
Recommended scale-out occupancy 90% → scale-out line can hold raw data ≈ 13,292 GB
Net growth margin ≈ 3,052 GB → expected to reach scale-out line around month 2 (scale-out needed within retention period ⚠️)
Recommendation: ① Storage-compute separated → OBS elastically absorbs growth + add nodes on demand; ② Storage-compute integrated → scale out data disk / add nodes by end-of-period volume, or reserve scale-out budget
```

## Scenario E: Storage-compute Separated — Cost-priority (50% cache)

| Item | Value |
|----|----|
| Scenario | New build scenario |
| Data volume loaded into warehouse | 50 TB |
| Workload | Non-compute-intensive (historical data warehouse) |
| Query characteristics | Ordinary reporting, index +30% |
| Architecture mode | Storage-compute separated |
| Cache strategy | Cost-priority (50% hot data cache) |
| Deployment region | Southwest-Guiyang 1 |

**CPU:**
```
V = ceil(51200/100) = 512; Ratio = 1:4
```

**Minimum spec selection (v2.2.0 no system disk → each combination near tie, take 4-node large spec within tolerance):**
```
dwsx3.16U64G.16DPU      16 cores 32 nodes 512 cores (surplus 0)  per-node 1300GB   (minimum surplus but 32 nodes)
dwsax3.128U512G.128DPU 128 cores  4 nodes 512 cores (surplus 0)  per-node 10400GB  ← optimal (near tie, take fewer nodes)
dwsx3.64U256G.64DPU     64 cores  8 nodes 512 cores (surplus 0)  per-node 5200GB
dwsx3.32U128G.32DPU     32 cores 16 nodes 512 cores (surplus 0)  per-node 2600GB
dwsax3.96U384G.96DPU    96 cores  6 nodes 576 cores (surplus 64) per-node 7000GB
→ dwsax3.128U512G.128DPU × 4 = 512 vCPU / 2048GB
  (16 cores × 32 and 128 cores × 4 have the same surplus, ≤0.5% tolerance → take 4 nodes, simplest operations)
```

**Cache (80% high watermark + 50% hot data + 30% index):**
```
Hot = 51200×0.5 = 25600GB; effective = 32000GB; with index = 41600GB
Per node (4 nodes) = 10400 GB (exact division)
```

**OBS: 50TB → 50TB package**
