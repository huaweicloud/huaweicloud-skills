# OKerberos Resource Abnormal (12005) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  +-- Accompanying alarm exists (12004 OLdap) -> Handle the OLdap resource abnormality first
  +-- No accompanying alarm -> Step 2

Step 2: Check the HA status of OKerberos and its dependent OLdap resource
  |
  +-- OLdap resource abnormal -> Root cause: OLdap resource abnormality causing OKerberos abnormality (refer to 12004)
  +-- OKerberos resource abnormal -> Step 3
  +-- Both normal -> Step 4

Step 3: Check Kerberos-related processes
  |
  +-- krb5/kadmind/kdc process does not exist -> Root cause: OKerberos process failure
  +-- Process exists -> Step 5

Step 4: Check system resources
  |
  +-- Insufficient resources -> Root cause: insufficient system resources
  +-- Resources normal -> Step 5

Step 5: Check HA script logs
  |
  +-- Log contains ERROR -> Match the root cause by log keyword
  +-- No obvious error -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Accompanying alarm 12004 (OLdap Resource Abnormal) exists | OKerberos abnormality is typically caused by OLdap | Refer to 12004 to handle the OLdap resource abnormality |
| No accompanying alarm | Continue diagnosing the OKerberos resource | Step 2 |

---

### Step 2: Check the HA status of OKerberos and its dependent OLdap resource

```bash
# Query OMS service status (including HA resource status)
python manager_api_client.py -a get_oms_services --json
```

> In the returned result, check the HA status of the `okerberos` and `oldap` resources. For more detailed dual-node information:

> **The Manager API cannot directly obtain the complete output of status-oms.sh. Execute it manually on the alarm node:**
> ```bash
> sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh
> ```
> Check the "ResHAStatus" column of the "okerberos" and "oldap" rows:
> - Single-node mode: Normal
> - Dual-node mode: primary node Active_normal, standby node Standby_normal

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| oldap ResHAStatus abnormal | **Root cause located**: OLdap resource abnormality causing OKerberos abnormality -> Root cause 1 (refer to 12004) | — |
| okerberos ResHAStatus abnormal | OKerberos resource abnormal | Step 3 |
| Both normal | HA status normal | Step 4 |

---

### Step 3: Check Kerberos-related processes

```bash
# Query the process list of the alarm node to find Kerberos-related processes
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> In the returned process list, look for Kerberos-related processes such as `krb5`, `kadmind`, and `kdc`, and confirm whether the processes exist and their status.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Kerberos-related processes do not exist | **Root cause located**: OKerberos process failure -> Root cause 2 | — |
| Process exists but status abnormal | Process abnormal | Step 5 |
| Process normal | Continue log troubleshooting | Step 5 |

---

### Step 4: Check system resources

```bash
# Query host CPU, memory, and disk metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min,dev_swap_used_ratio,dev_disk_useage,dev_host_disk_usage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| CPU load too high or memory close to 100% | **Root cause located**: insufficient system resources causing OKerberos abnormality -> Root cause 3 | — |
| Insufficient disk space | **Root cause located**: insufficient disk space -> Root cause 3 | — |
| Resources normal | Continue log troubleshooting | Step 5 |

---

### Step 5: Check HA script logs

```bash
# Search for error keywords in the OKerberos HA script logs (okerberos category of the OmmServer role)
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:OmmServer' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=okerberos.log' \
  --json

# View the search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> OKerberos depends on OLdap. Also search the OLdap HA script logs (oldap category of the OmmServer role):

```bash
# Search for error keywords in the OLdap HA script logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:OmmServer' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=oldap.log' \
  --json

# View the search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `Permission denied` | **Root cause located**: file permission issue -> Root cause 4 | — |
| `Cannot find` | **Root cause located**: configuration file missing -> Root cause 4 | — |
| `ERROR` / `Failed` | OKerberos resource startup/runtime failure -> Root cause 2 | — |
| None of the above keywords | No obvious error | Step 6 |

---

### Step 6: Check OmmServer logs

```bash
# Search for OKerberos/OLdap-related exceptions in the OmmServer logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=kerberos' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:OmmServer' \
  -p 'min_log_level=WARN' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords (e.g., `OKerberos`, `OLdap`, `ldap`, `slapd`), run multiple searches separately.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `kerberos` + `ERROR` / `exception` | **Root cause located**: Kerberos connection exception -> Root cause 2 | — |
| `ldap` / `slapd` + `ERROR` | **Root cause located**: OLdap dependency exception -> Root cause 1 | — |
| None of the above keywords | No obvious error | Collect fault logs and contact O&M personnel |

## Common Root Causes and Repair Suggestions

### 1. OLdap resource abnormality that OKerberos depends on

**Features**: OLdap resource HA status abnormal; slapd process does not exist or port 21750 is not listening

**Repair suggestions**:
- Refer to the handling steps for ALM-12004 OLdap Resource Abnormal
- Log in to the node as the omm user, execute `kill -2 <ldap_pid>` to restart the OLdap process
- After OLdap is restored, check whether the OKerberos resource status is restored
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 2. OKerberos process failure

**Features**: OLdap resource normal but OKerberos resource abnormal; Kerberos-related processes do not exist

**Repair suggestions**:
- Log in to the alarm node as the omm user
- Find the Kerberos process: `ps -ef | grep -E "krb5|kadmind|kdc" | grep -v grep`
- Execute `kill -2 <kerberos_pid>` to terminate the abnormal Kerberos process, wait 20 seconds for HA to automatically restart
- Re-execute `status-oms.sh` to check whether the OKerberos resource status is restored
- If not restored, check the HA script logs for the specific cause

### 3. Insufficient system resources causing OKerberos abnormality

**Features**: CPU load too high or memory close to 100%; insufficient disk space

**Repair suggestions**:
- Clean up unnecessary log files or temporary files to free disk space
- Check whether other processes are consuming excessive memory
- After resources are restored, restart the OKerberos or OLdap process (`kill -2`)
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 4. File permission or configuration issue

**Features**: HA log contains `Permission denied` or `Cannot find`

**Repair suggestions**:
- Fix file permissions: `chown omm:omm <file_path>` and `chmod 755 <directory>`
- Check whether the configuration file is complete
- After processing, re-execute `kill -2` to restart the relevant process

## Variable Description
