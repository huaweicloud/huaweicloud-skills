# `Process CPU Usage Exceeds Threshold`(12201) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain alarm details and confirm the alarm
  │
  ▼
Step 2: Obtain CPU usage and high-CPU processes on the alarm node
  │
  ├─ High-CPU process found → Step 3
  └─ No high-CPU process → Alarm may have recovered

Step 3: Determine the type of high-CPU process
  │
  ├─ Java process → Step 4: jstack thread analysis
  ├─ Non-Java process → Step 5: Non-Java process analysis
  └─ Undetermined → Step 6: Supplementary troubleshooting

Step 4: jstack thread analysis (Java process)
  │
  ├─ Many GC-related threads with high CPU → Step 5: GC log inspection
  ├─ Many BLOCKED threads → Root cause: Lock contention
  ├─ Same stack frame repeated → Root cause: Infinite loop
  └─ Many RUNNABLE business threads → Root cause: Business peak load

Step 5: GC log inspection
  │
  ├─ Frequent Full GC → Root cause: GC issue
  ├─ OutOfMemoryError → Root cause: Out of memory
  └─ GC normal → Root cause: Business peak load

> Once a root cause is identified, jump directly to "Common Root Causes and Repair Suggestions" without proceeding to subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full log file path | `browse_log` | `file_name` |
| `collect_instance_stack`/`collect_role_stack` | `taskID` | `get_stack_progress` | `task_id` |

## Diagnosis Steps

### Step 1: Obtain alarm details and confirm the alarm

```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> Obtain the alarm node name, service name, role name, and other locating information from the alarm details.

---

### Step 2: Determine virtual machine environment and obtain CPU usage

> **First determine whether this is a virtual machine environment. Run the following command manually on the alarm node:**
> ```bash
> systemd-detect-virt
> ```
> If the result is `none`, it is a physical machine; if the output is `kvm`/`vmware`, etc., it is a virtual machine.

```bash
# Obtain CPU usage and high-CPU processes on the alarm node

# Query host CPU usage metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_cpu_us,dev_cpu_sy,dev_load_one_min,dev_load_five_min' \
  --json

# Query host process list (including PID, process name, status)
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json

# Query host resource information (CPU/memory/disk usage per service)
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> **If `get_host_process` returns 500** (NodeAgent communication exception), fall back to `get_host_resource` to obtain service-level CPU usage. To obtain PIDs, run `ps aux --sort=-%cpu | head -20` manually on the alarm node.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| CPU usage exceeds threshold and high-CPU process exists | CPU high confirmed | Step 3 |
| CPU usage normal, alarm recovered | Alarm recovered | Check historical logs |
| Associated alarms exist | Handle associated alarms first | Refer to the corresponding alarm diagnosis |

> **Also check IO wait status:**
> High IO wait (iowait > 20%) may cause CPU usage to increase without an actual CPU problem.

```bash
# Query disk IO metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_read_byte_speed,dev_disk_write_byte_speed,dev_disk_util' \
  --json
```

| High iowait + high disk IO | **Root cause identified**: Disk IO bottleneck causing high CPU iowait → Root cause 3 | — |

---

### Step 3: Determine the type of high-CPU process

**Analysis**: Review the top 5 processes by CPU usage in descending order and determine the type of high-CPU process:

| Process type | Next step |
|----------|--------|
| Java process (tomcat/pms/controller/acs, etc.) | Step 4 |
| Non-Java system process (collectd/rsyslog/kswapd0, etc.) | Step 5 |
| Root cause undetermined | Step 6 (supplementary troubleshooting) |

---

### Step 4: Java process thread analysis

```bash
# Collect instance-level jstack
python manager_api_client.py -a collect_instance_stack \
  -p 'service_name=<service_name>' \
  -p 'instance_ids=[<instance_id>]' \
  -p 'stack_types=["JSTACK"]' \
  -p 'stack_file_size_limit=100' \
  -p 'stack_file_count=5' \
  -p 'use_live=false' \
  -p 'stack_file_save_path=/var/log/Bigdata/stack' \
  -p 'collect_timeout=300' \
  --json

# Or collect role-level jstack
python manager_api_client.py -a collect_role_stack \
  -p 'service_name=<service_name>' \
  -p 'role_names=["<role_name>"]' \
  -p 'stack_types=["JSTACK"]' \
  -p 'stack_file_size_limit=100' \
  -p 'stack_file_count=5' \
  -p 'use_live=false' \
  -p 'stack_file_save_path=/var/log/Bigdata/stack' \
  -p 'collect_timeout=300' \
  --json
```

> The collection command returns `{"taskID": "xxx"}`. Use this `taskID` to query the collection progress:

```bash
# Query stack collection progress
python manager_api_client.py -a get_stack_progress \
  -p 'service_name=<service_name>' \
  -p 'task_id=<taskID>' \
  --json
```

> After `taskState` becomes `COMPLETE`, view the jstack output file via the log API:

```bash
# Query the jstack output log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=jstack' \
  -p 'path=/var/log/Bigdata/stack' \
  --json

# Browse jstack output
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=<jstack_log_path>' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

**Analysis**:

| jstack thread characteristics | Conclusion | Next step |
|----------------|------|--------|
| GC-related threads present with high process CPU | Suspected GC causing high CPU | Step 5 (GC log confirmation) |
| Many BLOCKED threads | **Root cause identified**: Thread lock contention → Root cause 2 | — |
| Same stack frame repeated | **Root cause identified**: Infinite loop → Root cause 2 | — |
| Many RUNNABLE threads with business code stack frames | High business load or GC issue | Step 5 |

---

### Step 5: GC log inspection

> Find the corresponding GC log based on the process name (see the GC log mapping table in 12016.md).

```bash
# Browse GC log (using tomcat as an example)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=<gc_log_path>' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> To search GC keywords:

```bash
# Search for key events in GC logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=Pause Full' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=INFO' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

**Analysis**:

| GC log characteristics | Conclusion |
|-----------|------|
| Frequent and long Full GC | **Root cause identified**: Full GC causing high CPU → Root cause 1 |
| OutOfMemoryError | **Root cause identified**: Out of memory → Root cause 1 |
| GC normal | **Root cause identified**: Business peak load or inefficient tasks → Root cause 4 |

---

### Step 6: Supplementary troubleshooting

```bash
# View host process list
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json

# View host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> Manager API provides snapshot metrics. For real-time IO statistics or process-level diagnostics, run `iostat -x 1 3`, `ls /proc/<pid>/fd | wc -l`, etc. manually on the alarm node.

## Common Root Causes and Repair Suggestions

### 1. Frequent Java Full GC

**Features**: High Java process CPU + GC threads in jstack + frequent Full GC in GC logs

**Repair suggestions**:
- Check whether JVM heap memory configuration is reasonable; consider increasing `-Xmx`
- Analyze for memory leaks (`jmap -histo:live <pid>`)
- Optimize code to reduce large object allocations

### 2. Java thread leak / infinite loop

**Features**: Many BLOCKED threads in jstack or the same stack frame repeatedly appears

**Repair suggestions**:
- BLOCKED: Investigate lock contention code and optimize synchronization logic
- Infinite loop: Locate business code based on thread stack and fix the logic

### 3. Abnormal non-Java system process

**Features**: Non-Java system process has abnormally high CPU usage

**Repair suggestions**:
- collectd: Check collection plugin configuration and reduce collection frequency
- rsyslog: Check for log storms and optimize log levels
- kswapd0: Insufficient memory triggering swap; check memory and swap status

### 4. Unreasonable alarm threshold configuration

**Features**: CPU usage not high but alarm persists; alarm threshold and smoothing count configured too low

**Repair suggestions**:
- Check and modify alarm threshold and smoothing count configuration in the Manager UI
- Adjust thresholds based on actual business load (default: alarm triggers after 10 consecutive threshold exceedances)
- After adjustment, wait for the next system detection cycle to check whether the alarm is automatically cleared

### 5. Business peak load or inefficient tasks

**Features**: High Java process CPU + jstack shows RUNNABLE business threads + GC logs normal

**Repair suggestions**:
- Check for data skew tasks on Yarn
- Check for inefficient SQL (full table scans, no partition filtering)
- Consider business rate limiting or off-peak execution

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-225-6 |
| `<service_name>` | Service name | tomcat, pms, HDFS |
| `<role_name>` | Role name | Controller, NameNode |
| `<instance_id>` | Instance ID | 101 |
| `<gc_log_path>` | Full GC log path (look up mapping table by process name) | /var/log/Bigdata/tomcat/tomcat_gc.log |
| `<jstack_log_path>` | Full jstack output log path | — |
