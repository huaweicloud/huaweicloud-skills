# `Process Memory Usage Exceeds Threshold`(12202) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain alarm details and confirm the alarm
  │
  ▼
Step 2: Obtain memory usage and high-memory processes on the alarm node
  │
  ├─ High-memory process found → Step 3
  └─ No high-memory process → Alarm may have recovered

Step 3: Determine the type of high-memory process
  │
  ├─ Java process → Step 4: GC log and jstack analysis
  ├─ Non-Java process → Step 5: Non-Java process analysis
  └─ Undetermined → Step 6: Supplementary troubleshooting

Step 4: GC log and jstack analysis
  │
  ├─ Frequent Full GC → Root cause: GC issue
  ├─ OutOfMemoryError → Root cause: Out of memory
  ├─ Many BLOCKED threads → Root cause: Lock contention
  └─ GC normal → Root cause: Insufficient memory configuration

> Once a root cause is identified, jump directly to "Common Root Causes and Repair Suggestions" without proceeding to subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full log file path | `browse_log` | `file_name` |
| `collect_instance_stack`/`collect_role_stack` | `taskID` | `get_stack_progress` | `task_id` |

## Diagnosis Steps

### Step 1: Obtain alarm details and confirm the alarm

```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> Obtain the alarm node name, service name, role name, and other locating information from the alarm details. The default threshold is memory usage exceeding 90% of maximum memory.

---

### Step 2: Determine virtual machine environment and obtain memory usage

> **First determine whether this is a virtual machine environment. Run the following command manually on the alarm node:**
> ```bash
> systemd-detect-virt
> ```

```bash
# Obtain memory usage and high-memory processes on the alarm node

# Query host memory usage metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_swap_used_ratio' \
  --json

# Query host process list (including PID, process name, status)
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json

# Query host resource information (CPU/memory/disk usage per service)
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> **If `get_host_process` returns 500**, fall back to `get_host_resource` to obtain service-level memory usage. To obtain PIDs, run `ps aux --sort=-%mem | head -20` manually on the alarm node.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Memory usage exceeds threshold and high-memory process exists | Memory high confirmed | Step 3 |
| Memory usage normal, alarm recovered | Alarm recovered | Check historical logs |
| Associated alarms exist | Handle associated alarms first | Refer to the corresponding alarm diagnosis |

---

### Step 3: Determine the type of high-memory process

**Analysis**: Review the top 5 processes by memory usage in descending order and determine the type of high-memory process:

| Process type | Next step |
|----------|--------|
| Java process (tomcat/pms/controller/acs, etc.) | Step 4 |
| Non-Java system process (collectd/rsyslog, etc.) | Step 5 |
| Root cause undetermined | Step 6 (supplementary troubleshooting) |

---

### Step 4: GC log and jstack analysis

```bash
# Browse GC log (look up mapping table by process name, refer to 12016.md)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=<gc_log_path>' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> Search GC keywords:

```bash
# Search for key events in GC logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=Pause Full' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=INFO' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> Also collect jstack to analyze thread status:

```bash
# Collect instance-level jstack
python manager_api_client.py -a collect_instance_stack \
  -p 'service_name=<service_name>' \
  -p 'instance_ids=[<instance_id>]' \
  -p 'stack_types=["JSTACK"]' \
  -p 'stack_file_size_limit=100' \
  -p 'stack_file_count=5' \
  -p 'use_live=false' \
  -p 'stack_file_save_path=/var/log/Bigdata/stack' \
  -p 'collect_timeout=300' \
  --json

# Query stack collection progress
python manager_api_client.py -a get_stack_progress \
  -p 'service_name=<service_name>' \
  -p 'task_id=<taskID>' \
  --json
```

**Analysis**:

| GC log/jstack characteristics | Conclusion |
|------------------|------|
| Frequent and long Full GC | **Root cause identified**: Full GC causing high memory → Root cause 1 |
| OutOfMemoryError | **Root cause identified**: Out of memory → Root cause 1 |
| Many BLOCKED threads in jstack | **Root cause identified**: Thread lock contention → Root cause 2 |
| GC normal but memory persistently high | **Root cause identified**: Insufficient memory configuration or leak → Root cause 3 |

---

### Step 5: Non-Java process analysis

```bash
# View host process details
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json

# View host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> For real-time process-level diagnostics, run `ps aux --sort=-%mem | head -20` manually on the alarm node.

---

### Step 6: Supplementary troubleshooting

```bash
# View host resource information (memory, swap, etc.)
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> For real-time statistics, run `free -h`, `cat /proc/<pid>/status | grep VmRSS`, etc. manually on the alarm node.

## Common Root Causes and Repair Suggestions

### 1. Java out of memory / frequent Full GC

**Features**: High Java process memory + frequent Full GC in GC logs + possible OutOfMemoryError

**Repair suggestions**:
- Check whether JVM heap memory configuration is reasonable; consider increasing `-Xmx`
- Analyze for memory leaks (`jmap -histo:live <pid>`)
- Optimize code to reduce large object allocations
- Note: JVM parameters modified through the Manager UI are automatically distributed

### 2. Java thread leak

**Features**: Many BLOCKED threads in jstack; abnormally high thread count

**Repair suggestions**:
- Investigate lock contention code and optimize synchronization logic
- Check whether thread pool configuration is reasonable
- Investigate for thread leak in applications

### 3. Insufficient memory configuration or leak

**Features**: GC normal but memory persistently high; process memory keeps growing without release

**Repair suggestions**:
- Increase JVM heap memory configuration (`-Xmx`)
- Analyze object distribution: `jmap -histo:live <pid>`
- Investigate memory leak code
- Consider restarting the high-memory process to release memory

### 4. High memory usage in non-Java system processes

**Features**: Non-Java system process has abnormally high memory usage

**Repair suggestions**:
- Check whether the process has a memory leak
- Adjust process configuration parameters to limit memory usage
- Restart the abnormal process if necessary

### 5. Insufficient system memory

**Features**: Very low available system memory; high swap usage

**Repair suggestions**:
- Release unnecessary memory usage (restart leaking processes)
- Add physical memory or adjust swap strategy
- Adjust JVM heap memory quotas for each service

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-225-6 |
| `<service_name>` | Service name | tomcat, pms, HDFS |
| `<role_name>` | Role name | Controller, NameNode |
| `<instance_id>` | Instance ID | 101 |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
