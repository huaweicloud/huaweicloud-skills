# Disk Unavailable (12063) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 0: Alarm information pre-check (provided by the user; use if present, skip if absent)
  │
  ├─ additionalInfo contains "Disk not readable or writable" → jump to Step 2 (skip Step 1)
  ├─ additionalInfo contains "Disk file system exception"    → jump to Step 2
  ├─ additionalInfo contains "Disk sector exception"         → jump to Step 2
  │
  └─ No additional information → start from Step 1

Step 1: Disk space check
  │
  ├─ A partition with 100% usage exists ──→ Root cause: disk full
  │
  └─ Partition space normal → Step 2: Disk health check
                      │
                      ├─ Partition read-only ──→ Root cause: disk failure mounted as read-only
                      ├─ dmesg shows I/O error/medium error ──→ Root cause: disk hardware failure
                      ├─ dmesg shows remounting read-only/ext4-fs error ──→ Root cause: file system error switched to read-only
                      ├─ Software RAID degraded ──→ Root cause: array degraded
                      ├─ NFS/network mount abnormal ──→ Root cause: network storage issue
                      └─ All normal → Step 3: Disk I/O check
                                                  │
                                                  ├─ iowait/await/util abnormally high ──→ Root cause: abnormal disk I/O
                                                  └─ I/O normal → Step 4: In-depth log troubleshooting
                                                              │
                                                              ├─ diskAvailability.log has errors ──→ Corresponding root cause
                                                              ├─ messages has disk errors ──→ Root cause: disk hardware failure
                                                              └─ No errors ──→ Possibly a transient fault; observation is recommended

After locating the root cause → Step 5: MRS component impact check (as needed)

When the alarm has recovered:
  ├─ Disk full recovered ──→ Step 1 to confirm the current space + Step 4 to check diskAvailability.log to locate the cause of the earlier fullness
  ├─ Read-only/hardware failure recovered ──→ Unlikely to self-recover; possibly a transient error; Step 2 + Step 4 to check for traces of hardware damage
  └─ I/O abnormality recovered ──→ Step 3 to confirm the current I/O + Step 2 to check for traces of hardware damage

> Once the root cause is found, jump directly to "Common Root Causes and Repair Suggestions"; there is no need to continue with the subsequent steps.
```

## API Call Chain Dependencies

> The following API calls have forward/backward dependencies; the parameter of the next step requires the return value of the previous step:

| Previous API | Returned field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full path of log file | `browse_log` | `file_name` |

> The `file_name` parameter of `browse_log` must be the full path of the log file (for example, `/var/log/Bigdata/nodeagent/scriptlog/diskAvailability.log`); relative paths or file names are not supported.

## Diagnosis Steps

### Step 0: Alarm information pre-check

Ask the user to provide the alarm details (if any), including additionalInfo (additional information) and locationInfo (location information).

**Key fields in additionalInfo**:

| additionalInfo content | Meaning | Quick direction |
|---------------------|------|---------|
| `Disk serial number;Disk not readable or writable` | Disk read/write unavailable | jump directly to **Step 2** |
| `Disk serial number;Disk file system exception, fileSystem Type:xfs` | XFS file system exception | jump directly to **Step 2** |
| `Disk serial number;Disk file system exception, fileSystem Type:ext4` | EXT4 file system exception | jump directly to **Step 2** |
| `Disk serial number;Disk sector exception` | Damaged disk sector | jump directly to **Step 2** |

**Key fields in locationInfo**: The format is `OMS;NA;hostname;mount point`, from which the faulty host and the specific mount point can be extracted for targeted checks in the subsequent steps.

> If the alarm details cannot be provided, start a full investigation from Step 1.

---

### Step 1: Disk space check

```bash
# Query host disk usage, I/O rate, and other metrics (dev_disk_useage is the usage of each disk, dev_disk_util is the I/O utilization of each disk)
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage,dev_disk_read_byte_speed,dev_disk_write_byte_speed,dev_disk_util' \
  --json
```

```bash
# Query host resource information (CPU/memory/disk usage of each service)
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> `get_host_disk_config` is a report-level interface that returns the cluster disk summary (hostCount/diskCount/totalSpace) and does not return per-host disk details. For per-host disk usage, use `get_host_metrics` to query the `dev_disk_useage` metric.

```bash
# Query the cluster disk configuration summary (summary data only)
python manager_api_client.py -a get_host_disk_config \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| A partition with 100% usage exists | Disk full caused unavailability | **Root cause located** → Common Root Cause item 1 |
| Partition usage >85% but not full | Disk space is tight, may cause write failures | Alarm, clean up is recommended |
| Partition space normal | Not a space issue | Step 2 |

> **Note**: When `df -h` shows available space but writes actually fail, it may be a case of inode exhaustion. The `dev_disk_inode_usage` metric can be used to check inode usage; if this metric is unavailable, run `df -i` on the alarm node to confirm.

---

### Step 2: Disk health check

```bash
# Query the usage and I/O utilization of each disk
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_disk_util,dev_disk_iops,dev_disk_w_await_per_second,dev_disk_r_await_per_second' \
  --json
```

```bash
# Search for dmesg disk error keywords in nodeagent logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=I/O error' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=WARN' \
  --json

# View the search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If multiple keywords need to be searched, run the search multiple times (keyWord does not support command injection characters such as `|`).
> The `services` format is `component:service:role`; you can use `get_log_search_support_services` to query the available services.
> `start_time`/`end_time` format: `yyyy-MM-ddTHH:mm:ss`.

> The following checks must be executed manually on the alarm node (the Manager API cannot browse the `/proc` file system):

```bash
# View the mount information and check for read-only mounts
mount | grep 'ro,'

# View the software RAID status
cat /proc/mdstat

# Check NFS/network mounts
mount | grep -E 'nfs|cifs'
```

**Analysis**: Check the output item by item in the following order:

| Check item | How to obtain | Abnormality criterion | Conclusion |
|--------|---------|---------|------|
| Disk usage | Query `dev_disk_useage` via `get_host_metrics` | A disk usage is 100% or abnormal | Suspected disk failure → Common Root Cause item 3 |
| dmesg disk errors | Search nodeagent logs via `start_log_search` | `I/O error`, `medium error`, `blk_update_request` present | **Root cause located**: disk hardware failure → Common Root Cause item 3 |
| dmesg read-only switch | Search nodeagent logs via `start_log_search` | `remounting read-only`, `ext4-fs error` present | Kernel automatically switched to read-only after detecting errors → Common Root Cause item 2 |
| dmesg device errors | Search nodeagent logs via `start_log_search` | `ata.*error` present | Disk controller/connection exception → Common Root Cause item 3 |
| Read-only mount | Manual: `mount \| grep 'ro,'` | `ro,` present | **Root cause located**: disk failure mounted as read-only → Common Root Cause item 2 |
| Software RAID status | Manual: `cat /proc/mdstat` | `(U_)` or `(_U)` present | **Root cause located**: software RAID array degraded → Common Root Cause item 4 |
| NFS/network mount | Manual: `mount` | nfs/cifs mount present and abnormal | Network storage issue, not a local disk failure |
| All normal | — | - | Step 3 |

> **Correlation with Step 0**: If in Step 0 additionalInfo contains `Disk file system exception, fileSystem Type:xfs/ext4`, focus on the error lines corresponding to that file system type in dmesg; if it contains `Disk sector exception`, focus on the `I/O error` and `medium error` lines in dmesg.

---

### Step 3: Disk I/O check

> The Manager API provides snapshot metrics only, which cannot replace the real-time statistics of `iostat -x 1 3`. First obtain the snapshot metrics and process status as a reference:

```bash
# Query host disk I/O metric snapshot
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_read_byte_speed,dev_disk_write_byte_speed,dev_disk_useage,dev_disk_util,dev_disk_iops' \
  --json

# View the host process list (including D-state processes)
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> If real-time I/O statistics are needed, execute manually on the alarm node:

```bash
# Real-time disk I/O statistics
iostat -x 1 3
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| iowait high, await/util high | Abnormal disk I/O caused unavailability | **Root cause located** → Common Root Cause item 5 |
| iowait high but await/util normal | iowait may be caused by other reasons (such as NFS stalls) | Continue investigation in Step 4 |
| D-state processes present | Processes are blocked waiting for I/O, indirectly indicating slow disk response | Combine with the mount output in Step 2 to confirm whether it is a local disk or network storage |
| I/O normal | Not an I/O issue | Step 4 |

> High iowait is not necessarily a local disk issue; stalls in network storage such as NFS can also cause high iowait. Combine with the `mount` output in Step 2 to confirm the mount type.

---

### Step 4: In-depth log troubleshooting

If no abnormality is found in Steps 1-3 but the alarm persists, investigate in depth from the detection-script logs and system logs.

```bash
# Browse the disk availability detection script log
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/nodeagent/scriptlog/diskAvailability.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

```bash
# Search for disk error keywords in diskAvailability.log
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=not available' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=WARN' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

```bash
# Search for disk error keywords in messages
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=remounting read-only' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=WARN' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If the Manager log interface is unavailable or does not support browsing messages, execute manually on the alarm node:

```bash
# View disk errors in messages
grep -iE "I/O error|medium error|blk_update_request|ata|remounting read-only|ext4-fs error|xfs" /var/log/messages-<YYYYMMDD>

# If the rotated log does not exist, use messages
grep -iE "I/O error|medium error|blk_update_request|ata|remounting read-only|ext4-fs error|xfs" /var/log/messages
```

> `diskAvailability.log` records the detection process of `checkDiskAvailability.sh` and the file system check results of `diskFileSystemCheck.sh`, so you can directly see which disk has read/write failures.

**Analysis**:

| Actual result | Conclusion |
|----------|------|
| diskAvailability.log contains "not available"/"Touch file failed"/"Read file failed" | Confirms which specific disk is unavailable for read/write → Common Root Cause item 2/3 |
| diskAvailability.log contains file system check exceptions | File system exception → Common Root Cause item 2 |
| messages contains I/O error / medium error, etc. | Disk hardware failure → Common Root Cause item 3 |
| messages contains remounting read-only / ext4-fs error | Kernel switched to read-only after detecting errors → Common Root Cause item 2 |
| No errors at all | Possibly a transient fault; continuous observation is recommended |

---

### Step 5: MRS component impact check (as needed)

Disk unavailability may affect the MRS components on the node; execute this when the impact scope needs to be assessed.

```bash
# View the instance information of the affected service (returns all instances; filter the target node by host.hostname)
python manager_api_client.py -a get_instances \
  -p 'service_name=HDFS' \
  --json
```

```bash
# View the alarms and events on the host
python manager_api_client.py -a get_host_alarms_and_events \
  -p 'host_name=<node_name>' \
  --json
```

```bash
# Search for error keywords in the logs of affected components
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=HDFS:HDFS:DataNode' \
  -p 'min_log_level=ERROR' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If the Manager log search interface is unavailable, the component logs can be viewed manually on the alarm node:

```bash
# DataNode log (check when the faulty mount point contains hdfs data directories)
grep -E "ERROR|Exception|I/O error|read-only|disk" /var/log/Bigdata/hdfs/dn/hadoop-omm-datanode-*.log | tail -50

# NodeManager log (check when the faulty mount point contains yarn local directories)
grep -E "ERROR|Exception|read-only|disk|unhealthy" /var/log/Bigdata/yarn/nm/hadoop-omm-nodemanager-*.log | tail -50

# RegionServer log (check when the faulty mount point contains hbase data directories)
grep -E "ERROR|Exception|I/O error|read-only|WAL" /var/log/Bigdata/hbase/rs/hbase-hbase-regionserver-*.log | tail -50
```

**Analysis**:

| Actual result | Impact |
|----------|------|
| DataNode reports disk errors | HDFS blocks on that disk are unreadable; NameNode may have marked this DN as abnormal |
| NodeManager reports unhealthy/disk errors | NM marks the local directories as unhealthy and no longer accepts new container allocations |
| RegionServer reports WAL/HFile errors | RS may have crashed or is aborting; handle as soon as possible |
| Component logs normal | The disk failure may not yet have affected the components (e.g., the faulty disk is not a component data directory) |

## Common Root Causes and Repair Suggestions

> The following repair suggestions must be executed manually by the user; the automation tool is responsible only for diagnosis and locating the root cause.

### 1. Disk space full

**Features**: df -h shows partition usage at 100%

**Repair suggestions**:
- Clean up log files (before deletion, confirm the file is not held by a process; it is recommended to first `> file` to empty the contents, then delete)
- Clean up temporary files (before deletion, confirm no process depends on them)
- Expand the disk partition

**Notes**:
- **inode exhaustion**: When `df -h` shows available space but writes fail, it may be inode exhaustion; use `df -i` to confirm
- **Disk full may cause MRS component exceptions**: For example, NameNode edit logs cannot be written, ZooKeeper transaction logs cannot be written, etc. After freeing up the space, the corresponding services may need to be restarted to recover

### 2. Disk failure mounted as read-only

**Features**: mount shows ro read-only mount; dmesg contains "remounting read-only"

**Repair suggestions**:
- Disk hardware failure; replace the disk
- Before replacement, attempt to back up the data in the read-only partition
- After replacement, rebuild the RAID array

**Notes**:
- **Read-only mount is the kernel's self-protection mechanism**: Do not attempt `mount -o remount,rw` to force restore read/write; this may cause complete data damage
- **Back up data**: The read-only partition can still be read; copy the critical data to another location as soon as possible
- **MRS impact**: If the read-only directory is the NameNode data directory, HDFS will be unable to write new data; if it is the ZooKeeper data directory, ZK may be unable to elect

### 3. Disk bad sectors/hardware failure

**Features**: dmesg contains I/O error / medium error / blk_update_request; lsblk shows the disk missing

**Repair suggestions**:
- Replace the faulty disk
- After replacement, rebuild the RAID array (if applicable)

**Notes**:
- **HDFS data safety**: A single-disk failure does not lose data (HDFS has replicas), but the disk should be replaced promptly to avoid data loss from multiple disks failing simultaneously
- **Disk isolation**: MRS supports a slow-disk isolation feature, which can be triggered via the Manager REST API `POST /api/v2/clusters/{cluster_id}/hosts/{host_name}/disk_isolation`

### 4. RAID array degraded

**Features**: RAID status is Degraded; /proc/mdstat shows `(U_)` or `(_U)`

**Repair suggestions**:
- Confirm the location of the faulty disk and replace the corresponding disk
- After replacement, trigger a RAID rebuild
- Array performance degrades during the rebuild; avoid high-I/O operations

**Notes**:
- **Software RAID rebuild**: `mdadm --add /dev/md0 /dev/sdX` adds the new disk to the array and automatically starts the rebuild
- **Risk during rebuild**: Losing one more disk while the array is degraded will cause data loss (RAID5); the rebuild should be completed as soon as possible

### 5. Abnormal disk I/O

**Features**: iostat shows abnormally high iowait/await/util

**Repair suggestions**:
- Investigate whether there are abnormal I/O processes
- Check whether there is a large number of small-file random reads/writes
- Consider optimizing the I/O scheduler or upgrading the disk

**Notes**:
- High iowait is not necessarily a local disk issue; stalls in network storage such as NFS can also cause high iowait
- In MRS big-data scenarios, NameNode's edits writes and HBase's WAL writes are high-I/O operations and must be distinguished from normal business I/O

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-225-6 |
| `<alarm_time>` | Alarm trigger time | 2026/07/13 10:00:00 GMT+08:00 |
| `<YYYYMMDD>` | Alarm date, used in the messages log file name | 20260713 |
| `<additional_info>` | Alarm additional information (user provided, optional), containing the disk serial number and failure type | virtio-1;Disk not readable or writable |
| `<location_info>` | Alarm location information (user provided, optional), format OMS;NA;hostname;mount point | OMS;NA;8-5-225-6;/dev/sda1 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
