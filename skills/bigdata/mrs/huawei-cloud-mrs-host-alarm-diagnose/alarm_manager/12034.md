# Periodic Backup Task Failure (12034) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  v
Step 2: Check OMS node disk space
  |
  +-- Insufficient disk space -> Root cause: backup path disk space insufficient
  +-- Sufficient disk space -> Step 3

Step 3: Collect Controller backup logs
  |
  +-- Log contains "insufficient disk space" -> Root cause: insufficient disk space
  +-- Log contains "file failed" -> Root cause: network or storage unreachable
  +-- No obvious error -> Step 4

Step 4: Collect Controller business logs
  |
  +-- Log contains ERROR/exception -> Match the root cause by log keyword
  +-- No obvious error -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full path of the log file | `browse_log` | `file_name` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> From the alarm information, obtain the backup task name and primary OMS node information.

---

### Step 2: Check OMS node disk space

```bash
# Query the disk usage of the primary OMS node
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> **The Manager API cannot directly view the disk space of a specific directory. Execute manually on the OMS node:**
> ```bash
> df -h
> ```
> Check whether the remaining space on the backup path mount point is less than 20 GB.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Disk usage close to 100% | **Root cause located**: backup path disk space insufficient -> Root cause 1 | — |
| Sufficient disk space | Continue log troubleshooting | Step 3 |

---

### Step 3: Collect Controller backup logs

```bash
# First obtain the exact log file name (category_name=backup)
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=backup' \
  -p 'path=/var/log/Bigdata/controller/scriptlog' \
  --json
```

```bash
# Browse the Controller backup and recovery logs (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/scriptlog/backup.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If you need to search for specific keywords:

```bash
# Search for backup failure keywords
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=backup' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=INFO' \
  -p 'log_file_name=backupplugin.log' \
  --json

# View the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords (e.g., `file failed`, `insufficient disk space`), run multiple searches separately.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `insufficient disk space` | **Root cause located**: insufficient disk space -> Root cause 1 | — |
| `Upload backup files` + `file failed` | Backup file upload failure | Step 4 |
| `Failed to backup` | Backup execution failure | Step 4 |
| None of the above keywords | No clear error | Step 4 |

---

### Step 4: Collect Controller business logs

```bash
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=controller' \
  -p 'path=/var/log/Bigdata/controller' \
  --json
```

```bash
# Browse the Controller business logs (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/controller.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If you need to search for error keywords:

```bash
# Search for error keywords in the Controller logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=controller.log' \
  --json

# View the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `ERROR` / `exception` / `failed` | Locate based on the specific error message | Handle based on the log error |
| No obvious error | No clear error | Step 5 |

---

### Step 5: Check backup task configuration and verify with an ad-hoc backup

> **The Manager API cannot directly query the backup task list. View manually in the Manager UI:**
> 1. Log in to the FusionInsight Manager administration UI
> 2. Select "O&M > Backup & Restoration > Backup Management"
> 3. Find the corresponding backup task based on the "Task Name" in the alarm location information
> 4. Check whether the backup task configuration items are correct

> **To verify whether the backup can be executed, manually start an ad-hoc backup in the Manager UI:**
> 1. On the backup management page, find the corresponding backup task
> 2. In the "Operation" column, select "More > Ad-hoc Backup"
> 3. Check whether the ad-hoc backup is executed successfully

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Backup task configuration items incorrect | **Root cause located**: backup configuration item error -> Root cause 2 | — |
| Ad-hoc backup executed successfully | Configuration is correct; may be a transient issue | Check whether the alarm is automatically cleared |
| Ad-hoc backup execution failed | Backup task has an issue | Handle based on the failure information |

## Common Root Causes and Repair Suggestions

### 1. Backup path disk space insufficient

**Features**: Backup log contains `insufficient disk space` or `Upload backup files to *** file failed`; remaining space on the backup path mount point is less than 20 GB

**Repair suggestions**:
- Check the remaining space on the backup path mount point: `df -h`
- Clean up unnecessary old backup packages: `rm -rf /srv/BigData/LocalBackup/<old_backup_package_directory_name>`
- Modify "Maximum number of backups" in the Manager UI to reduce the number of backup file sets
- Manually start an ad-hoc backup to verify whether it succeeds

### 2. Backup configuration item error

**Features**: Backup task configuration items are incorrect; ad-hoc backup execution failed

**Repair suggestions**:
- Check the task configuration on the Manager backup management page
- Correct the configuration items and save
- Manually start an ad-hoc backup to verify

### 3. Network or storage unreachable

**Features**: Backup log shows upload failure but not a disk space issue; the remote backup server is unreachable

**Repair suggestions**:
- Check the network connectivity from the OMS node to the backup server (using the `check_remote` API)
- Check the storage space of the backup server
- Check the access permissions of the backup server

### 4. Alarm cannot be cleared

**Features**: Backup task continues to fail; the system cannot produce usable backup packages

**Repair suggestions**:
- Confirm the primary OMS node status. If a primary-standby switchover is needed:
  - Log in to the primary OMS node as the omm user
  - Execute the primary-standby switchover command: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=127.0.0.1 --port=20013 --switchover --name=product`
- After the primary-standby switchover, re-execute the backup task
- Collect Controller logs and contact O&M personnel

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Primary OMS node name | 8-5-225-5 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
