# Tomcat (12067) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm alarm and instance status
  |
  +-- Process normal -> Check historical logs
  +-- Associated alarms exist -> Handle the associated alarms first
  +-- Process abnormal -> Step 2
Step 2: Check host resource metrics
  |
  +-- Metric abnormal -> Resource bottleneck
  +-- Metric normal -> Step 3
Step 3: In-depth log troubleshooting
```

## API Call Chain Dependencies
| Previous API | Returned field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | Instance status | `get_host_process` | Confirm whether the process exists |

## Diagnosis Steps
### Step 1: Confirm alarm and instance status
```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query Tomcat instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=Tomcat' \
  --json
```

```bash
# Query the process status on the alarm node
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> In the process list, look for processes related to `tomcat` to confirm whether the process exists.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| The tomcat process exists and its status is normal | The alarm may have recovered | Check historical logs |
| The tomcat process does not exist | The process is not running | Step 2 |
| Associated alarms exist (ALM-12006/12017, etc.) | Handle the associated alarms first | Refer to the corresponding alarm diagnosis |

---
### Step 2: Check host resource metrics
```bash
# Query host monitoring metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min' \
  --json
```

```bash
# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion |
|----------|------|
| Metric abnormal | Resource bottleneck caused the alarm |
| Metric normal | Continue log troubleshooting |

### Step 3: In-depth log troubleshooting

#### 3.1 web*

```bash
# Browse web* logs
> **Note**: `/var/log/Bigdata/omm/oms/ha/scriptlog/web*` is process GC/directory-level logs; the Manager browse_log does not support wildcards, so run this manually on the node:
> ```bash
> tail -n 200 /var/log/Bigdata/omm/oms/ha/scriptlog/web*
> ```
```

```bash
# Search for log keywords
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'services=Manager:Manager:OmmServer' \
  -p 'min_log_level=WARN' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  --json

# View the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> The log time format requires passing the `time_pattern` parameter.

**Keyword analysis**:

| Log keyword | Conclusion |
|-----------|------|
| ERROR / EXCEPTION | Refer to Common Root Causes and Repair Suggestions for the corresponding root cause |
| None of the above keywords | No abnormality in this log |

## Common Root Causes and Repair Suggestions

### 1. Abnormal tomcat process

**Repair suggestions**:
- Restart the Tomcat service through the Manager interface
- Before restarting, check the logs to locate the cause of the crash
- The restart will briefly affect the related services

### 2. Insufficient disk space

**Features**: The log contains `no space left` / `No space left on device`

**Repair suggestions**:
- Clean up log files and temporary files
- Expand the disk

### 3. Abnormal configuration or file permissions

**Features**: The log contains `Permission denied` / `cannot open`

**Repair suggestions**:
- Check the relevant file permissions
- Wait 5 minutes after fixing the permissions

### 4. Network or connectivity issue

**Features**: The log contains `connection refused` / `timeout`

**Repair suggestions**:
- Check network connectivity between nodes
- Use the `check_remote` interface to test the reachability of the remote node
