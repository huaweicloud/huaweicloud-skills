# GaussDB (12076) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm alarm and instance status
  |
  +-- Process normal -> Check historical logs
  +-- Correlated alarms exist -> Handle correlated alarm first
  +-- Process abnormal -> Step 2
  Step 2: In-depth log troubleshooting
```

## API Call Chain Dependencies
| Previous API | Return fields | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | Instance status | `get_host_process` | Confirm whether the process exists |

---

## Diagnosis Steps
### Step 1: Confirm alarm and instance status
```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query the GaussDB instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=GaussDB' \
  --json
```

```bash
# Query the process status on the alarm node
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> Look for `gaussdb` related processes in the process list to confirm whether the process exists.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| gaussdb process exists and status is normal | The alarm may have recovered | Check historical logs |
| gaussdb process does not exist | Process not running | Step 2 |
| Correlated alarms exist (ALM-12006/12017, etc.) | Handle the correlated alarm first | Refer to the corresponding alarm diagnosis |

### Step 2: In-depth log troubleshooting

#### 2.1 omm_gaussdba.log

```bash
# Browse omm_gaussdba.log
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/dbservice/ha/runlog/omm_gaussdba.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

```bash
# Search log keywords
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'services=Manager:Manager:OmmServer' \
  -p 'min_log_level=WARN' \
  -p 'key_word=error' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  --json

# Check search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> The log time format requires the `time_pattern` parameter.

**Keyword analysis**:

| Log keyword | Conclusion |
|-----------|------|
| error | See Common Root Causes and Repair Suggestions for the corresponding root cause |
| None of the above keywords | No abnormality in this log |

## Common Root Causes and Repair Suggestions

### 1. GaussDB process anomaly

**Repair suggestions**:
- Restart the GaussDB service through the Manager UI
- Check logs to identify the crash cause before restarting
- Restarting will briefly affect related services

### 2. Insufficient disk space

**Feature**: The log contains `no space left` / `No space left on device`

**Repair suggestions**:
- Clean up log files and temporary files
- Expand disk capacity

### 3. Configuration or file permission anomaly

**Feature**: The log contains `Permission denied` / `cannot open`

**Repair suggestions**:
- Check the permissions of the related files
- Wait 5 minutes after fixing the permissions

### 4. Network or connectivity issue

**Feature**: The log contains `connection refused` / `timeout`

**Repair suggestions**:
- Check network connectivity between nodes
- Use the `check_remote` API to test the reachability of the remote node
