# Metadata Periodic Backup to Third-Party Server Not Configured (12057) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  │
  ▼
Step 2: Collect Controller logs (check backup task configuration and execution)
  │
  ├─ Logs contain backup related errors → Match the root cause by log keyword
  └─ No obvious errors → Step 3

Step 3: Check backup task configuration
  │
  ├─ Periodic metadata backup to third-party server task configured → Alarm may have recovered
  └─ Not configured → Root cause: periodic metadata backup task not configured

Step 4: Check third-party server connectivity
  │
  ├─ Third-party server unreachable → Root cause: third-party server unreachable
  └─ Third-party server reachable → Collect fault logs and contact O&M

> After locating the root cause, jump directly to "Common Root Causes and Repair Suggestions"; no need to continue with the subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list (focus on the additional information of the 12057 alarm)
python manager_api_client.py -a get_alarms -p 'id=12057' --json
```

> **Additional information is a key diagnostic clue**: The `additionalInfo` field of the 12057 alarm explicitly lists which data modules do not have periodic backup to the third-party server configured, for example:
> ```
> Detail=No periodic backup task is configured for [DBService, NameNode, IoTDB, Kafka, Flink] on the third-party server.
> ```
> When creating a backup task later, the backup data to be configured must be consistent with the additional information.

---

### Step 2: Collect Controller logs (check backup task configuration and execution)

```bash
# Search backup task related logs (Controller role backup category)
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=backup' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=controller_backup.log' \
  --json

# Check search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> To search for multiple keywords (such as `Backup`, `ERROR`, `exception`), you can perform multiple searches.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `backup` + `ERROR` | Backup task execution abnormal | Step 3 |
| `backup` + `not configured` | **Root cause located**: backup task not configured → Root cause 1 | — |
| None of the above keywords | No obvious error | Step 3 |

---

### Step 3: Check backup task configuration

> **The Manager API cannot directly query the backup task list. Manually check in the Manager UI:**
> 1. Log in to the FusionInsight Manager management UI
> 2. Select "O&M > Backup & Restoration > Backup Management"
> 3. Check whether a periodic metadata backup to third-party server task exists

> **Also check the backup related configuration file. Manually execute on the alarm node:**
> ```bash
> cat /opt/soft/om/properties.ini
> ```
> Confirm whether a periodic backup to third-party server task has been configured.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Periodic metadata backup to third-party server task configured | Alarm may have recovered | Check whether the alarm is automatically cleared |
| No periodic metadata backup to third-party server task configured | **Root cause located**: periodic metadata backup task not configured → Root cause 1 | — |
| Backup task exists but the destination path is not a third-party server | **Root cause located**: backup task configuration incomplete → Root cause 2 | — |

---

### Step 4: Check third-party server connectivity

```bash
# Test third-party server connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<third_party_server_ip>' \
  -p 'remote_port=22' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> Alternatively, manually execute on the alarm node:
> ```bash
> ping <third_party_server_ip>
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Third-party server unreachable | **Root cause located**: third-party server unreachable → Root cause 3 | — |
| Third-party server reachable | Continue troubleshooting | Collect fault logs and contact O&M |

## Common Root Causes and Repair Suggestions

### 1. Periodic metadata backup to third-party server task not configured

**Features**: After system installation or during the hourly check, it is found that the cluster metadata does not have a periodic backup to third-party server task configured

**Repair suggestions**:
- Create a periodic metadata backup to third-party server task in the FusionInsight Manager management UI:
  1. Log in to the FusionInsight Manager management UI
  2. Select "O&M > Backup & Restoration > Backup Management"
  3. Click "Create" to create a new backup task
  4. Select the backup type as "Metadata"
  5. Configure the backup destination path as the third-party server (SFTP/NFS path)
  6. Configure the backup period as periodic backup
  7. Save and start the backup task
- After creating the task, the alarm will be automatically cleared

### 2. Backup task configuration incomplete

**Features**: A backup task exists but the destination path is not a third-party server (e.g., configured as local backup)

**Repair suggestions**:
- Modify the configuration of the existing backup task and change the destination path to the third-party server
- Ensure the backup destination path is correct and the third-party server is accessible
- After configuration is complete, wait for the next system check (1 hour) and check whether the alarm is automatically cleared

### 3. Third-party server unreachable causing configuration to be ineffective

**Features**: A backup task has been configured but the third-party server is unreachable, causing the system to consider the backup task invalid

**Repair suggestions**:
- Check the network connectivity of the third-party server (using the `check_remote` API)
- Check the disk space and permissions of the third-party server
- After fixing the third-party server, reconfigure the backup task
- Wait for the next system check and check whether the alarm is automatically cleared

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (OMS primary node) | 8-5-225-5 |
| `<third_party_server_ip>` | Third-party server IP address | 10.0.0.100 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the return of `start_log_search`) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
