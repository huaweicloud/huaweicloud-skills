# diskmgt Disk Monitoring Service Unavailable (12188) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm alarm and instance status
  |
  +-- Instance normal -> Check monitoring metric trends
  +-- Instance abnormal -> Step 2
  Step 2: Check host resource metrics
    |
    +-- Metrics abnormal -> Resource bottleneck
    +-- Metrics normal -> Step 3
  Step 3: Manually verify system logs
```

## API Call Chain Dependencies
| Previous API | Returned field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | Instance status | `get_host_process` | Confirm whether the process exists |

---

## Diagnosis Steps
### Step 1: Confirm alarm and instance status
```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query OMS instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=OMS' \
  --json
```

```bash
# Query host process status
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Instance status normal | The alarm may have recovered or is a metric-type alarm | Step 2 |
| Instance status abnormal | Service exception | Step 2 |
| Companion alarm exists | Handle the companion alarm first | Refer to the corresponding alarm diagnosis |

---

### Step 2: Check host resource metrics
```bash
# Query host monitoring metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage,dev_disk_util' \
  --json
```

```bash
# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion |
|----------|------|
| Metrics abnormal | Resource bottleneck caused the alarm |
| Metrics normal | Continue log troubleshooting |

---

### Step 3: Manually verify system logs

> **The Manager API cannot directly access system log directories (such as /var/log/messages, etc.). Execute manually on the alarm node:**
> - Check `/var/log/messages` for keywords: diskmgt / diskmgtd / systemctl / failed / inactive / No such file

---

## Common Root Causes and Repair Suggestions

### 1. Resource metric exceeds threshold

**Repair suggestions**:
- Handle the specific exceeded metric accordingly
- Clean up resources or scale up

### 2. Insufficient disk space

**Features**: Logs contain `no space left` / `No space left on device`

**Repair suggestions**:
- Clean up log files and temporary files
- Scale up the disk

### 3. Configuration or file permission exception

**Features**: Logs contain `Permission denied` / `cannot open`

**Repair suggestions**:
- Check relevant file permissions
- Wait 5 minutes after fixing permissions

### 4. Network or connectivity issue

**Features**: Logs contain `connection refused` / `timeout`

**Repair suggestions**:
- Check network connectivity between nodes
- Use the `check_remote` interface to test remote node reachability
