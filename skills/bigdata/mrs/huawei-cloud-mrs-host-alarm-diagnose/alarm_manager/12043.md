# DNS Resolution Duration Exceeds Threshold (12043) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain alarm information and confirm the alarm
  │
  ▼
Step 2: Confirm the DNS configuration on the alarm node
  │
  ├─ DNS configuration error → Root cause: DNS configuration error
  └─ DNS configuration normal → Step 3

Step 3: Check DNS server connectivity
  │
  ├─ DNS server unreachable → Root cause: DNS server unreachable
  └─ DNS server reachable → Step 4

Step 4: Test DNS resolution speed
  │
  ├─ Resolution time exceeds threshold → Root cause: DNS resolution slow
  └─ Resolution time normal → Step 5

Step 5: Check NodeAgent logs
  │
  ├─ Logs contain DNS related errors → Match the root cause by log keyword
  └─ No obvious errors → Collect fault logs and contact O&M

> After locating the root cause, jump directly to "Common Root Causes and Repair Suggestions"; no need to continue with the subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full log file path | `browse_log` | `file_name` |

## Diagnosis Steps

### Step 1: Obtain alarm information and confirm the alarm

```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> This alarm applies only to MRS 3.6.0-LTS.1 and later versions. The system default threshold is 1000ms, and an alarm is generated after exceeding the threshold for 6 consecutive times by default.

---

### Step 2: Confirm the DNS configuration on the alarm node

> **The Manager API cannot directly read system configuration files. Manually execute on the alarm node:**
> ```bash
> cat /etc/resolv.conf
> ```
> Confirm whether the configured DNS server IP address is correct and check the nameserver line configuration.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| DNS server IP configuration error or missing | **Root cause located**: DNS configuration error → Root cause 1 | — |
| DNS configuration normal | Continue checking connectivity | Step 3 |

---

### Step 3: Check DNS server connectivity

```bash
# Test DNS server connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<dns_server_ip>' \
  -p 'remote_port=53' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> Alternatively, manually execute on the alarm node:
> ```bash
> ping <dns_server_ip>
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| DNS server unreachable | **Root cause located**: DNS server unreachable → Root cause 2 | — |
| DNS server reachable | Continue testing resolution speed | Step 4 |

---

### Step 4: Test DNS resolution speed

> **The Manager API cannot directly test DNS resolution speed. Manually execute on the alarm node:**
> ```bash
> # Test DNS resolution time (using dig)
> dig <test_domain> | grep "Query time"
> # Or use nslookup
> time nslookup <test_domain>
> # Test multiple times and take the average
> for i in $(seq 1 5); do dig <test_domain> | grep "Query time"; done
> ```
> The system default threshold is 1000ms. If the resolution time consistently exceeds this threshold, DNS resolution is slow.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Resolution time consistently exceeds 1000ms | **Root cause located**: DNS resolution slow → Root cause 3 | — |
| Resolution time normal | DNS resolution speed is normal | Step 5 |

---

### Step 5: Check NodeAgent logs

```bash
# Browse NodeAgent logs
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=agent' \
  -p 'path=/var/log/Bigdata/nodeagent/agentlog' \
  --json
```

```bash
# Browse logs (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/nodeagent/agentlog/agent.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> To search for specific keywords:

```bash
# Search DNS related logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=DNS' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=WARN' \
  --json

# Check search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> To search for multiple keywords (such as `dns`, `resolve`, `timeout`), you can perform multiple searches.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `DNS` + `timeout` | **Root cause located**: DNS resolution timeout → Root cause 3 | — |
| `DNS` + `ERROR` | DNS resolution abnormal | Handle based on the specific error |
| `resolve` + `fail` | Domain name resolution failed | Handle based on the specific error |
| None of the above keywords | No obvious error | Collect fault logs and contact O&M |

## Common Root Causes and Repair Suggestions

### 1. DNS configuration error

**Features**: The DNS server IP address in /etc/resolv.conf is incorrect or missing

**Repair suggestions**:
- Modify the DNS server IP address in `/etc/resolv.conf` to the correct address
- Ensure the `nameserver` line is configured correctly
- Test whether DNS resolution has returned to normal
- Wait for the next system detection (30 seconds) and check whether the alarm is automatically cleared

### 2. DNS server unreachable

**Features**: The DNS server cannot be pinged; network connectivity test failed

**Repair suggestions**:
- Check whether the DNS server is running normally
- Check whether the network link is normal
- Check whether the firewall allows the DNS port (53)
- Contact the network administrator to troubleshoot the network fault
- After the network recovers, wait for the next system detection

### 3. DNS resolution slow

**Features**: DNS resolution time consistently exceeds the 1000ms threshold

**Repair suggestions**:
- Check whether the DNS server load is too high
- Switch to a faster DNS server
- Consider configuring a local DNS cache (such as nscd or dnsmasq)
- Check whether there is network congestion
- Wait for the next system detection and check whether the alarm is automatically cleared

### 4. Alarm cannot be cleared

**Features**: The alarm is still not cleared after performing the above steps

**Repair suggestions**:
- Collect NodeAgent service logs (10 minutes before and after the alarm)
- Contact O&M personnel to send the fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-225-6 |
| `<dns_server_ip>` | DNS server IP address (obtained from /etc/resolv.conf) | 10.0.0.1 |
| `<test_domain>` | Test domain name | example.com |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the return of `start_log_search`) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
