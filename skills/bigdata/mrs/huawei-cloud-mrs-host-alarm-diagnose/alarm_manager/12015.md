# Device Partition File System Read-Only (12015) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Confirm whether the file system is in read-only mode
  |
  +-- Restored to read-write mode -> Check whether the alarm is automatically cleared
  +-- Still in read-only mode -> Step 2

Step 2: Confirm disk hardware failure
  |
  +-- Hardware failure confirmed -> Remove the faulty disk -> Refer to 12014
  +-- No obvious hardware failure -> Step 3

Step 3: Attempt to repair the file system
  |
  +-- Repair successful -> Remount -> Alarm cleared
  +-- Repair failed -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

| Previous API | Return field | Next API | Parameter |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> From the alarm information, obtain the hostname, device partition name, and mount directory name.

---

### Step 2: Confirm whether the file system is in read-only mode

```bash
# Query host disk metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_disk_util' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> **The Manager API cannot directly view file system mount options. Execute manually on the alarm node:**
> ```bash
> mount | grep <alarm_partition_name>
> ```
> If the mount options include "ro" (read-only), the file system is in read-only mode;
> If the mount options are "rw" (read-write), the file system has been restored to read-write mode.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Restored to read-write mode (rw) | Alarm may have been restored | Check whether the alarm is automatically cleared |
| Still in read-only mode (ro) | Confirm file system is read-only | Step 2 |

---

### Step 3: Confirm disk hardware failure

> **The Manager API cannot directly detect disk hardware status. Execute manually on the alarm node:**
> ```bash
> # Check disk SMART status
> smartctl -a /dev/<DISK_NAME>
> # View disk error logs
> smartctl -l error /dev/<DISK_NAME>
> ```
> Contact a hardware engineer to confirm whether the disk has hardware failures such as bad sectors.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Hardware failure confirmed (bad sectors, etc.) | **Root cause located**: disk bad sector failure -> Root cause 1 | — |
| No obvious hardware failure | Possibly a file system failure | Step 3 |

---

### Step 4: Attempt to repair the file system

> **Execute manually on the alarm node:**
> ```bash
> # First unmount the read-only partition
> umount <alarm_partition_name>
> # Execute file system check
> fsck -y <alarm_partition_name>
> # Remount after repair is complete
> mount <alarm_partition_name> <mount_dir>
> ```
> **Note**: Before executing fsck, ensure that the partition is unmounted. This operation may cause data loss. Execute only after confirming the risk.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Repair successful, read-write mode restored | File system repair complete | Check whether the alarm is cleared |
| Still read-only after repair | **Root cause located**: disk may have hidden hardware failure -> Root cause 1 | — |
| Repair failed | Cannot be repaired | Collect fault logs and contact O&M personnel |

---

## Common Root Causes and Repair Suggestions

### 1. Disk bad sector failure

**Features**: Device partition changed to read-only mode; disk SMART check shows abnormal "Reallocated_Sector_Ct" or "Elements in grown defect list" count

**Repair suggestions**:
- Contact a hardware engineer to confirm the disk hardware failure
- Online-remove the faulty disk from the server
- After removing the disk, the system will report "ALM-12014 Device Partition Lost" alarm. Refer to the 12014 alarm handling procedure
- After handling is complete, this alarm will be automatically cleared

### 2. File system failure

**Features**: No obvious disk hardware failure; the device partition is still in read-only mode

**Repair suggestions**:
- Unmount the read-only partition: `umount <alarm_partition_name>`
- Execute fsck to repair the file system: `fsck -y <alarm_partition_name>`
- After repair, remount and verify whether read-write mode is restored
- If it is still read-only after repair, the disk may have hidden hardware failure. Handle as in Root cause 1

### 3. Hardware failure causing system lag

**Features**: Device partition read-only causes system lag, slow page refresh, or slow interface response

**Repair suggestions**:
- Confirm whether the node with the faulty disk is the primary OMS node. If so, perform a primary-standby switchover:
  - Log in to the primary OMS node as the omm user
  - Execute: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=127.0.0.1 --port=20013 --switchover --name=product`
- After the primary-standby switchover is successful, contact a hardware engineer to remove the faulty disk
- After removing the disk, refer to the 12014 alarm handling procedure

### 4. Alarm cannot be cleared

**Features**: After the above steps, the alarm is still not cleared

**Repair suggestions**:
- Collect OmmServer service logs (10 minutes before and after the alarm)
- Contact O&M personnel to send the fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-225-6 |
| `<alarm_partition_name>` | Alarmed device partition name (obtained from the alarm information) | /dev/sda1 |
| `<mount_dir>` | Mount directory name (obtained from the alarm information) | /srv/BigData |
| `<DISK_NAME>` | Alarmed disk name | /dev/sda |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
