# Inter-Node Network Connectivity Anomaly (12089) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm alarm and instance status
  |
  +-- Instance normal -> Check monitoring metric trend
  +-- Instance abnormal -> Step 2
  Step 2: Check host resource metrics
    |
    +-- Metric abnormal -> Resource bottleneck
    +-- Metric normal -> Step 3
```

## API Call Chain Dependencies
| Previous API | Return fields | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | Instance status | `get_host_process` | Confirm whether the process exists |

## Diagnosis Steps
### Step 1: Confirm alarm and instance status
```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query the OMS instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=OMS' \
  --json
```

```bash
# Query the host process status
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Instance status normal | The alarm may have recovered or be a metric-based alarm | Step 2 |
| Instance status abnormal | Service abnormal | Step 2 |
| Correlated alarms exist | Handle the correlated alarm first | Refer to the corresponding alarm diagnosis |

---
### Step 2: Check host resource metrics
```bash
# Query host monitoring metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min' \
  --json
```

```bash
# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion |
|----------|------|
| Metric abnormal | Resource bottleneck causes the alarm |
| Metric normal | Continue network troubleshooting |

---
### Step 3: Network connectivity troubleshooting

```bash
# Use the check_remote API to test inter-node connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<peer_node_ip>' \
  -p 'remote_port=22' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Connectivity test succeeded | Network is normal; may be a transient jitter | Check whether the alarm is automatically cleared |
| Connectivity test failed | **Root cause identified**: Inter-node network unreachable -> Root cause 1 | — |

## Common Root Causes and Repair Suggestions

### 1. Inter-node network unreachable

**Feature**: `check_remote` connectivity test failed, or the log contains `connection refused` / `timed out`

**Repair suggestions**:
- Use the `check_remote` API to test the reachability of the remote node
- Manually execute `ping <peer_node_ip>` on the alarm node to confirm ICMP connectivity
- Check inter-node firewall rules: `iptables -L -n | grep -E "DROP|REJECT"`
- Check physical link and network adapter status: `ethtool <network_adapter_name>`, confirm `Link detected: yes`

### 2. SSH port not listening or service anomaly

**Feature**: Connectivity test on port 22 failed, but the node itself is reachable

**Repair suggestions**:
- Manually execute `ss -tlnp | grep 22` on the alarm node to confirm SSH port is listening
- Verify that the sshd service is normal: `systemctl status sshd`
- If the port is not 22, synchronize and modify the `remote_port` parameter of `check_remote`

### 3. Routing or network configuration anomaly

**Feature**: ping fails or severe packet loss occurs, network layer anomaly

**Repair suggestions**:
- Check the routing table: `ip route`
- Check for abnormal static routes causing incorrect forwarding
- Contact the network administrator to troubleshoot switch/firewall configurations
