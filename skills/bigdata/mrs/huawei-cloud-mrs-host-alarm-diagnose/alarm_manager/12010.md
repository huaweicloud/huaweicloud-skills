# Heartbeat Interruption Between Manager Primary and Standby Nodes (12010) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  v
Step 2: Check network connectivity between primary and standby Manager nodes
  |
  +-- ping failed -> Root cause: primary-standby link abnormality
  +-- ping successful -> Step 3

Step 3: Check heartbeat port status
  |
  +-- Port 20012 is disabled -> Step 4
  +-- Port normal -> Step 5

Step 4: Check firewall status
  |
  +-- Firewall disables the port -> Root cause: firewall blocking heartbeat port
  +-- Firewall no abnormality -> Step 5

Step 5: Check hacom_local.xml configuration
  |
  +-- Configuration error -> Root cause: node name configuration error
  +-- Configuration correct -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information (determine primary and standby OMS node information)
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> From the returned information, determine the IP addresses of the primary Manager node and the standby Manager (Peer Manager).

---

### Step 2: Check network connectivity between primary and standby Manager nodes

```bash
# Test the connectivity of the remote node (standby Manager)
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<peer_oms_ip>' \
  -p 'remote_port=22' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> You can also manually execute the ping command on the alarm node:
> ```bash
> ping <peer_oms_ip>
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| ping failed / check_remote failed | **Root cause located**: primary-standby link abnormality -> Root cause 1 | — |
| ping successful / check_remote successful | Network connectivity normal | Step 3 |

---

### Step 3: Check heartbeat port status

> **The Manager API cannot directly check port listening status. Execute manually on the alarm node:**
> ```bash
> netstat -anp | grep 20012
> # or
> lsof -i:20012
> ```
> The heartbeat port is 20012. Under normal conditions, it should be listening.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| No listening result for port 20012 | Heartbeat port is disabled | Step 4 |
| Port 20012 listening normally | Port normal | Step 5 |

---

### Step 4: Check firewall status

> **The Manager API cannot directly view firewall rules. Execute manually on the alarm node:**
> ```bash
> # View iptables firewall rules
> cat /etc/sysconfig/iptables
> # or
> iptables -L -n
> ```
> Check whether any rules disable port 20012.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Firewall rule disables port 20012 | **Root cause located**: firewall blocking heartbeat port -> Root cause 3 | — |
| Firewall no abnormality | Continue checking configuration | Step 5 |

---

### Step 5: Check hacom_local.xml configuration

> **The Manager API cannot directly read system configuration files. Execute manually on the alarm node:**
> ```bash
> # Find the hacom_local.xml configuration file
> find /opt -name hacom_local.xml
> # or directly view the standard path
> cat ${BIGDATA_HOME}/om-server/OMS/workspace0/ha/local/hacom/conf/hacom_local.xml
> ```
> Check whether the local and peer node configurations are correct:
> - local should be configured with the primary node information
> - peer should be configured with the standby node information

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| local/peer configuration swapped or IP incorrect | **Root cause located**: node name configuration error -> Root cause 2 | — |
| Configuration correct | No configuration issue | Step 6 |

---

### Step 6: Check OmmServer/Controller/NodeAgent logs

```bash
# Browse OmmServer logs
> **Note**: `/var/log/Bigdata/omm/oms/server/*.log*` are process GC/directory-level logs. Manager browse_log does not support wildcards. Execute manually on the node:
> ```bash
> tail -n 200 /var/log/Bigdata/omm/oms/server/.log*
> ```

# Browse Controller logs
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=controller_root' \
  -p 'path=/var/log/Bigdata/controller' \
  --json
```

```bash
# Browse the log (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/controller_root.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If you need to search for specific keywords:

```bash
# Search for heartbeat-related logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=heartbeat' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords (e.g., `heartbeat`, `timeout`, `peer`), run multiple searches separately.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `heartbeat` + `timeout` | **Root cause located**: heartbeat timeout -> Root cause 1 | — |
| `peer` + `connection refused` | **Root cause located**: primary-standby link abnormality -> Root cause 1 | — |
| `hacom` + `ERROR` | HA component abnormal | Handle based on the specific error |
| None of the above keywords | No clear error | Collect fault logs and contact O&M personnel |

## Common Root Causes and Repair Suggestions

### 1. Primary-standby Manager link abnormality

**Features**: The primary Manager node cannot ping the standby Manager node; network connectivity test failed

**Repair suggestions**:
- Contact the network administrator to troubleshoot the network link failure
- After the network failure is repaired, check whether the alarm is automatically cleared

### 2. Node name configuration error

**Features**: The local and peer node configurations in hacom_local.xml are incorrect; network connectivity is normal but the alarm persists

**Repair suggestions**:
- Modify the primary and standby node configuration in hacom_local.xml: configure local as the primary node and peer as the standby node
- After saving and exiting, check whether the alarm is automatically cleared

### 3. Firewall blocking heartbeat port

**Features**: Port 20012 is not listening; a firewall rule exists that disables port 20012

**Repair suggestions**:
- Log in to the alarm node as the root user
- Prevent disconnection: `iptables -P INPUT ACCEPT`
- Clear firewall rules: `iptables -F`
- After processing, check whether the alarm is cleared

### 4. Alarm cannot be cleared

**Features**: After network, configuration, and firewall checks, the alarm is still not cleared

**Repair suggestions**:
- Collect OmmServer, Controller, and NodeAgent service logs (10 minutes before and after the alarm)
- Contact O&M personnel to send the fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (primary Manager node) | 8-5-225-5 |
| `<peer_oms_ip>` | Standby Manager (Peer Manager) IP address | 10.0.0.101 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
