# Critical File Configuration Anomaly (12042) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm the alarm and instance status
  |
  +-- Instance normal -> Check the monitoring metric trend
  +-- Instance abnormal -> Step 2
Step 2: Check host resource metrics
  |
  +-- Metric abnormal -> Resource bottleneck
  +-- Metric normal -> Step 3
Step 3: Manually confirm the system logs
```

## API Call Chain Dependencies
| Previous API | Returned field | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | Instance status | `get_host_process` | Confirm whether the process exists |

---

## Diagnosis Steps
### Step 1: Confirm the alarm and instance status
```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query the OMS instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=OMS' \
  --json
```

```bash
# Query the host process status
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| The instance status is normal | The alarm may have recovered or is a metric-type alarm | Step 2 |
| The instance status is abnormal | Service anomaly | Step 2 |
| Accompanied alarms exist | Handle the accompanied alarms first | Refer to the diagnosis of the corresponding alarm |

---
### Step 2: Check host resource metrics
```bash
# Query host monitoring metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min' \
  --json
```

```bash
# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion |
|----------|------|
| The metric is abnormal | A resource bottleneck causes the alarm |
| The metric is normal | Continue the log investigation |

---
### Step 3: In-depth log investigation

```bash
# Search for error keywords related to the critical file configuration
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=check_ssh|UseDNS|MaxStartups|PasswordAuthentication|not equal' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:NodeMetricAgent' \
  -p 'min_log_level=INFO' \
  -p 'log_file_name=checkfileconfig.log' \
  --json

# Check the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

**Keyword analysis**:

| Log keyword | Conclusion |
|-----------|------|
| check_ssh / UseDNS / MaxStartups / PasswordAuthentication / not equal | The critical file configuration was modified. See Common Root Causes and Repair Suggestions for the corresponding root cause |
| None of the above keywords | This log has no anomaly |

---
### Step 4: Manually confirm the system logs

> **The Manager API cannot directly access the system log directory (such as /var/log/messages). It must be manually executed on the alarm node:**
> - Check the keywords in `${BIGDATA_LOG_HOME}/nodeagent/scriptlog/checkfileconfig.log*`: check_ssh / UseDNS / MaxStartups / PasswordAuthentication

---

## Common Root Causes and Repair Suggestions

### 1. The resource metric exceeds the threshold

**Repair suggestions**:
- Handle it in a targeted manner according to the specific metric that exceeds the threshold
- Clean up resources or expand capacity

### 2. Insufficient disk space

**Features**: The log contains `no space left` / `No space left on device`

**Repair suggestions**:
- Clean up log files and temporary files
- Expand the disk

### 3. Abnormal configuration or file permissions

**Features**: The log contains `Permission denied` / `cannot open`

**Repair suggestions**:
- Check the permissions of the related files
- After fixing the permissions, wait for 5 minutes

### 4. Network or connectivity issues

**Features**: The log contains `connection refused` / `timeout`

**Repair suggestions**:
- Check the network connectivity between nodes
- Use the `check_remote` API to test whether the remote node is reachable
