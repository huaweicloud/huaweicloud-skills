# Monitoring Metric Dump Failure (12038) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  │
  ▼
Step 2: Check the dump configuration
  │
  ├─ Dump not enabled → Anomaly: alarm should not trigger when the switch is off
  └─ Dump enabled → Step 3

Step 3: Check network connectivity from the OMS node to the dump server
  │
  ├─ Ping failed → Root cause: dump server unreachable
  └─ Ping succeeded → Step 4

Step 4: Check the dump server status
  │
  ├─ Server disk full / insufficient permissions → Root cause: dump server anomaly
  └─ Server normal → Step 5

Step 5: Check the monitoring dump logs
  │
  ├─ Logs contain errors → Match the root cause by log keyword
  └─ No obvious errors → Collect fault logs and contact O&M

> After locating the root cause, jump directly to "Common Root Causes and Repair Suggestions"; no need to continue with the subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

---

### Step 2: Check the dump configuration

```bash
# Query the monitoring dump configuration
python manager_api_client.py -a get_monitor_dump_config --json
```

> The return fields include the function switch and protocol parameters (FTP/SFTP server IP, port, username, path, etc.).

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Dump not enabled | Anomaly: alarm should not trigger when the switch is off | Check whether this is a false alarm |
| Dump enabled | Dump is configured | Step 3 |

---

### Step 3: Check network connectivity from the OMS node to the dump server

```bash
# Test dump server connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<dump_server_ip>' \
  -p 'remote_port=<dump_server_port>' \
  -p 'remote_user_name=<dump_server_user>' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> Alternatively, manually execute on the alarm node:
> ```bash
> ping <dump_server_ip>
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Ping failed / check_remote failed | **Root cause located**: dump server unreachable → Root cause 1 | — |
| Ping succeeded / check_remote succeeded | Network connectivity is normal | Step 4 |

---

### Step 4: Check the dump server status (FTP/SFTP mode)

> **The Manager API cannot directly check the dump server status. Manually execute on the dump server:**
>
> **FTP mode:**
> ```bash
> # Check the FTP mode server-side save path permissions
> ls -ld <dump_path>
> # Check disk space
> df -h <dump_path>
> ```
>
> **SFTP mode:**
> ```bash
> # Check the SFTP mode server-side save path permissions
> ls -ld <dump_path>
> # Check disk space
> df -h <dump_path>
> # Check whether the SFTP user has write permission
> sudo -u <dump_server_user> touch <dump_path>/test_write && rm <dump_path>/test_write
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Dump server disk full | **Root cause located**: dump server disk space insufficient → Root cause 2 | — |
| Dump directory permissions insufficient | **Root cause located**: dump directory permissions insufficient → Root cause 3 | — |
| Server status normal | Continue with log troubleshooting | Step 5 |

> **Also check whether the OMS node local disk space is sufficient:**

```bash
# Query the OMS node disk usage
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage' \
  --json
```

| OMS node local disk space insufficient | **Root cause located**: OMS node local disk space insufficient → Root cause 5 | — |
| OMS node local disk space sufficient | Continue with log troubleshooting | Step 5 |

---

### Step 5: Check the monitoring dump logs

```bash
# Browse Controller logs (monitoring dump is executed by the controller module)
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=controller_root' \
  -p 'path=/var/log/Bigdata/controller' \
  --json
```

```bash
# Browse logs (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/controller_root.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> To search for specific keywords:

```bash
# Search for monitoring dump related errors
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=dump' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

# Check search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `connection refused` / `timeout` | **Root cause located**: network or storage unreachable → Root cause 1 | — |
| `Permission denied` | **Root cause located**: dump directory permissions insufficient → Root cause 3 | — |
| `No space left` | **Root cause located**: dump server disk full → Root cause 2 | — |
| None of the above keywords | No obvious error | Collect fault logs and contact O&M |

## Common Root Causes and Repair Suggestions

### 1. Dump server unreachable

**Features**: The OMS node cannot ping the dump server; logs contain `connection refused` or `timeout`

**Repair suggestions**:
- Check whether the dump server IP/port is correct
- Check whether the firewall allows the dump port
- Check whether the network link is normal
- Use the `check_remote` API to test remote node reachability
- After the network recovers, wait for the next system detection and check whether the alarm is automatically cleared

### 2. Dump server disk space insufficient

**Features**: Dump server disk is full; logs contain `No space left`

**Repair suggestions**:
- Clean up unnecessary files on the dump server to free up disk space
- Expand the dump server disk
- Check whether the dump directory has a large number of historical files that need to be cleaned up
- After disk space recovers, wait for the next system detection

### 3. Dump directory permissions insufficient

**Features**: Logs contain `Permission denied`; dump directory has no write permission

**Repair suggestions**:
- Check the dump directory permissions on the dump server
- Modify directory permissions: `chmod 755 <dump_path>` and `chown <user>:<group> <dump_path>`
- After permissions are restored, wait for the next system detection

### 4. OMS node local disk space insufficient

**Features**: OMS node local disk usage is close to 100%; monitoring metric dump needs to be cached locally first before uploading

**Repair suggestions**:
- Clean up unnecessary log files or temporary files on the OMS node
- Expand the OMS node disk
- After disk space recovers, wait for the next system detection

### 5. Dump configuration error

**Features**: The server IP, port, username, or path in the dump configuration is incorrect

**Repair suggestions**:
- Check the monitoring dump configuration in the Manager UI
- Correct the configuration and save
- Wait for the next system detection

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (OMS node) | 8-5-225-5 |
| `<dump_server_ip>` | Dump server IP (obtained from the dump configuration) | 10.0.0.100 |
| `<dump_server_port>` | Dump server port (obtained from the dump configuration) | 22 |
| `<dump_server_user>` | Dump server username (obtained from the dump configuration) | sftpuser |
| `<dump_path>` | Dump target path (obtained from the dump configuration) | /data/monitor |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the return of `start_log_search`) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
