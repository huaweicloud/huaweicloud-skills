# Executor (12103) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm alarm and instance status
  |
  +-- Process normal -> Check historical logs
  +-- Companion alarm exists -> Handle the companion alarm first
  +-- Process abnormal -> Step 2
  Step 2: In-depth log troubleshooting
  Step 3: Manually verify system logs
```

## API Call Chain Dependencies
| Previous API | Returned field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | Instance status | `get_host_process` | Confirm whether the process exists |

---

## Diagnosis Steps
### Step 1: Confirm alarm and instance status
```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query Executor instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=Executor' \
  --json
```

```bash
# Query process status on the alarm node
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> Search for `executor` related processes in the process list to confirm whether the process exists.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| executor process exists and status is normal | The alarm may have recovered | Check historical logs |
| executor process does not exist | Process is not running | Step 2 |
| Companion alarm exists (ALM-12006/12017, etc.) | Handle the companion alarm first | Refer to the corresponding alarm diagnosis |

### Step 2: In-depth log troubleshooting

#### 2.1 exe.log

```bash
# First obtain the exact log file name (category_name=exe_log)
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=exe_log' \
  -p 'path=/var/log/Bigdata/executor' \
  --json
```

```bash
# Browse exe.log (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/executor/exe.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

```bash
# Search log keywords
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=error' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:executor' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=exe.log' \
  --json

# View search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> The log time format requires passing the `time_pattern` parameter.

**Keyword analysis**:

| Log keyword | Conclusion |
|-----------|------|
| error / exception | See Common Root Causes and Repair Suggestions for the corresponding root cause |
| None of the above keywords | No exception in this log |

### Step 3: Manually verify system logs

> **The Manager API cannot directly access system log directories (such as /var/log/messages, etc.). Execute manually on the alarm node:**
> - Check `/var/log/gc.log*` for keywords: error / exception

## Common Root Causes and Repair Suggestions

### 1. executor process exception

**Repair suggestions**:
- Restart the Executor service through the Manager UI
- Check logs before restart to locate the crash cause
- Restart will briefly affect related services

### 2. Insufficient disk space

**Features**: Logs contain `no space left` / `No space left on device`

**Repair suggestions**:
- Clean up log files and temporary files
- Scale up the disk

### 3. Configuration or file permission exception

**Features**: Logs contain `Permission denied` / `cannot open`

**Repair suggestions**:
- Check relevant file permissions
- Wait 5 minutes after fixing permissions

### 4. Network or connectivity issue

**Features**: Logs contain `connection refused` / `timeout`

**Repair suggestions**:
- Check network connectivity between nodes
- Use the `check_remote` interface to test remote node reachability
