# `Process Full GC Duration Exceeds Threshold`(12203) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  │
  ▼
Step 2: Check process status and system resources
  │
  ├─ Process abnormal → Root cause: Process failure
  └─ Process normal → Step 3

Step 3: Check GC logs (locate GC log path by process name)
  │
  ├─ Full GC duration exceeds threshold → Step 4
  └─ GC normal → Alarm may have recovered

Step 4: Analyze Full GC cause
  │
  ├─ Memory usage too high → Root cause: Insufficient memory
  ├─ OutOfMemoryError → Root cause: Out of memory
  ├─ Metadata GC Threshold → Root cause: Insufficient metaspace
  └─ GC normal → Step 5

Step 5: Collect jstack to analyze thread status
  │
  ├─ Many BLOCKED threads → Root cause: Lock contention
  ├─ Same stack frame repeated → Root cause: Infinite loop
  └─ Many RUNNABLE business threads → Root cause: Unreasonable memory configuration

> Once a root cause is identified, jump directly to "Common Root Causes and Repair Suggestions" without proceeding to subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full log file path | `browse_log` | `file_name` |
| `collect_instance_stack`/`collect_role_stack` | `taskID` | `get_stack_progress` | `task_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> Obtain the alarm node name, service name, role name, process name, and other locating information from the alarm details. Full GC duration exceeding the threshold usually indicates that the process memory usage is too high or the memory configuration is unreasonable.

---

### Step 2: Check process status and system resources

```bash
# Query host CPU and memory metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min,dev_swap_used_ratio' \
  --json

# Query host process list to find Java processes
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json

# Query disk usage
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Process does not exist or status abnormal | **Root cause identified**: Process failure → Root cause 1 | — |
| Insufficient disk space | **Root cause identified**: Insufficient system resources → Root cause 3 | — |
| Process normal | Continue checking GC logs | Step 3 |

---

### Step 3: Check GC logs (locate GC log path by process name)

> OMS process to GC log path mapping (refer to 12016.md):
>
> | Process name | GC log path | GC format | Notes |
> |--------|-----------|--------|------|
> | tomcat | /var/log/Bigdata/tomcat/tomcat_gc.log* | JDK11+ `-Xlog:gc*` | Rotated files |
> | pms | /var/log/Bigdata/oms/pms_gc.log* | JDK11+ `-Xlog:gc*` | Filename includes date-time stamp |
> | controller | /var/log/Bigdata/controller/oms_gc.log* | JDK11+ `-Xlog:gc*` | Rotated files |
> | acs | — | — | No GC log output |

```bash
# Browse GC log (using tomcat as an example)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=<gc_log_path>' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If unsure of the GC log file name, first query available log files:

```bash
# Query log file names for the specified service
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=<gc_log_category>' \
  -p 'path=<gc_log_dir>' \
  --json
```

> To search GC keywords:

```bash
# Search for Full GC events in GC logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=Pause Full' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=INFO' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> To search other keywords (e.g., `OutOfMemoryError`, `Concurrent mode failure`), perform multiple searches.
> GC format notes:
> - JDK11+ `-Xlog:gc*` (G1): search for `Pause`, `Full`
> - JDK8 `-Xloggc` (CMS): search for `Full GC`, `Concurrent mode failure`

**Analysis**:

| GC log characteristics | Conclusion | Next step |
|-----------|------|--------|
| Full GC duration exceeds threshold | Full GC duration confirmed over limit | Step 4 |
| GC normal | Alarm may have recovered | Check whether the alarm is automatically cleared |

### Step 4: Analyze Full GC cause

> Analyze Full GC cause based on specific keywords in GC logs:

| GC log keyword | Conclusion | Next step |
|-------------|------|--------|
| Frequent and long Full GC | **Root cause identified**: Insufficient memory causing Full GC → Root cause 2 | — |
| OutOfMemoryError | **Root cause identified**: Out of memory → Root cause 2 | — |
| Metadata GC Threshold | **Root cause identified**: Insufficient metaspace → Root cause 2 | — |
| Concurrent mode failure (CMS) | **Root cause identified**: CMS concurrent collection failure → Root cause 2 | — |
| GC normal but duration over limit | Further analysis of memory and thread status needed | Step 5 |

> **Also check process memory details. Run the following commands manually on the alarm node:**
> ```bash
> # Use jstat to view process GC statistics (GC count, duration)
> jstat -gcutil <java_pid> 1000 5
> # Use jmap to view process heap memory usage
> jmap -heap <java_pid>
> # View object distribution
> jmap -histo:live <java_pid> | head -20
> # View process JVM parameter configuration
> jcmd <java_pid> VM.flags
> ```
> Use jstat to view memory usage and GC count/duration for each generation; use jmap to view heap memory details.

| jstat shows Full GC count/duration exceeding threshold | **Root cause identified**: Frequent Full GC → Root cause 2 | — |
| jmap shows old generation usage continuously growing | **Root cause identified**: Memory leak → Root cause 2 | — |
| JVM parameter -Xmx too small | **Root cause identified**: Unreasonable memory configuration → Root cause 5 | — |

---

### Step 5: Collect jstack to analyze thread status

```bash
# Collect instance-level jstack
python manager_api_client.py -a collect_instance_stack \
  -p 'service_name=<service_name>' \
  -p 'instance_ids=[<instance_id>]' \
  -p 'stack_types=["JSTACK"]' \
  -p 'stack_file_size_limit=100' \
  -p 'stack_file_count=5' \
  -p 'use_live=false' \
  -p 'stack_file_save_path=/var/log/Bigdata/stack' \
  -p 'collect_timeout=300' \
  --json

# Or collect role-level jstack
python manager_api_client.py -a collect_role_stack \
  -p 'service_name=<service_name>' \
  -p 'role_names=["<role_name>"]' \
  -p 'stack_types=["JSTACK"]' \
  -p 'stack_file_size_limit=100' \
  -p 'stack_file_count=5' \
  -p 'use_live=false' \
  -p 'stack_file_save_path=/var/log/Bigdata/stack' \
  -p 'collect_timeout=300' \
  --json
```

> The collection command returns `{"taskID": "xxx"}`. Use this `taskID` to query the collection progress:

```bash
# Query stack collection progress
python manager_api_client.py -a get_stack_progress \
  -p 'service_name=<service_name>' \
  -p 'task_id=<taskID>' \
  --json
```

> After `taskState` becomes `COMPLETE`, view the jstack output file via the log API:

```bash
# Query the jstack output log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=jstack' \
  -p 'path=/var/log/Bigdata/stack' \
  --json

# Browse jstack output
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=<jstack_log_path>' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

**Analysis**:

| jstack thread characteristics | Conclusion |
|----------------|------|
| Many BLOCKED threads | **Root cause identified**: Thread lock contention → Root cause 4 |
| Same stack frame repeated | **Root cause identified**: Infinite loop → Root cause 4 |
| Many RUNNABLE threads with business code stack frames | **Root cause identified**: Unreasonable memory configuration → Root cause 5 |

## Common Root Causes and Repair Suggestions

### 1. Process failure

**Features**: Alarm process does not exist or status is abnormal

**Repair suggestions**:
- Restart the corresponding service through the Manager UI
- Check logs before restarting to determine the crash cause
- Wait for the next system detection cycle to check whether the alarm is automatically cleared

### 2. Insufficient memory / out of memory

**Features**: Frequent and long Full GC in GC logs; possible OutOfMemoryError or Metadata GC Threshold

**Repair suggestions**:
- Check whether JVM heap memory configuration is reasonable; consider increasing `-Xmx`
- Analyze for memory leaks (`jmap -histo:live <pid>`)
- If metaspace is insufficient, increase `-XX:MaxMetaspaceSize`
- Optimize code to reduce large object allocations
- Note: JVM parameters modified through the Manager UI are automatically distributed

### 3. Insufficient system resources

**Features**: CPU load too high or memory/swap insufficient

**Repair suggestions**:
- Clean up unnecessary processes to release resources
- Check for abnormal processes consuming excessive resources
- Restart related services after resources are restored
- Wait for the next system detection cycle to check whether the alarm is automatically cleared

### 4. Thread lock contention / infinite loop

**Features**: Many BLOCKED threads in jstack or the same stack frame repeatedly appears

**Repair suggestions**:
- BLOCKED: Investigate lock contention code and optimize synchronization logic
- Infinite loop: Locate business code based on thread stack and fix the logic
- Check whether thread pool configuration is reasonable

### 5. Unreasonable memory configuration

**Features**: GC normal but Full GC duration still exceeds threshold; JVM heap memory configuration too small

**Repair suggestions**:
- Adjust JVM heap memory configuration in the Manager UI
- Adjust `-Xmx` and `-Xms` based on actual business load
- Confirm sufficient remaining physical memory on the node before increasing heap memory
- Wait for the next system detection cycle to check whether the alarm is automatically cleared

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-225-5 |
| `<service_name>` | Service name | tomcat, pms |
| `<role_name>` | Role name | Controller |
| `<instance_id>` | Instance ID | 101 |
| `<gc_log_path>` | Full GC log path (look up mapping table by process name) | /var/log/Bigdata/tomcat/tomcat_gc.log |
| `<gc_log_category>` | GC log category name | tomcat_gc, pms_gc, oms_gc |
| `<gc_log_dir>` | GC log directory | /var/log/Bigdata/tomcat |
| `<jstack_log_path>` | Full jstack output log path | — |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from `start_log_search` response) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
