# Manager Primary and Standby Node Data Synchronization Abnormal (12011) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  v
Step 2: Check network connectivity between primary and standby OMS nodes
  |
  +-- ping failed -> Root cause: primary-standby link interrupted
  +-- ping successful -> Step 3

Step 3: Check LocalBackup directory disk space
  |
  +-- Disk full -> Root cause: LocalBackup directory space full
  +-- Sufficient space -> Step 4

Step 4: Check whether sync files exist and their permissions
  |
  +-- Sync file does not exist or is a garbage file -> Root cause: sync file abnormality
  +-- Insufficient file permissions -> Root cause: insufficient directory permissions
  +-- File normal -> Step 5

Step 5: Check HA runtime logs
  |
  +-- Log contains errors -> Match the root cause by log keyword
  +-- No errors -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information (determine primary and standby OMS nodes)
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> From the alarm information, obtain the standby OMS (Peer Manager) IP and primary OMS node information.

---

### Step 2: Check network connectivity between primary and standby OMS nodes

```bash
# Test the connectivity of the remote node (standby OMS)
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<standby_oms_ip>' \
  -p 'remote_port=22' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> You can also manually execute on the primary OMS node:
> ```bash
> ping <standby_oms_ip>
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| ping failed / check_remote failed | **Root cause located**: primary-standby link interrupted -> Root cause 1 | — |
| ping successful / check_remote successful | Network connectivity normal | Step 3 |

---

### Step 3: Check LocalBackup directory disk space

```bash
# Query the disk usage of the standby OMS node
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<standby_oms_node>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<standby_oms_node>' \
  --json
```

> **The Manager API cannot directly view the disk space of a specific directory. Execute manually on the standby OMS node:**
> ```bash
> df -hl /srv/BigData/LocalBackup
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| /srv/BigData/LocalBackup partition usage 100% | **Root cause located**: LocalBackup directory space full -> Root cause 2 | — |
| Sufficient disk space | Continue checking sync files | Step 4 |

---

### Step 4: Check whether sync files exist and their permissions

> **The Manager API cannot directly check sync files. Execute manually on the standby OMS node:**
> ```bash
> # Find sync files
> find /srv/BigData/ -name "sed*"
> find /opt -name "sed*"
> # View file information and permissions
> ll <sync_file_path>
> ```
> - If the file size is 0 and all permission fields are "-", it is a garbage file
> - If the file size is not 0, check the HA runtime logs for troubleshooting

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| find command returns no results | Sync file does not exist | Step 5 |
| File size is 0 and all permissions are "-" | **Root cause located**: garbage file -> Root cause 3 | — |
| Insufficient file permissions | **Root cause located**: insufficient directory permissions -> Root cause 4 | — |
| File normal | Continue log troubleshooting | Step 5 |

---

### Step 5: Check HA runtime logs

```bash
# Search for sync abnormality keywords in the HA runtime logs (ha category of the OmmServer role)
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=sync' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:OmmServer' \
  -p 'min_log_level=INFO' \
  -p 'log_file_name=ha.log' \
  --json

# View the search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords (e.g., `Permission denied`, `No space`, `rsync`), run multiple searches separately.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `Permission denied` | **Root cause located**: insufficient directory permissions -> Root cause 4 | — |
| `No space left on device` | **Root cause located**: insufficient disk space -> Root cause 2 | — |
| `rsync` / `sync` related errors | Sync process abnormality | Handle based on the error |
| No obvious errors | No clear error | Collect fault logs and contact O&M personnel |

## Common Root Causes and Repair Suggestions

### 1. Primary-standby link interrupted

**Features**: The primary OMS node cannot ping the standby OMS node; the HA log shows connection timeout or unreachable errors

**Repair suggestions**:
- Contact the network administrator to troubleshoot the network failure
- After the network is restored, wait approximately 1 minute and check whether the alarm is cleared

### 2. LocalBackup directory space full

**Features**: /srv/BigData/LocalBackup partition usage is 100%; the HA log contains `No space left on device`

**Repair suggestions**:
- Clean up unnecessary old backup files: `rm -rf /srv/BigData/LocalBackup/<old_backup_directory_path>`
- Modify "Maximum number of backups" in the Manager UI to reduce the number of backup files
- Wait approximately 1 minute and check whether the alarm is cleared

### 3. Sync file does not exist or is a garbage file

**Features**: The find command did not find the sync file; or the sync file size is 0 and all permissions are "-"

**Repair suggestions**:
- If it is a garbage file, delete the file: `rm -rf <file_path>`
- Wait a few minutes and observe whether the alarm is cleared

### 4. Insufficient directory permissions

**Features**: HA log contains `Permission denied`

**Repair suggestions**:
- Modify directory permissions to be consistent with a normal node
- Wait a few minutes and observe whether the alarm is cleared

### 5. Emergency recovery system failure

**Features**: Primary-standby synchronization is persistently abnormal, with a risk of primary-standby switchover

**Repair suggestions**:
- Log in to the standby OMS node as the omm user and check the core process status
- If a forced primary-standby switchover is needed: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=127.0.0.1 --port=20013 --switchover --name=product`
- Collect OmmServer, Controller, and NodeAgent logs and contact O&M personnel

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<standby_oms_node>` | Standby OMS node name | 8-5-225-6 |
| `<standby_oms_ip>` | Standby OMS node IP address | 10.0.0.101 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
