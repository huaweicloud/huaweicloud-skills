# Failed to Report Metrics to CES (12172) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  │
  ▼
Step 2: Check Controller process status
  │
  ├─ Controller process abnormal → Root cause: Controller process failure
  └─ Controller process normal → Step 3

Step 3: Check network connectivity from the OMS node to the CES service
  │
  ├─ CES service unreachable → Root cause: CES service unreachable
  └─ CES service reachable → Step 4

Step 4: View Controller logs (search for CES reporting keywords)
  │
  ├─ Logs contain CES reporting errors → Match root cause by log keywords
  └─ No obvious errors → Collect fault logs and contact O&M

> Once the root cause is found, jump directly to "Common Root Causes and Repair Suggestions"; there is no need to continue with the subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Returned field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list (focus on the additionalInfo of alarm 12172)
python manager_api_client.py -a get_alarms -p 'id=12172' --json
```

> After metric sharing is enabled for the MRS cluster, the controller module periodically collects metric information within the cluster and reports it to the CES service.
>
> **The additionalInfo is a key diagnostic clue.** Match the root cause according to the following scenarios (official alarm semantics):
> | AdditionalInfo keyword | Conclusion |
> |---------------|------|
> | `Call CES to send metrics fail. Permission exception` | The resource tenant token has expired; restart controller to obtain a new token |
> | `Call CES to send metrics fail. Request CES error code xxx` / `CES internal error code xxx` | CES functional service exception |
> | `Call CES to send metrics fail. Too many request` | Service requests triggered flow control |

---

### Step 2: Check Controller process status

```bash
# Query the process list on the alarm node to find the Controller process
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> Search for `Controller` related processes in the returned process list to confirm whether the process exists and its status.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Controller process does not exist | **Root cause located**: Controller process failure → Root cause 1 | — |
| Controller process exists but status is abnormal | Process exception | Step 4 |
| Controller process normal | Continue checking network | Step 3 |

---

### Step 3: Check network connectivity from the OMS node to the CES service

> **The Manager API cannot directly test connectivity to the CES service. Execute manually on the alarm node:**
> ```bash
> # Check connectivity to the CES service (CES domain/IP obtained from configuration)
> ping <ces_endpoint>
> # Or use curl to test the CES API
> curl -v https://<ces_endpoint>
> # Test HTTPS port connectivity
> nc -zv <ces_endpoint> 443
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| CES service unreachable | **Root cause located**: CES service unreachable → Root cause 2 | — |
| CES service reachable | Network connectivity normal | Step 4 |

---

### Step 4: View Controller logs (search for CES reporting keywords)

```bash
# Search for CES reporting related errors (Controller role, controller category)
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=CES' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

# View search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search for multiple keywords (such as `report`, `metric`, `upload`, `auth`, `Permission exception`), run the search multiple times, or append `-p 'log_file_name=controller.log'` to precisely locate the Controller main log.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `CES` + `connection refused` / `timeout` | **Root cause located**: CES service unreachable → Root cause 2 | — |
| `CES` + `auth` / `token` / `403` / `401` | **Root cause located**: Authentication failure → Root cause 3 | — |
| `CES` + `report` + `fail` / `error` | **Root cause located**: Metric reporting failure → Root cause 4 | — |
| `metric` + `upload` + `fail` | **Root cause located**: Metric upload failure → Root cause 4 | — |
| None of the above keywords | No clear error | Collect fault logs and contact O&M |

## Common Root Causes and Repair Suggestions

### 1. Controller process failure

**Features**: Controller process does not exist or status is abnormal; metrics cannot be collected and reported

**Repair suggestions**:
- Restart the Controller service through the Manager UI
- Check logs before restart to locate the crash cause
- Restart will briefly affect related services
- Wait for the next system detection and check whether the alarm is automatically cleared

### 2. CES service unreachable

**Features**: The OMS node cannot ping the CES service; logs contain `connection refused` or `timeout`

**Repair suggestions**:
- Check network connectivity from the OMS node to the CES service
- Check whether the firewall allows the CES service port (443)
- Check whether DNS resolution is correct (if CES uses a domain name)
- After the network recovers, wait for the next system detection and check whether the alarm is automatically cleared

### 3. CES authentication failure

**Features**: Logs contain authentication-related errors (`auth`, `token`, `403`, `401`); CES service is reachable but reporting fails

**Repair suggestions**:
- Check whether the CES authentication credentials are correct
- Check whether the AK/SK configuration has expired
- Update the CES authentication configuration in the Manager UI
- Wait for the next system detection and check whether the alarm is automatically cleared

### 4. Metric reporting failure

**Features**: Logs contain `report fail` or `upload fail`; CES service is reachable and authentication is normal but reporting fails

**Repair suggestions**:
- Check whether the metric data format is correct
- Check whether the CES service quota is full
- Restart the Controller service and retry
- Wait for the next system detection and check whether the alarm is automatically cleared

### 5. Metric sharing configuration issue

**Features**: The metric sharing switch is not enabled or the configuration is incorrect

**Repair suggestions**:
- Check the metric sharing configuration in the Manager UI
- Confirm that the metric sharing function is correctly enabled
- Wait for the next system detection and check whether the alarm is automatically cleared

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (active OMS node) | 8-5-225-5 |
| `<ces_endpoint>` | CES service address (obtained from configuration) | ces.example.com |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
