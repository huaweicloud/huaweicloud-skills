# Device Partition Lost (12014) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Confirm the alarm and device partition status
  |
  +-- Device partition exists -> Alarm may have been restored
  +-- Device partition lost -> Step 2

Step 2: Determine whether it is a virtual machine environment
  |
  +-- Virtual machine -> Contact the virtualization administrator
  +-- Physical machine -> Step 3

Step 3: Check disk and partition mapping
  |
  +-- No mapping -> Root cause: disk removed
  +-- Mapping exists -> Step 4
  +-- Involves OMS critical directory -> Step 5

Step 4: Check RAID and SMART status
  |
  +-- Disk has RAID configured -> Root cause: RAID disk failure
  +-- Non-RAID disk -> Check SMART support

Step 5: Check system resources
  |
  +-- Insufficient resources -> Root cause: insufficient resources
  +-- Resources normal -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## Diagnosis Steps

### Step 1: Confirm the alarm and device partition status

```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> **The Manager API cannot directly view disk partition mount status. Execute manually on the alarm node:**
> ```bash
> # View disk mount status
> mount
> # View disk usage
> df -h
> # View block device information
> lsblk
> ```
> If the command results do not include the alarmed device partition name, the device partition has been lost.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Device partition still exists | Alarm may have been restored | Check historical logs |
| Device partition lost | Confirm device partition lost | Step 2 |

---

### Step 2: Determine whether it is a virtual machine environment

> **The Manager API cannot directly detect the virtualization environment. Execute manually on the alarm node:**
> ```bash
> systemd-detect-virt
> ```
> If the result is "none", it is a physical machine; if the output is a virtualization platform name such as kvm, vmware, or oracle, it is a virtual machine environment.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Virtual machine environment | Contact the virtualization administrator | — |
| Physical machine | Continue checking the disk | Step 3 |

---

### Step 3: Check disk and partition mapping

> **The Manager API cannot directly execute disk diagnostic commands such as lsblk/lsscsi. Execute manually on the alarm node:**
> ```bash
> # View block device mapping
> lsblk
> # View SCSI device information
> lsscsi
> # View disk SMART information
> smartctl -i <DISK_NAME>
> ```
> Determine whether the device partition and disk device mapping can be seen, and whether the disk has RAID configured.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| No mapping | **Root cause located**: disk removed -> Root cause 1 | — |
| Mapping exists | Continue checking RAID | Step 4 |
| Involves OMS critical directory | Data migration needed | Step 5 |

> **Also check whether /etc/fstab contains the alarmed mount directory name. Execute manually on the alarm node:**
> ```bash
> cat /etc/fstab
> ```
> Check whether the fstab file contains a line with the "mount directory name":
> - If it does, the system is configured for automatic mounting. Before replacing the disk, this line must be deleted
> - If it does not, the system is not configured for automatic mounting. A new disk can be inserted directly

---

### Step 4: Check RAID and SMART status

> Continue manual checking on the alarm node:
> ```bash
> # Check disk SMART status
> smartctl -i /dev/<DISK_NAME>
> ```
> - If the lsscsi result shows ATA/SATA/SAS in the third column, the disk does not have RAID configured
> - If other information is displayed, the disk may have RAID configured
> - If the smartctl result contains "SMART support is: Enabled", the disk supports SMART

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Disk has RAID configured | **Root cause located**: RAID disk failure -> Root cause 2 | — |
| Non-RAID disk but SMART abnormal | **Root cause located**: disk hardware failure -> Root cause 1 | — |

---

### Step 5: Check system resources

```bash
# Query host CPU, memory, and disk metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min,dev_disk_useage,dev_host_disk_usage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Insufficient system resources | **Root cause located**: insufficient system resources -> Root cause 3 | — |
| Resources normal | Continue troubleshooting | Collect fault logs and contact O&M personnel |

## Common Root Causes and Repair Suggestions

### 1. Disk removed

**Features**: Device partition lost; the mount/lsblk command results do not include the alarmed device partition name; the corresponding disk is not in the slot on the server

**Repair suggestions**:
- Confirm whether the node with the faulty disk is the primary OMS node. If so, perform a primary-standby switchover before replacing the disk
- Check whether the "/etc/fstab" file contains a line with the "mount directory name". If so, delete that line
- Contact a hardware engineer to insert a new disk
- If the original faulty disk had RAID, configure RAID according to the corresponding RAID card configuration method
- Wait 20-30 minutes and execute the mount command to check whether the disk is mounted

### 2. Disk offline failure

**Features**: The disk is in the slot but cannot be recognized; the lsblk command results do not include the alarmed device partition name but the disk is physically present

**Repair suggestions**:
- Contact a hardware engineer to check whether the disk is loose and reseat the disk
- Check whether the disk power cable and data cable are properly connected
- If the disk still cannot be recognized after reseating, replace it with a new disk
- After replacement, check the "/etc/fstab" file and handle it as in Root cause 1

### 3. Disk has bad sectors

**Features**: smartctl check shows abnormal "Reallocated_Sector_Ct" or "Elements in grown defect list" count; disk read/write is slow

**Repair suggestions**:
- Contact a hardware engineer to confirm the disk bad sectors
- Replace with a new disk
- After replacement, handle fstab and mounting as in Root cause 1

### 4. Disk circuit board failure

**Features**: The disk cannot be powered on or recognized; the disk indicator light is abnormal

**Repair suggestions**:
- Contact a hardware engineer to check the disk circuit board
- Replace with a new disk
- After replacement, handle fstab and mounting as in Root cause 1

### 5. Disk SMART self-test failure

**Features**: smartctl -i shows "Device does not support SMART" or SMART check failed

**Repair suggestions**:
- Contact a hardware engineer to confirm the disk SMART status
- Replace with a new disk
- After replacement, handle fstab and mounting as in Root cause 1

### 6. RAID disk failure

**Features**: The disk has RAID configured; RAID configuration abnormality causes partition loss

**Repair suggestions**:
- Contact a hardware engineer to check the RAID card configuration
- Reconfigure RAID and insert a new disk
- Restore the RAID array according to the RAID configuration documentation

### 7. Insufficient system resources

**Features**: CPU load too high, insufficient memory, or insufficient disk space

**Repair suggestions**:
- Clean up unnecessary log files or temporary files to free resources
- Expand disk capacity
- After resources are restored, check whether the alarm is automatically cleared

### 8. Alarm cannot be cleared

**Features**: After the above steps, the alarm is still not cleared

**Repair suggestions**:
- Collect OmmServer service logs (10 minutes before and after the alarm)
- Contact O&M personnel to send the fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-225-6 |
| `<DISK_NAME>` | Alarmed disk name (obtained from the device partition name; e.g., if the partition is /dev/sda1, the disk is /dev/sda) | /dev/sda |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
