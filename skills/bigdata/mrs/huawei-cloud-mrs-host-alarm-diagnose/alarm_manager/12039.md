# OMS Database Primary/Standby Out of Sync (12039) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  │
  ▼
Step 2: Check network connectivity between primary and standby OMS nodes
  │
  ├─ Ping failed → Root cause: primary-standby link interrupted
  └─ Ping succeeded → Step 3

Step 3: Check the primary and standby database process status
  │
  ├─ Database process abnormal → Root cause: database process failure
  └─ Process normal → Step 4

Step 4: Check disk space
  │
  ├─ Disk space insufficient → Root cause: disk space insufficient
  └─ Disk space sufficient → Step 5

Step 5: Check database sync logs
  │
  ├─ Logs contain sync errors → Match the root cause by log keyword
  └─ No obvious errors → Collect fault logs and contact O&M

> After locating the root cause, jump directly to "Common Root Causes and Repair Suggestions"; no need to continue with the subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information (determine primary and standby OMS nodes)
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

---

### Step 2: Check network connectivity between primary and standby OMS nodes

```bash
# Test standby OMS node connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<standby_oms_ip>' \
  -p 'remote_port=22' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> Alternatively, manually execute on the primary OMS node:
> ```bash
> ping <standby_oms_ip>
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Ping failed / check_remote failed | **Root cause located**: primary-standby link interrupted → Root cause 1 | — |
| Ping succeeded / check_remote succeeded | Network connectivity is normal | Step 3 |

---

### Step 3: Check the primary and standby database process status

> **First obtain the OMS key directories to determine the OMS database data directory path. Manually execute on the primary OMS node:**
> ```bash
> # Obtain OMS key directories
> echo $BIGDATA_HOME
> echo $OMS_RUN_PATH
> ```

```bash
# Query the primary OMS node process list
python manager_api_client.py -a get_host_process \
  -p 'hostname=<oms_master_node>' \
  --json

# Query the standby OMS node process list
python manager_api_client.py -a get_host_process \
  -p 'hostname=<oms_standby_node>' \
  --json
```

> In the returned process list, look for database-related processes (such as `gaussdb`, `postgres`, `dbservice`, etc.) and confirm whether the primary and standby node database processes are running normally.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Primary or standby database process missing | **Root cause located**: database process failure → Root cause 2 | — |
| Process normal | Continue checking the standby DB status | Step 4 |

> **Also check the standby OMS database status. Manually execute on the standby OMS node:**
> ```bash
> # Check the standby OMS database HA status
> sh ${BIGDATA_HOME}/om-server/OMS/workspace0/ha/module/hacom/script/status_ha.sh
> ```
> Check the "ResHAStatus" column of the "dbservice" row to confirm whether the standby database is normal.

| Standby OMS database status abnormal | **Root cause located**: standby OMS database abnormal → Root cause 2 | — |
| Standby OMS database status normal | Continue checking disk space | Step 4 |

---

### Step 4: Check disk space

```bash
# Query the primary and standby OMS node disk usage
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<oms_master_node>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage' \
  --json

python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<oms_standby_node>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<oms_master_node>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Disk space insufficient | **Root cause located**: disk space insufficient → Root cause 3 | — |
| Disk space sufficient | Continue with log troubleshooting | Step 5 |

---

### Step 5: Check database sync logs

```bash
# Browse HA runtime logs
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=ha' \
  -p 'path=/var/log/Bigdata/omm/oms/ha/runlog' \
  --json
```

```bash
# Browse logs (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/omm/oms/ha/runlog/ha.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> To search for specific keywords:

```bash
# Search for database sync related errors
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=sync' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

# Check search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> To search for multiple keywords (such as `dbservice`, `replication`, `error`), you can perform multiple searches.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `replication` + `error` | **Root cause located**: database sync abnormal → Root cause 4 | — |
| `connection refused` / `timeout` | **Root cause located**: primary-standby communication abnormal → Root cause 1 | — |
| `No space left` | **Root cause located**: disk space insufficient → Root cause 3 | — |
| None of the above keywords | No obvious error | Collect fault logs and contact O&M |

## Common Root Causes and Repair Suggestions

### 1. Primary-standby link interrupted

**Features**: The primary OMS node cannot ping the standby OMS node; HA logs show connection timeout

**Repair suggestions**:
- Contact the network administrator to troubleshoot the network fault
- After the network recovers, wait about 1 minute and check whether the alarm is cleared

### 2. Database process failure

**Features**: The primary or standby node database process is missing or in an abnormal state

**Repair suggestions**:
- Restart the database process on the abnormal node
- Wait for the database to automatically recover sync
- If automatic recovery is not possible, refer to the database O&M documentation to manually recover sync

### 3. Disk space insufficient

**Features**: Disk usage is close to 100%; the database cannot write sync data normally

**Repair suggestions**:
- Clean up unnecessary log files or temporary files to free up disk space
- Expand the disk
- After disk space recovers, wait for the database to automatically recover sync

### 4. Database sync abnormal

**Features**: The database process is normal but the sync status is abnormal; HA logs contain `replication error`

**Repair suggestions**:
- Check the database sync configuration
- Restart the standby database to re-establish sync
- If sync remains abnormal, refer to the database O&M documentation to manually recover
- Collect fault logs and contact O&M personnel

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<oms_master_node>` | Primary OMS node name | 8-5-225-5 |
| `<oms_standby_node>` | Standby OMS node name | 8-5-225-6 |
| `<standby_oms_ip>` | Standby OMS node IP address | 10.0.0.101 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the return of `start_log_search`) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
