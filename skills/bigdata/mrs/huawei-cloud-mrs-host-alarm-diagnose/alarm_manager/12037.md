# NTP Server Abnormal (12037) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  v
Step 2: Check network connectivity from the OMS node to the NTP server
  |
  +-- ping failed -> Root cause: NTP server unreachable
  +-- ping successful -> Step 3

Step 3: Check NTP server configuration
  |
  +-- Configuration error -> Root cause: NTP server configuration error
  +-- Configuration correct -> Step 4

Step 4: Check NTP service process status
  |
  +-- ntpd/chronyd process does not exist -> Root cause: NTP process not started
  +-- Process exists -> Step 5

Step 5: Check NTP sync status
  |
  +-- Sync abnormal -> Root cause: NTP sync abnormality
  +-- Sync normal -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information (determine the primary OMS node)
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> From the returned information, determine the IP address and hostname of the OMS node (primary OMS node) that generated the alarm.

---

### Step 2: Check network connectivity from the OMS node to the NTP server

```bash
# Test NTP server connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<ntp_server_ip>' \
  -p 'remote_port=123' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> You can also manually execute on the primary OMS node:
> ```bash
> ping <ntp_server_ip>
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| ping failed / check_remote failed | **Root cause located**: NTP server unreachable -> Root cause 1 | — |
| ping successful / check_remote successful | Network connectivity normal | Step 3 |

---

### Step 3: Check NTP server configuration

> **The Manager API cannot directly read system configuration files. Execute manually on the alarm node:**
> ```bash
> # View the NTP configuration file
> cat /etc/ntp.conf
> # or view the chrony configuration
> cat /etc/chrony.conf
> ```
> Confirm whether the configured NTP server IP address is correct.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| NTP server IP configuration error | **Root cause located**: NTP server configuration error -> Root cause 2 | — |
| Configuration correct | Continue checking the process | Step 4 |

---

### Step 4: Check NTP service mode and process

> **The Manager API cannot directly view the NTP service mode. Execute manually on the alarm node:**
> ```bash
> # Check the chronyd service status
> systemctl status chronyd
> # Check the ntpd service status
> systemctl status ntpd
> # Determine the current NTP service mode
> sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh
> ```
> If the "ResName" column in the output contains "chrony", the chrony mode is in use; if it contains "ntp", the ntp mode is in use.

```bash
# Query the process list of the alarm node to find ntpd/chronyd processes
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> In the returned process list, look for `ntpd` or `chronyd` related processes.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| ntpd/chronyd process does not exist | **Root cause located**: NTP process not started -> Root cause 3 | — |
| Process exists | Continue checking sync status | Step 5 |

---

### Step 5: Check NTP sync status and time retrieval

> **The Manager API cannot directly query NTP sync status. Execute manually on the alarm node:**
> ```bash
> # View NTP sync status
> ntpq -np
> # or view chrony sync status
> chronyc sources
> ```
> If the NTP server IP address is preceded by an asterisk "*", sync is normal; if there is no "*" before the IP, sync is abnormal.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| NTP sync abnormal | **Root cause located**: NTP sync abnormality -> Root cause 4 | — |
| NTP sync normal | Sync normal | Check whether the time retrieved from the NTP server is being updated |

> **Check whether the time retrieved from the NTP server is persistently not updating. Execute manually on the alarm node:**
> ```bash
> # Check whether time can be retrieved from the NTP server
> ntpdate -q <ntp_server_ip>
> # or
> chronyc tracking
> ```
> If the retrieved time is persistently not updating, it indicates that the NTP server is reachable but not properly providing time service.

| Time retrieval result | Conclusion | Next step |
|----------|------|--------|
| Time retrieval normal | Alarm may have been restored | Check whether the alarm is automatically cleared |
| Time persistently not updating | **Root cause located**: cannot retrieve time from the NTP server -> Root cause 4 | — |

## Common Root Causes and Repair Suggestions

### 1. NTP server unreachable

**Features**: The primary OMS node cannot ping the NTP server; network connectivity test failed

**Repair suggestions**:
- Check whether the NTP server is running normally
- Check whether the network link is normal
- Contact the network administrator to troubleshoot the network failure
- Check whether the firewall allows the NTP port (123)
- After the network is restored, wait for the next system detection cycle and check whether the alarm is automatically cleared

### 2. NTP server configuration error

**Features**: The NTP server IP address in the NTP configuration file is incorrect

**Repair suggestions**:
- Modify the NTP server IP address in `/etc/ntp.conf` or `/etc/chrony.conf`
- Restart the NTP service: `systemctl restart ntpd` or `systemctl restart chronyd`
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 3. NTP process not started

**Features**: ntpd or chronyd process does not exist

**Repair suggestions**:
- Start the NTP service: `systemctl start ntpd` or `systemctl start chronyd`
- Enable auto-start on boot: `systemctl enable ntpd` or `systemctl enable chronyd`
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 4. NTP sync abnormality

**Features**: NTP process exists but sync status is abnormal; ntpq/chronyc shows sync is not normal

**Repair suggestions**:
- Restart the NTP service and wait for sync
- Check whether the NTP server is properly providing time service
- Check whether the NTP authentication key is consistent
- Replace with an available NTP server if necessary

### 5. Cannot retrieve time from the NTP server

**Features**: The NTP server is reachable but time cannot be retrieved; time is persistently not updating

**Repair suggestions**:
- Check whether the NTP server is properly providing time service
- Check whether the NTP authentication key is consistent
- Restart the NTP service and retry
- Replace with an available NTP server if necessary

### 6. NTP service mode switching in progress

**Features**: Both chrony and ntp modes appear simultaneously; the system is switching the NTP service mode

**Repair suggestions**:
- Wait 10 minutes and check again
- After confirming the NTP service mode switch is complete, recheck the sync status

### 7. Alarm cannot be cleared

**Features**: After the above steps, the alarm is still not cleared

**Repair suggestions**:
- Collect OmmServer service logs (10 minutes before and after the alarm)
- Contact O&M personnel to send the fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (primary OMS node) | 8-5-225-5 |
| `<ntp_server_ip>` | NTP server IP address (obtained from the alarm information or configuration file) | 10.0.0.1 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
