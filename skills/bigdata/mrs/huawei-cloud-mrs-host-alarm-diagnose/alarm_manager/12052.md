# TCP Temporary Port Usage Rate Exceeds the Threshold for Advanced Diagnosis (12052) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm the alarm and instance status
  |
  +-- Instance normal -> Check the monitoring metric trend
  +-- Instance abnormal -> Step 2
Step 2: Check host resource metrics
  |
  +-- Metric abnormal -> Resource bottleneck
  +-- Metric normal -> Step 3
```

## API Call Chain Dependencies
| Previous API | Returned field | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | Instance status | `get_host_process` | Confirm whether the process exists |

---

## Diagnosis Steps
### Step 1: Confirm the alarm and instance status
```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query the OMS instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=OMS' \
  --json
```

```bash
# Query the host process status
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| The instance status is normal | The alarm may have recovered or is a metric-type alarm | Step 2 |
| The instance status is abnormal | Service anomaly | Step 2 |
| Accompanied alarms exist | Handle the accompanied alarms first | Refer to the diagnosis of the corresponding alarm |

---
### Step 2: Check host resource metrics
```bash
# Query host monitoring metrics (TCP temporary port usage rate)
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_temp_port_usage' \
  --json
```

```bash
# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion |
|----------|------|
| The metric is abnormal | TCP temporary ports are exhausted or there are too many connections, and a resource bottleneck causes the alarm |
| The metric is normal | Continue the log investigation |

---
### Step 3: In-depth log investigation

```bash
# Search for error keywords related to TCP ports/connections
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=Connection refused|Too many open files|Address already in use|Cannot assign' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=controller.log' \
  --json

# Check the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

**Keyword analysis**:

| Log keyword | Conclusion |
|-----------|------|
| Connection refused / Address already in use / Cannot assign | TCP ports are exhausted. See Common Root Causes and Repair Suggestions for the corresponding root cause |
| None of the above keywords | This log has no anomaly. It must be manually executed on the alarm node: `ss -s` / `netstat -anp | grep TIME_WAIT | wc -l` to confirm port usage |

---

## Common Root Causes and Repair Suggestions

### 1. The TCP temporary port range is exhausted

**Features**: Many new connections report `Cannot assign requested address` / `Address already in use`

**Repair suggestions**:
- Manually execute `sysctl net.ipv4.ip_local_port_range` on the alarm node to view the temporary port range
- If the port range is too small, expand it appropriately: `sysctl -w net.ipv4.ip_local_port_range="1024 65535"`
- Check whether a large number of `TIME_WAIT` connections have accumulated: `netstat -anp | grep TIME_WAIT | wc -l`
- If there are too many TIME_WAIT connections, adjust the kernel parameter `net.ipv4.tcp_tw_reuse=1`

### 2. Too many connections to the business process

**Features**: The number of connections remains high, and port usage approaches the upper limit

**Repair suggestions**:
- Use `get_host_process` to locate the process that occupies the largest number of connections
- Check whether the business side has a connection leak (connections not released)
- Adjust the process's `ulimit -n` (number of file handles) according to business needs

### 3. The number of system file handles reaches the upper limit

**Features**: The log contains `Too many open files`

**Repair suggestions**:
- Manually execute `ulimit -n` on the alarm node to view the handle upper limit
- Increase the `nofile` limit appropriately: `echo "ulimit -n 65535" >> /etc/profile`
- Investigate the handle usage of abnormal processes: `ls /proc/<PID>/fd | wc -l`
