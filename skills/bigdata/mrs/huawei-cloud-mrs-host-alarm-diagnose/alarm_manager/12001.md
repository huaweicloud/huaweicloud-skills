# Audit Log Dump Failure (12001) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Check the dump configuration and status
  |
  +-- enableDump=OFF -> Abnormal: with the switch off, this alarm should not be triggered. Verify whether this is a false alarm
  |
  +-- enableDump=ON -> Step 2

Step 2: Check audit log accumulation
  |
  +-- totalCount < 100000 -> Logs are not accumulated. Possibly a historical transient failure alarm that has not been cleared
  |
  +-- totalCount >= 100000 -> Logs are accumulated and the dump has not taken effect -> Step 3

Step 3: Collect ACS logs
  |
  +-- ACS log has no dump-related errors -> Step 4 (possibly the dump has never been triggered or there is a configuration issue)
  |
  +-- ACS log has dump-related errors -> Match the root cause by error keyword
       |
       +-- write file failed -> Root cause: dump directory disk full / insufficient permissions
       +-- exec commond failed -> Root cause: database connection exception or script execution failure
       +-- Sftp server public key is illegal -> Root cause: SFTP public key mismatch
       +-- connectFTP path exception -> Root cause: SFTP target path invalid
       +-- connectFTP exception + JSchException -> Step 5 (refine the SFTP connection/authentication issue)
       +-- SFTP transfer file.*failed -> Root cause: SFTP upload failure (peer disk full or network interruption)

Step 4: Dump has never been triggered or there is a configuration issue
  |
  +-- mode=0 (by count) and totalCount < 100000 -> The dump condition is not met. Wait until the logs accumulate to the threshold and it triggers automatically
  +-- mode=1 (by time) and date has not expired -> The scheduled dump has not reached its trigger time
  +-- Others -> Check whether the ACS process is running normally (see the Step 4 notes)

Step 5: Refine the SFTP connection/authentication issue
  |
  +-- check_remote unreachable -> Root cause: SFTP server unreachable
  +-- check_remote reachable but JSchException -> Root cause: SFTP authentication failure (incorrect user/password/public key) or port unreachable
  +-- Further verification needed -> Supplementary manual troubleshooting (port test / SFTP authentication test)

Step 6: Check related alarms (as needed)
  |
  +-- Check whether the alarm node has other active alarms such as disk full or SFTP-related ones

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

> The following API calls have front-to-back dependencies; the parameters of a later step need the return value of the previous step:

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `get_audit_config` | `ftpIp` | `check_remote` | `remote_ip` |
| `get_audit_config` | `ftpPort` | Manual troubleshooting | Port test parameters |
| `get_audit_config` | `ftpUserName` | Manual troubleshooting | SFTP authentication parameters |
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | full path of the log file | `browse_log` | `file_name` |

> The `file_name` parameter of `browse_log` must be the full path of the log file (for example, `/var/log/Bigdata/controller/acs/acs.log`). Relative paths or file names are not supported.

## Diagnosis Steps

### Step 1: Check the dump configuration and status

```bash
# Query the audit log dump configuration
python manager_api_client.py -a get_audit_config --json
```

**Return field description** (`APIAuditConfig`, no nested wrapper; returned directly):

| Field | Type | Meaning | Key value |
|------|------|------|--------|
| `enableDump` | String | Dump switch | ON=enabled, OFF=disabled |
| `ftpIp` | String | SFTP server IP | — |
| `ipMode` | String | IP protocol | IPv4/IPv6 |
| `ftpPort` | String | SFTP port | Default is 22 |
| `ftpUserName` | String | SFTP username | — |
| `ftpPassword` | String | SFTP password | **Always empty when queried** |
| `ftpServicePublicKey` | String | SFTP server public key | — |
| `savePath` | String | SFTP target path | — |
| `mode` | int | Dump mode | 0=by record count (when reaching 100,000 records), 1=by time |
| `date` | String | Scheduled dump trigger time | ISO8601 format |

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| `enableDump=OFF` | Abnormal: with the switch off, this alarm should not be triggered | Verify whether it is a false alarm |
| `enableDump=ON` | Dump is enabled | Step 2 |

---

### Step 2: Check audit log accumulation

```bash
# Query the total number of audit logs
python manager_api_client.py -a get_audits -p 'limit=1' --json
```

> The returned `APIAuditItems` contains `totalCount` (int), the total number of audit logs.
> The default value of oplogMax is 100000 (100,000 records), used here as the accumulation threshold.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| `totalCount < 100000` | Logs are not accumulated. Possibly a historical transient failure alarm that has not been cleared | Step 4 |
| `totalCount >= 100000` | Logs are accumulated and the dump has not taken effect | Step 3 |

---

### Step 3: Collect ACS logs

```bash
# Browse the ACS logs
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/acs/acs.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If `acs.log` returns no results, you can try the rotated logs `acs.log.1`, `acs.log.2`, etc. You can also use the log search API to search by keyword:

```bash
# Search the ACS logs for dump error keywords
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=write file failed' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=INFO' \
  --json

# View the search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords, run multiple searches separately (keyWord does not support characters such as `|` that enable command injection).
> The `services` format is `component:service:role`. You can use `get_log_search_support_services` to query available services.
> The `start_time`/`end_time` format is `yyyy-MM-ddTHH:mm:ss`.

> If the log file name is uncertain, first confirm the available log files:

```bash
# Query the ACS log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=acs' \
  -p 'path=/var/log/Bigdata/audit/acs' \
  --json
```

> `category_name` is the log category name and `path` is the log directory. Both the category name and path of the corresponding categorys can be queried via `get_log_search_support_services`.

> If none of the above APIs are available, use the `gather_log` API to collect a log package and then inspect it:

```bash
# Collect the ACS log package
python manager_api_client.py -a gather_log \
  -p 'cluster_name=<cluster_name>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  --json
```

**Log keyword analysis** (matched by priority from high to low; stop at the first hit):

| Log keyword | Failed stage | Conclusion | Next step |
|-----------|---------|------|--------|
| `write file failed` | CSV write | **Root cause located**: dump directory disk full or insufficient permissions -> Root cause 1 | — |
| `exec commond failed` | Script execution | **Root cause located**: database connection exception or dump script missing -> Root cause 2/3 | — |
| `Sftp server public key is illegal` | SFTP public key | **Root cause located**: SFTP public key mismatch -> Root cause 5 | — |
| `connectFTP path exception` + `SftpException` | SFTP path | **Root cause located**: SFTP target path invalid -> Root cause 6 | — |
| `connectFTP exception` + `JSchException` | SFTP connection | SFTP connection failure (network/authentication/port) -> Root cause 4 | Step 5 |
| `SFTP transfer file.*failed` | SFTP upload | SFTP upload failure -> Root cause 4/6 | Step 5 |
| None of the above keywords | — | No clear dump error in the logs | Step 4 |

---

### Step 4: Dump has never been triggered or there is a configuration issue

> When the ACS logs from Step 3 contain no dump-related errors, check the dump trigger conditions.

| Condition | Analysis |
|------|------|
| `mode=0` (by count) and `totalCount < 100000` | The dump condition is not met and the log volume has not reached the threshold, so the dump will not be triggered. Wait until the logs accumulate to the threshold and it triggers automatically |
| `mode=1` (by time) and `date` has not expired | The scheduled dump has not reached its trigger time |
| None of the above is satisfied but there is still no dump record | The ACS process may be abnormal. Check the process status |

```bash
# View the host process list to confirm whether the ACS process is running
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> Look for the ACS-related processes (such as `acs`, `Controller`) in the returned process list. If the process does not exist, the ACS process is abnormal and needs to be restarted.

---

### Step 5: Refine the SFTP connection/authentication issue

> When the logs from Step 3 point to an SFTP connection failure (`connectFTP exception` + `JSchException`), further determination is needed.

```bash
# Test the SFTP server connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<ftpip>' \
  -p 'remote_port=22' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

**Comprehensive determination**:

| Network test result | ACS log keyword | Conclusion | Next step |
|-------------|-------------|------|--------|
| check_remote unreachable | `connectFTP exception` | **Root cause located**: SFTP server unreachable -> Root cause 4 | — |
| check_remote reachable | `connectFTP exception` + `JSchException` | SFTP port unreachable or authentication failure | Supplementary manual troubleshooting |
| check_remote reachable | `SFTP transfer file.*failed` | SFTP is connectable but upload fails (peer disk full or no write permission on the path) | Supplementary manual troubleshooting |

> **Supplementary manual troubleshooting**:
> - Port test: `python3 -c "import socket; s=socket.socket(); s.settimeout(3); s.connect(('<ftpip>',<ftpport>)); print('PORT OPEN'); s.close()" 2>&1 || echo "PORT CLOSED/TIMEOUT"`
> - SFTP authentication test: `sftp -P <ftpport> <ftpusername>@<ftpip>`
> - Peer disk/path permission: check on the SFTP server
>
> **Note**: You can precisely locate the SFTP failure cause using the return codes of `PUT /api/v2/audits/config`:
> - `6400001` -> SFTP connection failure (network/port unreachable)
> - `6400002` -> SFTP path does not exist
> - `6400003` -> SFTP authentication failure (incorrect user/password/public key)
>
> Because this Skill is restricted to read-only operations, the PUT configuration change cannot be executed to verify automatically. If precise location is required, ask the user to reconfigure the SFTP dump parameters manually in the Manager UI (the same as the current configuration is fine). After submission, the UI will display the specific error.

## Common Root Causes and Repair Suggestions

### 1. Dump directory issue

**Features**: The ACS log contains `write file failed`; disk usage is 100%; the CSV directory does not exist or has insufficient permissions

**Repair suggestions**:
- Check and set the `$GAUSSDATA` environment variable
- Create the directory and grant permissions: `mkdir -p ${GAUSSDATA}/../dumpData/iam/operatelog/ && chmod 755 ${GAUSSDATA}/../dumpData/iam/operatelog/`
- Clean up disk space

### 2. Database connection exception

**Features**: The ACS log contains `exec commond failed`; the gsql connection fails

**Repair suggestions**:
- Check whether GaussDB is running normally: `gsql -U omm -d omm -p $OMS_GAUSS_PORT -c "SELECT 1"`
- Check whether the `$OMS_GAUSS_PORT` environment variable is correct
- Check whether GaussDB has long transactions blocking: `SELECT * FROM pg_locks WHERE NOT granted`
- Restart GaussDB if necessary

### 3. Dump script missing

**Features**: The ACS log contains `exec commond failed`; `createCSV.sh` or `createByBlogTimeCSV.sh` does not exist or has no execute permission

**Repair suggestions**:
- Check whether the scripts exist under `$OMS_RUN_PATH/workspace0/bin/`
- Grant execute permission: `chmod +x $OMS_RUN_PATH/workspace0/bin/createCSV.sh $OMS_RUN_PATH/workspace0/bin/createByBlogTimeCSV.sh`
- If the scripts are missing, copy them from another normal node

### 4. SFTP connection failure

**Features**: The ACS log contains `connectFTP exception`, `JSchException`; the network is unreachable

**Repair suggestions**:
- Check whether the SFTP server IP/port is correct
- Check whether the firewall allows the SFTP port
- Test port connectivity on the alarm node: `python3 -c "import socket; s=socket.socket(); s.settimeout(3); s.connect(('<ftpip>',<ftpport>)); s.close()" 2>&1 || echo "PORT CLOSED"`
- Verify whether the username/password is correct (manually test with `sftp` or reconfigure in the MRS Manager UI to trigger validation)
- Check whether the SFTP server disk is full

### 5. SFTP public key mismatch

**Features**: The ACS log contains `Sftp server public key is illegal`

**Repair suggestions**:
- The SFTP server certificate may have been changed. Update the public key in the dump configuration
- Reconfigure the SFTP dump parameters in the MRS Manager UI

### 6. SFTP target path invalid

**Features**: The ACS log contains `connectFTP path exception`

**Repair suggestions**:
- Confirm that `savePath` exists on the SFTP server and has write permission
- Create the target directory on the SFTP server and grant permissions

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (OMS primary node) | 8-5-225-5 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<ftpip>` | SFTP server IP (obtained from the `ftpIp` returned in Step 1; also used for the `remote_ip` parameter of check_remote) | 10.0.0.100 |
| `<ftpport>` | SFTP port (obtained from the `ftpPort` returned in Step 1) | 22 |
| `<ftpusername>` | SFTP username (obtained from the `ftpUserName` returned in Step 1) | sftpuser |
| `<savepath>` | SFTP target path (obtained from the `savePath` returned in Step 1) | /data/audit |
| `<task_id>` | Log search task ID (obtained from the return of `start_log_search`) | — |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
