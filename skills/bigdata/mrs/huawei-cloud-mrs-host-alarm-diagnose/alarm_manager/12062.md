# OMS Parameter Configuration Mismatch with Cluster Scale (12062) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm alarm
  |
  v
Step 2: Check cluster scale and OMS configuration
  |
  +-- Configuration insufficient for cluster scale -> Root cause: OMS parameter configuration insufficient
  +-- Configuration matches -> Step 3

Step 3: Check modify_manager_param.log keywords
  |
  +-- Log contains "Current oms configurations can not support" -> Root cause: OMS configuration insufficient confirmed
  +-- No such keyword -> Step 4

Step 4: Check system resources
  |
  +-- Resources insufficient -> Root cause: Insufficient system resources
  +-- Resources normal -> Collect fault logs and contact O&M personnel

> After identifying the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing to subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return fields | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full log file path | `browse_log` | `file_name` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json

# Query cluster information (cluster scale)
python manager_api_client.py -a get_cluster_info \
  -p 'cluster_id=<cluster_id>' \
  --json

# Query host statistics (node count)
python manager_api_client.py -a get_host_stats --json

# Query all host lists
python manager_api_client.py -a get_hosts --json
```

> Obtain cluster node count and other scale information from cluster information and host statistics.

---

### Step 2: Check cluster scale and OMS configuration

```bash
# Query OMS configuration
python manager_api_client.py -a get_oms_config --json
```

> Compare the OMS parameter configuration with the cluster scale to check for mismatches. Key parameters to check include:
> - Database connection pool size
> - Thread pool size
> - JVM heap memory configuration
> - Maximum connections for each component, etc.

> **The Manager API cannot directly determine whether parameters match the cluster scale. Manually check in the Manager UI:**
> 1. Log in to the FusionInsight Manager management interface
> 2. Select "System > OMS > Configuration"
> 3. Verify whether the OMS parameter configuration matches the current cluster scale

> **To view the current Manager configuration parameters, manually execute on the active OMS node:**
> ```bash
> su - omm
> cd ${BIGDATA_HOME}/om-server/om/sbin
> sh oms_config_info.sh -q
> ```
> This outputs the current Manager-related configuration parameters (Controller Xmx, Xms, heartbeat timeout threshold, Pms memory configuration, etc.) to compare against the configuration standards required by the cluster node scale.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| OMS parameter configuration insufficient for cluster scale | **Root cause identified**: OMS parameter configuration insufficient -> Root cause 1 | — |
| OMS parameter configuration matches cluster scale | Continue log troubleshooting | Step 3 |

---

### Step 3: Check modify_manager_param.log keywords

```bash
# Browse the Manager parameter modification log
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=modify_manager_param' \
  -p 'path=/var/log/Bigdata/controller/scriptlog' \
  --json
```

```bash
# Browse log (using exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/scriptlog/modify_manager_param.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> To search for specific keywords:

```bash
# Search for "Current oms configurations can not support" keyword
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=Current oms configurations can not support' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

# Check search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> To search for other keywords (such as `ERROR`, `WARN`), run multiple searches.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `Current oms configurations can not support xx nodes` | **Root cause identified**: OMS configuration insufficient for current cluster scale -> Root cause 1 | — |
| `ERROR` / `WARN` | Configuration modification anomaly | Handle based on the specific error |
| None of the above keywords | No clear error | Step 4 |

---

### Step 4: Check system resources

```bash
# Query host CPU and memory metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min,dev_swap_used_ratio' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| System resources insufficient | **Root cause identified**: Insufficient system resources -> Root cause 2 | — |
| Resources normal | Continue troubleshooting | Collect fault logs and contact O&M personnel |

## Common Root Causes and Repair Suggestions

### 1. OMS parameter configuration insufficient for cluster scale

**Feature**: modify_manager_param.log contains "Current oms configurations can not support xx nodes"; OMS configured parameters are insufficient to support the current cluster scale

**Repair suggestions**:
- Log in to the active OMS node as the omm user
- Run `sh ${BIGDATA_HOME}/om-server/om/sbin/oms_config_info.sh -q` to view the current configuration
- Optimize the Manager configuration based on the cluster node count: `sh ${BIGDATA_HOME}/om-server/om/sbin/oms_config_info.sh -m`
- Alternatively, modify the OMS parameter configuration in the Manager UI
- After modification, wait approximately 1 hour (the system checks hourly on the hour) and verify whether the alarm is automatically cleared
- If the OMS process becomes abnormal after modification, check the logs and roll back the configuration

### 2. Insufficient system resources

**Feature**: CPU load too high, insufficient memory; OMS process running abnormally due to resource shortage

**Repair suggestions**:
- Clean up unnecessary processes to free resources
- Check for abnormal processes consuming excessive resources
- Consider capacity expansion or adjusting the cluster scale
- After resources recover, verify whether the alarm is automatically cleared

### 3. Configuration not adjusted after cluster scale change

**Feature**: OMS parameter configuration was not adjusted after cluster scale-in or scale-out operations

**Repair suggestions**:
- Adjust the OMS parameter configuration based on the new cluster scale
- Modify the relevant parameters in the Manager UI or execute oms_config_info.sh
- Wait approximately 1 hour and verify whether the alarm is automatically cleared

### 4. Alarm cannot be cleared

**Feature**: The alarm persists after configuration adjustment

**Repair suggestions**:
- Collect OmmServer and Controller service logs (10 minutes before and after the alarm)
- Contact O&M personnel and send the fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (active OMS node) | 8-5-225-5 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from `start_log_search` return value) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
