# AD Server Connection Exception (12100) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  │
  ▼
Step 2: Test network connectivity to the AD server
  │
  ├─ Ping failed → Root cause: AD server unreachable
  └─ Ping succeeded → Step 3

Step 3: Check AD service status
  │
  ├─ AD service unavailable → Root cause: AD service exception
  └─ AD service normal → Step 4

Step 4: Check AD integration configuration
  │
  ├─ Configuration error → Root cause: AD integration configuration error
  └─ Configuration correct → Collect fault logs and contact O&M

> Once the root cause is found, jump directly to "Common Root Causes and Repair Suggestions"; there is no need to continue with the subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Returned field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

---

### Step 2: Test network connectivity to the AD server

```bash
# Test AD server connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<ad_server_ip>' \
  -p 'remote_port=389' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> Alternatively, execute manually on the active OMS node:
> ```bash
> ping <ad_server_ip>
> ```

> The AD server uses LDAP port 389 or LDAPS port 636 by default.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| AD server ping failed / check_remote failed | **Root cause located**: AD server unreachable → Root cause 1 | — |
| AD server reachable | Network connectivity normal | Step 3 |

---

### Step 3: Check AD service port connectivity

> **The Manager API cannot directly check the AD service port. Execute manually on the active OMS node:**
> ```bash
> # Check AD server LDAP port (389) connectivity
> nc -zv <ad_server_ip> 389
> # Or check LDAPS port (636) connectivity
> nc -zv <ad_server_ip> 636
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| AD port unreachable | **Root cause located**: AD service port unreachable → Root cause 2 | — |
| AD port reachable | Continue checking AD service status | Step 4 |

---

### Step 4: Check AD service status

> **The Manager API cannot directly check the AD service status. Execute manually on the active OMS node:**
> ```bash
> # Test LDAP connection (default port 389)
> ldapsearch -H ldap://<ad_server_ip>:389 -D "<bind_dn>" -W -b "<base_dn>"
> # Or test LDAPS connection (port 636)
> ldapsearch -H ldaps://<ad_server_ip>:636 -D "<bind_dn>" -W -b "<base_dn>"
> ```
> You can also check whether the AD domain service is running normally on the AD server.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| LDAP connection failed | **Root cause located**: AD service exception → Root cause 2 | — |
| LDAP connection normal | AD service normal | Step 4 |

---

### Step 5: Collect Controller logs

```bash
# Browse Controller logs
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=controller_root' \
  -p 'path=/var/log/Bigdata/controller' \
  --json
```

```bash
# Browse the log (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/controller_root.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If you need to search for specific keywords:

```bash
# Search AD-related logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=AD' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search for multiple keywords (such as `Ldap`, `ldap`, `bind`, `sync`), run the search multiple times.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `AD` + `connection refused` / `timeout` | **Root cause located**: AD server unreachable → Root cause 2 | — |
| `AD` + `bind` + `fail` | **Root cause located**: AD bind failure → Root cause 3 | — |
| `AD` + `sync` + `fail` | **Root cause located**: AD sync failure → Root cause 3 | — |
| `ldap` + `ERROR` | LDAP connection exception | Handle according to the specific error |
| None of the above keywords | No clear error | Collect fault logs and contact O&M |

---

### Step 6: Check AD integration configuration

> **The Manager API cannot directly view the AD integration configuration. Check manually in the Manager UI:**
> 1. Log in to the FusionInsight Manager admin interface
> 2. Select "System > Permission > Domain User/User Group"
> 3. Check whether the AD domain integration configuration is correct

> You can also check the relevant configuration files on the active OMS node.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| AD integration configuration error | **Root cause located**: AD integration configuration error → Root cause 3 | — |
| Configuration correct | Continue troubleshooting | Collect fault logs and contact O&M |

## Common Root Causes and Repair Suggestions

### 1. AD server unreachable

**Features**: The active OMS node cannot ping the AD server; network connectivity test failed

**Repair suggestions**:
- Check whether the AD server is running normally
- Check whether the network link is normal
- Check whether the firewall allows LDAP ports (389 or 636)
- Contact the network administrator to troubleshoot network issues
- After the network recovers, wait for the next system sync (default 60 minutes) and check whether the alarm is automatically cleared

### 2. AD service exception

**Features**: The AD server is reachable but the LDAP connection fails; the AD domain service is unavailable

**Repair suggestions**:
- Check whether the AD domain service is running normally on the AD server
- Restart the AD domain service
- Check the AD server system logs to troubleshoot the exception cause
- After the AD service recovers, wait for the next system sync and check whether the alarm is automatically cleared

### 3. AD integration configuration error

**Features**: Parameters such as server IP, port, bind DN, base DN in the AD integration configuration are incorrect

**Repair suggestions**:
- Check and correct the AD integration configuration in the Manager UI
- Confirm the bind user account and password are correct
- Confirm the base DN configuration is correct
- After the configuration is corrected, wait for the next system sync and check whether the alarm is automatically cleared

### 4. Alarm cannot be cleared

**Features**: The alarm is not cleared after the above steps

**Repair suggestions**:
- Collect OmmServer service logs (10 minutes before and after the alarm)
- Contact O&M personnel to send the fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (active OMS node) | 8-5-225-5 |
| `<ad_server_ip>` | AD server IP address (obtained from alarm information or configuration) | 10.0.0.50 |
| `<bind_dn>` | AD bind DN | cn=admin,dc=example,dc=com |
| `<base_dn>` | AD base DN | dc=example,dc=com |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
