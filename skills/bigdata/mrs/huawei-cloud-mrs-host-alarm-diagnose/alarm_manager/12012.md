# NTP Service Abnormal (12012) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  v
Step 2: Check the NTP service mode and process on the alarm node
  |
  +-- chrony mode -> Check chronyd process -> Step 3
  +-- ntp mode -> Check ntpd process -> Step 4
  +-- Both chrony and ntp appear -> Mode is being switched, wait 10 minutes

Step 3: Check chrony sync status
  |
  +-- Sync abnormal -> Step 5
  +-- Sync normal -> Step 5

Step 4: Check NTP sync status
  |
  +-- Sync abnormal -> Step 5
  +-- Sync normal -> Step 5

Step 5: Check NTP authentication key consistency
  |
  +-- Key inconsistent -> Root cause: NTP authentication key mismatch
  +-- Key consistent -> Step 6

Step 6: Check system resources
  |
  +-- Insufficient resources -> Root cause: insufficient system resources
  +-- Resources normal -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information (determine the primary OMS node)
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms -p 'id=12012' --json
```

---

### Step 2: Check the NTP service mode and process on the alarm node

```bash
# Query OMS service status and confirm the HA status of the NTP resource (ntp service: active=Active_normal/standby=Standby_normal is normal)
python manager_api_client.py -a get_oms_services --json

# Query the process list of the alarm node to find chronyd/ntpd processes
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> In the returned process list, look for `chronyd` and `ntpd` related processes.

> **The Manager API cannot directly view the NTP service mode (ResName column in ha-resource-status). Execute manually on the alarm node:**
> ```bash
> sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh
> ```
> If the "ResName" column in the output contains "chrony", the chrony mode is in use; if it contains "ntp", the ntp mode is in use.
> If both "chrony" and "ntp" appear simultaneously, the NTP service mode is being switched. Wait 10 minutes and check again.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| chrony mode (chronyd process exists) | Using chrony | Step 3 |
| ntp mode (ntpd process exists) | Using ntp | Step 4 |
| Both chrony and ntp appear | Mode is being switched | Wait 10 minutes and recheck |
| Neither chronyd nor ntpd process exists | **Root cause located**: NTP process not started -> Root cause 1 | — |
| ntp service HA status abnormal in get_oms_services (not Active_normal/Standby_normal) | **Root cause located**: NTP resource abnormal -> Root cause 1 | — |

---

### Step 3: Check chrony sync status

> **The Manager API cannot directly query chrony sync status. Execute manually on the alarm node:**
> ```bash
> # Check the chronyd service status
> systemctl status chronyd
> # View chrony sync status
> chronyc sources
> ```
> If the primary OMS node IP address is preceded by an asterisk "*", sync is normal; if there is no "*" before the IP and the "Reach" field is "0", sync is abnormal.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Sync normal ("*" before IP) | chrony sync normal | Step 5 |
| Sync abnormal (Reach is 0) | chrony sync abnormal | Step 5 |

---

### Step 4: Check NTP sync status

> **The Manager API cannot directly query NTP sync status. Execute manually on the alarm node:**
> ```bash
> # Check the ntpd service status
> systemctl status ntpd
> # View NTP sync status
> ntpq -np
> ```
> If the primary OMS node IP address is preceded by an asterisk "*", sync is normal; if there is no "*" before the IP and the "refid" field is ".INIT.", sync is abnormal.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Sync normal ("*" before IP) | NTP sync normal | Step 5 |
| Sync abnormal (refid is .INIT.) | NTP sync abnormal | Step 5 |

---

### Step 5: Check NTP authentication key consistency

> **The Manager API cannot directly read system configuration files. Execute manually on the alarm node:**
>
> **chrony mode:**
> ```bash
> # Get the chrony.keys content from the primary OMS node
> cat /etc/chrony.keys
> # Get the chrony.keys content from the alarm node
> cat /etc/chrony.keys
> ```
>
> **ntp mode:**
> ```bash
> # Get the ntpkeys content from the primary OMS node
> cat /etc/ntp/ntpkeys
> # Get the ntpkeys content from the alarm node
> cat /etc/ntp/ntpkeys
> ```
>
> Compare whether the key value with authentication key index "1M" is consistent.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Key values inconsistent | **Root cause located**: NTP authentication key mismatch -> Root cause 2 | — |
| Key values consistent | Key value normal | Step 6 |

---

### Step 6: Check firewall status

> **The Manager API cannot directly view firewall rules. Execute manually on the alarm node:**
> ```bash
> # Check firewall status
> systemctl status firewalld
> # or check iptables rules
> iptables -L -n
> ```
> Check whether any rules block NTP port (123) communication.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Firewall blocks NTP port | **Root cause located**: firewall blocking NTP sync -> Root cause 4 | — |
| Firewall no abnormality | Continue checking system resources | Step 7 |

---

### Step 7: Check system resources

```bash
# Query host CPU, memory, and disk metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min,dev_swap_used_ratio,dev_disk_useage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Insufficient system resources | **Root cause located**: insufficient system resources causing NTP abnormality -> Root cause 3 | — |
| Resources normal | Continue troubleshooting | Step 8 |

---

### Step 8: Check NTP-related logs

```bash
# Search the NTP check script logs (ntpChecker category of the Agent role)
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=ntpChecker.log' \
  --json

# View the search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords (e.g., `sync`, `fail`, `chrony`, `ntp`), run multiple searches separately, or append `-p 'log_file_name=ntpMonitor.log'` to view the NTP monitoring logs.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `sync` + `fail` / `ERROR` | NTP sync abnormality | Confirm with the sync status in Step 3/4 |
| `key` / `auth` + `fail` | NTP authentication abnormality | Confirm with the key value in Step 5 |
| No obvious errors | No clear error | Collect fault logs and contact O&M personnel |

## Common Root Causes and Repair Suggestions

### 1. NTP process not started

**Features**: chronyd or ntpd process does not exist; no corresponding process found in the NTP service mode check

**Repair suggestions**:
- Start the NTP service:
  - chrony mode: `systemctl start chronyd`
  - ntp mode: `systemctl start ntpd`
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 2. NTP authentication key mismatch

**Features**: The NTP authentication key values (index "1M") are inconsistent between the primary OMS node and the alarm node

**Repair suggestions**:
- Sync the key file content from the primary OMS node to the alarm node
- Restart the NTP service
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 3. Insufficient system resources causing NTP abnormality

**Features**: CPU load too high or insufficient memory/disk space

**Repair suggestions**:
- Clean up unnecessary log files or temporary files to free resources
- After resources are restored, restart the NTP service
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 4. Firewall blocking NTP sync

**Features**: Firewall rules block NTP port (123) communication

**Repair suggestions**:
- Disable the firewall or configure firewall rules to allow NTP port:
  - `systemctl stop firewalld` or `iptables -I INPUT -p udp --dport 123 -j ACCEPT`
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 5. Excessive time deviation

**Features**: The time deviation between the node and the primary OMS node is greater than or equal to 20 seconds

**Repair suggestions**:
- Manually correct the system time: `ntpdate <oms_master_ip>` or `chronyc makestep`
- After correction, wait for the next system detection cycle and check whether the alarm is automatically cleared

### 6. NTP server unreachable

**Features**: The alarm node cannot communicate with the NTP service on the primary OMS node

**Repair suggestions**:
- Check the network connectivity between nodes
- Check whether the firewall allows the NTP port (123)
- Use the `check_remote` API to test the remote node reachability

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-235-6 |
| `<oms_master_node>` | Primary OMS node name | 8-5-225-5 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
