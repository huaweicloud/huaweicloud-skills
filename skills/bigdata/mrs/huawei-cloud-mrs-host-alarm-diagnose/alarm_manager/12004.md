# OLdap Resource Abnormal (12004) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  +-- Accompanying alarms exist (12005/12010, etc.) -> Handle the accompanying alarms first
  +-- No accompanying alarms -> Step 2

Step 2: Check OLdap resource HA status
  |
  +-- oldap ResHAStatus abnormal -> Step 3
  +-- oldap ResHAStatus normal -> Step 4

Step 3: Check slapd process and port
  |
  +-- slapd process does not exist or port 21750 is not listening -> Root cause: OLdap process failure
  +-- slapd process exists and port is normal -> Step 5

Step 4: Check system resources
  |
  +-- Insufficient resources (CPU/memory/disk) -> Root cause: insufficient system resources causing OLdap abnormality
  +-- Resources normal -> Step 5

Step 5: Check HA script logs
  |
  +-- Log contains ERROR/Permission denied -> Match the root cause by log keyword
  +-- No obvious error -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

> The following API calls have front-to-back dependencies; the parameters of a later step need the return value of the previous step:

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information (HA mode, primary and standby status)
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Accompanying alarms exist (12005/12010, etc.) | Handle the accompanying alarms first | Refer to the corresponding alarm diagnosis |
| No accompanying alarms | Continue diagnosing the OLdap resource | Step 2 |

---

### Step 2: Check OLdap resource HA status

```bash
# Query OMS service status (including HA resource status)
python manager_api_client.py -a get_oms_services --json
```

> In the OMS service list returned by the Manager API, you can check the HA status of the oldap resource. For more detailed dual-node information:

> **The Manager API cannot directly obtain the complete output of status-oms.sh. Execute it manually on the alarm node:**
> ```bash
> sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh
> ```
> Check the "ResHAStatus" column of the "oldap" row:
> - Single-node mode: Normal
> - Dual-node mode: primary node Active_normal, standby node Standby_normal

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| oldap ResHAStatus is Normal/Active_normal/Standby_normal | OLdap resource HA status normal | Step 4 |
| oldap ResHAStatus abnormal | OLdap resource abnormal | Step 3 |

---

### Step 3: Check slapd process and port

```bash
# Query the process list of the alarm node to find the slapd process
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> In the returned process list, look for `slapd`-related processes and confirm whether the process exists and its status.

> **The Manager API cannot directly check port listening status. Execute manually on the alarm node:**
> ```bash
> netstat -anp | grep 21750
> # or
> lsof -i:21750
> ```
> Under normal conditions, a slapd process listening on port 21750 should exist.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| slapd process does not exist | **Root cause located**: OLdap process failure -> Root cause 1 | — |
| slapd process exists but port 21750 is not listening | **Root cause located**: OLdap process abnormal -> Root cause 1 | — |
| slapd process exists and port 21750 is listening normally | Process normal | Step 5 |

---

### Step 4: Check system resources

```bash
# Query host CPU, memory, and disk metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min,dev_swap_used_ratio,dev_disk_useage,dev_host_disk_usage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| CPU load too high or memory close to 100% | **Root cause located**: insufficient system resources causing OLdap abnormality -> Root cause 2 | — |
| Insufficient disk space | **Root cause located**: insufficient disk space causing OLdap abnormality -> Root cause 2 | — |
| Resources normal | Continue log troubleshooting | Step 5 |

---

### Step 5: Check HA script logs

```bash
# Browse the OLdap HA script logs
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=oldap' \
  -p 'path=/var/log/Bigdata/omm/oms/ha/scriptlog' \
  --json
```

```bash
# Browse the log (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/omm/oms/ha/scriptlog/oldap.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If you need to search for specific keywords:

```bash
# Search for error keywords in the OLdap HA logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

# View the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords (e.g., `Permission denied`, `Cannot find`), run multiple searches separately.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `Permission denied` | **Root cause located**: file permission issue -> Root cause 3 | — |
| `Cannot find` | **Root cause located**: configuration file missing -> Root cause 3 | — |
| `ERROR` / `Failed` | OLdap resource startup/runtime failure -> Root cause 1 | — |
| None of the above keywords | No obvious error | Step 6 |

---

### Step 6: Check OmmServer logs

```bash
# Browse OmmServer logs
> **Note**: `/var/log/Bigdata/omm/oms/server/*.log*` are process GC/directory-level logs. Manager browse_log does not support wildcards. Execute manually on the node:
> ```bash
> tail -n 200 /var/log/Bigdata/omm/oms/server/.log*
> ```
```

> If you need to search for specific keywords:

```bash
# Search for OLdap-related exceptions in the OmmServer logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=ldap' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords (e.g., `slapd`, `OLdap`), run multiple searches separately.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `ldap` + `ERROR` / `exception` | **Root cause located**: OLdap connection exception -> Root cause 1 | — |
| `slapd` + `ERROR` | **Root cause located**: slapd process exception -> Root cause 1 | — |
| None of the above keywords | No obvious error | Collect fault logs and contact O&M personnel |

## Common Root Causes and Repair Suggestions

### 1. OLdap process failure

**Features**: slapd process does not exist or port 21750 is not listening; HA status abnormal

**Repair suggestions**:
- Log in to the Manager node as the omm user
- Find the ldap process PID: `ps -ef | grep slapd | grep -v grep`
- Terminate the abnormal ldap process: `kill -2 <ldap_pid>`, wait 20 seconds for HA to automatically restart the OLdap process
- Re-execute `status-oms.sh` to check whether the OLdap resource status is restored
- If not restored, check the HA script logs for the specific cause

### 2. Insufficient system resources causing OLdap abnormality

**Features**: CPU load too high, memory close to 100%, or insufficient disk space; slapd process may be killed by OOM

**Repair suggestions**:
- Clean up unnecessary log files or temporary files to free disk space
- Check whether other processes are consuming excessive memory
- After resources are restored, execute `kill -2 <ldap_pid>` to restart the OLdap process
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 3. File permission or configuration issue

**Features**: HA log contains `Permission denied` or `Cannot find`

**Repair suggestions**:
- Fix file permissions: `chown omm:omm <file_path>` and `chmod 755 <directory>`
- Check the LdapServer configuration under the `${BIGDATA_HOME}/om-server/om/` path
- After processing, re-execute `kill -2` to restart the OLdap process

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (Manager node) | 8-5-225-5 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
