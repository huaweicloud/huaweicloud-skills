# HA Resource Abnormal (2.x and Earlier Versions) (12002) Alarm Diagnosis Skill

> **Note**: This alarm is a legacy alarm for MRS 2.x and earlier versions. In the current version (MRS 3.x+), this alarm has been split into independent alarms for each HA resource (e.g., 12004 OLdap Resource Abnormal, 12005 OKerberos Resource Abnormal, 12012 NTP Service Abnormal, etc.). The diagnosis logic is consistent with HA resource status checking.

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  v
Step 2: Query the HA status of each OMS resource
  |
  +-- HA resource status abnormal -> Step 3
  +-- All HA resource statuses normal -> Step 4

Step 3: Locate the abnormal HA resource and check the corresponding HA logs
  |
  +-- Log contains ERROR/Permission denied -> Match the root cause by log keyword
  +-- No obvious error -> Step 4

Step 4: Check system resources
  |
  +-- Insufficient resources (CPU/memory/disk) -> Root cause: insufficient system resources
  +-- Resources normal -> Collect fault logs and contact O&M personnel

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information (HA mode, primary and standby nodes)
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> Confirm the alarm location information (source/service name/hostname) to determine which HA resource is abnormal. In the current version, this alarm has typically been replaced by specific resource alarms such as 12004/12005/12012. If this alarm is received, locate the specific abnormal resource in combination with accompanying alarms.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Accompanying alarms exist (12004/12005/12012, etc.) | Diagnose based on the specific resource alarm | Refer to the corresponding alarm diagnosis |
| No accompanying alarms | Continue checking HA resource status | Step 2 |

---

### Step 2: Query the HA status of each OMS resource

```bash
# Query the HA status of all services in OMS
python manager_api_client.py -a get_oms_services --json
```

> In the returned result, check the HA status of each resource one by one (haMode/activeStatus/standbyStatus):
> - `haMode=ACTIVE_STANDBY` (dual-node): active=Active_normal, standby=Standby_normal is normal
> - `haMode=SINGLE_ACTIVE` (single-node): active=Normal, standby=Stopped is normal
> - In the current cluster, all resource statuses are normal: okerberos/oldap/ntp/gaussDB are ACTIVE_STANDBY (Active_normal/Standby_normal), controller/aos/tomcat/httpd/fms/disaster/acs/floatip/iam/pms are SINGLE_ACTIVE (Normal/Stopped)

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Resource status abnormal | **Root cause located**: corresponding HA resource abnormal | Step 3 |
| All resource statuses normal | HA status normal | Step 4 |

---

### Step 3: Check the HA script logs of the abnormal resource

Based on the abnormal resource name identified in Step 2 (e.g., okerberos/oldap/ntp), search the corresponding HA script logs:

```bash
# Search the HA script logs for the abnormal resource (OmmServer role, replace log_file_name with the resource name)
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:OmmServer' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=<ha_log_file_name>' \
  --json

# View the search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> **Mapping between HA log file names and resources** (under the OmmServer role in the /var/log/Bigdata/omm/oms/ha/scriptlog/ directory):
>
> | Abnormal resource | log_file_name |
> |----------|---------------|
> | okerberos | okerberos.log |
> | oldap | oldap.log |
> | ntp | ha_ntp.log |
> | httpd | httpd.log |
> | tomcat | tomcat.log |
> | Others (general HA runtime logs) | ha.log (/var/log/Bigdata/omm/oms/ha/runlog/) |

> If you need to search multiple keywords (e.g., `Permission denied`, `Cannot find`, `Failed`), run multiple searches separately.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `Permission denied` | **Root cause located**: file permission issue -> Root cause 3 | — |
| `Cannot find` / `No such file` | **Root cause located**: configuration file missing -> Root cause 3 | — |
| `ERROR` / `Failed` | HA resource startup/runtime failure -> Root cause 1 | — |
| `No space left on device` | **Root cause located**: insufficient disk space -> Root cause 2 | — |
| None of the above keywords | No obvious error | Step 4 |

---

### Step 4: Check system resources

```bash
# Query host CPU, memory, and disk metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min,dev_swap_used_ratio,dev_disk_useage,dev_host_disk_usage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| CPU load too high or memory close to 100% | **Root cause located**: insufficient system resources causing HA resource abnormality -> Root cause 2 | — |
| Insufficient disk space | **Root cause located**: insufficient disk space -> Root cause 2 | — |
| Resources normal | Continue troubleshooting | Collect fault logs and contact O&M personnel |

## Common Root Causes and Repair Suggestions

### 1. HA resource process/service failure

**Features**: In get_oms_services, a resource HA status is abnormal; the corresponding HA log contains ERROR/Failed

**Repair suggestions**:
- Log in to the Manager node as the omm user
- Check the process status of the abnormal resource: `ps -ef | grep <resource_name>` (e.g., `ps -ef | grep okerberos`)
- Execute `kill -2 <abnormal_process_pid>` to terminate the abnormal process, wait 20 seconds for HA to automatically restart
- Re-execute `get_oms_services` or `status-oms.sh` to check whether the resource status is restored
- If not restored, check the corresponding HA script logs for the specific cause

**Notes**:
- `kill -2` is a graceful termination; HA will detect the resource abnormality and automatically restart it. Do not use `kill -9` directly
- Some resources (e.g., oldap/okerberos) have dependencies; the depended-on resource must be restored first

### 2. Insufficient system resources causing HA resource abnormality

**Features**: CPU load too high, memory close to 100%, or insufficient disk space; HA resources may be killed by OOM

**Repair suggestions**:
- Clean up unnecessary log files or temporary files to free disk space
- Check whether other processes are consuming excessive memory
- After resources are restored, execute `kill -2 <abnormal_process_pid>` to restart the corresponding HA resource
- Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 3. File permission or configuration issue

**Features**: HA log contains `Permission denied` or `Cannot find`

**Repair suggestions**:
- Fix file permissions: `chown omm:omm <file_path>` and `chmod 755 <directory>`
- Check whether the configuration file of the corresponding resource is complete
- After processing, re-execute `kill -2` to restart the corresponding HA resource

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (Manager node) | 8-5-235-6 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |
| `<ha_log_file_name>` | HA log file name corresponding to the abnormal resource (see the mapping table in Step 3) | okerberos.log |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
