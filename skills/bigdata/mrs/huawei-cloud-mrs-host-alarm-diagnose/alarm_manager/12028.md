# Host D-State and Z-State Process Count Exceeds Threshold (12028) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm the alarm and instance status
  |
  +-- Instance normal -> Check monitoring metric trends
  +-- Instance abnormal -> Step 2
Step 2: Check host resource metrics
  |
  +-- Metrics abnormal -> Resource bottleneck
  +-- Metrics normal -> Step 3
Step 3: Manually check system logs
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | Instance status | `get_host_process` | Confirm whether process exists |

---

## Diagnosis Steps

### Step 1: Confirm the alarm and instance status

```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query OMS instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=OMS' \
  --json
```

```bash
# Query host process status
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Instance status normal | Alarm may have been restored or is a metric-type alarm | Step 2 |
| Instance status abnormal | Service abnormal | Step 2 |
| Accompanying alarms exist | Handle the accompanying alarms first | Refer to the corresponding alarm diagnosis |

---

### Step 2: Check host resource metrics

```bash
# Query host monitoring metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min' \
  --json
```

```bash
# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion |
|----------|------|
| Metrics abnormal | Resource bottleneck causing the alarm |
| Metrics normal | Continue log troubleshooting |

---

### Step 3: Manually check system logs

> **The Manager API cannot directly access system log directories (such as /var/log/messages). Execute manually on the alarm node:**
> - Check keywords in `/var/log/messages`: ERROR / oom / killed process / I/O error / segfault

---

## Common Root Causes and Repair Suggestions

### 1. Resource metrics exceed threshold

**Repair suggestions**:
- Perform targeted handling based on the specific exceeded metric
- Clean up resources or expand capacity

### 2. Insufficient disk space

**Features**: Log contains `no space left` / `No space left on device`

**Repair suggestions**:
- Clean up log files and temporary files
- Expand disk capacity

### 3. Configuration or file permission abnormality

**Features**: Log contains `Permission denied` / `cannot open`

**Repair suggestions**:
- Check relevant file permissions
- After fixing permissions, wait 5 minutes

### 4. Network or connectivity issue

**Features**: Log contains `connection refused` / `timeout`

**Repair suggestions**:
- Check network connectivity between nodes
- Use the `check_remote` API to test remote node reachability
