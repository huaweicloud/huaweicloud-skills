# `Slow Disk Handling Timeout`(12207) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  │
  ▼
Step 2: Query slow disk isolation information
  │
  ├─ Disk in isolation state timed out → Root cause: Disk isolation timeout
  ├─ Node in isolation state timed out → Root cause: Node isolation timeout
  └─ No isolation record → Alarm may have recovered

Step 3: Check alarm node connectivity
  │
  ├─ Node unreachable → Root cause: Alarm node unreachable
  └─ Node reachable → Step 4

Step 4: View Controller logs (check slow disk handling timeout cause)
  │
  ├─ Logs contain ERROR/isolation → Match root cause by log keywords
  └─ No obvious error → Step 5

Step 5: View NodeAgent logs and disk status
  │
  ├─ Logs contain ERROR/isolate → Root cause: Node-side isolation failure
  ├─ Alarm disk not present in df -h → Root cause: Disk lost
  └─ No abnormality → Collect fault logs and contact operations

> Once a root cause is identified, jump directly to "Common Root Causes and Repair Suggestions" without proceeding to subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full log file path | `browse_log` | `file_name` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> Obtain the alarm node name, host name, disk name, and slow disk isolation description from the alarm details.

---

### Step 2: Query slow disk isolation information

```bash
# Query slow disk isolation information
python manager_api_client.py -a get_disk_isolation \
  -p 'cluster_id=<cluster_id>' \
  -p 'host_name=<node_name>' \
  --json
```

> diskStatus values:
> - 0=Pending isolation
> - 1=Isolating
> - 2=Auto-isolation aborted
> - 3=Isolated
> - 4=Isolation released
> - 5=Isolation failed
> - 6=Release isolation failed
> - 7=Node isolated
> - 10=Recovered

> A disk or node is considered to have timed out if it remains in any of the following states for more than 10 hours without change:
> - Disk: Auto-isolation aborted (2), Isolated (3), Isolation failed (5), Release isolation failed (6)
> - Node: Isolated (7), Isolation failed (5), Cancel isolation failed (6), Node startup failed, Isolation released (4)

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Disk in isolation state and timed out | **Root cause identified**: Disk isolation handling timeout → Root cause 1 | — |
| Node in isolation state and timed out | **Root cause identified**: Node isolation handling timeout → Root cause 2 | — |
| Isolation failed | **Root cause identified**: Isolation/release isolation failure → Root cause 3 | — |
| No isolation record or status normal | Alarm may have recovered | Check whether the alarm is automatically cleared |

---

### Step 3: Check alarm node connectivity

```bash
# Test alarm node connectivity
python manager_api_client.py -a check_remote \
  -p 'remote_ip=<alarm_node_ip>' \
  -p 'remote_port=22' \
  -p 'remote_user_name=root' \
  -p 'remote_client_path=/opt/client' \
  --json
```

> Alternatively, run manually on the OMS master node:
> ```bash
> ping <alarm_node_ip>
> ```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Node unreachable | **Root cause identified**: Alarm node unreachable → Root cause 4 | — |
| Node reachable | Continue checking logs | Step 4 |

---

### Step 4: View Controller logs (check slow disk handling timeout cause)

```bash
# Browse Controller logs (on the master OMS node)
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=controller_root' \
  -p 'path=/var/log/Bigdata/controller' \
  --json
```

```bash
# Browse logs (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/controller_root.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> To search for specific keywords:

```bash
# Search for slow disk isolation related logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=isolation' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=INFO' \
  --json

# View the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> To search for multiple keywords (e.g., `isolate`, `fence`, `unfence`, `timeout`, `ERROR`), perform multiple searches.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `isolate` + `ERROR` / `timeout` | **Root cause identified**: Disk isolation operation timeout → Root cause 1 | — |
| `fence` + `ERROR` / `timeout` | **Root cause identified**: Node isolation operation timeout → Root cause 2 | — |
| `unfence` + `ERROR` / `fail` | **Root cause identified**: Release isolation failure → Root cause 3 | — |
| None of the above keywords | No obvious error | Step 5 |

---

### Step 5: View NodeAgent logs and disk status

```bash
# Browse NodeAgent logs (on the alarm node)
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=agent' \
  -p 'path=/var/log/Bigdata/nodeagent/agentlog' \
  --json
```

```bash
# Browse logs (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/nodeagent/agentlog/agent.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> To search NodeAgent logs for keywords:

```bash
# Search for isolation-related errors in NodeAgent logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=isolate' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=WARN' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> **Also check whether the alarm disk exists. Run the following manually on the alarm node:**
> ```bash
> df -h
> ```
> If the command output does not include the alarm disk name, the disk has been lost. Refer to the 12014 device partition loss alarm handling.

```bash
# Query host disk metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_disk_util,dev_disk_read_byte_speed,dev_disk_write_byte_speed' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| NodeAgent logs contain `isolate` + `ERROR` | **Root cause identified**: Node-side isolation failure → Root cause 3 | — |
| Alarm disk not present in df -h | **Root cause identified**: Disk lost → Refer to 12014 | — |
| No abnormality | No obvious error | Collect fault logs and contact operations |

## Common Root Causes and Repair Suggestions

### 1. Disk isolation operation timeout

**Features**: Disk status in alarm details is "Isolated", "Isolation failed", or "Auto-isolation aborted"; Controller logs show disk isolation-related operations timed out or failed

**Repair suggestions**:
- Review Controller logs to confirm the specific cause of disk isolation timeout
- Review `df -h` output to confirm whether the alarm disk exists
- Based on the current disk status, manually perform the corresponding isolation or release isolation operation:
  - If disk status is "Isolated", perform release isolation operation
  - If disk status is "Isolation failed" or "Auto-isolation aborted", re-execute isolation operation
  - If disk status is "Release isolation failed", re-execute release isolation operation
- Wait 5 minutes after command execution to check whether the alarm is cleared
- If not cleared, collect fault log information and contact operations personnel

### 2. Node isolation operation timeout

**Features**: Node status in alarm details is "Isolated", "Isolation failed", "Cancel isolation failed", "Node startup failed", or "Isolation released"; Controller logs show node isolation-related operations timed out or failed

**Repair suggestions**:
- Review Controller logs to confirm the specific cause of node isolation timeout
- Review NodeAgent logs to confirm whether there are errors on the node side
- Based on the current node status, manually perform the corresponding isolation or release isolation operation:
  - If node status is "Isolated", perform cancel isolation operation
  - If node status is "Isolation failed", re-execute isolation operation
  - If node status is "Cancel isolation failed", re-execute cancel isolation operation
  - If node status is "Node startup failed", re-execute node startup operation
  - If node status is "Isolation released", confirm whether the node status has returned to normal
- Wait 5 minutes after command execution to check whether the alarm is cleared
- If not cleared, collect fault log information and contact operations personnel

### 3. Disk/node release isolation failure

**Features**: Disk or node status in alarm details is "Release isolation failed" or "Cancel isolation failed"; Controller or Agent logs show release isolation operation failed

**Repair suggestions**:
- Review Controller and NodeAgent logs to confirm the specific cause of release isolation failure
- Check alarm node connectivity to confirm whether the node is reachable
- Re-execute release isolation operation
- Wait 5 minutes after command execution to check whether the alarm is cleared
- If not cleared, collect fault log information and contact operations personnel

### 4. Alarm node unreachable

**Features**: Alarm node cannot be pinged; network connectivity test failed

**Repair suggestions**:
- Contact network/hardware administrator to troubleshoot node failure
- After node recovery, wait for the next system detection cycle to check whether the alarm is automatically cleared

### 5. Alarm cannot be cleared

**Features**: After handling, the disk or node status has changed but the alarm persists

**Repair suggestions**:
- Confirm whether the current disk or node status has returned to normal
- Wait for the next system detection cycle (10 minutes) to confirm whether the alarm is automatically cleared
- Collect Controller and NodeAgent service logs (10 minutes before and after the alarm)
- Contact operations personnel to send fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name | 8-5-225-6 |
| `<oms_master_node>` | OMS master node name | 8-5-225-5 |
| `<alarm_node_ip>` | Alarm node IP address | 10.0.0.101 |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
