# System in Upgrade Observation Period (12087) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm alarm
  |
  v
Step 2: Collect Controller logs (check upgrade-related logs)
  |
  +-- Logs contain upgrade/UpdateTool related errors -> Match root cause by log keywords
  +-- No obvious errors -> Step 3

Step 3: Confirm system upgrade observation period status
  |
  +-- upgradObservationPeriod isON=true -> Root cause: Upgrade observation period timeout
  +-- upgradObservationPeriod isON=false -> Alarm may have recovered

> After identifying the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing to subsequent steps.
```

## API Call Chain Dependencies

| Previous API | Return fields | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full log file path | `browse_log` | `file_name` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

---

### Step 2: Collect Controller logs (check upgrade-related logs)

```bash
# Browse Controller logs
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=controller_root' \
  -p 'path=/var/log/Bigdata/controller' \
  --json
```

```bash
# Browse log (using exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/controller_root.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> To search for specific keywords:

```bash
# Search upgrade-related logs
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=upgrade' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=WARN' \
  --json

# Check search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> To search for multiple keywords (such as `UpdateTool`, `ERROR`, `WARN`), run multiple searches.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `upgrade` + `ERROR` | Upgrade process anomaly | Step 3 |
| `UpdateTool` + `ERROR` | Upgrade tool execution anomaly | Step 3 |
| None of the above keywords | No clear error | Step 3 |

---

### Step 3: Confirm system upgrade observation period status

> **The Manager API cannot directly view the upgrade observation period status. Manually execute on the active OMS node:**
> ```bash
> # Log in to the active management node as root, then switch to the omm user
> su - omm
>
> # Log in to the omm database
> gsql -U omm -W <omm_database_password> -p 20015
> ```
> Execute the following SQL query to obtain cluster information:
> ```sql
> select * from OM_CLUSTERS;
> ```
> Check the `upgradObservationPeriod isON` value in the query results:
> - If `true`, the system is currently in the upgrade observation period; use the UpdateTool to commit or roll back the upgrade
> - If `false`, the system is not currently in the upgrade observation period

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| upgradObservationPeriod isON=true and exceeds the reserved time | **Root cause identified**: Upgrade observation period timeout -> Root cause 1 | — |
| upgradObservationPeriod isON=false | The alarm may have recovered | Check whether the alarm is automatically cleared |

## Common Root Causes and Repair Suggestions

### 1. Upgrade observation period timeout

**Feature**: The system is in the upgrade observation period (upgradObservationPeriod isON=true), and the time elapsed since entering the upgrade observation period exceeds the reserved time (default 10 days)

**Repair suggestions**:
- Evaluate whether the system is running normally after the upgrade
- If the system is running normally, execute the upgrade commit operation to exit the upgrade observation period:
  1. Use the UpdateTool to execute the upgrade commit (refer to the upgrade guide for the corresponding version)
  2. After committing, the system exits the upgrade observation period and the alarm is automatically cleared
- If there are issues with the upgrade, execute the rollback operation:
  1. Use the UpdateTool to execute the upgrade rollback (refer to the upgrade guide for the corresponding version)
  2. After rollback, the system exits the upgrade observation period and the alarm is automatically cleared
- After completing the operation, wait until the next day's early morning to verify whether the alarm is cleared

### 2. Upgrade observation period impact

**Feature**: During the upgrade observation period, operations that affect the management topology (such as adding or deleting users, instances, roles, services, hosts, and resource pools) are prohibited

**Repair suggestions**:
- If management operations need to be performed, first complete the upgrade commit or rollback to exit the upgrade observation period
- After exiting the upgrade observation period, the prohibited topology operations will be restored

### 3. Alarm cannot be cleared

**Feature**: The system is not in the upgrade observation period or the alarm persists after the upgrade commit

**Repair suggestions**:
- Collect Controller service logs (10 minutes before and after the alarm)
- Contact O&M personnel and send the fault log information

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Alarm node name (active OMS node) | 8-5-225-5 |
| `<omm_database_password>` | omm database password (consult the system administrator) | — |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
