# CPU Usage Exceeds Threshold (12016) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Confirm CPU load
  |
  ├─ iowait significantly high (>20%) → Step 5: disk-io
  │     |
  │     ├─ iowait high + disk await/util high → Root cause: disk IO bottleneck
  │     └─ No disk IO anomaly → Continue to Step 2 to investigate other causes
  |
  ├─ Load < number of cores (normal), alarm recovered → Alarm-recovered branch
  │                                |
  │                                First step: infer the process at that time from alarm info + messages
  │                                  |
  │                                  Second step: look up the GC log by process name
  │                                    |
  │                                    ├─ Frequent Full GC → Root cause: GC
  │                                    ├─ OOM → Root cause: insufficient memory
  │                                    └─ No anomaly → Summarize the current state and suggest observation
  |
  └─ Load >= number of cores (high load) → Step 2: high-CPU process
                     |
                     |  Handle each high-CPU process separately:
                     |
                     ├─ Java process ──→ Step 3: jstack thread analysis
                     |                 |
                     |                 ├─ GC-related threads present ("GC task#"/"G1 Conc#" etc. for G1; "Gang worker#" etc. for CMS)
                     |                 |      and that process has high CPU in Step 2 ──→ Step 4: GC log → locate root cause
                     |                 ├─ Many BLOCKED threads ──→ Root cause: lock contention → end
                     |                 ├─ Same stack frame repeatedly appears ──→ Root cause: infinite loop → end
                     |                 └─ Many RUNNABLE threads whose stack frames are business code ──→ Step 4: check GC
                     |                      └─ GC normal ──→ Root cause: business peak/inefficient task → end
                     |
                     ├─ Non-Java process ──→ Step 6: non-Java process analysis → locate root cause
                     |
                     └─ Root cause not located ──→ Step 5: supplementary checks (as needed)

> Once the root cause is found, jump directly to "Common Root Causes and Repair Suggestions" without continuing with the subsequent steps.
```

## API Call Chain Dependencies

> The following API calls have forward-backward dependencies; the parameters of a later step require the return values of the previous step:

| Previous-step API | Return field | Next-step API | Parameter |
|-------------------|--------------|---------------|-----------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full path of the log file | `browse_log` | `file_name` |
| `get_host_process` | Process name/type | Step 3 or Step 6 | Determines the subsequent diagnosis direction (Java→Step 3, non-Java→Step 6) |
| `collect_instance_stack`/`collect_role_stack` | `taskID` | `get_stack_progress` | `task_id` (to check collection progress) |

> The `file_name` parameter of `browse_log` must be the full path of the log file (e.g. `/var/log/Bigdata/tomcat/tomcat_gc.log`). Relative paths or file names are not supported.

## Diagnosis Steps

### Step 1: Confirm CPU load

```bash
# Query host CPU usage, load and other metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_cpu_us,dev_cpu_sy,dev_load_one_min,dev_load_five_min,dev_load_fifteen_min' \
  --json
```

> If Manager does not have monitoring metrics at this granularity, supplement with `get_host_resource`:

```bash
# Query host resource information (CPU/memory/disk usage of each service)
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|---------------|------------|-----------|
| iowait > 20% | High CPU may be caused by a disk IO bottleneck, but this needs to be verified | Step 5 (disk-io); if there is no IO anomaly, continue with Step 2 |
| Load > number of cores (overloaded) | Alarm is ongoing | Step 2 |
| Load ≈ number of cores (saturated) | Alarm is ongoing | Step 2 |
| Load < number of cores (normal), alarm recovered | Need to investigate from historical traces | "Alarm-recovered" branch below |

### Investigation branch when the alarm has recovered

Once the alarm has recovered, historical `top` cannot be retrieved. Investigate in the following order:

#### First step: obtain clues about the high-CPU process at that time

Determine the abnormal process at that time from the following sources (in order of priority):
1. Whether the **alarm details** contain a process name or service name
2. OOM/killed process records in the **messages log**
3. **User confirmation** — directly ask the user which service may have been abnormal at that time

```bash
# Browse the messages log
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/messages' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If `browse_log` does not support directly browsing `/var/log/messages`, the log-search interface can be used instead:

```bash
# Search for OOM/killed records in messages
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=oom' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Agent' \
  -p 'min_log_level=WARN' \
  -p 'log_file_name=messages' \
  --json

# Check search progress and results
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If multiple keywords need to be searched, they can be searched in several separate searches (`keyWord` does not support command-injection characters such as `|`).
> The `services` format is `component:service:role`; the available services can be queried via `get_log_search_support_services`.
> The `start_time`/`end_time` format is: `yyyy-MM-ddTHH:mm:ss`.

#### Second step: look up the GC log by process name

Based on the process name obtained in the first step, browse the corresponding GC log:

```bash
# Browse the GC log
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=<gc_log_path>' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If the GC log file name is uncertain, first query the available log files:

```bash
# Query the log file names of the specified service
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=<gc_log_category>' \
  -p 'path=<gc_log_dir>' \
  --json
```

> `category_name` is the log category name and `path` is the log directory. Both can be obtained by querying the `name` and `path` of the corresponding categories via `get_log_search_support_services`. The mapping is as follows:

**Process name and GC log `category_name`, path mapping**:

| Process name | category_name | path | GC format | Remarks |
|--------------|---------------|------|-----------|---------|
| tomcat | tomcat_gc | /var/log/Bigdata/tomcat | JDK11+ `-Xlog:gc*` | Rotating files: .log/.log.0/.log.1... |
| pms | pms_gc | /var/log/Bigdata/oms | JDK11+ `-Xlog:gc*` | File name contains date/time stamp |
| controller | oms_gc | /var/log/Bigdata/controller | JDK11+ `-Xlog:gc*` | Rotating files: .log/.log.0/.log.1... |
| acs | — | — | — | **No GC log output**; only ErrorFile and HeapDump |
| nodeagent | agent_gc | /var/log/Bigdata/nodeagent | JDK11+ `-Xlog:gc*` | File name contains time stamp |
| metric_agent | gc | /var/log/Bigdata/metric_agent | JDK11+ `-Xlog:gc*` | This directory may not exist on some nodes |
| disaster | disaster_gc | /var/log/Bigdata/disaster | JDK11+ `-Xlog:gc*` | |
| cep | cep_gc | /var/log/Bigdata/cep | JDK8 `-Xloggc` | This directory may not exist on some nodes |
| hdfs-nn | namenode-omm-gc | /var/log/Bigdata/hdfs/nn | JDK8 CMS | Exists only on the node where NameNode resides |
| hdfs-dn | datanode-omm-gc | /var/log/Bigdata/hdfs/dn | JDK8 CMS | Exists only on the node where DataNode resides |
| yarn-rm | resourcemanager-omm-gc | /var/log/Bigdata/yarn/rm | JDK8 CMS | Exists only on the node where ResourceManager resides |
| yarn-nm | nodemanager-omm-gc | /var/log/Bigdata/yarn/nm | JDK8 CMS | Exists only on the node where NodeManager resides |

> **JDK11+ `-Xlog:gc*` format**: the log line format is `[2026-07-13T14:52:24.801+0800][gc,start] GC(0) Pause Young (Normal)...`
>
> **JDK8 `-Xloggc` format**: the log line format is `2026-07-13T14:52:24.801+0800: GC pause (young)...`
>
> **ACS has no GC log**: if high CPU is located to an acs process, it cannot be investigated through the GC log; you must directly use jstack to analyze the thread state.

**GC keywords are selected by format**:

| GC format | Search keywords | Description |
|-----------|-----------------|-------------|
| JDK11+ `-Xlog:gc*` (G1) | `Pause`, `Full`, `OutOfMemoryError`, `Metadata GC Threshold` | Both G1 Young and Old GC contain the `Pause` keyword |
| JDK8 CMS `-Xloggc` | `Full GC`, `Concurrent mode failure`, `OutOfMemoryError`, `Metadata GC Threshold` | CMS-specific `Concurrent mode failure` |

**You can also search GC keywords directly through the log-search interface**:

```bash
# Search for key events in the GC log (fill in `services` with the component the high-CPU process belongs to, e.g. HDFS:HDFS:NameNode)
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=Pause Full' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=<component:service:role>' \
  -p 'min_log_level=INFO' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If multiple keywords need to be searched, they can be searched in several separate searches (`keyWord` does not support command-injection characters such as `|`).
> The `services` format is `component:service:role` (e.g. `HDFS:HDFS:NameNode`); the available services can be queried via `get_log_search_support_services`.

### Step 2: Find the high-CPU process

```bash
# Query the host process list (includes PID, process name, status)
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

> **If `get_host_process` returns 500** (NodeAgent communication anomaly), degrade to using `get_host_resource` to obtain service-level CPU usage:

```bash
# Degradation: query host resource information (CPU/memory/disk usage of each service, no PID)
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> `get_host_resource` returns service-level `cpuUsage`/`memoryUsage`/`diskUsage`, which can locate which service has high CPU, but **does not provide the process PID or process-level details**. If a PID is needed, you must manually execute `ps aux --sort=-%cpu | head -20` on the alarm node.

**Analysis**: view the Top5 processes (or services) in descending order of CPU usage to determine which process is consuming high CPU. Handle each of the **top 5** high-CPU processes separately by type:

| Process type | Next step |
|--------------|-----------|
| Java process (tomcat/pms/controller/acs, etc.) | Step 3 |
| Non-Java system process (collectd/rsyslog/kswapd0, etc.) | Step 6 |
| Root cause still not located after analyzing each one | Step 5 (supplementary checks) |

### Step 3: Java process thread analysis

For the high-CPU Java process confirmed in Step 2, collect the jstack thread dump:

```bash
# Collect instance-level jstack
python manager_api_client.py -a collect_instance_stack \
  -p 'service_name=<service_name>' \
  -p 'instance_ids=[<instance_id>]' \
  -p 'stack_types=["JSTACK"]' \
  -p 'stack_file_size_limit=100' \
  -p 'stack_file_count=5' \
  -p 'use_live=false' \
  -p 'stack_file_save_path=/var/log/Bigdata/stack' \
  -p 'collect_timeout=300' \
  --json

# Or collect role-level jstack
python manager_api_client.py -a collect_role_stack \
  -p 'service_name=<service_name>' \
  -p 'role_names=["<role_name>"]' \
  -p 'stack_types=["JSTACK"]' \
  -p 'stack_file_size_limit=100' \
  -p 'stack_file_count=5' \
  -p 'use_live=false' \
  -p 'stack_file_save_path=/var/log/Bigdata/stack' \
  -p 'collect_timeout=300' \
  --json
```

> The collection command returns `{"taskID": "xxx"}`. Use this `taskID` to query the collection progress:

```bash
# Query the stack collection progress (task_id comes from the taskID returned in the previous step)
python manager_api_client.py -a get_stack_progress \
  -p 'service_name=<service_name>' \
  -p 'task_id=<taskID>' \
  --json
```

> Once `taskState` is `COMPLETE`, view the jstack output file through the log interface:

```bash
# Query the jstack output log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=jstack' \
  -p 'path=/var/log/Bigdata/stack' \
  --json
```

> `category_name` is the log category name (here it is `jstack`). If the category name is uncertain, it can be obtained by querying `categorys[].name` via `get_log_search_support_services`.

```bash
# Browse the jstack output
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=<jstack_log_path>' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If the Manager API does not support jstack collection, you can also obtain the log bundle through the `gather_log` interface and then view it:

```bash
# Collect the service log bundle
python manager_api_client.py -a gather_log \
  -p 'cluster_name=<cluster_name>' \
  -p 'services=<service_name>:<role_name>' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  --json
```

**Analysis points**:

- jstack itself does not contain CPU-usage information; it must be combined with that process's CPU usage from Step 2 for a comprehensive judgment
- Search the complete jstack output for GC-related thread names:
  - **G1 GC** (JDK11+ default): `"GC task#"` or `"G1 Main Marker"` or `"G1 Conc#"`
  - **CMS GC** (JDK8): `"GC task#"` or `"Gang worker#"` or `"Concurrent Mark-Sweep GC Thread"`
  - Common: `"GC Daemon"`

| jstack thread characteristic | Conclusion | Next step |
|------------------------------|------------|-----------|
| GC-related threads present and that process has high CPU in Step 2 | Suspected high CPU caused by GC | Step 4 (GC log confirmation) |
| Many BLOCKED threads | Thread lock contention | **Root cause located** → common root cause No. 2 |
| Same stack frame repeatedly appears | Infinite loop or busy wait | **Root cause located** → common root cause No. 2 |
| Many RUNNABLE threads whose stack frames are business code | High business load or GC problem | Step 4 (rule out GC first) |

### Step 4: GC log check

Based on the Java process name confirmed in Step 2/3, browse the corresponding GC log (see the mapping in "Alarm-recovered" second step).

```bash
# Browse the GC log (latest content)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=<gc_log_path>' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

```bash
# Search for key events in the GC log (fill in `services` with the component the high-CPU process belongs to, e.g. HDFS:HDFS:NameNode)
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=Pause Full' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=<component:service:role>' \
  -p 'min_log_level=INFO' \
  --json

python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If other keywords need to be searched (such as `OutOfMemoryError`, `Concurrent mode failure`), they can be searched in several separate searches.

**Analysis**:

| GC log characteristic | Conclusion |
|----------------------|------------|
| **G1 format**: `Pause Full` or contains the `Full` keyword and lasts a long time | **Root cause located**: G1 Full GC causes high CPU; the root cause is usually insufficient memory or large-object allocation |
| **G1 format**: `Pause Young` is frequent but each pause is not long | Frequent Young GC may indicate an excessively high allocation rate, which is not a serious problem; it is suggested to observe |
| **CMS format**: `Full GC` is frequent and lasts a long time | **Root cause located**: CMS Full GC causes high CPU |
| **CMS format**: `Concurrent mode failure` | **Root cause located**: the CMS concurrent collection failed and degraded into Full GC |
| Common: `OutOfMemoryError` | **Root cause located**: a memory overflow causes repeated Full GC |
| Common: `Metadata GC Threshold` | **Root cause located**: insufficient metaspace triggers Full GC |
| GC normal | Not a GC problem; high CPU may be due to a business peak or an inefficient task |

### Step 5: Supplementary checks (as needed)

When Steps 2-4 do not locate a clear root cause, execute the following checks **as needed** (choose according to the phenomenon):

```bash
# View the host process list (includes zombie/D-state processes)
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json

# View host resource information (memory, swap, etc.)
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json

# Query host disk IO and disk usage metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_read_byte_speed,dev_disk_write_byte_speed,dev_disk_useage,dev_disk_util,dev_swap_used_ratio,dev_file_used_ratio' \
  --json
```

> The Manager API provides snapshot metrics, which cannot replace the real-time statistics of `iostat -x 1 3`. If real-time IO statistics or process-level diagnosis (fd count, network connections, file handles) are needed, you must manually execute them on the alarm node:

```bash
# Real-time disk IO statistics
iostat -x 1 3

# Process file descriptor count
ls /proc/<pid>/fd | wc -l

# Process network connections
ss -tnp | grep '<pid>'

# System file handle usage
cat /proc/sys/fs/file-nr
```

**Analysis**:

| Phenomenon | Conclusion |
|-----------|------------|
| Many zombie processes | The parent process has not reaped its child processes; the parent process needs to be restarted |
| Many D-state processes | Processes are waiting for IO and not releasing; combine with disk-io to judge whether it is a disk bottleneck |
| Thread usage close to 100% | Threads are exhausted; new requests cannot create threads |
| Insufficient memory + large swap usage | Insufficient memory causes frequent swapping, and the CPU is spent paging |
| High iowait + high disk await/util | A disk IO bottleneck indirectly causes high CPU iowait |
| File-handle usage close to 100% | Handles are exhausted; the process retries repeatedly, consuming CPU |
| A process has an abnormally high fd count | That process has an fd leak |
| Abnormally many network connections or many CLOSE_WAIT | Network storm or connection leak |

### Step 6: Non-Java system process analysis

For the high-CPU non-Java process confirmed in Step 2:

```bash
# View the host process details
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json

# View host resource information (memory, swap, etc.)
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

> Look up the detailed information (command line, PID, etc.) of the target process in the returned process list.

**Common situations**:

| Process | Common cause | Related check |
|---------|-------------|---------------|
| collectd | Abnormal collection plugin or excessively high collection frequency | Check whether there is an fd leak: `ls /proc/<pid>/fd \| wc -l` |
| rsyslog | A surge in log volume causes log writing to consume CPU | Check disk usage via `get_host_resource` |
| python/shell script | Scheduled task or abnormal script infinite loop | Confirm the script path and parameters |
| kswapd0 | Kernel paging process, indicating insufficient memory | Confirm the memory and swap state via `get_host_resource` |

## Common Root Causes and Repair Suggestions

> The following repair suggestions need to be executed manually by the user; automation tools are only responsible for diagnosis and locating the cause.

### 1. Frequent Java Full GC

**Features**: high CPU of the Java process in Step 2 + GC threads in jstack + dense Full GC in the GC log

**Repair suggestions**:
- Check whether the JVM heap memory configuration is reasonable; consider increasing `-Xmx`
- Analyze whether there is a memory leak
- Optimize the code to reduce large-object allocation

**Notes**:
- **Increase `-Xmx`**: you need to SSH to the target node and modify the corresponding service's `application.properties` or startup script; the service must be restarted for the change to take effect. Increasing heap memory consumes more physical memory, so confirm that the node has sufficient remaining memory
- **Analyze a memory leak**: you can run `jmap -histo:live <pid>` to view the object distribution, but note: ① this command requires a JDK environment; ② running it triggers a Full GC, causing a brief STW; ③ the output may be large, so it is recommended to redirect it to a file
- **JVM parameter changes**: in MRS, JVM parameters modified through the Manager UI are automatically distributed; manually modifying a startup script will be overwritten at the next configuration distribution

### 2. Java thread leak/infinite loop

**Features**: many BLOCKED threads in jstack, or the same stack frame repeatedly appears

**Repair suggestions**:
- BLOCKED: investigate the lock-contention code and optimize the synchronization logic
- Infinite loop: locate the business code by the thread stack and fix the logic

### 3. Disk IO bottleneck (high iowait)

**Features**: iowait > 20% in Step 1; iostat shows high await/util

**Repair suggestions**:
- Investigate whether there is a large amount of log writing
- Investigate whether there is an abnormal disk-read/write process
- Consider expanding the disk or optimizing the IO scheduler

### 4. Insufficient memory triggering swap

**Features**: `free -h` shows extremely low available memory and large swap usage; or the kswapd0 process has high CPU

**Repair suggestions**:
- Release unnecessary memory usage (restart the leaking process)
- Add physical memory or adjust the swap policy
- Adjust the JVM heap memory quotas of each service

### 5. D-state process accumulation

**Features**: D-state processes present

**Repair suggestions**:
- Investigate whether the underlying IO device is faulty
- Check whether NFS and other network storage is slow
- If necessary, restart the parent process of the D-state process

**Notes**:
- D-state processes cannot be terminated with `kill`; you can only wait for the IO to complete or restart the system
- If a D-state process persists and does not disappear, it usually means the underlying storage device is faulty or the NFS mount point is unreachable

### 6. Exhausted threads/file handles

**Features**: thread usage close to 100%; file-handle usage close to 100%

**Repair suggestions**:
- Increase the system limits (`ulimit -u` / `ulimit -n`; these need to be written to `/etc/security/limits.conf` for persistence)
- Investigate the application with thread/connection leaks
- Optimize the connection-pool configuration

### 7. Abnormal system process

**Features**: a non-Java system process occupies abnormally high CPU

**Repair suggestions**:
- collectd: check the collection plugin configuration and reduce the collection frequency
- rsyslog: check whether there is a log storm and optimize the log level
- Scheduled scripts: investigate abnormal tasks in crontab

### 8. Business peak or inefficient task

**Features**: high CPU of the Java process + RUNNABLE business threads shown in jstack + normal GC log

**Repair suggestions**:
- Investigate whether there is a data-skew task on Yarn
- Investigate whether there are inefficient SQL statements (full table scans, no partition filtering)
- Consider throttling the business or executing off-peak

## Variable Description

| Variable | Description | Example |
|----------|-------------|---------|
| `<node_name>` | Alarm node name | 8-5-225-6 |
| `<alarm_time>` | Alarm trigger time | 2026/07/13 10:00:00 GMT+08:00 |
| `<java_pid>` | Java process PID | 12345 |
| `<service_name>` | Service name | tomcat, pms, HDFS |
| `<role_name>` | Role name | Controller, NameNode |
| `<instance_name>` | Instance name | Controller-1 |
| `<gc_log_path>` | Full path of the GC log (the `file_name` parameter of browse_log); look it up in the mapping by process name | /var/log/Bigdata/tomcat/tomcat_gc.log |
| `<jstack_log_path>` | Full path of the jstack output log (the `file_name` parameter of browse_log) | — |
| `<component:service:role>` | Component triplet, the `services` parameter of start_log_search; fill it in according to the component the high-CPU process belongs to; it can be queried via `get_log_search_support_services` | HDFS:HDFS:NameNode |
| `<task_id>` | Log-search task ID (obtained from the return of `start_log_search`) | — |

> `<cluster_id>` does not need to be specified manually; it is automatically obtained from the cluster.
