# `Controller`(12070) Alarm Diagnosis Skill

## Diagnosis Flow
```
Step 1: Confirm the alarm and instance status
  |
  +-- Instance normal -> Check monitoring metric trends
  +-- Instance abnormal -> Step 2
Step 2: Check host resource metrics
  |
  +-- Metrics abnormal -> Resource bottleneck
  +-- Metrics normal -> Step 3
Step 3: In-depth log troubleshooting
```

## API Call Chain Dependencies
| Previous API | Return field | Next API | Parameters |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_instances` | instance status | `get_host_process` | confirm whether the process exists |

---

## Diagnosis Steps
### Step 1: Confirm the alarm and instance status
```bash
# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

```bash
# Query the Controller instance status
python manager_api_client.py -a get_instances \
  -p 'cluster_id=<cluster_id>' \
  -p 'service_name=Controller' \
  --json
```

```bash
# Query the host process status
python manager_api_client.py -a get_host_process \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Instance status normal | The alarm may have recovered, or it is a metric-type alarm | Step 2 |
| Instance status abnormal | Service exception | Step 2 |
| Associated alarms exist | Handle the associated alarms first | Refer to the corresponding alarm diagnosis |

---
### Step 2: Check host resource metrics
```bash
# Query host monitoring metrics
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_cpu_surp_avg,dev_load_one_min' \
  --json
```

```bash
# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion |
|----------|------|
| Metrics abnormal | Resource bottleneck caused the alarm |
| Metrics normal | Continue log troubleshooting |

---
### Step 3: In-depth log troubleshooting

#### 3.1 oms_gc.log*

```bash
# Browse the oms_gc.log* logs
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=oms_gc' \
  -p 'path=/var/log/Bigdata/controller/scriptlog' \
  --json
```

```bash
# Browse the logs (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/scriptlog/oms_gc.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

```bash
# Search log keywords
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'services=Manager:Manager:OmmServer' \
  -p 'min_log_level=WARN' \
  -p 'key_word=ERROR' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  --json

# View the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> The `time_pattern` parameter must be passed for the log time format.

**Keyword analysis**:

| Log keyword | Conclusion |
|-----------|------|
| ERROR | See the corresponding root cause in Common Root Causes and Repair Suggestions |
| None of the above keywords | No exception in this log |

## Common Root Causes and Repair Suggestions

### 1. Resource metrics exceed the threshold

**Repair suggestions**:
- Take targeted actions based on the specific metric that exceeds the threshold
- Clean up resources or scale up

### 2. Insufficient disk space

**Features**: The log contains `no space left` / `No space left on device`

**Repair suggestions**:
- Clean up log files and temporary files
- Expand the disk

### 3. Abnormal configuration or file permissions

**Features**: The log contains `Permission denied` / `cannot open`

**Repair suggestions**:
- Check the permissions of the relevant files
- Wait 5 minutes after fixing the permissions

### 4. Network or connectivity issues

**Features**: The log contains `connection refused` / `timeout`

**Repair suggestions**:
- Check network connectivity between nodes
- Use the `check_remote` API to test the reachability of remote nodes
