# Data Status Unknown After Recovery Task Failure (12035) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Obtain OMS information and confirm the alarm
  |
  v
Step 2: Search Controller backup and recovery logs
  |
  +-- Log contains restore/rollback/fail -> Match the root cause by log keyword
  +-- No obvious error -> Step 3

Step 3: Check node disk space
  |
  +-- Insufficient disk space -> Root cause: insufficient disk space causing recovery failure
  +-- Sufficient disk space -> Step 4

Step 4: Check component running status
  |
  +-- Status does not meet recovery requirements -> Root cause: component status does not meet requirements
  +-- Status normal -> Restart the recovery task to verify

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions" without continuing the following steps.
```

## API Call Chain Dependencies

| Previous API | Return field | Next API | Parameter |
|-----------|---------|-----------|------|
| `start_log_search` | `task_id` | `get_log_search_progress` | `search_id` |
| `get_log_filename` | Full path of the log file | `browse_log` | `file_name` |

## Diagnosis Steps

### Step 1: Obtain OMS information and confirm the alarm

```bash
# Query OMS basic information
python manager_api_client.py -a get_oms_info --json

# Query the current alarm list
python manager_api_client.py -a get_alarms --json
```

> From the alarm information, obtain the recovery task name and hostname.

---

### Step 2: Search Controller backup and recovery logs

```bash
# Browse the Controller backup and recovery logs
# First obtain the exact log file name
python manager_api_client.py -a get_log_filename \
  -p 'hostname=<node_name>' \
  -p 'category_name=backupplugin' \
  -p 'path=/var/log/Bigdata/controller/backup' \
  --json
```

```bash
# Browse the log (using the exact file name)
python manager_api_client.py -a browse_log \
  -p 'hostname=<node_name>' \
  -p 'file_name=/var/log/Bigdata/controller/backup/backupplugin.log' \
  -p 'start_line=1' \
  -p 'end_line=200' \
  --json
```

> If you need to search for specific keywords:

```bash
# Search for recovery/rollback-related keywords
python manager_api_client.py -a start_log_search \
  -p 'cluster_id=<cluster_id>' \
  -p 'key_word=restore' \
  -p 'start_time=<alarm_time>' \
  -p 'end_time=<current_time>' \
  -p 'services=Manager:Manager:Controller' \
  -p 'min_log_level=INFO' \
  --json

# View the search progress
python manager_api_client.py -a get_log_search_progress \
  -p 'search_id=<task_id>' \
  --json
```

> If you need to search multiple keywords (e.g., `rollback`, `fail`, `error`), run multiple searches separately.

**Log keyword analysis**:

| Log keyword | Conclusion | Next step |
|-----------|------|--------|
| `restore` / `recover` + `fail` | Recovery task execution failed | Step 3 |
| `rollback` + `fail` | **Root cause located**: rollback failure causing data status unknown -> Root cause 4 | — |
| `error` / `exception` | Error during the recovery process | Step 3 |
| `insufficient disk space` | **Root cause located**: insufficient disk space -> Root cause 3 | — |
| None of the above keywords | No clear error | Step 3 |

---

### Step 3: Check node disk space

```bash
# Query the disk usage of the alarm node
python manager_api_client.py -a get_host_metrics \
  -p 'hostname=<node_name>' \
  -p 'metric_names=dev_disk_useage,dev_host_disk_usage' \
  --json

# Query host resource information
python manager_api_client.py -a get_host_resource \
  -p 'hostname=<node_name>' \
  --json
```

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Insufficient disk space | **Root cause located**: insufficient disk space causing recovery failure -> Root cause 3 | — |
| Sufficient disk space | Continue checking component status | Step 4 |

---

### Step 4: Check component running status

```bash
# Query the status of all cluster services
python manager_api_client.py -a get_cluster_services \
  -p 'cluster_id=<cluster_id>' \
  --json
```

> Check whether the component running status meets the recovery task requirements:
> - OMS and DBService must be in normal status
> - Other components must have their services stopped

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Component status does not meet requirements | **Root cause located**: component status does not meet recovery requirements -> Root cause 1 | — |
| Component status normal | Continue troubleshooting | Step 5 |

---

### Step 5: Check recovery task details and restart

> **The Manager API cannot directly operate recovery tasks. View manually in the Manager UI:**
> 1. Log in to the FusionInsight Manager administration UI
> 2. Select "O&M > Backup & Restoration > Restoration Management"
> 3. Find the corresponding recovery task based on the "Task Name" in the alarm location information
> 4. View the detailed information of the recovery task and confirm the failure reason
> 5. Start the recovery task and check whether it is executed successfully
> 6. If the recovery task is executed successfully, wait 2 minutes and check whether the alarm is cleared
> 7. If the recovery task execution fails, collect Controller service logs

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Recovery task executed successfully | Alarm should be automatically cleared | Check whether the alarm is cleared |
| Recovery task execution failed | **Root cause located**: error in a step during recovery task execution -> Root cause 2 | — |
| Component status does not meet requirements | **Root cause located**: component status does not meet recovery requirements -> Root cause 1 | — |

## Common Root Causes and Repair Suggestions

### 1. Component status does not meet recovery requirements

**Features**: Before executing the recovery task, the component running status does not meet requirements; OMS or DBService status is abnormal, or other components have not stopped their services

**Repair suggestions**:
- View the running status of each component in the Manager UI
- Restore OMS and DBService to normal status
- Stop the services of other components that need to be recovered
- After the component status meets the requirements, restart the recovery task
- Wait 2 minutes and check whether the alarm is cleared

### 2. Error in a step during recovery task execution

**Features**: Component status meets requirements, but the recovery task execution failed; the Controller backup and recovery log contains error information

**Repair suggestions**:
- View the detailed information of the recovery task in the Manager UI
- Confirm the detailed reason for the recovery task failure
- Fix the failure reason and restart the recovery task
- Wait 2 minutes and check whether the alarm is cleared

### 3. Insufficient disk space causing recovery failure

**Features**: Node disk space is insufficient; data writing failed during the recovery task execution; the Controller log may contain `insufficient disk space`

**Repair suggestions**:
- Check the disk space of the alarm node
- Clean up redundant files (such as old backup packages, installation packages, coredump files) to free disk space
- Ensure sufficient remaining space on the backup and recovery directory mount point
- Restart the recovery task

### 4. Rollback failure causing data status unknown

**Features**: After the recovery task fails, the system automatically rolls back on a 60-minute cycle; the rollback operation also fails; data status is unknown

**Repair suggestions**:
- Confirm the recovery task failure reason and prioritize fixing the root cause of the recovery task failure
- Check whether the component status meets requirements
- Check whether the disk space is sufficient
- After fixing the issues, restart the recovery task
- If it still fails, collect Controller service logs and contact O&M personnel for handling

## Variable Description

| Variable | Description | Example |
|------|------|------|
| `<node_name>` | Node name where the alarm occurred (typically the primary OMS node) | 8-5-225-5 |
| `<alarm_time>` | Alarm trigger time | 2026/07/15 10:00:00 GMT+08:00 |
| `<current_time>` | Current time | 2026/07/15 11:00:00 GMT+08:00 |
| `<task_id>` | Log search task ID (obtained from the `start_log_search` return) | — |

> `<cluster_id>` does not need to be specified manually; it is obtained automatically from the cluster.
