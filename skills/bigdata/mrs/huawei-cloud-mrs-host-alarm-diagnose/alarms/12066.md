# FusionInsight Manager omm User Inter-Node Mutual Trust Failure Diagnosis

## Metadata

- **Alarm Name**: Inter-node mutual trust failure
- **Applicable Product**: FusionInsight Manager
- **Impact Scope**: May cause operations requiring connection to this node (such as restart, configuration synchronization, instance status query) to fail. Mutual trust failure on multiple nodes may affect services
- **Alarm Mechanism**: The system checks the mutual trust status between the primary OMS node and other Agent nodes once every hour. The alarm is automatically cleared after the issue is resolved

---

## Phase 0: Information Collection

**Objective**: Collect alarm context, identify involved nodes

### Step 0.1: Obtain Alarm Node List

- **Action**: Obtain the mutual trust exception node information from the additional information in the alarm details. Distinguish between node name and node IP
- **Output**: Record all node IPs/hostnames involved in the mutual trust failure

### Step 0.2: Confirm Mutual Trust Failure Node Information

- **Action**: Confirm whether the current node is the primary OMS, standby OMS, or an Agent node
- **Command**: Obtain cluster active/standby node names
```bash
  python3 lakewatch_api_client.py -a query-management-node-info \
    -p 'cluster_id=<cluster_id>'
```
Parameter description:
<cluster_id>: Cluster ID

- **Determination**:
  - Primary node contains the mutual trust failure node IP/hostname → Current node is the primary OMS node
  - Standby node contains the mutual trust failure node IP/hostname → Current node is the standby OMS node
  - No such file → Current node is an Agent node

---

## Phase 1: Mutual Trust Problem Classification

**Objective**: Determine the specific type of mutual trust failure, decide the subsequent troubleshooting direction

### Step 1.1: Test SSH Connectivity

- **Action**: On the primary OMS node, as the omm user, SSH to each other node listed in the alarm details
- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ssh-check' \
  -p 'env={"TARGET_IP":"<hostname>"}' \
  -p 'node_name=<node_name>'
```
Parameter description:
<cluster_id>: Cluster ID of the alarm cluster
<node_name>: Node where the alarm occurred, obtained from alarm information
<hostname>: Cluster OMS primary node

- **Observe the return result and proceed to the corresponding branch**:

| Return Behavior | Problem Type | Jump To |
|---------|---------|------|
| Prompts `Enter passphrase for key '/home/omm/.ssh/id_rsa':` | **Type A: Private key encryption issue** | → Phase 2A |
| Prompts `Password:` | **Type B: Public/private key authentication issue** | → Phase 2B |
| Shows `Connection refused` | **Type C: Network/SSH port issue** | → Phase 2C |
| Shows `Permission denied (publickey,...)` | **Type D: Public key/trust list mismatch** | → Phase 2D |
| Passwordless connection succeeds normally | **Intermittent issue** | → Phase 2E |

---

## Phase 2A: Private Key Encryption Issue Troubleshooting

**Basis**: SSH prompts for passphrase, indicating ssh-agent is not properly managing the passphrase

### Step 2A.1: Check ssh-agent Process

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"ssh-agent"}' \
  -p 'node_name=<node_name>'
```
Parameter description:
<cluster_id>: Cluster ID
<node_name>: IP of the mutual trust failure node

- **Expected**: The following 3 processes should exist:
  - `ssh-agent-monitor-startup.sh`
  - `ssh-agent-monitor.sh`
  - `ssh-agent -a /home/omm/.ssh/agent.pid`
- **Determination**:
  - Processes incomplete or nonexistent → **Instruct user to manually confirm and execute**: `kill` all ssh-agent related processes, wait for the monitor to automatically restart them, then return to Step 1.1 to verify
  - Processes normal → Continue to Step 2A.2

### Step 2A.2: Check Whether Private Key Is Registered with ssh-agent

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ssh-agent-keys' \
  -p 'node_name=<node_name>'
```
- **Expected**: Returns public key fingerprint information, such as `2048 83:53:3d:... /home/omm/.ssh/id_rsa (RSA)`
- **Determination**:
  - Shows `The agent has no identities` or no output → **Private key not registered**, **instruct user to manually confirm and execute**:
    ```bash
    ssh-add
    # Enter passphrase (decrypt from /home/omm/passphrase.file, or provided by O&M)
    ```
  - Returns normal fingerprint → Continue to Step 2A.3

### Step 2A.3: Check Whether Private Key Is Encrypted

- **Instruct user to manually confirm and execute**: Check whether the private key file is encrypted
  ```bash
  head -5 /home/omm/.ssh/id_rsa
  grep -c "ENCRYPTED" /home/omm/.ssh/id_rsa 2>/dev/null && echo "ENCRYPTED: YES" || echo "ENCRYPTED: NO"
  ```
- **Expected**: The file contains the `ENCRYPTED` keyword
- **Determination**:
  - No `ENCRYPTED` field → **User regenerated an unencrypted private key**, **instruct user to manually confirm and execute**: Regenerate an encrypted private key following the product documentation "Update omm user SSH key" procedure
  - Has `ENCRYPTED` field → Continue to Step 2A.4

### Step 2A.4: Check Passphrase File

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-exist-check' \
  -p 'env={"FILE_PATH":"/home/omm/passphrase.file"}' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - File does not exist → **Passphrase file was accidentally deleted**, **instruct user to manually confirm and execute**:
    - If current node is primary OMS: Copy `/home/omm/passphrase.file` and `/home/omm/passphrase.file.sha256` from the standby OMS node
    - If current node is standby OMS: Copy the above files from the primary OMS node
  - File exists → Continue to Step 2A.5

### Step 2A.5: Check crond Service

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=service-status' \
  -p 'env={"SERVICE_NAME":"crond"}' \
  -p 'node_name=<node_name>'
```
- **Expected**: `active (running)`
- **Determination**:
  - Not running → **Instruct user to manually confirm and execute**: `systemctl start crond && systemctl enable crond`
  - Running normally → Continue to Step 2A.6

### Step 2A.6: Check ssh-agent-monitor Log

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'log_type=local' \
  -p 'log_directory=/var/log/Bigdata/nodeagent/scriptlog' \
  -p 'log_file_name=ssh-agent-monitor.log' \
  -p 'keywords=fork child failed|has no private keys|passphrase.file and id_rsa is changed|reload private key' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=60' \
  -p 'node_name=<node_name>'
```
- **Key keywords to watch**:
  - `fork child failed` → Insufficient system resources, proceed to Phase 3 to troubleshoot resources
  - `ssh-agent has no private keys` → PATH environment variable may be too long, proceed to Step 2A.7 to check PATH length
  - `passphrase.file and id_rsa is changed, reload private key` → File was modified, check whether someone performed manual operations
  - Log has only one line with no follow-up → Monitor process may have been killed by cron restart

### Step 2A.7: Check JAVA_HOME Environment Variable

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ssh-env-check' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - JAVA_HOME is empty → **Instruct user to manually confirm and execute**: `source /home/omm/.profile` to reload environment variables
  - PATH_LENGTH too long → **Instruct user to manually confirm and execute**: Check and reset the PATH environment variable
  - Non-empty and PATH length normal → Continue to Step 2A.8

### Step 2A.8: Check expect Process

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"expect"}' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - Long-running expect process exists (date is long ago) → Process is stuck, **instruct user to manually confirm and execute**: `kill <PID>` to kill the stuck process
  - No expect process → Normal

## Phase 2B: Public/Private Key Authentication Issue Troubleshooting

**Basis**: SSH prompts for Password, indicating public/private key authentication is not effective

### Step 2B.1: Check Trust List

- **Action**: Obtain public keys from both ends respectively, compare trust lists
- **Instruct user to manually confirm and execute (local end)**:
  ```bash
  cat /home/omm/.ssh/id_rsa.pub
  ```
- **Instruct user to manually confirm and execute (remote end)**:
  ```bash
  cat /home/omm/.ssh/authorized_keys
  ```
- **Determination**:
  - authorized_keys does **not contain** local end public key → **Trust list missing**, **instruct user to manually confirm and execute**:
    ```bash
    cat /home/omm/.ssh/id_rsa.pub | ssh <remote_node> "cat >> /home/omm/.ssh/authorized_keys"
    ```
  - authorized_keys **contains** local end public key → Continue to Step 2B.2

### Step 2B.2: Check sshd_config Configuration

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/ssh/sshd_config"}' \
  -p 'node_name=<node_name>'
```
- **Check items**:
  - `PubkeyAuthentication yes` → Must be yes
  - `RSAAuthentication yes` → Must be yes (older versions)
  - `AllowUsers` → If a whitelist exists, omm must be included
  - `DenyUsers` → omm must not appear in the blacklist
  - `ListenAddress` → If set, confirm the listening IP is correct
- **Determination**:
  - Configuration abnormal → **Instruct user to manually confirm and execute**: Modify configuration then execute `systemctl restart sshd`
  - Configuration normal → Continue to Step 2B.3

### Step 2B.3: Check hosts.allow and hosts.deny

- **Command**:
```bash
# Check hosts.allow
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/hosts.allow"}' \
  -p 'node_name=<node_name>'

# Check hosts.deny
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/hosts.deny"}' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - Configuration blocks omm user SSH → **Instruct user to manually confirm and execute**: Modify configuration to ensure omm user is not blocked
  - Configuration normal → Continue to Step 2B.4

### Step 2B.4: Check sshd Service Status

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=service-status' \
  -p 'env={"SERVICE_NAME":"sshd"}' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - Not running → **Instruct user to manually confirm and execute**: `systemctl restart sshd`
  - Running normally → Continue to Step 2B.5

### Step 2B.5: Check Directory and File Permissions

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ssh-file-permission-check' \
  -p 'node_name=<node_name>'
```
- **Expected permissions**:

  | Path | Expected Permission | Expected Owner |
  |------|---------|---------|
  | `/home` | 755 | root:root |
  | `/home/omm` | 750 | omm:wheel |
  | `/home/omm/.ssh` | 700 | omm:wheel |
  | `id_rsa` | 600 | omm:wheel |
  | `id_rsa.pub` | 600 | omm:wheel |
  | `authorized_keys` | 600 | omm:wheel |

- **Determination**:
  - Permissions do not match → **Instruct user to manually confirm and execute**:
    ```bash
    chmod 750 /home/omm
    chown omm:wheel /home/omm
    chmod 700 /home/omm/.ssh
    chmod 600 /home/omm/.ssh/id_rsa /home/omm/.ssh/id_rsa.pub /home/omm/.ssh/authorized_keys
    ```
  - Permissions normal → Continue to Step 2B.6

### Step 2B.6: Check Whether omm User Password Has Expired

- **Command**:
```bash
# Check omm user
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=user-password-expire' \
  -p 'env={"USER_NAME":"omm"}' \
  -p 'node_name=<node_name>'

# Check ommdba user
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=user-password-expire' \
  -p 'env={"USER_NAME":"ommdba"}' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - Password expired → **Instruct user to manually confirm and execute**: Update omm user password
  - Password not expired → Proceed to Phase 2C/2D for further troubleshooting

## Phase 2C: Network/SSH Port Issue Troubleshooting

**Basis**: SSH connection shows `Connection refused`

### Step 2C.1: Check Network Connectivity

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ping-check' \
  -p 'env={"TARGET_IP":"<target_node_IP>"}' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - Unreachable → Contact network administrator to troubleshoot network issues
  - Reachable → Continue to Step 2C.2

### Step 2C.2: Check SSH Port Reachability

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=port-connectivity-check' \
  -p 'env={"HOST_IP":"<target_node_IP>","PORT":"22"}' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - Port unreachable → **Instruct user to manually confirm and execute**: Check firewall rules `iptables -L -n | grep 22`
  - Port reachable → Continue to Step 2C.3

### Step 2C.3: Check SSH Port Consistency

- **Instruct user to manually confirm and execute**: Execute the following commands on both active and standby nodes to view SSH port configuration (omm user does not have permission to read `/etc/ssh/sshd_config` and `/etc/ssh/ssh_config`, user needs to execute as root or a user with appropriate permissions):
  ```bash
  echo "=== sshd_config Port ==="
  grep -i "^Port" /etc/ssh/sshd_config 2>/dev/null || echo "Port not specified (default 22)"
  echo "=== ssh_config Port ==="
  grep -i "^Port" /etc/ssh/ssh_config 2>/dev/null || echo "Port not specified (default 22)"
  ```
- **Determination**:
  - Port values inconsistent between both ends → **Instruct user to manually confirm and execute**: Modify the inconsistent end's configuration to match the primary node, then execute `service sshd restart`
  - Ports consistent → Continue to Step 2C.4

### Step 2C.4: Check Floating IP (OMS Nodes Only)

- **Command**:
```bash
# Check floating IP configuration in oms-config.ini
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/opt/huawei/Bigdata/om-server_8.2.0/om/inst/conf/oms-config.ini"}' \
  -p 'node_name=<node_name>'

# Check network interface information
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=network-interface-info' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - Floating IP network interface does not exist → **Instruct user to manually confirm and execute**: Check network interface configuration
  - `Link detected: no` → Network port fault, contact network administrator for handling
  - Normal → Continue

## Phase 2D: Public Key/Trust List Mismatch Troubleshooting

**Basis**: SSH shows `Permission denied (publickey,...)`

### Step 2D.1: Check known_hosts Public Key Consistency

- **Action**: Log in to the OMS primary node, check known_hosts
- **Command (OMS node)**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/opt/huawei/Bigdata/om-server_8.2.0/om/etc/om/known_hosts"}' \
  -p 'node_name=<oms_node_name>'
```
- **Determination**:
  - File contains abnormal IP lines (e.g., residual old IPs after node IP change) → **Instruct user to manually confirm and execute**: Edit `${BIGDATA_HOME}/om-server/om/etc/om/known_hosts`, delete lines containing the abnormal IP
  - File normal → Continue to Step 2D.2

### Step 2D.2: Restart Controller to Re-register Public Key

- **Instruct user to manually confirm and execute**:
  ```bash
  sh ${BIGDATA_HOME}/om-server/om/sbin/restart-controller.sh
  ```
- **Description**: After deleting the corresponding IP public key from known_hosts, restart the controller. The node will re-register its public key

### Step 2D.3: Verify Mutual Trust Recovery

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ssh-check' \
  -p 'env={"TARGET_IP":"<alarm_node>"}' \
  -p 'node_name=<oms_node_name>'
```
- **Determination**:
  - Passwordless connection succeeds → Issue resolved, wait for alarm to auto-clear
  - Still fails → Continue to Step 2D.4

### Step 2D.4: Update SSH Key

- **Instruct user to manually confirm and execute**:
  ```bash
  sh ${CONTROLLER_HOME}/sbin/update-ssh-key.sh
  ```
- **Description**: Follow the product documentation "Update omm user SSH key" procedure

## Phase 2E: Intermittent Issue Troubleshooting

**Basis**: Manual SSH can connect, but the system still reports mutual trust failure

### Step 2E.1: Restart ssh-agent

- **Instruct user to manually confirm and execute**:
  ```bash
  ps -ef | grep ssh-agent | grep -v grep | awk '{print $2}' | xargs kill -9
  ```
- **Description**: After killing ssh-agent, the monitor process will automatically restart it

### Step 2E.2: Check Whether .bashrc Sources .profile

- **Command**:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/home/omm/.bashrc"}' \
  -p 'node_name=<node_name>'
```
- **Determination**:
  - No `source.*\.profile` line → **Instruct user to manually confirm and execute**: Add `source /home/omm/.profile` to `/home/omm/.bashrc`
- **Description**: This issue causes "single SSH succeeds, consecutive SSH fails"

### Step 2E.3: Observe Whether Alarm Auto-Clears

- **Action**: Wait 1-2 check cycles (once per hour), observe whether the alarm auto-clears

## Phase 5: Recovery Operations Summary

Execute in priority order from high to low. **All operations require instructing the user to manually confirm and execute**:

| Priority | Recovery Method | Applicable Scenario | Command (instruct user to manually confirm and execute) |
|--------|----------|----------|----------|
| P1 | Restart ssh-agent | ssh-agent process abnormal/passphrase not loaded | `ps -ef \| grep ssh-agent \| grep -v grep \| awk '{print $2}' \| xargs kill -9` |
| P2 | Copy mutual trust files | Public/private key/passphrase file corrupted or missing | Copy `passphrase.file`, `id_rsa`, `id_rsa.pub` from OMS node (OMS also needs `.sha256` file), kill ssh-agent after copying |
| P3 | Restart sshd | After sshd configuration modification | `systemctl restart sshd` |
| P4 | Update omm user SSH key | Above methods ineffective | Follow product documentation "Update omm user SSH key" procedure |
| P5 | Clean known_hosts and restart controller | Public key registration abnormal | Delete abnormal IP lines from OMS node known_hosts, execute `sh ${BIGDATA_HOME}/om-server/om/sbin/restart-controller.sh` |

## Phase 6: Typical Scenario Quick Match

Before troubleshooting, first match the following typical scenarios. If matched, directly follow the recommended remediation:

| # | Scenario | Key Features | Root Cause | Quick Fix (instruct user to manually confirm and execute) |
|---|------|----------|------|----------|
| 1 | User regenerated private key | ssh-agent not running, id_rsa has no ENCRYPTED field | Private key replaced with unencrypted version | Update SSH key per documentation |
| 2 | Expansion distribution failure | Log reports "Password is null" | passphrase.file accidentally deleted | Copy passphrase.file from standby OMS |
| 3 | Java SSH fails, manual works | Only Java ssh4j call fails | Private key not encrypted, Java reloads file | Regenerate encrypted private key |
| 4 | Mutual trust failure after key replacement | Manual SSH works, automated operations fail | New public key not synced to other nodes' authorized_keys | Sync new public key to all nodes |
| 5 | AllowUsers whitelist | SSH to any node requires password | sshd_config does not include omm | Add omm to AllowUsers and restart sshd |
| 6 | Mutual trust failure after OS reboot | SSH requires passphrase | crond not started | `systemctl start crond` |
| 7 | HA sync failure | Standby OMS SSH to primary OMS fails | Root permission file blocks HA sync | Fix file ownership, manually copy mutual trust files |
| 8 | /home/omm permission abnormal | SSH requires password | Directory permission not 750 or owner incorrect | `chmod 750 /home/omm && chown omm:wheel /home/omm` |
| 9 | No recovery after resource exhaustion | Log has "fork child failed", expect stuck | Process count exhausted causing encryption/decryption failure | Clean up resources, kill ssh-agent, kill stuck expect process |
| 10 | PATH too long | Log reports "ssh-agent has no private keys" | Repeated source causes PATH too long | Reset PATH and re-register key |
| 11 | Password expired | `chage -l omm` shows expired | omm/ommdba password expired | Update password |
| 12 | Consecutive SSH failures | Single SSH works, consecutive SSH fails | .bashrc does not source .profile | Add `source /home/omm/.profile` to .bashrc |
