# `Device Partition File System Read-Only` (12015) Alarm Diagnosis Skill

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **Device Partition File System Read-Only (12015)** alarm. The system scans at 60-second intervals. If it detects that a device partition mounting service directories has become read-only (due to disk bad sectors, file system failure, etc.), this alarm is triggered. When the system detects that the read-only mode of the device partition mounting service directories has disappeared (e.g., the file system has been repaired to read-write mode, the device has been removed, or the device has been reformatted), the alarm is cleared.

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12015 |
| Alarm Name | Device Partition File System Read-Only |
| Alarm Severity | Important |
| Alarm Type | Disk Fault Monitoring |
| Auto-cleared | Yes |
| System Impact | Business failure (jobs that need to modify data on the read-only partition will fail), business latency (components that need to synchronize data to the read-only partition will experience sync abnormalities or timeouts) |

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Confirm Whether the File System Is in Read-Only Mode

Execute the following command. If the mount options for the alarm device partition in the command output contain "ro" (read-only), the file system is indeed in read-only mode; if the mount options are "rw" (read-write), the file system has recovered to read-write mode.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-health-check' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.2 Obtain Cluster OMS Active/Standby Node Information

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.3 Obtain OMS Key Directories

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., commands that require manual login to the node).

### 3.1 Contact Hardware Engineer to Confirm Disk Hardware Failure

Obtain the "hostname" and "device partition name" from the alarm location information, where "hostname" is the node with the fault alarm and "device partition name" is the partition of the failed disk. Contact a hardware engineer to confirm the disk hardware failure, then online-remove the failed disk from the server.

### 3.2 Refer to 12014 Alarm Handling

After removing the disk, the system will report the "ALM-12014 Device Partition Lost" alarm. Refer to ALM-12014 Device Partition Lost alarm handling. After processing is complete, this alarm will be automatically cleared.

For specific handling steps, see the diagnosis flow in `12014.md`.

### 3.3 Attempt File System Repair (Optional)

If the hardware engineer confirms that the disk has no obvious hardware failure, you can attempt to repair the file system to restore read-write mode:

1. First unmount the read-only partition: `umount <alarm_partition_name>`
2. Execute file system check: `fsck -y <alarm_partition_name>`
3. After repair is complete, remount: `mount <alarm_partition_name> <mount_dir>`

- `<alarm_partition_name>`: Alarm device partition name, obtained from the alarm information
- `<mount_dir>`: Mount directory name, obtained from the alarm information

> **Note**: Before executing fsck, ensure that the partition has been unmounted. This operation may cause data loss; execute it only after confirming the risk.

### 3.4 Collect Fault Information

If the above steps do not clear the alarm, fault information needs to be collected:

1. In the FusionInsight Manager UI, select "Maintenance > Logs > Download"
2. In "Services", select "OmmServer", then click "OK"
3. In the upper right corner, set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm generation time, then click "Download"
4. Contact operations personnel and send the collected fault log information

## 4. Common Fault Repair Solutions

### 4.1 Disk Has Bad Sectors

**Symptoms**:
- Device partition has become read-only
- Disk SMART check shows "Reallocated_Sector_Ct" or "Elements in grown defect list" count abnormal

**Repair solution**:
1. Contact a hardware engineer to confirm the disk hardware failure
2. Online-remove the failed disk from the server
3. After removing the disk, the system will report the "ALM-12014 Device Partition Lost" alarm; refer to 12014 alarm handling
4. After processing is complete, this alarm will be automatically cleared

### 4.2 File System Failure

**Symptoms**:
- No obvious disk hardware failure
- Device partition remains in read-only mode
- File system has corruption or log errors

**Repair solution**:
1. Unmount the read-only partition
2. Execute fsck to repair the file system
3. After repair, remount and verify whether read-write mode has been restored
4. If it remains read-only after repair, the disk may have hidden hardware failure; handle according to 4.1

### 4.3 Emergency System Recovery

**Scenario**: Device partition read-only causes system running lag, delayed page refresh, or slow API response

**Repair solution**:
1. Confirm whether the node with the failed disk is the OMS active node; if so, perform an active/standby switchover:
   - Log in to the active OMS node as the omm user
   - Execute: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=127.0.0.1 --port=20013 --switchover --name=product`
2. After the active/standby switchover succeeds, contact a hardware engineer to remove the failed disk
3. After removing the disk, refer to 12014 alarm handling
4. After processing is complete, this alarm will be automatically cleared

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Diagram

```
Start
  |
  v
Obtain hostname, device partition name, and mount directory name from alarm information
  |
  v
Confirm whether file system is in read-only mode (mount command)
  |
  +--- Recovered to read-write mode ---> Is alarm automatically cleared?
  |                                        |
  |                                        +--- Yes ---> End
  |                                        |
  |                                        +--- No ---> Contact hardware engineer
  |
  +--- Still read-only mode ---> Contact hardware engineer to confirm disk hardware failure
                                   |
                                   +--- Hardware failure confirmed ---> Online-remove failed disk
                                   |                    |
                                   |                    v
                                   |            System reports 12014 alarm
                                   |                    |
                                   |                    v
                                   |            Refer to 12014 alarm handling
                                   |                    |
                                   |                    v
                                   |            This alarm is automatically cleared
                                   |
                                   +--- No obvious hardware failure ---> Attempt file system repair (fsck)
                                                                        |
                                                                        +--- Repair successful ---> Remount ---> Alarm cleared
                                                                        |
                                                                        +--- Repair failed ---> Collect fault logs
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis conclusion | Recommended action |
|----------|----------|
| Disk bad sector failure | Contact hardware engineer to remove failed disk, refer to 12014 handling |
| File system failure | Unmount partition, execute fsck repair, remount |
| Hardware failure causing system lag | Perform active/standby switchover, remove failed disk, refer to 12014 handling |
| Alarm still persists after processing | Collect OmmServer logs, contact operations personnel |
