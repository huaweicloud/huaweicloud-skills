# Process Full GC Time Exceeds Threshold Alarm Diagnosis

## 1. Diagnosis Overview

This document covers the diagnosis and handling of the **Process Full GC Time Exceeds Threshold (12203)** alarm. This alarm indicates that the Full GC (Full Garbage Collection) time of the OMS main process exceeds the threshold, typically meaning that the process memory usage is too high or the memory configuration is unreasonable, which may lead to slower task execution or even abnormal service restarts.

Alarm basic information:

| Item | Content |
|------|---------|
| Alarm ID | 12203 |
| Alarm Name | Process Full GC Time Exceeds Threshold |
| Alarm Severity | Important |
| Alarm Type | Process performance alarm |
| Auto-clearable | Yes |
| System Impact | GC time exceeding the threshold affects the read/write operations of OMS main processes, which may cause task execution to slow down or even trigger abnormal service restarts |

Alarm parameter description:

| Category | Parameter Name | Description |
|----------|----------------|-------------|
| Location Information | Source | Name of the cluster where the alarm was generated |
| Location Information | Service Name | Name of the service where the alarm was generated |
| Location Information | Role Name | Name of the role where the alarm was generated |
| Location Information | Host Name | Host name where the alarm was generated |
| Additional Information | Trigger condition | The current system metric value meets the custom alarm setting condition |

## 2. Executable Operations

This section provides the operations that can be executed during alarm analysis.

### 2.1 Obtain OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information and confirm whether the alarm node is the OMS active node.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 View Alarm Node Process Status

Execute the following command to view the process running status on the alarm node and confirm whether the OMS process that generated the alarm is running normally.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"java"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.3 View Alarm Node Memory Usage

Execute the following command to view the system memory usage on the alarm node to determine whether insufficient system memory is causing frequent process GC.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.4 View OMS Process GC Logs

Execute the following command to view the GC logs of the OMS process on the alarm node to confirm the frequency and duration of Full GC occurrences.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=30' \
  -p 'log_directory=/var/log/Bigdata/omm/oms' \
  -p 'log_file_name=controller.log*' \
  -p 'keywords=["Full GC","GC","OutOfMemory","ERROR","exception"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm trigger time
- `<node_name>`: OMS active node name

### 2.5 Obtain OMS Key Directories

Execute the following command to obtain OMS key directory information for locating process log and configuration file paths.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.6 View Alarm Node Disk Usage

Execute the following command to view the disk space usage on the alarm node to rule out the possibility of GC anomalies caused by insufficient disk space.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

## 3. Non-Executable Operations

This section provides the operations that cannot be executed through the API during alarm analysis (i.e., commands that require logging into the node for manual execution).

### 3.1 Use jstat to View Process GC Statistics

Log in to the alarm node as the omm user and execute the `jstat -gcutil <pid> 1000 20` command, sampling once per second for a total of 20 samples, to view the process GC statistics.

- `<pid>`: PID of the OMS process that generated the alarm, obtainable via the `jps -l` command

For example:
```bash
jps -l
jstat -gcutil <pid> 1000 20
```

Review the command result:
- Focus on the `OGC` (Old Generation GC count) and `OGCT` (Old Generation GC time) columns
- If the `OGCT` column grows rapidly in a short time, it indicates frequent and time-consuming Full GC
- Focus on the `FGC` (Full GC count) and `FGCT` (Full GC time) columns. If FGC increases frequently and the single FGCT exceeds 12 seconds, confirm the alarm cause

### 3.2 Use jmap to View Process Memory Heap Usage

Log in to the alarm node as the omm user and execute the `jmap -heap <pid>` command to view the process memory heap usage.

- `<pid>`: PID of the OMS process that generated the alarm

For example:
```bash
jmap -heap <pid>
```

Review the command result:
- Focus on the `Old Generation` usage rate. If the usage rate is close to 100%, it indicates insufficient old generation memory, causing frequent Full GC
- Focus on `MaxHeapCapacity` (maximum heap memory) to determine whether the current heap memory configuration is reasonable

### 3.3 View Process JVM Parameter Configuration

Log in to the alarm node as the omm user and execute the `jinfo -flags <pid>` command to view the process JVM startup parameter configuration.

- `<pid>`: PID of the OMS process that generated the alarm

For example:
```bash
jinfo -flags <pid>
```

Review the command result:
- Focus on the `-Xmx` (maximum heap memory) and `-Xms` (initial heap memory) parameters to determine whether the memory configuration is reasonable
- Focus on the `-XX:NewRatio` (new generation to old generation ratio) parameter to determine whether the old generation space is too small
- Focus on the `-XX:MaxMetaspaceSize` (metaspace size) parameter to determine whether the metaspace configuration is reasonable

### 3.4 View Process GC Log Details

Log in to the alarm node as the omm user and view the process GC log file to analyze the detailed cause of Full GC.

GC log path is typically:
```bash
# OMS process GC log path example
${OMS_RUN_PATH}/workspace/logs/<process_name>/gc.log
# or
${OMS_RUN_PATH}/log/<process_name>/gc.log
```

View GC logs:
```bash
# View the latest GC log
tail -200f ${OMS_RUN_PATH}/workspace/logs/<process_name>/gc.log

# View Full GC records
grep "Full GC" ${OMS_RUN_PATH}/workspace/logs/<process_name>/gc.log | tail -50
```

Analyze GC log content:
- Focus on the Full GC trigger reason (such as `Allocation Failure`, `System.gc()`, `Metadata`, etc.)
- Focus on the heap memory changes before and after Full GC to determine whether there is a memory leak
- If the old generation usage rate remains high after Full GC, there may be a memory leak

### 3.5 View Process Configuration Files

Log in to the alarm node as the omm user and view the process memory configuration file to confirm whether the memory configuration meets expectations.

OMS process memory configuration is typically located at:
```bash
# Process environment configuration file
${OMS_RUN_PATH}/etc/<process_name>/env_user

# or JVM parameter configuration file
${OMS_RUN_PATH}/etc/<process_name>/jvm.config
```

View configuration files:
```bash
cat ${OMS_RUN_PATH}/etc/<process_name>/env_user
cat ${OMS_RUN_PATH}/etc/<process_name>/jvm.config
```

Check memory configuration parameters:
- Confirm whether the `-Xmx` and `-Xms` parameter values are reasonable
- Confirm whether the `-XX:NewRatio` or `-Xmn` parameter is reasonable
- If the memory configuration is too small, the memory parameters need to be increased

### 3.6 Modify Process Memory Configuration and Restart

Based on the analysis results from 3.2 through 3.5, if you need to adjust the process memory configuration, perform the following operations:

1. Back up the original configuration file:
```bash
cp ${OMS_RUN_PATH}/etc/<process_name>/env_user ${OMS_RUN_PATH}/etc/<process_name>/env_user.bak
```

2. Modify memory configuration parameters (such as increasing `-Xmx`):
```bash
vi ${OMS_RUN_PATH}/etc/<process_name>/env_user
# Modify the -Xmx parameter value, e.g., from -Xmx2G to -Xmx4G
```

3. Restart the corresponding process (via the FusionInsight Manager interface or by executing the restart command on the node)

### 3.7 Collect OmmServer Logs

Collect OmmServer logs on the FusionInsight Manager page for further analysis.

1. On the FusionInsight Manager page, navigate to "Operation and Maintenance > Log > Download"
2. Check "OmmServer" for the target cluster in "Services"
3. Click the edit button in the upper right corner to set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm occurrence time
4. Click "Download"
5. Contact O&M personnel and send the collected fault log information

## 4. Common Fault Handling Solutions

### 4.1 Unreasonable Process Memory Configuration

**Symptoms:**
- Full GC occurs frequently, with single GC time exceeding 12 seconds
- jmap shows old generation usage rate close to 100%
- JVM parameter `-Xmx` configuration value is too small

**Solution:**
1. Confirm the current memory configuration of the alarm process (refer to 3.3 and 3.5)
2. Based on the node's physical memory, reasonably increase the `-Xmx` and `-Xms` parameters
3. Adjust the `-XX:NewRatio` parameter to appropriately increase the old generation space ratio
4. Restart the corresponding process for the configuration to take effect
5. Observe whether the alarm is cleared

### 4.2 Process Memory Leak

**Symptoms:**
- Old generation usage rate remains high after Full GC, memory cannot be reclaimed
- GC logs show frequent Full GC but poor reclamation effect
- Over time, Full GC frequency gradually increases

**Solution:**
1. Use `jmap -histo:live <pid>` to view object occupancy
2. Use `jmap -dump:format=b,file=heap.hprof <pid>` to export a heap memory snapshot
3. Use MAT (Memory Analyzer Tool) to analyze the heap memory snapshot and locate the memory leak point
4. Collect OmmServer logs (refer to 3.7) and contact O&M personnel for further analysis
5. Restart the process as a temporary mitigation if necessary

### 4.3 Insufficient System Memory

**Symptoms:**
- Node system memory usage is too high (the free command shows very little available memory)
- Multiple processes compete for memory resources
- The system experiences frequent swap operations

**Solution:**
1. View system memory usage (refer to 2.3)
2. View memory consumption of each process on the node to confirm whether there are abnormal processes
3. If non-essential processes are consuming large amounts of memory, stop those processes
4. Appropriately reduce the memory configuration of non-core processes
5. If physical memory is genuinely insufficient, consider scaling up node memory
6. Restart the alarm process and observe whether the alarm is cleared

### 4.4 GC Anomaly Caused by Process Abnormality

**Symptoms:**
- Process running status is abnormal
- GC logs contain abnormal error messages
- Process may restart frequently

**Solution:**
1. View process status (refer to 2.2)
2. View process GC logs (refer to 3.4) to locate the abnormal cause
3. Collect OmmServer logs (refer to 3.7)
4. Contact O&M personnel and send the collected fault log information
5. Restart the process if necessary

### 4.5 Emergency System Recovery

**Scenario:** Excessively long Full GC time causes the OMS active node system to lag, with delayed page refreshes or slow API responses, making normal O&M operations impossible.

**Solution:**
- **OMS active node:**
  1. Log in to the active OMS node as the omm user
  2. Execute the active/standby switchover command:
     - IPv4 mode: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=127.0.0.1 --port=20013 --switchover --name=product`
     - IPv6 mode: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=::1 --port=20013 --switchover --name=product`
  3. After the switchover succeeds, the system resumes normal operation
  4. Investigate and resolve the Full GC issue on the original active node
  5. Restart the abnormal process or adjust the memory configuration

## 5. Alarm Diagnosis Process

### 5.1 Diagnosis Flowchart

```
Start
  |
  v
Obtain cluster name, service name, role name, host name, process name from alarm information
  |
  v
Obtain OMS active/standby node information, determine whether the alarm node is the OMS active node
  |
  v
View alarm node process status (process_status)
  |
  +--- Process abnormal ---> View process GC log details ---> Collect OmmServer logs ---> Contact O&M personnel
  |
  +--- Process normal ---> View system memory usage (free)
                              |
                              +--- System memory insufficient ---> Investigate abnormal process memory usage ---> Stop non-essential processes or scale up memory
                              |
                              +--- System memory normal ---> View OMS process GC logs (oms_gc_log)
                                                            |
                                                            v
                                                  Use jstat to view GC statistics
                                                            |
                                                            +--- Full GC frequent and time-consuming ---> Use jmap to view memory heap usage
                                                            |                                                  |
                                                            |                                                  +--- High old gen usage ---> View JVM parameter configuration
                                                            |                                                  |                               |
                                                            |                                                  |                               +--- Memory config too small ---> Increase memory parameters and restart
                                                            |                                                  |                               |
                                                            |                                                  |                               +--- Memory config reasonable ---> Suspect memory leak ---> Export heap snapshot for analysis
                                                            |                                                  |
                                                            |                                                  +--- Normal old gen usage ---> Collect OmmServer logs ---> Contact O&M personnel
                                                            |
                                                            +--- Full GC not frequent ---> View disk usage ---> Confirm whether it is sporadic
                                                                                           |
                                                                                           +--- Insufficient disk space ---> Clean up disk space
                                                                                           |
                                                                                           +--- Normal disk space ---> Observe whether alarm auto-clears
  |
  v
Determine whether active/standby switchover is needed
  |
  +--- OMS active node and system lagging ---> Trigger active/standby switchover for emergency recovery
  |                                                |
  |                                                v
  |                                         Investigate and resolve Full GC issue
  |
  +--- Non-active node or system normal ---> Directly handle Full GC issue
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the above diagnosis process, output one of the following conclusions:

| Diagnosis Conclusion | Recommended Action |
|----------------------|---------------------|
| Unreasonable process memory configuration | Increase memory parameters and restart process |
| Process memory leak | Export heap snapshot for analysis, contact O&M personnel |
| Insufficient system memory | Stop non-essential processes or scale up node memory |
| GC anomaly caused by process abnormality | Collect logs, contact O&M personnel |
| Emergency system recovery | Perform active/standby switchover then investigate Full GC issue |
| Alarm persists after handling | Collect OmmServer logs, contact O&M personnel |
