# `NTP Service Abnormal` (12012) Alarm Diagnosis Skill

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **NTP Service Abnormal (12012)** alarm. NTP service abnormality typically refers to the node's NTP service being unable to synchronize time normally with the active OMS node's NTP service, or the time deviation being too large (greater than or equal to 20s), resulting in time desynchronization between cluster nodes, which may affect Kerberos authentication and normal business operation.

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12012 |
| Alarm Name | NTP Service Abnormal |
| Alarm Severity | Important |
| Alarm Type | System Alarm |
| Auto-cleared | Yes |
| System Impact | Node time is not synchronized with other cluster nodes, which may prevent FusionInsight applications on that node from running normally; continuously increasing time deviation may cause Kerberos authentication failure, leading to business abnormalities |

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information and determine the active OMS node name and IP address.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Check Alarm Node NTP Service Mode

Execute the following command to check the NTP service mode of the alarm node. If "chrony" appears in the "ResName" column of the output, chrony mode is in use; if "ntp" appears, ntp mode is in use; if both "chrony" and "ntp" appear simultaneously, the NTP service mode is being switched; wait 10 minutes and check again.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.3 Check Alarm Node chronyd Process Status

Execute the following command to check whether the chronyd process is running on the alarm node. If the command output contains chronyd process information, the process is running normally; otherwise, the process has not started.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"chronyd"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.4 Check Alarm Node chrony Service Sync Status

Execute the following command to check the chrony service synchronization status between the alarm node and the active OMS node. If the active OMS node IP address is preceded by an asterisk (*), synchronization is normal; if the IP has no asterisk and the "Reach" item is "0", synchronization is abnormal.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=service-status' \
  -p 'env={"SERVICE_NAME":"chronyd"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.5 Check Alarm Node ntpd Process Status

Execute the following command to check whether the ntpd process is running on the alarm node. If the command output contains ntpd process information, the process is running normally; otherwise, the process has not started.


### 2.6 Check Alarm Node NTP Service Sync Status

Execute the following command to check the NTP service synchronization status between the alarm node and the active OMS node. If the active OMS node IP address is preceded by an asterisk (*), synchronization is normal; if the IP has no asterisk and the "refid" item is ".INIT.", synchronization is abnormal.

### 2.7 Check NTP Authentication Key Consistency

Execute the following command to obtain the NTP authentication key values from both the active OMS node and the alarm node, and compare whether the key value with authentication key index "1M" is consistent.

**chrony mode:**

Get active OMS node chrony.keys content:

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/chrony.keys"}' \
  -p 'node_name=<oms_master_node>'
```

Get active OMS node ntpKeyFile content:

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/chrony.keys"}' \
  -p 'node_name=<oms_master_node>'
```

Get alarm node chrony.keys content:

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/ntp/ntpkeys"}' \
  -p 'node_name=<node_name>'
```

**ntp mode:**

Get active OMS node ntpkeys content:

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/ntp/ntpkeys"}' \
  -p 'node_name=<oms_master_node>'
```

Get active OMS node ntpKeyFile content:

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/ntp/ntpkeys"}' \
  -p 'node_name=<oms_master_node>'
```

Get alarm node ntpkeys content:

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/ntp/ntpkeys"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<oms_master_node>`: Active OMS node name, obtained from 2.1
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

Compare the key value with authentication key index "1M":
- If the key values from all three sources (active OMS node key file, ntpKeyFile, alarm node key file) are consistent, the key value is normal
- If inconsistent, the key value needs to be modified (refer to 3.2 or 3.5)

### 2.8 Check Firewall Status

Execute the following command to check the firewall status of the alarm node and confirm whether UDP ports 123 and 323 are blocked.


## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., commands that require manual login to the node).

### 3.1 Start chrony Service

When the chronyd process is not running, log in to the alarm node as the root user and execute the following command to start the chrony service:

```bash
systemctl start chronyd
```

After starting, wait 10 minutes and check whether the alarm has recovered.

### 3.2 Modify chrony Authentication Key

**Modify active OMS node chrony.keys:**

Log in to the active OMS node as the root user or omm user and execute the following commands:

```bash
cd ${BIGDATA_HOME}/om-server/OMS/workspace/conf
sed -i "`cat chrony.keys | grep -n '1 M'|awk -F ':' '{print $1}'`d" chrony.keys
echo "1 M `cat ${BIGDATA_HOME}/om-server/om/packaged-distributables/ntpKeyFile`" >> chrony.keys
```

Confirm that the key value with authentication key index "1M" in chrony.keys is the same as the value in ntpKeyFile. If inconsistent, modify it manually.

**Modify alarm node chrony.keys:**

Log in to the alarm node as the omm user and execute the following commands:

```bash
su - omm
vi ${NODE_AGENT_HOME}/chrony.keys
```

Modify the key value with authentication key index "1M" to the key value from ntpKeyFile.

### 3.3 Restart chrony Service

After modifying the key value, log in to the active OMS node as the root user and execute the following command to restart the chrony service:

```bash
systemctl restart chronyd
```

Wait 15 minutes and check whether the alarm has been cleared.

### 3.4 Start NTP Service

When the ntpd process is not running, log in to the alarm node as the root user and execute the following command to start the NTP service:

- SUSE system:
```bash
service ntp start
```

- Red Hat system:
```bash
service ntpd start
```

After starting, wait 10 minutes and check whether the alarm has recovered.

### 3.5 Modify NTP Authentication Key

**Modify active OMS node ntp.keys:**

Log in to the active OMS node as the root user or omm user and execute the following commands:

```bash
cd ${BIGDATA_HOME}/om-server/OMS/workspace/conf
sed -i "`cat ntp.keys | grep -n '1 M'|awk -F ':' '{print $1}'`d" ntp.keys
echo "1 M `cat ${BIGDATA_HOME}/om-server/om/packaged-distributables/ntpKeyFile`" >> ntp.keys
```

> **Note**: For Red Hat systems, change ntp.keys to ntpkeys.

Confirm that the key value with authentication key index "1M" in ntp.keys is the same as the value in ntpKeyFile. If inconsistent, modify it manually.

**Modify alarm node ntp.keys:**

Log in to the alarm node as the omm user and execute the following commands:

```bash
su - omm
vi ${NODE_AGENT_HOME}/ntp.keys
```

> **Note**: For Red Hat systems, the path is `${NODE_AGENT_HOME}/ntpkeys`.

Modify the key value with authentication key index "1M" to the key value from ntpKeyFile.

### 3.6 Restart NTP Service

After modifying the key value, log in to the active OMS node as the root user and execute the following command to restart the NTP service:

```bash
service ntp restart
```

> **Note**: For Red Hat systems, execute `service ntpd restart`.

Wait 15 minutes and check whether the alarm has been cleared.

### 3.7 Disable Firewall or Configure Firewall Policy

When the firewall blocks NTP synchronization, log in to the alarm node as the root user:

**Disable firewall (if allowed):**

```bash
iptables -F
```

**Configure firewall policy (if firewall cannot be disabled):**

Check the firewall configuration policy to ensure that UDP ports 123 and 323 are not blocked:

```bash
iptables -L
```

Add the appropriate allow rules based on the actual firewall configuration. After handling the firewall, wait 10 minutes and check whether the alarm has recovered.

### 3.8 Correct System Time

When the time deviation between the alarm node and the active OMS node is too large:

1. In the FusionInsight Manager "Hosts" page, select the alarm node host
2. Select "More > Stop All Instances" to stop all services on the alarm node
3. Correct the alarm node system time:
   - If the alarm node time is behind the active OMS node, correct the time directly
   - If the alarm node time is ahead of the active OMS node, wait for the corresponding time difference before correcting the time (**failure to wait may cause data loss risk**)
4. After correction, select "More > Start All Instances" to start the services on the alarm node
5. Wait 10 minutes and check whether the alarm has recovered

### 3.9 Collect Fault Logs

If the above steps do not clear the alarm, collect fault log information:

1. In the FusionInsight Manager UI, select "Maintenance > Logs > Download"
2. In "Services", select "NodeAgent" and "OmmServer", then click "OK"
3. Set "Host" to the alarm node and the active OMS node
4. Set the log collection "Start Time" and "End Time" to 30 minutes before and after the alarm generation time
5. Click "Download"
6. Contact operations personnel and send the collected fault log information

## 4. Common Fault Repair Solutions

### 4.1 NTP Service Not Started

**Symptoms**:
- chronyd/ntpd process does not exist
- Alarm node NTP service cannot start normally

**Repair solution**:
1. Confirm the NTP service mode (chrony or ntp)
2. chrony mode: execute `systemctl start chronyd` to start the service
3. ntp mode: execute `service ntp start` (Red Hat: `service ntpd start`) to start the service
4. Wait 10 minutes and verify whether the alarm has recovered

### 4.2 Firewall Blocking NTP Synchronization

**Symptoms**:
- chrony mode: `chronyc sources` shows no asterisk before the active OMS node IP, "Reach" item is "0"
- ntp mode: `ntpq -np` shows no asterisk before the active OMS node IP, "refid" item is ".INIT."
- NTP service process is running normally but cannot synchronize

**Repair solution**:
1. Check firewall status (`iptables -L`)
2. If allowed to disable the firewall, execute `iptables -F`
3. If the firewall cannot be disabled, configure policies to allow UDP ports 123 and 323
4. After processing, wait 10 minutes and verify whether the alarm has recovered

### 4.3 NTP Authentication Key Inconsistency

**Symptoms**:
- Active OMS node chrony.keys/ntp.keys and alarm node key values are inconsistent
- Key value in ntpKeyFile does not match chrony.keys/ntp.keys
- NTP service process is normal, firewall is normal, but synchronization fails

**Repair solution**:
1. Confirm the NTP service mode (chrony or ntp)
2. Obtain and compare the key values from the active OMS node and the alarm node
3. Modify inconsistent key values to match those in ntpKeyFile
4. Restart the NTP service
5. Wait 15 minutes and verify whether the alarm has recovered

### 4.4 Time Deviation Too Large

**Symptoms**:
- NTP alarm additional information describes "time deviation too large"
- Node time deviation from the active OMS node is greater than or equal to 20s

**Repair solution**:
1. Stop all instances on the alarm node from the Manager page
2. Correct the alarm node system time
   - Node time behind: correct directly
   - Node time ahead: wait for the time difference before correcting (to avoid data loss)
3. Start all instances on the alarm node
4. Wait 10 minutes and verify whether the alarm has recovered

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis conclusion | Recommended action |
|----------|----------|
| NTP service not started | Start chrony/NTP service |
| Firewall blocking NTP synchronization | Disable firewall or allow UDP 123/323 ports |
| NTP authentication key inconsistency | Modify key value and restart NTP service |
| Time deviation too large | Stop instances, correct system time, start instances |
| Alarm still persists after processing | Collect fault logs, contact operations personnel |
