# Memory Usage Over Threshold (12018) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Confirm the alarm and memory status (memory-usage)
  |
  +-- Memory usage high + swap large -> Step 2
  +-- Memory usage recovered -> verify via log/GC trace
Step 2: Check high-memory processes (high-memory-process, process-basic-info)
  |
  +-- Java process -> check GC logs for OOM / Frequent Full GC
  +-- Non-Java process -> check process resource/basic info
  +-- Metric normal -> Step 3
Step 3: In-depth log investigation (collect_alarm_log_data)
  |
  +-- OutOfMemoryError / killed process found -> root cause located
  +-- No keywords found -> manually confirm on the node
```

## API Call Chain Dependencies

| Previous-step API | Return field | Next-step API | Parameter |
|-------------------|--------------|---------------|-----------|
| `collect_alarm_node_res_data` | Memory usage / swap info | `high-memory-process` | `node_name` |
| `high-memory-process` | Top memory processes + PID | `process-basic-info` | `env={"process_name":"<process_name>"}` |
| `high-memory-process` | Java process PID | `collect_alarm_log_data` | `log_directory`/`log_file_name` by process GC mapping |

## Diagnosis Steps

### Step 1: Confirm the alarm and memory status

```bash
# Query the current memory usage of the alarm node
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'
```

```bash
# Query the system load to judge the overall pressure on the node
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=system-load' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Actual result | Conclusion | Next step |
|---------------|------------|-----------|
| Memory usage high and swap usage large | The node has a memory bottleneck | Step 2 |
| Memory usage normal / alarm recovered | May be a transient spike or metric alarm; investigate historical traces | Step 3 |
| Companion alarm present (e.g. 12016 CPU / 12017 disk) | Handle the companion alarm first | Refer to the corresponding alarm diagnosis |

---

### Step 2: Check host high-memory processes

```bash
# Query the processes occupying the most memory
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=high-memory-process' \
  -p 'node_name=<node_name>'
```

```bash
# Query basic info of the suspected process
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"<process_name>"}' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Actual result | Conclusion |
|---------------|------------|
| A Java process (pms/controller/tomcat/nodeagent etc.) occupies abnormally high memory | Suspect GC/OOM issue; check the GC logs in Step 3 |
| A non-Java process occupies abnormally high memory | Check the process memory leak or configuration |
| No single process is abnormal but the overall usage is high | Possible swap or system cache (page cache) growth; judge together with the `d-state-process`/zombie status if needed |

---

### Step 3: In-depth log investigation

```bash
# First search the messages log of the alarm node for OOM-related records
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log' \
  -p 'log_file_name=messages*' \
  -p 'keywords=["OutOfMemoryError","Out of memory","killed process","oom","GC overhead"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^([A-Za-z]{3}) +([0-9]{1,2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||bdHMS'
```

```bash
# If a Java process is suspected, query its GC log around the alarm time.
# Select <gc_log_directory>/<gc_log_file_name>/<time_pattern> by process name
# (see the process -> GC log mapping table in alarm 12016).
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=<gc_log_directory>' \
  -p 'log_file_name=<gc_log_file_name>' \
  -p 'keywords=<gc_keywords>' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=<gc_time_pattern>' \
  -p 'alarm_duration_minutes=60'
```

**Keyword analysis**:

| Log keyword | Conclusion |
|-------------|------------|
| `OutOfMemoryError` / `Out of memory` / `GC overhead` in GC logs | The process heap is insufficient; frequent Full GC consumes memory/CPU |
| `killed process` / `oom` in messages log | The OS OOM Killer terminated the process due to insufficient physical memory |
| None of the above keywords | No anomaly in this log; manually confirm the memory status with `free -g` and `dmesg -T` on the alarm node |

## Common Root Causes and Repair Suggestions

### 1. Resource metric exceeds the threshold

**Repair suggestions**:
- Handle it specifically according to the metric that exceeds the threshold
- Clear resources or expand capacity

### 2. Java process heap insufficient / Full GC

**Features**: GC log contains `OutOfMemoryError` or dense `Full GC` during the alarm period

**Repair suggestions**:
- Check whether the JVM heap memory configuration is reasonable; consider increasing `-Xmx` via the Manager configuration
- Analyze whether there is a memory leak (e.g. `jmap -histo:live <pid>`)
- Optimize code to reduce large object allocation

### 3. Insufficient physical memory (OOM Killer)

**Features**: messages log contains `killed process` / `Out of memory`

**Repair suggestions**:
- Release unnecessary memory usage (restart leaking processes)
- Add physical memory or adjust the swap strategy
- Adjust JVM heap memory quotas of each service co-located on the node

### 4. Configuration or file permission anomaly

**Features**: `Permission denied` / `cannot open` appears in the logs

**Repair suggestions**:
- Check the permissions of the relevant files
- Wait 5 minutes after fixing the permissions

### 5. Network or connectivity problem

**Features**: `connection refused` / `timeout` appears in the logs

**Repair suggestions**:
- Check the network connectivity between nodes
- Use the `network-connectivity-test` strategy to test the reachability of the remote node
