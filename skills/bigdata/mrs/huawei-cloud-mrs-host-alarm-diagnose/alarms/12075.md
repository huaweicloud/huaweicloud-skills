# PMS Process Exception Diagnosis and Remediation

## Diagnosis Flow Chart

```
Alarm occurs
    |
    v
Step 1: Obtain alarm basic information
    |
    v
Step 2: Log analysis
    +- 2.1 View pms startup log, determine whether there is a root cause for pms process exception
    +- 2.2 View pms runtime log, determine whether there is a root cause for pms process exception
    +- 2.3 View pms process error log, determine whether there is a root cause for pms process exception
    +- 2.4 View pms process GC log, determine whether there is a root cause for pms process exception
    +- 2.5 View pms process HA log
    |
    v
Step 3: pms running process information
    +- 3.1 Obtain pms HA resource status
            pms running node same as alarm node: -> 3.2 Obtain pms process information -> 3.3 Obtain pms process port information, determine whether there is `port unavailable` or `process stuck`
            pms running node different from alarm node: -> 3.3 Obtain pms process port information, determine whether other processes occupy pms process ports
    |
    v
Step 4: Obtain node resource information, determine whether node resources may cause pms exception
    |
    v
Confirm alarm root cause
    |
    v
Provide remediation recommendation
    |
    v
End
```

## Diagnosis Method

### Step 1: Obtain Alarm Basic Information

Obtain from the alarm information:
- Alarm occurrence time
- Alarm host address
- Alarm occurrence node

### Step 2: Log Analysis

> In the following log collection commands, `<alarm_time>` format is `yyyy/MM/dd HH:mm:ss GMT+X:XX` (e.g., `2026/07/01 20:54:00 GMT+08:00`), `<cluster_id>` is the cluster ID, `<node_name>` is the alarm node hostname.
> Use `python` on Windows, `python3` on Linux.

#### 2.1 View pms Startup Log

View the pms startup log on the alarm occurrence node
```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/pms/scriptlog' \
  -p 'log_file_name=pms_script*.log' \
  -p 'keywords=["Exception","OutOfMemoryError"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'alarm_duration_minutes=60' \
  -p 'time_pattern=^\[([0-9]{4})-([0-9]{2})-([0-9]{2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||ymdHMS'
```
Analyze the log content to determine whether there is a direct cause of pms exception


#### 2.2 View pms Runtime Log

View the pms runtime log on the alarm occurrence node
```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/pms' \
  -p 'log_file_name=pms*.log.*' \
  -p 'keywords=["OutOfMemoryError","Out of memory","Exception","Error"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^\[([0-9]{4})-([0-9]{2})-([0-9]{2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||ymdHMS'
```
Analyze the log content to determine whether there is a direct cause of pms exception

#### 2.3 View pms Process Error Log

View the pms process error log on the alarm occurrence node
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'node_name=<node_name>' \
  -p 'env={"process_name":"PMSMain"}'
```
Based on the returned PID, check whether the corresponding hs_err file exists:
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-file-descriptor' \
  -p 'node_name=<node_name>' \
  -p 'env={"PID":"<pms_pid>"}'
```
Based on the alarm time and process information, determine whether there is a direct cause of pms exception

#### 2.4 View pms Process GC Log

View the `pms process GC log` on the alarm occurrence node

Full GC log
```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/pms/scriptlog' \
  -p 'log_file_name=pms_gc_*' \
  -p 'keywords=["Full GC"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^\[([0-9]{4})-([0-9]{2})-([0-9]{2})T([0-9]{2}):([0-9]{2}):([0-9]{2})||ymdHMS'
```

GC duration log
```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/pms/scriptlog' \
  -p 'log_file_name=pms_gc_*' \
  -p 'keywords=["user=","sys=","real="]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^\[([0-9]{4})-([0-9]{2})-([0-9]{2})T([0-9]{2}):([0-9]{2}):([0-9]{2})||ymdHMS'
```

Analyze pms process memory usage through GC logs to determine whether there is a direct cause of pms exception.

### Step 3: pms Running Process Information

#### 3.1 Obtain pms HA Resource Status

Execute on the alarm occurrence node
```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

<command result example>
NodeName  ResName ResStatus  ResHAStatus  ResType
8-5-225-6 pms      Normal    Normal    Single_active
8-5-225-5 pms      Stopped   Normal    Single_active
</command result example>

**Key observations**:
- Confirm the ResStatus of pms resource on the current node
- Standalone mode: pms should be Normal
- Active/standby mode: primary node pms should be Normal, standby node should be Stopped
- pms running node

#### 3.2 Obtain pms Process Information

Execute the command on the **Normal node obtained in 3.1 Obtain pms HA Resource Status**

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'node_name=<pms_normal_node>' \
  -p 'env={"process_name":"PMSMain"}'
```

Execution result example
```
omm      2159931  1.0  1.2 27257356 3281916 ?    Sl   Jun07  35:36 java -Dprocess.name=pmsd -Xms8192m -Xmx8192m ...
```

**Key observations**:
- Process allocated memory
- Process PID

## Common Root Cause Classification and Remediation

### Root Cause Type 1: Out of Memory (OutOfMemoryError)

**Diagnosis conditions** (any one is sufficient):
- Log contains `OutOfMemoryError` or `Out of memory`
- GC log shows frequent Full GC or GC time too long
- System memory insufficient causing process to be killed by OOM Killer

**Remediation**:
```bash
# 1. Increase PMS JVM heap memory configuration
# Recommendation: Edit configuration file
# vim ${BIGDATA_HOME}/om-server/OMS/workspace/conf/pms/application.properties

# Recommendation: Modify or add the following configuration
# pms.mem=8GB  # Adjust according to actual memory

# 2. Restart PMS service
# Recommendation: Confirm with relevant personnel before executing `restart_app pms`
```

### 3.2 Root Cause Type 2: Port Conflict

**Diagnosis conditions**:
- Startup log shows `BindException` or port binding failure
- `netstat` shows port 20018/20019 already occupied by another process

**Remediation**:
```bash
# 1. Kill the process occupying the port
# Recommendation: Confirm with relevant personnel before executing kill -9 <PID_of_port_occupying_process>

# 2. Confirm port is released
netstat -apn | grep -E "20018|20019" | grep LISTEN

# 3. Restart PMS service
# Recommendation: Confirm with relevant personnel before executing restart_app pms
```
