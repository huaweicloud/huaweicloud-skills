# Host PID Usage Over Threshold (12027) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Confirm the alarm and process status (total-process-count, process-status-distribution)
  |
  +-- Process count is close to the system pid_max limit -> Step 2
  +-- Process count normal / alarm recovered -> Step 3
Step 2: Check the abnormal process distribution (thread-statistics, high-thread-process)
  |
  +-- A single process creates too many threads -> suspect thread leak
  +-- Too many repetitive processes -> suspect process fork storm
  +-- Metric normal -> Step 3
Step 3: In-depth log investigation (collect_alarm_log_data)
  |
  +-- fork/Cannot allocate/Too many open files found -> root cause located
  +-- No keywords found -> manually confirm on the node
```

## API Call Chain Dependencies

| Previous-step API | Return field | Next-step API | Parameter |
|-------------------|--------------|---------------|-----------|
| `collect_alarm_node_res_data` | Process total / status distribution | `thread-statistics` | `node_name` |
| `collect_alarm_node_res_data` | High thread / repetitive processes | `process-basic-info` | `env={"process_name":"<process_name>"}` |
| `collect_alarm_node_res_data` | Suspicious process PID | `collect_alarm_log_data` | `node_name` / `log_directory` |

## Diagnosis Steps

### Step 1: Confirm the alarm and process status

```bash
# Query the total process count of the alarm node
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=total-process-count' \
  -p 'node_name=<node_name>'
```

```bash
# Query the process status distribution (R/S/D/T/Z states)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-status-distribution' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Actual result | Conclusion | Next step |
|---------------|------------|-----------|
| Total process count close to / reaching the system `pid_max` limit | The system PID resource is about to be exhausted | Step 2 |
| Large proportion of D-state / zombie processes | Some processes are stuck and not released | Step 2 |
| Process count normal / alarm recovered | May be a transient spike or metric alarm | Step 3 |

---

### Step 2: Check the abnormal process distribution

```bash
# Query thread statistics to detect a single process that creates too many threads
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=thread-statistics' \
  -p 'node_name=<node_name>'
```

```bash
# Query the processes with the highest thread count
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=high-thread-process' \
  -p 'node_name=<node_name>'
```

```bash
# Query repetitive processes to detect a fork storm
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=repetitive-processes' \
  -p 'node_name=<node_name>'
```

```bash
# Query basic info of the suspected process
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"<process_name>"}' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Actual result | Conclusion |
|---------------|------------|
| A single process has an abnormally high thread count | Suspect a thread leak in the process; locate the process and check its thread stack |
| A large number of repetitive processes | Suspect a fork storm (e.g. a scheduled task spawning processes continuously) |
| Many zombie processes | The parent process does not reap child processes; need to restart the parent process |
| No obvious abnormal process | Continue the log investigation |

---

### Step 3: In-depth log investigation

```bash
# Search the messages log and NodeAgent log for process/thread-related errors
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log' \
  -p 'log_file_name=messages*' \
  -p 'keywords=["Too many open files","fork","Cannot allocate","Resource temporarily unavailable"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^([A-Za-z]{3}) +([0-9]{1,2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||bdHMS'
```

```bash
# Search the NodeAgent runtime log for pid/thread exhaustion records
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/nodeagent' \
  -p 'log_file_name=*.log' \
  -p 'keywords=["fork","Cannot allocate","pid","thread"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

**Keyword analysis**:

| Log keyword | Conclusion |
|-------------|------------|
| `Too many open files` | The file handle / per-process pid limit of a process is exhausted |
| `fork` / `Cannot allocate` / `Resource temporarily unavailable` | Process creation failed; the system pid/thread resources are exhausted |
| None of the above keywords | No abnormality in this log; manually run `ps -eLf | wc -l` and `cat /proc/sys/kernel/pid_max` on the alarm node |

## Common Root Causes and Repair Suggestions

### 1. Resource metric exceeds threshold

**Repair suggestions**:
- Handle the specific over-threshold metric accordingly
- Clean up resources or expand capacity

### 2. The system PID/thread resource is exhausted

**Features**: Process creation reports `Cannot allocate` / `Resource temporarily unavailable`, process count approaches `pid_max`

**Repair suggestions**:
- Manually execute `cat /proc/sys/kernel/pid_max` and `ps -eLf | wc -l` on the alarm node to confirm the boundary
- Locate the process that keeps creating threads/processes via `thread-statistics` / `repetitive-processes`
- Check for a thread leak (unclosed threads/connections) and fix the application logic; restart the leaking process for temporary relief

### 3. Insufficient disk space

**Feature**: The log contains `no space left` / `No space left on device`

**Repair suggestions**:
- Clean up log files and temporary files
- Expand disk capacity

### 4. Configuration or file permission anomaly

**Feature**: The log contains `Permission denied` / `cannot open`

**Repair suggestions**:
- Check the permissions of the related files
- Wait 5 minutes after fixing the permissions

### 5. Network or connectivity issue

**Feature**: The log contains `connection refused` / `timeout`

**Repair suggestions**:
- Check network connectivity between nodes
- Use the `network-connectivity-test` strategy to test the reachability of the remote node
