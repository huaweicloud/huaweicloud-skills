# `NTP Server Abnormal` (12037) Alarm Diagnosis Skill

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **NTP Server Abnormal (12037)** alarm. The system periodically checks the NTP server status at 60-second intervals. When the NTP server is detected as abnormal for 10 consecutive monitoring cycles, this alarm is generated. NTP server abnormality prevents the active OMS node from synchronizing time with the external server, which may cause cluster time deviation and job execution failures.

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12037 |
| Alarm Name | NTP Server Abnormal |
| Alarm Severity | Important |
| Alarm Type | NTP Service Abnormal Alarm |
| Auto-cleared | Yes |
| System Impact | NTP server abnormality prevents the active OMS node from synchronizing time; a time deviation exceeding 5 minutes will cause cluster external client authentication abnormalities and job execution failures |

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information and determine the IP address and hostname of the OMS node (active OMS node) that generated the alarm.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Check Network Connectivity from OMS Node to NTP Server

Execute the following command to check the network connectivity between the active OMS node and the abnormal NTP server. If the command output shows that ping succeeds, the network connection is normal; if ping fails, the network is abnormal.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=network-connectivity-test' \
  -p 'env={"TARGET_IP":"<IP_ADDRESS>"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Active OMS node name, determined from the OMS node information obtained in 2.1
- `<IP_ADDRESS>`: IP address of the abnormal NTP server, obtained from the "hostname" field in the alarm parameters

### 2.3 Determine OMS Node NTP Service Mode

Execute the following command to view the OMS node active/standby resource status and determine the current NTP service mode (chrony or ntp).

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Active OMS node name, determined from the OMS node information obtained in 2.1

How to determine:
- If "chrony" appears in the "ResName" column of the output, chrony service is in use; proceed to 2.4
- If "ntp" appears in the "ResName" column, ntp service is in use; proceed to 2.5
- If both "chrony" and "ntp" appear in the "ResName" column simultaneously, the NTP service mode is being switched; wait 10 minutes and re-execute this step; if both still appear after 10 minutes, contact operations personnel

### 2.4 Check chrony Service Authentication Status with NTP Server

When 2.3 determines that chrony service is in use, execute the following command to check the authentication status between the cluster and the NTP server.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=service-status' \
  -p 'env={"SERVICE_NAME":"chronyd"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Active OMS node name, determined from the OMS node information obtained in 2.1

How to determine:
- If the "Reach" item shows "0", the connection or authentication has failed
- If the "Reach" item shows a non-"0" value, the connection or authentication is normal

### 2.5 Check ntp Service Authentication Status with NTP Server

When 2.3 determines that ntp service is in use, execute the following command to check the authentication status between the cluster and the NTP server.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=service-status' \
  -p 'env={"SERVICE_NAME":"ntpd"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Active OMS node name, determined from the OMS node information obtained in 2.1

How to determine:
- If the "refid" item shows ".AUTH.", authentication has failed
- If the "refid" item shows other values, authentication is normal

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., operations that require the Manager UI or contacting external personnel).

### 3.1 View Alarm Additional Information

View the alarm additional information in the FusionInsight Manager UI to determine the specific cause hints for the alarm.

1. Open the FusionInsight Manager page
2. Select "Maintenance > Alarms > Alarms"
3. Click the details button in the row of this alarm
4. View the alarm additional information, focusing on the following hints:
   - Whether it indicates that the NTP server IP cannot be pinged
   - Whether it indicates that time cannot be obtained from the NTP server
   - Whether it indicates that the time obtained from the NTP server has not been updated continuously

### 3.2 Check Whether Time Can Be Obtained from the NTP Server

Continue viewing the alarm additional information to check whether it indicates that time cannot be obtained from the NTP server.

- If it indicates that time cannot be obtained from the NTP server, contact the NTP server service provider to resolve the NTP server abnormality; after ensuring the NTP server is normal, check whether the alarm has recovered
- If this issue is not indicated, proceed to 3.3

### 3.3 Check Whether the Time Obtained from the NTP Server Has Not Been Updated Continuously

Continue viewing the alarm additional information to check whether it indicates that the time obtained from the NTP server has not been updated continuously.

- If it indicates that the time has not been updated continuously, contact the NTP server service provider to resolve the NTP server abnormality; after ensuring the NTP server is normal, check whether the alarm has recovered
- If this issue is not indicated, proceed to 3.4

### 3.4 Collect Fault Information

When the above steps do not resolve the issue, fault log information needs to be collected.

1. In the FusionInsight Manager UI, select "Maintenance > Logs > Download"
2. In "Services", select "NodeAgent" and "OmmServer", then click "OK"
3. In the upper right corner, set the log collection "Start Time" and "End Time" to 30 minutes before and after the alarm generation time, then click "Download"
4. Contact operations personnel and send the collected fault log information

## 4. Common Fault Repair Solutions

### 4.1 NTP Server Network Abnormality

**Symptoms**:
- Alarm additional information indicates that the NTP server IP cannot be pinged
- Network between the OMS node and the NTP server is unreachable

**Repair solution**:
1. Contact the network administrator to check network configuration and ensure that the network between the NTP server and the active OMS node is normal
2. Check whether firewall rules allow the NTP service port (UDP 123)
3. After the network recovers, wait for the next system NTP detection (60-second cycle) and check whether the alarm is automatically cleared
4. If the alarm is not cleared, continue with subsequent diagnosis steps

### 4.2 Authentication Failure with NTP Server

**Symptoms**:
- chrony service: "Reach" item shows "0"
- ntp service: "refid" item shows ".AUTH."
- Network between the OMS node and the NTP server is normal, but authentication fails

**Repair solution**:
1. Check the NTP server-side authentication configuration (keys, authentication method, etc.)
2. Check whether the authentication information in the OMS node's NTP/chrony configuration file matches the NTP server
3. After correcting the authentication configuration, wait for the next system NTP detection and check whether the alarm is automatically cleared
4. If the authentication configuration cannot be corrected, contact operations personnel

### 4.3 Cannot Obtain Time from NTP Server

**Symptoms**:
- Alarm additional information indicates that time cannot be obtained from the NTP server
- NTP server network is normal and authentication passes, but time cannot be obtained

**Repair solution**:
1. Contact the NTP server service provider to resolve the NTP server abnormality
2. After ensuring the NTP server is normal, wait for the next system NTP detection and check whether the alarm is automatically cleared
3. If the alarm is not cleared, continue with subsequent diagnosis steps

### 4.4 Time Obtained from NTP Server Not Updated Continuously

**Symptoms**:
- Alarm additional information indicates that the time obtained from the NTP server has not been updated continuously
- NTP server is reachable but time synchronization is stalled

**Repair solution**:
1. Contact the NTP server service provider to resolve the NTP server abnormality
2. After ensuring the NTP server is normal, wait for the next system NTP detection and check whether the alarm is automatically cleared
3. If the alarm is not cleared, collect fault logs and contact operations personnel

### 4.5 NTP Service Mode Switching In Progress

**Symptoms**:
- Both "chrony" and "ntp" appear simultaneously in the "ResName" column of status-oms.sh output
- Indicates that the NTP service mode is being switched

**Repair solution**:
1. Wait 10 minutes for the NTP service mode switch to complete
2. After 10 minutes, re-execute status-oms.sh to check
3. If both "chrony" and "ntp" still appear after 10 minutes, contact operations personnel

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Diagram

```
Start
  |
  v
Obtain OMS node hostname and NTP server IP address from alarm information
  |
  v
Obtain cluster OMS active/standby node information; determine active OMS node
  |
  v
Check network connectivity from OMS node to NTP server (ping)
  |
  +--- Network unreachable ---> Contact network administrator to troubleshoot network fault
  |                                |
  |                                v
  |                       Repair network fault; check whether alarm is cleared
  |                                |
  |                                +--- Alarm cleared ---> Processing complete
  |                                |
  |                                +--- Alarm not cleared ---> Continue with subsequent steps
  |
  +--- Network normal ---> Determine OMS node NTP service mode (status-oms.sh)
                            |
                            +--- chrony mode ---> Check chrony authentication status (chronyc sources)
                            |                        |
                            |                        +--- Reach=0 (authentication failed) ---> Contact operations personnel
                            |                        |
                            |                        +--- Reach!=0 (normal) ---> Check whether time can be obtained from NTP server
                            |
                            +--- ntp mode ---> Check ntp authentication status (ntpq -np)
                            |                     |
                            |                     +--- refid=.AUTH. (authentication failed) ---> Contact operations personnel
                            |                     |
                            |                     +--- refid!=.AUTH. (normal) ---> Check whether time can be obtained from NTP server
                            |
                            +--- Both chrony and ntp appear ---> Wait 10 minutes and re-check
  |
  v
Check whether time can be obtained from NTP server (view alarm additional information)
  |
  +--- Cannot obtain time ---> Contact NTP service provider to resolve NTP server abnormality
  |                                |
  |                                v
  |                       Check whether alarm is cleared
  |                                |
  |                                +--- Alarm cleared ---> Processing complete
  |                                |
  |                                +--- Alarm not cleared ---> Continue with subsequent steps
  |
  +--- Can obtain time ---> Check whether time obtained from NTP server has not been updated continuously
                              |
                              +--- Time not updated ---> Contact NTP service provider to resolve NTP server abnormality
                              |                            |
                              |                            v
                              |                   Check whether alarm is cleared
                              |                            |
                              |                            +--- Alarm cleared ---> Processing complete
                              |                            |
                              |                            +--- Alarm not cleared ---> Collect fault information
                              |
                              +--- Time updated normally ---> Collect fault information
  |
  v
Collect fault logs (NodeAgent, OmmServer, 30 minutes before and after alarm)
  |
  v
Contact operations personnel for handling
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis conclusion | Recommended action |
|----------|----------|
| NTP server network abnormality | Contact network administrator to repair network; wait for alarm to be automatically cleared |
| Authentication failure with NTP server | Check authentication configuration; contact operations personnel; wait for alarm to be automatically cleared |
| Cannot obtain time from NTP server | Contact NTP service provider to resolve NTP server abnormality; wait for alarm to be automatically cleared |
| Time obtained from NTP server not updated continuously | Contact NTP service provider to resolve NTP server abnormality; wait for alarm to be automatically cleared |
| NTP service mode switching in progress | Wait 10 minutes and re-check; if persistent abnormality, contact operations personnel |
| Cause not located | Collect NodeAgent and OmmServer logs; contact operations personnel |
