# `D-State and Z-State Process Count Exceeds Threshold` (12028) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Confirm D-state and Z-state processes (d-state-process + zombie-process + process-status-distribution)
  |
  +- D-state process count = 0 and Z-state process count = 0, alarm recovered -> Alarm recovered branch
  |                                              |
  |                                              Step 1: Infer abnormality at that time from messages log
  |                                                |
  |                                                +- I/O error -> Root cause: Disk IO failure
  |                                                +- oom/killed process -> Root cause: Insufficient memory
  |                                                +- No abnormality -> Summarize current status, suggest observation
  |
  +- D-state processes exist -> Step 2: D-state process in-depth analysis
  |     |
  |     +- disk-io: await/util high -> Root cause: Disk IO bottleneck
  |     +- disk-health-check: Disk failure/mount read-only -> Root cause: Disk hardware failure
  |     +- NFS or network storage lag -> Root cause: Network storage unreachable
  |     +- IO normal, D-state processes persist -> Root cause: Kernel-level IO stuck, system reboot needed
  |
  +- Z-state processes exist -> Step 3: Z-state process in-depth analysis (find parent process)
  |     |
  |     +- Parent process is Java service (tomcat/pms/controller etc.) -> Check service for abnormality
  |     +- Parent process is system process (collectd/rsyslog etc.) -> Check system component
  |     +- Parent process is script/cron job -> Root cause: Script not properly reaping child processes
  |
  +- Both D-state and Z-state processes exist -> Step 2 + Step 3 parallel investigation
        |
        +- Continue steps 4-6 comprehensive check

> After locating the root cause, jump directly to "Common Root Causes and Repair Suggestions"; no need to continue subsequent steps.
> D-state and Z-state may coexist or appear independently; select the corresponding branch based on actual symptoms.
```

## Diagnosis Steps

### Step 1: Confirm D-state and Z-state Processes

```bash
# D-state process list
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=d-state-process' \
  -p 'node_name=<node_name>'

# Z-state (zombie) process list
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=zombie-process' \
  -p 'node_name=<node_name>'

# Process status distribution (overall view of process counts in each state)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-status-distribution' \
  -p 'node_name=<node_name>'
```

**Analysis**: Cross-confirm the actual D-state and Z-state process situation through the three strategies. `process-status-distribution` provides a global view (process counts in each state: R/D/Z/S/T, etc.), while `d-state-process` and `zombie-process` provide specific process lists (including PID, process name, parent process PPID, etc.).

| Actual result | Conclusion | Next step |
|----------|------|--------|
| D-state process count > 0 | Processes stuck in IO wait exist | Step 2 (D-state in-depth analysis) |
| Z-state process count > 0 | Child processes not reaped by parent exist | Step 3 (Z-state in-depth analysis) |
| Both D-state and Z-state exist | Both problems coexist | Step 2 + Step 3 parallel investigation |
| Both D-state and Z-state count = 0, alarm recovered | Need to investigate from historical traces | "Alarm recovered" branch below |

### Alarm Recovered Investigation Branch

After the alarm recovers, D/Z-state processes may have disappeared. Investigate in the following order:

#### Step 1: Obtain Abnormality Clues from That Time

Determine the abnormality cause at that time from the following sources (by priority):
1. **Alarm details** - whether they contain process name and count threshold
2. **messages log** - I/O error, OOM, killed process records
3. **User confirmation** - directly ask the user which service may have been abnormal at that time

```bash
# Abnormal records in messages log during the alarm period
# First try the rotated log with date suffix; if no results, use messages
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log' \
  -p 'log_file_name=messages-<YYYYMMDD>' \
  -p 'keywords=["ERROR","oom","killed process","I/O error","segfault"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^([A-Za-z]{3}) +([0-9]{1,2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||bdHMS'
```

> If `messages-<YYYYMMDD>` does not exist (logs not rotated by date), retry with `log_file_name=messages`.

> **messages log permissions**: The omm user may not have permission to read `/var/log/messages`; sudo is required. If API collection fails, suggest that the user manually check with sudo on the node.

**Comprehensive analysis**:

| Symptom | Conclusion |
|------|------|
| I/O error in messages | Root cause: Disk IO failure caused processes to enter D-state |
| oom/killed process in messages | Root cause: Insufficient memory triggered OOM Killer; child processes became Z-state after being killed |
| segfault in messages | Root cause: Process segfault abnormal exit; may produce Z-state |
| No abnormal records | Problem has recovered; suggest continued observation or immediately execute steps 1-3 at the next alarm |

### Step 2: D-state Process In-Depth Analysis

D-state (Uninterruptible Sleep) processes are typically waiting for IO to complete and cannot be terminated with `kill`. Disk IO and disk health need to be investigated in correlation.

```bash
# Disk IO status (iostat -x, sar -d)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-io' \
  -p 'node_name=<node_name>'

# Disk health check (lsblk, mount read-only check, /proc/mdstat)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-health-check' \
  -p 'node_name=<node_name>'
```

**Analysis**: Combine the D-state process list with disk IO/health status for comprehensive judgment.

| disk-io result | disk-health-check result | Conclusion | Next step |
|-------------|----------------------|------|--------|
| await high (>10ms), %util near 100% | Disk normal | **Root cause located**: Disk IO bottleneck causing process D-state -> Common root cause 1 | — |
| await normal | Disk failure/RAID degraded | **Root cause located**: Disk hardware failure causing IO stuck -> Common root cause 2 | — |
| await normal | Mount point read-only (ro) | **Root cause located**: File system read-only causing IO operations to stuck -> Common root cause 2 | — |
| await normal, but D-state process mount point is NFS | NFS mount normal | Suspected NFS network storage lag -> Common root cause 3 | — |
| IO and disk both normal, D-state processes persist | Disk normal | **Root cause located**: Kernel-level IO stuck, system reboot needed -> Common root cause 4 | — |

> **D-state process name and mount point correlation**: Obtain the process name and PID from the `d-state-process` output; combined with `/proc/<pid>/mountinfo`, you can determine which file system the process is accessing. If D-state processes are concentrated on a certain NFS mount path, prioritize investigating the NFS server.

> **D-state processes cannot be terminated with kill**: `kill -9` has no effect on D-state processes; you can only wait for IO to complete or the underlying device to recover. If D-state processes persist for a long time, it usually means the underlying storage device has failed.

### Step 3: Z-state Process In-Depth Analysis

Z-state (Zombie) child processes have exited but their parent process has not called `wait/waitpid` to reap them. You need to find the parent process (PPID) of the zombie process and analyze whether the parent process is abnormal.

```bash
# View parent process information of zombie processes (need to obtain the process name corresponding to PPID from step 1's zombie-process output)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"<parent_process_name>"}' \
  -p 'node_name=<node_name>'
```

> The `zombie-process` output contains the PID, PPID, and process name of each zombie process. **PPID is the parent process PID of the zombie process**; you need to find the parent process name based on PPID and pass it to the `process_name` parameter of `process-basic-info`.

**Analysis**: Handle based on parent process type:

| Parent process type | Common cause | Next step |
|-----------|---------|--------|
| Java service (tomcat/pms/controller/acs etc.) | Service created child processes without proper reaping, or service exited abnormally | Check service logs, consider restarting service |
| System component (collectd/rsyslog etc.) | Component forked child process then exited abnormally | Check component configuration, consider restarting component |
| Script/cron job (python/shell etc.) | Script started child process without wait, or child process exited abnormally | Check script logic, fix child process reaping logic |
| Parent process no longer exists (PPID=1, adopted by init) | Original parent process has exited; zombie process adopted by init | Zombie process normally auto-reaped by init; if not reaped, system abnormality |
| Parent process is also Z-state | Parent-child process chain all zombified | Trace up the PPID chain to find the first non-Z-state ancestor process |

> **PPID tracing**: If the parent process is also in an abnormal state, continue tracing up the PPID chain. Obtain the current process's PPID from the `process-basic-info` output, then query the parent process one level up by its process name, until the root cause process is found.

Excessive D-state and Z-state processes are often accompanied by system resource abnormalities. A comprehensive check of system load, memory, and disk space is needed.

```bash

  -p 'cluster_id=<cluster_id>' \

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'

# Disk space
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Check item | Abnormal symptom | Related conclusion |
|--------|---------|---------|
| system-load | 1-minute load far exceeds core count, and iowait high | D-state process accumulation causing high load; corroborates with step 2 |
| system-load | High load but low iowait | Z-state processes occupying PID resources; may cause difficulty forking new processes |
| memory-usage | Available memory very low, high swap usage | Insufficient memory may cause abnormal process exit producing Z-state; kswapd entering D-state |
| memory-usage | Sufficient memory | Rule out insufficient memory factor; continue investigating other root causes |
| disk-space | Some partition usage >90% | Insufficient disk space may cause IO operation failure; processes enter D-state |
| disk-space | /tmp or /var full | May cause services unable to write temp files; forking child processes fails producing abnormalities |

> **system-load iowait and D-state correlation**: When D-state processes are waiting for IO, CPU time is counted as iowait. If iowait is high and D-state processes exist, they corroborate each other; the root cause points to disk IO or the storage layer.

### Step 5: System Log Check

Check the messages log for IO errors, OOM, segfault, and other kernel records related to D/Z-state processes.

```bash
# Abnormal records such as IO errors, OOM, segfault in messages log
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log' \
  -p 'log_file_name=messages-<YYYYMMDD>' \
  -p 'keywords=["ERROR","oom","killed process","I/O error","segfault"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^([A-Za-z]{3}) +([0-9]{1,2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||bdHMS'
```

> If `messages-<YYYYMMDD>` does not exist (logs not rotated by date), retry with `log_file_name=messages`.

**Analysis**:

| Log keyword | Meaning | Related conclusion |
|-----------|------|---------|
| `I/O error` | Disk IO error | **Root cause located**: Disk hardware failure causing process D-state -> Common root cause 2 |
| `Buffer I/O error` | Buffer IO error | Disk or file system abnormality; may be accompanied by file system damage |
| `oom` / `Out of memory` | OOM Killer triggered | Insufficient memory; processes may produce Z-state after being killed -> Common root cause 5 |
| `killed process` | Process killed by OOM Killer | Confirm killed process name; its child processes may become Z-state |
| `segfault` | Segmentation fault | Process abnormal crash; may produce Z-state |
| `task blocked for more than` | Process blocked beyond threshold | D-state process long IO wait; kernel records alarm |
| `hung_task_timeout_secs` | Process stuck timeout | D-state process long blocked; need to monitor underlying storage status |
| No abnormal records | No directly related records in logs | Problem may be caused by application layer; continue step 6 |

> **hung_task log**: The kernel checks every 120 seconds by default whether D-state processes have unblocked; if timeout occurs, it outputs `INFO: task <process_name>:<pid> blocked for more than 120 seconds.` log. This is the most direct evidence of D-state process long-term stuck.

## Common Root Causes and Repair Suggestions

> The following repair suggestions must be executed manually by the user; the automated tool is only responsible for diagnosis and localization.

### 1. Disk IO Bottleneck

**Characteristics**: In step 2, disk-io shows await high, %util near 100%; D-state processes concentrated on processes accessing that disk

**Repair suggestions**:
- Investigate whether there are large log writes or abnormal IO operations
- Check disk scheduler configuration (e.g., deadline/noop/cfq); consider optimizing scheduling policy
- Consider scaling up disks or using higher-performance storage devices
- Limit write frequency of high-IO processes

**Notes**:
- High iowait is not necessarily a local disk issue; it may also be caused by NFS or other network storage lag; comprehensive judgment based on mount type is needed
- Before cleaning up large log files, confirm that no process is holding the file (otherwise disk space will not be released after deletion); it is recommended to first `> file` to clear content, then delete
- Disk scaling involves MRS cluster O&M operations and must follow the change management process

### 2. Disk Hardware Failure / File System Read-Only

**Characteristics**: In step 2, disk-health-check shows disk failure/RAID degraded/mount point read-only; messages log has `I/O error` or `Buffer I/O error`

**Repair suggestions**:
- Disk hardware failure: Contact operations to replace the failed disk and rebuild the RAID array
- File system read-only: Check dmesg for file system errors; attempt `fsck` repair (partition must be unmounted first)
- After mount point becomes read-only, use `mount -o remount,rw <mount_point>` to remount as read-write

**Notes**:
- `fsck` file system repair must be executed when the partition is unmounted or in read-only state; in production environments, services must be stopped before operating
- Disk replacement and RAID rebuild are high-risk operations; strictly follow hardware O&M procedures
- Mount point becoming read-only is usually a protection mechanism after the kernel detects disk errors; directly remounting as rw may lose data; prioritize repairing the underlying disk issue

### 3. NFS or Network Storage Lag

**Characteristics**: D-state process file operations concentrated on NFS mount path; local disk IO normal but NFS mount point unresponsive

**Repair suggestions**:
- Check whether the NFS server is running normally and the network is reachable
- Check whether NFS mount parameters are reasonable (e.g., hard/soft, timeo, retrans)
- Consider using `umount -f` to force unmount the stuck NFS mount point, then remount
- Investigate NFS server load and disk status

**Notes**:
- When NFS mount is stuck, `umount` may also hang; use `umount -f` or `umount -l` (lazy umount)
- After force unmounting NFS, D-state processes may still not disappear; need to wait for kernel timeout or reboot the system
- NFS hard mount mode causes processes to retry IO operations indefinitely; consider using soft mount for critical scenarios (but may lose data)
- Investigating NFS issues requires checking both client and server; recommend contacting the storage administrator for assistance

### 4. D-state Processes Persisting (Kernel-Level IO Stuck)

**Characteristics**: In step 2, both disk-io and disk-health-check are normal, but D-state processes persist for a long time; messages log has `hung_task_timeout_secs` records

**Repair suggestions**:
- If the number of D-state processes is small and they are not critical services, temporarily observe and wait for IO timeout to auto-resolve
- If D-state processes affect critical services, reboot the node operating system
- Before rebooting, ensure that services on this node are prepared for failover

**Notes**:
- **D-state processes cannot be terminated with `kill`**: Including `kill -9` has no effect on D-state processes; the process is waiting for IO completion in kernel mode; signals cannot interrupt
- Rebooting the system is the last resort for D-state process accumulation; before rebooting:
  - Confirm the node's roles (e.g., NameNode/ResourceManager and other critical roles) and assess failover impact
  - Ensure through MRS Manager that critical services have been migrated to other nodes
  - Record current D-state process information for subsequent root cause analysis
- D-state processes persisting is usually a symptom of underlying storage device failure; after reboot, still investigate storage layer issues to prevent recurrence

### 5. Insufficient Memory Triggering OOM Killer

**Characteristics**: In step 5, messages log has `oom` / `Out of memory` / `killed process`; in step 4, memory-usage shows very low available memory

**Repair suggestions**:
- Release unnecessary memory usage (restart memory-leaking processes)
- Add physical memory or adjust swap strategy
- Adjust JVM heap memory quotas for each service to avoid single-node memory overcommit

**Notes**:
- Processes killed by OOM Killer may have their child processes become Z-state; need to find the Z-state process's parent process to confirm whether it was OOM-killed
- **Adjusting JVM heap memory**: When multiple services share the same node, increasing a service's `-Xmx` requires confirming it will not cause other services to have insufficient memory. It is recommended to first use `omm-process-tree` to understand the memory usage distribution of all services on the node, then adjust holistically
- **Disabling swap**: `swapoff -a` can immediately disable swap; but before disabling, ensure physical memory is sufficient to accommodate all processes' working sets, otherwise OOM Killer will be triggered
- The fundamental solution to OOM requires locating the memory leak source; merely restarting processes is a temporary measure

### 6. Parent Process Not Reaping Child Processes (Z-state Root Cause)

**Characteristics**: In step 3, the Z-state process's parent process was identified as abnormal; parent process is a Java service/system component/script

**Repair suggestions**:
- **Java service**: Check service logs for abnormal exit records; consider restarting the service. After restart, zombie processes will be adopted by init and automatically reaped
- **System component** (collectd/rsyslog etc.): Check component configuration for abnormalities; restart the corresponding component through MRS Manager
- **Script/cron job**: Check script logic to ensure `wait/waitpid` is called after child process exit; investigate abnormal tasks in crontab
- **Parent process already exited (PPID=1)**: Zombie process adopted by init; normally init will auto-reap; if not reaped, system init abnormality, system reboot needed

**Notes**:
- **Z-state processes cannot be directly killed**: Zombie processes have already exited; only the process table entry has not been reaped; `kill` has no effect on them
- **The correct approach is to fix/restart the parent process**: After the parent process restarts, the zombie process's PPID becomes 1 (init), which is automatically reaped by init calling wait
- Restarting the parent process may cause business interruption; assess the impact; recommend first confirming the service's failover capability
- Common causes of Z-state in Java services: Using `Runtime.exec()` or `ProcessBuilder` to create child processes without properly calling `process.waitFor()` or handling `InputStream/OutputStream`, causing child processes to block and become zombies

### 7. Process Abnormal Crash (Segfault)

**Characteristics**: In step 5, messages log has `segfault` records; crashed process's child processes become Z-state

**Repair suggestions**:
- Confirm segfault process name and crash time; check corresponding service logs
- Collect the process's core dump file (if any) for analysis
- Investigate version compatibility issues or known bugs
- Consider upgrading or rolling back the component version

**Notes**:
- Segfaults are usually caused by software bugs; core dump analysis requires developer assistance
- Confirm whether core dump generation is enabled (`ulimit -c`); if output is 0, it is not enabled and crash memory images cannot be obtained
- Z-state processes produced by segfault need to find their parent process and handle according to root cause 6

### 8. System PID Resource Exhaustion

**Characteristics**: In step 1, Z-state process count is extremely high; in step 4, system load abnormal; `process-status-distribution` shows Z-state process count near the system PID limit

**Repair suggestions**:
- Batch find the common parent process of Z-state processes and restart that parent process
- Increase system PID limit: modify `/proc/sys/kernel/pid_max` (confirm kernel version support)
- Investigate the root cause application producing large numbers of child processes

**Notes**:
- PID resource exhaustion causes the system to be unable to fork new processes; all operations requiring child process creation will fail
- Z-state processes occupy process table entries (task_struct); large numbers of Z-state processes directly exhaust PID space
- Increasing `pid_max` is a temporary measure; the fundamental solution requires finding and fixing the application producing zombie processes
- After modifying `pid_max`, newly created processes can use the extended PID range, but existing Z-state processes still need to be reaped by fixing the parent process
