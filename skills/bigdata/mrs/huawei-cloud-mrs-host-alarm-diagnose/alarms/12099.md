## 2. Log Directory

### 2.1 Log Priority

> When analyzing process core dumps, it is recommended to view logs in the following priority order:
>
> | Priority | Log Type | Description |
> |----------|----------|-------------|
> | 1 | System log | System-level process crash log |
> | 2 | Core file | Process crash stack trace |
> | 3 | Process log | Process runtime log |

### 2.2 Log Path

| Log File | Path | Purpose | Priority |
|----------|------|---------|----------|
| System log | `/var/log/messages` | System-level process crash log | 1 |
| Core file | `DumpedFilePath` in alarm additional info | Process crash stack trace | 2 |
| Process log | `${BIGDATA_LOG_HOME}/<service>/` | Process runtime log | 3 |

## 7. Common Root Causes and Repair Suggestions

| Root Cause | Characteristics | Repair Suggestion |
|------------|----------------|-------------------|
| Out of memory causing OOM | System log shows `OOM` or `out of memory`, process killed | Expand memory or adjust process memory configuration, restart process |
| Segmentation fault (code defect) | gdb analysis of core file shows `SIGSEGV`, accessing illegal memory address | Contact technical support to fix code defect |
| Null pointer dereference | gdb stack trace shows null pointer access | Contact technical support to fix code |
| Stack overflow | gdb stack trace shows recursive call or insufficient stack space | Contact technical support to fix code, or increase stack size |
| Double free | gdb stack trace shows `SIGABRT`, memory freed twice | Contact technical support to fix code |
| Insufficient disk space | Core file write failed, system log shows insufficient disk space | Clean up disk space, ensure core file directory is writable |
| Process killed by external signal | System log shows `Killed`, not OOM | Check for accidental kill operation or resource limit |

### Core File Analysis Steps

1. Obtain `DumpedFilePath` (core file path) from alarm additional info
2. Confirm gdb tool is installed: `gdb --version`
3. Obtain core file symbol table and decompress
4. Execute: `gdb --batch -n -ex thread -ex bt <core_file_path>`
5. Analyze stack trace to locate crash position
6. Core files are retained for 72 hours by default and automatically deleted after expiration
