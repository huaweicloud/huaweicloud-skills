# AD Server Connection Exception (12100) Alarm Diagnosis

## 1. Diagnosis Introduction

This document covers the diagnosis and handling of the **AD Server Connection Exception (12100)** alarm. After third-party AD integration, AD domain users are synchronized on a periodic basis (default 60 minutes) or manually. During synchronization, the AD service status is checked. An alarm is generated when the AD service is detected as unavailable for 3 consecutive checks. The alarm is cleared when the AD service recovers.

This alarm applies only to MRS 3.1.5 and later versions.

Alarm basic information:

| Item | Content |
|------|---------|
| Alarm ID | 12100 |
| Alarm Name | AD Server Connection Exception |
| Alarm Severity | Important |
| Alarm Type | Service Connection Monitoring Alarm |
| Auto-clearable | Yes |
| System Impact | AD service unavailable, AD domain user synchronization fails; AD domain users cannot log in to FusionInsight Manager, AD domain users cannot execute business operations |

## 2. Executable Operations

This section provides operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information, identify the active management node, and use it for subsequent login to the active management node for diagnostic operations.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameters:
- `<cluster_id>`: Cluster ID

### 2.2 Test Network Connectivity to AD Server

Execute the following command to test network connectivity from the management node to the third-party AD server and confirm whether the AD server is reachable via ping.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=network-connectivity-test' \
  -p 'env={"TARGET_IP":"<ad_server_ip>"}' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<ad_server_ip>`: Third-party AD server IP address
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.3 Check AD Service Port Connectivity

Execute the following command to check connectivity from the management node to the LDAP port of the third-party AD server, confirming whether the AD service port is reachable.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=port-connectivity-check' \
  -p 'env={"HOST_IP":"<ad_server_ip>","PORT":"<ad_ldap_port>"}' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<ad_server_ip>`: Third-party AD server IP address
- `<ad_ldap_port>`: Third-party AD server LDAP port
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.4 Obtain OMS Key Directories

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.5 Collect Controller Logs

Execute the following command to collect Controller service logs and search for AD synchronization related keywords.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=30' \
  -p 'log_directory=/var/log/Bigdata/controller' \
  -p 'log_file_name=controller.log*' \
  -p 'keywords=["AD","Ldap","ldap","bind","sync","ERROR","exception"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm trigger time
- `<node_name>`: OMS active node name

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the automation tool during the alarm analysis process (i.e., commands that require manual login to the node or operations through the Manager UI).

### 3.1 Check Third-Party AD Configuration

Check third-party AD configuration through the FusionInsight Manager UI.

1. On the FusionInsight Manager page, navigate to "System > Permission > Third-party AD" to open the third-party AD configuration page.
2. Check whether the following configuration items are correct:
   - **AD IP Address**: Third-party AD server IP address
   - **LDAP Port**: Third-party AD server LDAP port
   - **Bind DN**: DN (Distinguished Name) for binding to AD
   - **Bind DN Password**: Password corresponding to the Bind DN

Parameters:
- If any configuration item is incorrect, proceed to `3.2 Modify AD Configuration and Manual Sync`.
- If all configuration items are correct, proceed to `3.3 Check Network Connectivity`.

### 3.2 Modify AD Configuration and Manual Sync

1. Modify the incorrect parameters and click "OK".
2. Navigate to "System > Permission > Users > AD Domain Users" and click "Manual Sync".
3. Check whether the top-right corner displays "Manual sync succeeded.":
   - Yes: Alarm handling complete.
   - No: Proceed to `3.3 Check Network Connectivity`.

### 3.3 Check Network Connectivity

Log in to the active management node as the root user. The password is set by the user before installation; consult the system administrator. The active/standby status and corresponding IP addresses of the management nodes can be viewed in the FusionInsight Manager host management interface.

Execute the following command on the logged-in host node to confirm whether the third-party AD server is reachable via ping:

```bash
ping <ad_server_ip>
```

Parameters:
- `<ad_server_ip>`: Third-party AD server IP address

- If ping succeeds, proceed to `3.4 Check Port Connectivity`.
- If ping fails, contact O&M personnel to check the network.

### 3.4 Check Port Connectivity

Execute the following command to check whether the LDAP port of the third-party AD service is reachable:

```bash
telnet <ad_server_ip> <ad_ldap_port>
```

Parameters:
- `<ad_server_ip>`: Third-party AD server IP address
- `<ad_ldap_port>`: Third-party AD server LDAP port

- If the port is reachable, proceed to `3.5 Check AD Service Status`.
- If the port is not reachable, contact O&M personnel to check the network or firewall configuration.

### 3.5 Check AD Service Status

Contact the third-party AD service administrator to check whether the AD service is normal.

- If the AD service is normal, proceed to `3.6 Collect Fault Information`.
- If the AD service is abnormal, contact the third-party AD service administrator to resolve the AD server issue.

### 3.6 Collect Fault Information

If the above steps do not resolve the issue, collect fault information.

1. On the FusionInsight Manager page, navigate to "O&M > Logs > Download".
2. Under "Service", select the "Controller" module under "OMS" and click "OK".
3. Set the "Start Time" and "End Time" for log collection to 10 minutes before and after the alarm generation time respectively, then click "Download".
4. Contact O&M personnel and send the collected fault log information.

## 4. Common Fault Handling Solutions

### 4.1 AD Configuration Error

**Symptoms**:
- AD IP address, LDAP port, Bind DN, or Bind DN password is incorrectly configured
- Manual sync of AD domain users fails
- Alarm persists and does not auto-clear after generation

**Solution**:
1. On the FusionInsight Manager page, navigate to "System > Permission > Third-party AD" to open the third-party AD configuration page
2. Verify and correct the four configuration items: "AD IP Address", "LDAP Port", "Bind DN", "Bind DN Password"
3. After modification, click "OK" to save the configuration
4. Navigate to "System > Permission > Users > AD Domain Users" and click "Manual Sync" to verify the configuration
5. After confirming "Manual sync succeeded" is displayed, wait for the alarm to auto-clear

### 4.2 Network Connection Fault

**Symptoms**:
- Ping to third-party AD server IP fails
- Telnet to AD server port fails
- AD domain user synchronization fails

**Solution**:
1. Log in to the active management node and execute the ping command to verify network connectivity
2. If ping fails, check network routing and firewall rules
3. If ping succeeds but telnet port fails, check whether the AD server firewall allows the LDAP port
4. After network recovery, manually sync AD domain users on the Manager page to verify
5. After confirming successful sync, wait for the alarm to auto-clear

### 4.3 AD Server Fault

**Symptoms**:
- Network connectivity is normal (ping succeeds, telnet port reachable)
- AD service status is abnormal
- AD domain user synchronization fails

**Solution**:
1. Contact the third-party AD service administrator to confirm AD server running status
2. Check whether the AD server service process is running normally
3. Check whether the AD server system resources (CPU, memory, disk) are sufficient
4. After AD service recovery, manually sync AD domain users on the Manager page to verify
5. After confirming successful sync, wait for the alarm to auto-clear

### 4.4 AD Service Fault

**Symptoms**:
- AD server is running normally but the AD service is abnormal
- LDAP connection established but authentication cannot complete
- Bind DN authentication fails

**Solution**:
1. Contact the third-party AD service administrator to check AD service status
2. Check AD service logs to investigate the cause of the service exception
3. Confirm whether the Bind DN account is locked or the password has expired
4. After AD service recovery, manually sync AD domain users on the Manager page to verify
5. After confirming successful sync, wait for the alarm to auto-clear

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flowchart

```
Start
  │
  ▼
Obtain cluster ID and hostname from alarm information
  │
  ▼
Obtain cluster OMS active/standby node information, identify active management node
  │
  ▼
Check third-party AD configuration (AD IP, LDAP port, Bind DN, Bind DN password)
  │
  ├─── Configuration error ──→ Modify AD configuration and manual sync
  │                     │
  │                     ├─── Sync succeeded ──→ Alarm handling complete
  │                     │
  │                     └─── Sync failed ──→ Check network connectivity
  │
  └─── Configuration correct ──→ Test network connectivity to AD server
                        │
                        ├─── Ping fails ──→ Contact O&M personnel to check network
                        │
                        └─── Ping succeeds ──→ Check AD service port connectivity
                                           │
                                           ├─── Port unreachable ──→ Contact O&M personnel to check network/firewall
                                           │
                                           └─── Port reachable ──→ Contact AD administrator to check AD service status
                                                              │
                                                              ├─── AD service normal ──→ Collect Controller logs, contact O&M
                                                              │
                                                              └─── AD service abnormal ──→ Contact AD administrator to resolve AD server issue
  │
  ▼
End (alarm auto-clears)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis Conclusion | Recommended Action |
|----------------------|---------------------|
| AD configuration error | Correct AD configuration items, verify with manual sync |
| Network connection fault | Investigate network routing and firewall, restore network connectivity |
| AD server fault | Contact AD administrator to repair AD server |
| AD service fault | Contact AD administrator to repair AD service, check Bind DN status |
| Alarm persists after handling | Collect Controller logs, contact O&M personnel |

## 6 Alarm 12100 Diagnosis Notes

Based on the `2. Executable Operations` and `3. Non-Executable Operations` in the 12100 alarm diagnosis process, combined with the `5. Alarm Diagnosis Flow`, the alarm troubleshooting methods and common error handling solutions are provided. Users should confirm the alarm cause based on the provided information.

**Notes**:
- This alarm applies only to MRS 3.1.5 and later versions.
- The AD service status check requires 3 consecutive failures before generating an alarm; occasional network jitter will not immediately trigger the alarm.
- The alarm auto-clears when the AD service recovers; no manual clearing is required.
- When checking AD configuration, focus on verifying whether the four configuration items "AD IP Address", "LDAP Port", "Bind DN", and "Bind DN Password" are correct.
- Network troubleshooting must be initiated from the management node (not the Agent node); the active/standby status of the management node can be viewed in the FusionInsight Manager host management interface.
- If the AD configuration uses a hostname instead of an IP address, additionally check whether DNS resolution is normal.
- When collecting fault logs, collect the Controller module logs under OMS, with a time range of 10 minutes before and after the alarm generation time.
