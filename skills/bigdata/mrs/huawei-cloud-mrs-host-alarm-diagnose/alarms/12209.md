# OMS Process Full GC Count Exceeds Threshold Alarm Diagnosis

## 1. Diagnosis Overview

This document covers the diagnosis and handling of the **OMS Process Full GC Count Exceeds Threshold (12209)** alarm. This alarm indicates that the Full GC (Full Garbage Collection) count of the OMS main process is frequently triggered and exceeds the configured threshold, which may lead to slower task execution or even abnormal service restarts.

Alarm basic information:

| Item | Content |
|------|---------|
| Alarm ID | 12209 |
| Alarm Name | OMS Process Full GC Count Exceeds Threshold |
| Alarm Severity | Important |
| Alarm Type | Service fault alarm |
| Auto-clearable | Yes |
| System Impact | Full GC count exceeding the threshold affects the read/write operations of OMS main processes, which may cause task execution to slow down or even trigger abnormal service restarts and false alarms for other alarms |

## 2. Executable Operations

This section provides the operations that can be executed during alarm analysis.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Obtain the cluster OMS active/standby node information to determine whether the alarm node is the OMS active node.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Obtain OMS Process GC Monitoring Data

Execute the following command to obtain the Full GC count monitoring data for the OMS process and determine whether the Full GC count exceeds the threshold.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"java"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.3 Obtain OMS Process Memory Usage

Execute the following command to obtain the memory usage of the OMS process and determine whether excessive memory usage is causing frequent Full GC.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.4 View OMS Process GC Logs

Execute the following command to obtain the GC logs of the OMS process and analyze the frequency and cause of Full GC.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=30' \
  -p 'log_directory=/var/log/Bigdata/omm/oms' \
  -p 'log_file_name=controller.log*' \
  -p 'keywords=["Full GC","GC","OutOfMemory","ERROR","exception"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm trigger time
- `<node_name>`: OMS active node name

## 3. Non-Executable Operations

This section provides the operations that cannot be executed through the API during alarm analysis (i.e., commands that require logging into the node for manual execution).

### 3.1 View OMS Process Full GC Count Monitoring Metrics

View the OMS process Full GC count on the FusionInsight Manager interface:

1. Log in to the FusionInsight Manager interface
2. Navigate to "Operation and Maintenance > Alarm > Alarm" and expand the detailed information of this alarm in the alarm list
3. Record the process name from the location information, click the reported host name and record the host's service IP address
4. Navigate to "System > OMS" and view the "OMS Process Full GC Count - <process_name>" in the monitoring charts
5. Check whether the Full GC count is greater than 1 (default)
   - If there is no corresponding chart, click the drop-down triangle on the right of the "Monitoring" area, select "Customize", check the corresponding item, and click "OK"

Judgment criteria:
- If the Full GC count is greater than 1, it confirms frequent Full GC and further analysis of the cause is needed
- If the Full GC count is not greater than 1, it indicates recovery has occurred; check whether the alarm has been automatically cleared

### 3.2 Modify OMS Process Memory Configuration and Restart Process

When it is confirmed that the Full GC count exceeds the threshold, contact O&M personnel to modify the memory configuration of the corresponding process:

1. Log in to the alarm node as the omm user
2. Edit the configuration file of the corresponding OMS process and adjust memory-related parameters (such as JVM heap memory size `-Xmx`, `-Xms`)
3. Restart the corresponding OMS process
4. Observe whether the alarm is cleared on the UI

### 3.3 Collect Fault Information

When the above handling steps cannot clear the alarm, collect fault log information:

1. On the FusionInsight Manager page, navigate to "Operation and Maintenance > Log > Download"
2. Check "OmmServer" for the target cluster in "Services"
3. Click the edit button in the upper right corner to set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm occurrence time
4. Click "Download"
5. Contact O&M personnel and send the collected fault log information

## 4. Common Fault Handling Solutions

### 4.1 Unreasonable OMS Process Memory Configuration

**Symptoms:**
- Full GC count frequently exceeds the threshold
- Process memory usage remains persistently high
- OMS service response is slow

**Solution:**
1. View the OMS process Full GC count monitoring metrics to confirm whether the Full GC count exceeds the threshold
2. Analyze GC logs to confirm the cause of Full GC (memory leak or insufficient memory configuration)
3. Contact O&M personnel to modify the memory configuration of the corresponding process (increase JVM heap memory parameters)
4. Restart the corresponding OMS process
5. Observe whether the alarm is automatically cleared

### 4.2 OMS Process Memory Leak

**Symptoms:**
- Full GC remains frequent after adjusting memory configuration
- GC logs show old generation usage continuously growing
- Memory cannot be reclaimed after long-term process operation

**Solution:**
1. Collect fault log information (OmmServer service logs, 10 minutes before and after the alarm occurrence time)
2. Export the process memory Dump file for analysis
3. Contact O&M personnel to locate the memory leak cause
4. Fix the code or adjust configuration based on the analysis results
5. Restart the corresponding OMS process
6. Observe whether the alarm is automatically cleared

### 4.3 Alarm Not Automatically Cleared

**Symptoms:**
- Full GC count has returned to normal after handling
- The alarm still exists and has not been cleared

**Solution:**
1. Confirm whether the current Full GC count has dropped below the threshold
2. Wait for the next system detection cycle (60 seconds) and confirm whether the alarm is automatically cleared
3. If still not cleared, collect fault log information and contact O&M personnel

## 5. Alarm Diagnosis Process

### 5.1 Diagnosis Flowchart

```
Start
  |
  v
Obtain host name and process name from alarm information
  |
  v
Obtain cluster OMS active/standby node information
  |
  v
Obtain OMS process Full GC count monitoring data
  |
  +--- Full GC count > threshold ---> Obtain OMS process memory usage
  |                                        |
  |                                        v
  |                               Obtain OMS process GC logs
  |                                        |
  |                                        v
  |                               Analyze Full GC cause
  |                                        |
  |                                        +--- Unreasonable memory config ---> Modify memory config and restart process
  |                                        |
  |                                        +--- Suspected memory leak ---> Collect fault logs, contact O&M personnel
  |
  +--- Full GC count <= threshold ---> Confirm whether alarm has been auto-cleared
                                             |
                                             +--- Cleared ---> Handling complete
                                             |
                                             +--- Not cleared ---> Collect fault logs, contact O&M personnel
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the above diagnosis process, output one of the following conclusions:

| Diagnosis Conclusion | Recommended Action |
|----------------------|---------------------|
| Unreasonable OMS process memory configuration | Modify memory configuration and restart process |
| OMS process memory leak | Collect fault logs, contact O&M personnel for analysis and handling |
| Full GC has returned to normal, alarm not cleared | Wait for next detection cycle; if still not cleared, collect logs and contact O&M |
| Alarm persists after handling | Collect fault logs, contact O&M personnel |
