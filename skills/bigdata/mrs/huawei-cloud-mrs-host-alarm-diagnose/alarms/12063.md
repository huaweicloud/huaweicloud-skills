# Disk Unavailable (12063) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 0: Alarm information pre-check (provided by user, utilize if present, skip if absent)
  │
  ├─ additionalInfo contains "Disk not readable or writable" → jump to Step 2 (skip Step 1)
  ├─ additionalInfo contains "Disk file system exception"    → jump to Step 2
  ├─ additionalInfo contains "Disk sector exception"         → jump to Step 2
  │
  └─ No additional information → start from Step 1

Step 1: Disk space check (disk-space + log-disk-space + tmp-file)
  │
  ├─ Partition with 100% usage exists ──→ Root cause: Disk full
  │
  └─ Partition space normal → Step 2: Disk health check (disk-health-check)
                        │
                        ├─ Partition read-only ──→ Root cause: Disk failure mounted as read-only
                        ├─ dmesg has I/O error/medium error ──→ Root cause: Disk hardware failure
                        ├─ dmesg has remounting read-only/ext4-fs error ──→ Root cause: Filesystem error switched to read-only
                        ├─ Soft RAID degraded ──→ Root cause: Array degraded
                        ├─ NFS/network mount exception ──→ Root cause: Network storage issue
                        └─ All normal → Step 3: Disk IO check (disk-io + d-state-process)
                                                    │
                                                    ├─ iowait/await/util abnormally high ──→ Root cause: Disk IO exception
                                                    └─ IO normal → Step 4: Log deep investigation
                                                                │
                                                                ├─ diskAvailability.log has errors ──→ Corresponding root cause
                                                                ├─ messages has disk errors ──→ Root cause: Disk hardware failure
                                                                └─ No errors ──→ Possibly transient failure, recommend observation

After root cause located → Step 5: MRS component impact check (as needed)

When alarm has recovered:
  ├─ Disk full recovered ──→ Step 1 confirm current space + Step 4 check diskAvailability.log to locate the cause of being filled at that time
  ├─ Read-only/hardware failure recovered ──→ Unlikely to self-recover, possibly transient error, Step 2+4 check for hardware damage traces
  └─ IO exception recovered ──→ Step 3 confirm current IO + Step 2 check for hardware damage traces

> After finding the root cause, jump directly to "Common Root Causes and Repair Suggestions", no need to continue subsequent steps.
```

## Diagnosis Steps

### Step 0: Alarm Information Pre-check

Ask the user to provide alarm details (if any), including additionalInfo and locationInfo.

**Key fields in additionalInfo**:

| additionalInfo Content | Meaning | Quick Direction |
|---------------------|------|---------|
| `Disk serial number;Disk not readable or writable` | Disk read/write unavailable | Jump directly to **Step 2** |
| `Disk serial number;Disk file system exception, fileSystem Type:xfs` | XFS filesystem exception | Jump directly to **Step 2** |
| `Disk serial number;Disk file system exception, fileSystem Type:ext4` | EXT4 filesystem exception | Jump directly to **Step 2** |
| `Disk serial number;Disk sector exception` | Disk sector damage | Jump directly to **Step 2** |

**Key fields in locationInfo**: Format is `OMS;NA;hostname;mount point`, from which the faulty host and specific mount point can be extracted for targeted checks in subsequent steps.

> If alarm details cannot be provided, start complete investigation from Step 1.

---

### Step 1: Disk Space Check

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=log-disk-space' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=tmp-file' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Actual Result | Conclusion | Next Step |
|----------|------|--------|
| Partition with 100% usage exists | Disk full causing unavailable | **Root cause located** → Common root cause #1 |
| Partition usage >85% but not full | Disk space tight, may cause write failures | Alarm, recommend cleanup |
| Log directory abnormally large | Log files are the root cause of disk full | Common root cause #1 |
| /tmp abnormally large | Temporary files are the root cause of disk full | Common root cause #1 |
| Partition space normal | Not a space issue | Step 2 |

> **Locating full partition**: Find the mount point with 100% usage from `disk-space` (`df -h`) output, then combine with `log-disk-space` (`du -sh /var/log/*`) and `tmp-file` (`du -sh /tmp/*`) to determine what filled that partition.

> **Note**: When `df -h` shows space available but writes fail, it may be inode exhaustion (confirm with `df -i`). The disk-space strategy currently only includes `df -h`; if inode issues are suspected, manual supplementary check is required.

---

### Step 2: Disk Health Check

Covers: block device list, read-only mount, mount information, dmesg disk errors, soft RAID status.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-health-check' \
  -p 'node_name=<node_name>'
```

**Analysis**: Check the output item by item in the following order:

| Check Item | Output Source | Exception Criteria | Conclusion |
|--------|---------|---------|------|
| Read-only mount | `mount` output | Contains `ro,` | **Root cause located**: Disk failure mounted as read-only → Common root cause #2 |
| dmesg disk errors | `dmesg` output | Has `I/O error`, `medium error`, `blk_update_request` | **Root cause located**: Disk hardware failure → Common root cause #3 |
| dmesg read-only conversion | `dmesg` output | Has `remounting read-only`, `ext4-fs error` | Kernel detected error and auto-switched to read-only → Common root cause #2 |
| dmesg device errors | `dmesg` output | Has `ata.*error` | Disk controller/connection exception → Common root cause #3 |
| Soft RAID status | `cat /proc/mdstat` output | Has `(U_)` or `(_U)` | **Root cause located**: Soft RAID array degraded → Common root cause #4 |
| Disk status in lsblk | `lsblk` output | Disk missing or status abnormal | Suspected disk failure → Common root cause #3 |
| NFS/network mount | `mount`/`/proc/mounts` output | Has nfs/cifs mount and abnormal | Network storage issue, not local disk failure |
| All normal | - | - | Step 3 |

> **Linkage with Step 0**: If additionalInfo in Step 0 contains `Disk file system exception, fileSystem Type:xfs/ext4`, focus on dmesg error lines for the corresponding filesystem type; if it contains `Disk sector exception`, focus on `I/O error`, `medium error` lines in dmesg.

### Step 3: Disk IO Check

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-io' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=d-state-process' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Actual Result | Conclusion | Next Step |
|----------|------|--------|
| iowait high, await/util high | Disk IO exception causing unavailable | **Root cause located** → Common root cause #5 |
| iowait high but disk-io shows await/util normal | iowait may be caused by other reasons (such as NFS lag), not local disk IO issue | Continue investigation in Step 4 |
| D-state process exists | Process blocked on IO, indirectly indicates slow disk response | Combine with Step 2 mount output to confirm local disk or network storage |
| IO normal | Not an IO issue | Step 4 |

> High iowait is not necessarily a local disk issue; NFS and other network storage lag also causes high iowait. Combine with Step 2 `mount` output to confirm the mount type.

---

### Step 4: Log Deep Investigation

If Steps 1-3 find no exceptions but the alarm persists, perform deep investigation from detection script logs and system logs:

```bash
# View disk availability detection script log
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/nodeagent/scriptlog' \
  -p 'log_file_name=diskAvailability.log' \
  -p 'keywords=["not available","Touch file failed","Read file failed","fileSystem error","sector exception"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^\[([0-9]{4})-([0-9]{2})-([0-9]{2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||ymdHMS'

# View system messages log (first try rotated log with date suffix)
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log' \
  -p 'log_file_name=messages-<YYYYMMDD>' \
  -p 'keywords=["I/O error","medium error","blk_update_request","ata","remounting read-only","ext4-fs error","xfs"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^([A-Za-z]{3}) +([0-9]{1,2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||bdHMS'
```

> If `messages-<YYYYMMDD>` does not exist (EulerOS/SUSE may use systemd journal instead of messages), retry with `log_file_name=messages`. If still not present, this node does not use messages log, skip this step.

> **messages log permissions**: The omm user may not have permission to read `/var/log/messages`. If API collection fails, recommend the user manually view with sudo on the node.

> The `diskAvailability.log` path is `/var/log/Bigdata/nodeagent/scriptlog/diskAvailability.log`, which records the detection process of `checkDiskAvailability.sh` and the filesystem check results of `diskFileSystemCheck.sh`, directly showing which disk failed read/write.

**Analysis**:

| Actual Result | Conclusion |
|----------|------|
| diskAvailability.log contains "not available"/"Touch file failed"/"Read file failed" | Confirm which disk specifically has read/write unavailable → Common root cause #2/#3 |
| diskAvailability.log contains filesystem check exception | Filesystem exception → Common root cause #2 |
| messages contains I/O error / medium error etc. | Disk hardware failure → Common root cause #3 |
| messages contains remounting read-only / ext4-fs error | Kernel detected error and switched to read-only → Common root cause #2 |
| No errors in either | Possibly transient failure, recommend continued observation |

Disk unavailability may affect MRS components on this node; execute when impact assessment is needed. Based on the components corresponding to the faulty mount point in Step 2, check the corresponding component logs:

```bash

  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/hdfs/dn' \
  -p 'log_file_name=hadoop-omm-datanode-*.log' \
  -p 'keywords=["ERROR","Exception","I/O error","read-only","disk"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'

# NodeManager log (check when faulty mount point contains yarn local directory)
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/yarn/nm' \
  -p 'log_file_name=hadoop-omm-nodemanager-*.log' \
  -p 'keywords=["ERROR","Exception","read-only","disk","unhealthy"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'

# RegionServer log (check when faulty mount point contains hbase data directory)
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/hbase/rs' \
  -p 'log_file_name=hbase-hbase-regionserver-*.log' \
  -p 'keywords=["ERROR","Exception","I/O error","read-only","WAL"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

> The above are the most commonly affected components. If other components (such as ZooKeeper, JournalNode, etc.) are also deployed on the node, refer to the directory structure `ls /var/log/Bigdata/<service_name>/<role_name>/` to determine the log path.

**Analysis**:

| Actual Result | Impact |
|----------|------|
| DataNode reports disk error | HDFS blocks on that disk unreadable, NameNode may have marked this DN as abnormal |
| NodeManager reports unhealthy/disk error | NM marks local directory as unhealthy, no longer accepts new container allocation |
| RegionServer reports WAL/HFile error | RS may have crashed or is aborting, needs immediate handling |
| Component logs normal | Disk failure may not have affected components yet (e.g., faulty disk is not a component data directory) |

## Common Root Causes and Repair Suggestions

> The following repair suggestions need to be manually executed by the user; the automation tool is only responsible for diagnosis and localization.

### 1. Disk Space Full

**Symptom**: disk-space shows partition usage 100%

**Repair Suggestions**:
- Clean up log files
- Clean up temporary files
- Expand disk partition

**Notes**:
- **Cleaning log files**: Before deletion, confirm the file is not held by a process (`lsof <file>` to check if opened), otherwise disk space will not be released after deletion. Recommend `> file` to clear content first, then delete. MRS component logs are usually under `/var/log/Bigdata/`; locate large files by directory size (`log-disk-space` already provides this)
- **Cleaning temporary files**: Files under `/tmp` may be in use by running processes; confirm no process dependency before deletion. Can check with `lsof +D /tmp`
- **Expanding disk**: Involves MRS cluster O&M operations and possible downtime; must follow change management process. Confirm available disk space on virtualization platform/physical machine before expansion
- **Disk full may cause MRS component exceptions**: Such as NameNode edit log unable to write, ZooKeeper transaction log unable to write, etc.; may need to restart corresponding services to recover after cleaning space
- **Inode exhaustion**: When `df -h` shows space but writes fail, it may be inode exhaustion; confirm with `df -i`

### 2. Disk Failure Mounted as Read-only

**Symptom**: mount shows ro read-only mount; dmesg contains "remounting read-only"

**Repair Suggestions**:
- Disk hardware failure, need to replace disk
- Before replacement, try to back up data in read-only partition
- After replacement, rebuild RAID array

**Notes**:
- **Read-only mount is kernel self-protection mechanism**: When ext4 and other filesystems detect severe errors, they automatically switch to read-only to prevent further data corruption. Do not attempt `mount -o remount,rw` to force read-write recovery, which may cause complete data corruption
- **Backing up data**: Read-only partition can be read; copy critical data (such as NameNode fsimage/edits, database files) to another location as soon as possible
- **After disk replacement**: Need to rebuild filesystem (`mkfs`), restore data, rebuild RAID (if applicable); the entire process requires downtime
- **MRS impact**: If the read-only partition is the NameNode data directory, HDFS cannot write new data; if it is the ZooKeeper data directory, ZK may not be able to hold elections

### 3. Disk Bad Sectors/Hardware Failure

**Symptom**: dmesg contains I/O error / medium error / blk_update_request; lsblk shows disk missing

**Repair Suggestions**:
- Replace faulty disk
- After replacement, rebuild RAID array (if applicable)

**Notes**:
- **HDFS data safety**: Single disk failure does not lose data (HDFS has replicas), but replace as soon as possible to avoid simultaneous multi-disk failure causing data loss
- **Disk replacement process**: Locate physical disk position (slot number) → confirm corresponding logical disk → back up data → hot-swap replacement → rebuild RAID → verify status. Refer to server vendor manual for specific operations
- **Disk isolation**: MRS supports slow disk isolation; can trigger via `POST /api/v2/clusters/{cluster_id}/hosts/{host_name}/disk_isolation` to isolate the faulty disk from HDFS, avoiding impact on read/write performance

### 4. RAID Array Degraded

**Symptom**: RAID status is Degraded; /proc/mdstat shows `(U_)` or `(_U)`

**Repair Suggestions**:
- Confirm faulty disk location, replace corresponding disk
- After replacement, trigger RAID rebuild
- During rebuild, array performance degrades; avoid high IO operations

**Notes**:
- **Soft RAID rebuild**: `mdadm --add /dev/md0 /dev/sdX` adds the new disk to the array and auto-starts rebuild; monitor rebuild progress with `cat /proc/mdstat`
- **Hard RAID rebuild**: Operate via MegaCLI/storcli; refer to RAID controller manual for specific commands
- **Rebuild period risk**: Losing another disk while array is degraded will cause data loss (RAID5); complete rebuild as soon as possible
- **Rebuild period performance degradation**: Rebuild requires extensive IO operations; recommend executing during off-peak hours, or set rebuild rate cap via RAID controller

### 5. Disk IO Exception

**Symptom**: disk-io shows iowait/await/util abnormally high

**Repair Suggestions**:
- Investigate abnormal IO processes
- Check for large amounts of small-file random read/write
- Consider optimizing IO scheduler or upgrading disk

**Notes**:
- High iowait is not necessarily a local disk issue; NFS and other network storage lag also causes high iowait. Combine with Step 2 `mount` output to confirm mount type
- Abnormal IO processes can be located via the iowait column of processes in the `high-cpu-processes` strategy
- IO scheduler optimization (such as changing deadline to noop) requires writing to kernel parameters for persistence, and effectiveness depends on disk type (SSD typically uses noop, HDD uses deadline)
- In MRS big data scenarios, NameNode edits writes, HBase WAL writes are high IO operations; need to distinguish from normal business IO
