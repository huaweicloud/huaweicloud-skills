# Process CPU Usage Exceeds Threshold Alarm Diagnosis

## 1. Diagnosis Overview

This document covers the diagnosis and handling of the **Process CPU Usage Exceeds Threshold (12201)** alarm. The system periodically checks CPU usage every 30 seconds. An alarm is generated when CPU usage exceeds the threshold for multiple consecutive checks (default: 10 times). This type of alarm is typically caused by unreasonable alarm threshold configuration, CPU capacity insufficient for business requirements, or peak business periods.

Alarm basic information:

| Item | Content |
|------|---------|
| Alarm ID | 12201 |
| Alarm Name | Process CPU Usage Exceeds Threshold |
| Alarm Severity | Important |
| Alarm Type | System resource alarm |
| Auto-clearable | Yes |
| System Impact | When host CPU usage is too high, it may cause slow processing of business processes and increased latency. In severe cases, it may lead to business processing timeouts, failures, and job execution failures |

## 2. Executable Operations

This section provides the operations that can be executed during alarm analysis.

### 2.1 Check Whether the Alarm Cluster Is a Virtual Machine

Execute the following command. If the result is `none`, it indicates a physical machine; if the output is `kvm`, `vmware`, `oracle`, or other virtualization platform names, it indicates a virtual machine environment.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=systemd-detect-virt' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.2 Obtain CPU Usage and High-CPU Processes on the Alarm Node

Execute the following command to obtain the CPU usage and the list of processes with high CPU consumption on the alarm node, to determine whether abnormal processes are causing excessive CPU usage.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=high-cpu-processes' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.3 Obtain System Load on the Alarm Node

Execute the following command to obtain the system load (1-minute, 5-minute, 15-minute average load) on the alarm node, to determine whether the high CPU load is persistent or transient.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=system-load' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.4 Obtain IO Wait Statistics on the Alarm Node

Execute the following command to obtain IO statistics on the alarm node, to determine whether the high CPU usage is caused by IO wait (iowait).

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-io' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.5 Obtain Memory Usage on the Alarm Node

Execute the following command to obtain the memory usage on the alarm node, to help determine whether insufficient memory is causing frequent swap operations, which in turn increases CPU usage.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.6 Obtain Cluster OMS Active/Standby Node Information

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.7 Obtain OMS Key Directories

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

## 3. Non-Executable Operations

This section provides the operations that cannot be executed through the API during alarm analysis (i.e., commands that require logging into the node or executing manually via FusionInsight Manager).

### 3.1 Check and Modify Alarm Threshold and Smoothing Count Configuration

Log in to FusionInsight Manager to check and modify the alarm threshold and smoothing count configuration for process CPU usage.

Steps:
1. Log in to FusionInsight Manager
2. Navigate to "Operation and Maintenance > Alarm > Threshold Settings > OMS > OMS Service > CPU > Process CPU Usage"
3. Based on actual service usage, click the edit button next to "Smoothing Count" to change the alarm smoothing count
   - This option specifies how many consecutive checks exceeding the threshold are required before an alarm is triggered
4. Click "Modify" in the "Operation" column to change the alarm threshold as needed
5. Wait 2 minutes and check whether the alarm is automatically cleared

### 3.2 View Real-Time CPU Usage Data in FusionInsight Manager

View the real-time CPU usage data of the alarm host in FusionInsight Manager to determine whether CPU usage consistently exceeds the threshold.

Steps:
1. On the FusionInsight Manager page, navigate to "Operation and Maintenance > Alarm > Alarm"
2. Expand the detailed information of this alarm in the alarm list
3. Click the host name that generated the alarm in the location information
4. Observe the "Host CPU Usage" real-time data on the host overview page for about 5 minutes
   - If there is no corresponding chart, click the drop-down triangle on the right, select "Customize", check the corresponding item, and click "OK"
5. If CPU usage exceeds the configured threshold multiple times, contact the MRS cluster administrator to upgrade the CPU

### 3.3 Check Whether the Business Is in a Peak Period

Check whether the current business volume is in a peak period to determine whether the high CPU usage is caused by peak business activity.

Investigation method:
1. Review the business task scheduling plan to confirm whether a large number of jobs are executed concurrently during the alarm period
2. Review historical CPU usage trends and compare current CPU usage with historical levels for the same period
3. If the alarm is caused by a peak period, it is recommended to scale up the node or contact the MRS cluster administrator to upgrade the CPU
4. Check whether the alarm has been cleared

### 3.4 Collect Fault Log Information

When the alarm cannot be cleared through the above steps, collect fault log information and contact O&M personnel.

Steps:
1. On the FusionInsight Manager page, navigate to "Operation and Maintenance > Log > Download"
2. Check "OmmServer" in "Services" and click "OK"
3. Click the edit button in the upper right corner to set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm occurrence time
4. Click "Download"
5. Contact O&M personnel and send the collected fault log information

### 3.5 Investigate Abnormal Processes

When an abnormal process consuming a large amount of CPU is found through `2.2 Obtain CPU Usage and High-CPU Processes on the Alarm Node`, further investigation is required.

Investigation method:
1. Log in to the alarm node and execute `top -c` to view real-time process CPU usage
2. Record the process name, PID, and usage rate of the process with the highest CPU consumption
3. Execute `ps -ef | grep <PID>` to view detailed process information and confirm the service to which the process belongs
4. If it is a known business process, check whether the business has abnormalities (such as infinite loops, large-scale computation tasks, etc.)
5. If it is an unknown process, further investigate potential security risks
6. If necessary, execute `kill -15 <PID>` to terminate the abnormal process (exercise caution and confirm the impact scope)

## 4. Common Fault Handling Solutions

### 4.1 Unreasonable Alarm Threshold or Smoothing Count Configuration

**Symptoms:**
- Alarms are frequently triggered but CPU usage is only slightly above the threshold
- Business runs normally with no significant performance impact
- CPU usage fluctuates around the threshold

**Solution:**
1. Log in to FusionInsight Manager and check the threshold and smoothing count configuration for "Process CPU Usage"
2. Based on actual business CPU usage, appropriately increase the alarm threshold
3. Increase the smoothing count to reduce false alarms caused by transient fluctuations
4. Wait 2 minutes and confirm whether the alarm is automatically cleared

### 4.2 CPU Capacity Insufficient for Business Requirements

**Symptoms:**
- CPU usage consistently exceeds the threshold, exceeding the configured value multiple times
- The node's CPU resources are under high load for an extended period
- Business processing is slow with increased latency

**Solution:**
1. Confirm CPU usage through `2.2 Obtain CPU Usage and High-CPU Processes on the Alarm Node`
2. Confirm that the load is persistent rather than transient through `2.3 Obtain System Load on the Alarm Node`
3. Confirm whether the faulty node is the OMS active node. If so, consider performing an active/standby switchover before handling the issue
4. Contact the MRS cluster administrator to scale up or upgrade the node's CPU
5. After replacement or scaling, verify whether the alarm is automatically cleared

### 4.3 CPU Usage Exceeding Threshold Due to Peak Business Period

**Symptoms:**
- CPU usage consistently exceeds the threshold during specific time periods (such as peak business hours)
- CPU usage returns to normal after the peak period
- Alarms are repeatedly triggered during peak periods and automatically cleared during non-peak periods

**Solution:**
1. Review the business task scheduling plan to confirm whether the alarm time corresponds to peak business hours
2. If the high load is normal during peak periods, evaluate whether scaling is needed
3. It is recommended to scale up the node or contact the MRS cluster administrator to upgrade the CPU
4. Based on actual business conditions, appropriately adjust the alarm threshold and smoothing count
5. Verify whether the alarm is automatically cleared during non-peak periods

### 4.4 High CPU Usage Caused by Abnormal Process

**Symptoms:**
- A single process has abnormally high CPU usage (e.g., a single process consuming nearly 100%)
- CPU usage exceeds the threshold even during non-peak periods
- System load remains persistently high

**Solution:**
1. Identify the abnormal process through `2.2 Obtain CPU Usage and High-CPU Processes on the Alarm Node`
2. Log in to the node to investigate the abnormal process details (refer to `3.5 Investigate Abnormal Processes`)
3. If it is a business process abnormality (such as an infinite loop), attempt to restart the corresponding service
4. If it is a system process abnormality, collect logs and contact O&M personnel
5. After restarting the service or handling the abnormal process, verify whether the alarm is automatically cleared

### 4.5 CPU Usage Increase Caused by IO Wait

**Symptoms:**
- CPU usage is high, with a large proportion of iowait
- The system has a large amount of IO operations, indicating disk performance bottlenecks

**Solution:**
1. Confirm the IO wait situation through `2.4 Obtain IO Wait Statistics on the Alarm Node`
2. Check whether insufficient memory is causing frequent swap through `2.5 Obtain Memory Usage on the Alarm Node`
3. If it is a disk IO bottleneck, investigate disk performance issues (refer to slow disk fault 12033 alarm diagnosis)
4. If insufficient memory is causing frequent swap, consider increasing memory or optimizing business memory configuration
5. After handling, verify whether the alarm is automatically cleared

### 4.6 Emergency System Recovery

**Scenario:** CPU usage is too high, causing system lag, Manager page refresh delays, or slow API responses, making normal O&M operations impossible

**Solution:**
- **Active OMS node:**
  1. Log in to the active OMS node as the omm user
  2. Execute the active/standby switchover command:
     - IPv4 mode: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=127.0.0.1 --port=20013 --switchover --name=product`
     - IPv6 mode: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=::1 --port=20013 --switchover --name=product`
  3. After the switchover succeeds, the system resumes normal operation
  4. Investigate and handle the root cause of the high CPU usage

- **Active node of active/standby service instances:**
  1. Log in to FusionInsight Manager
  2. Navigate to "Cluster > Services > <target_service_name>"
  3. On the service detail page, click "More" and select "Perform <service> Switchover"
  4. Enter the current login user password to confirm identity and click "OK"
  5. Click "OK" on the popup to execute the role instance active/standby switchover
  6. After the switchover succeeds, the system resumes normal operation
  7. Investigate and handle the root cause of the high CPU usage

## 5. Alarm Diagnosis Process

### 5.1 Diagnosis Flowchart

```
Start
  |
  v
Obtain host name, service name, role name, and trigger condition from alarm information
  |
  v
Check whether the alarm cluster is a virtual machine (systemd-detect-virt)
  |
  +--- Virtual machine ---> Obtain CPU usage and high-CPU processes
  |                            |
  |                            v
  |                     Obtain system load and IO wait statistics
  |
  +--- Physical machine ---> Obtain CPU usage and high-CPU processes
                               |
                               v
                        Obtain system load and IO wait statistics
  |
  v
Determine whether CPU usage consistently exceeds the threshold
  |
  +--- Not consistently exceeding ---> Check whether alarm threshold and smoothing count are reasonable
  |                                        |
  |                                        +--- Unreasonable ---> Modify threshold and smoothing count -> Wait for alarm to auto-clear
  |                                        |
  |                                        +--- Reasonable ---> Collect fault logs, contact O&M personnel
  |
  +--- Consistently exceeding ---> Determine whether abnormal processes are consuming excessive CPU
                                      |
                                      +--- Abnormal process exists ---> Investigate abnormal process
                                      |                                    |
                                      |                                    +--- Business process abnormal ---> Restart service
                                      |                                    |
                                      |                                    +--- Unknown process ---> Collect logs, contact O&M
                                      |
                                      +--- No obvious abnormal process ---> Determine whether IO wait is high
                                                                               |
                                                                               +--- High iowait ---> Investigate disk IO and memory issues
                                                                               |
                                                                               +--- Normal iowait ---> Determine whether it is peak business period
                                                                                                        |
                                                                                                        +--- Peak period ---> Scale up or adjust threshold
                                                                                                        |
                                                                                                        +--- Non-peak ---> CPU capacity insufficient, contact administrator to upgrade CPU
  |
  v
Determine whether active/standby switchover is needed
  |
  +--- OMS active node and system lagging ---> Trigger active/standby switchover for emergency recovery
  |                                                |
  |                                                v
  |                                         Investigate and handle CPU root cause
  |
  +--- Non-active node or system normal ---> Directly handle CPU root cause
  |
  v
End (alarm auto-cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the above diagnosis process, output one of the following conclusions:

| Diagnosis Conclusion | Recommended Action |
|----------------------|---------------------|
| Unreasonable alarm threshold configuration | Modify threshold and smoothing count configuration |
| CPU capacity insufficient for business requirements | Contact administrator to upgrade CPU or scale up node |
| CPU exceeding threshold due to peak business period | Scale up node or adjust threshold configuration |
| High CPU caused by abnormal process | Restart abnormal service or terminate abnormal process |
| CPU increase caused by IO wait | Investigate disk IO and memory issues |
| Alarm persists after handling | Collect fault logs, contact O&M personnel |
