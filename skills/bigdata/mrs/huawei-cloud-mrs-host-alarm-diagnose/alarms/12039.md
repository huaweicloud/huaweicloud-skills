# OMS Database Primary-Standby Out of Sync (12039) Alarm Diagnosis

## 1. Diagnosis Introduction

This document covers the diagnosis and handling of the **OMS Database Primary-Standby Out of Sync (12039)** alarm. OMS database primary-standby out of sync means that data on the primary database cannot be synchronized to the standby database normally. The system checks the primary-standby data synchronization status every 10 seconds. If the synchronization status is not found or is abnormal for 30 consecutive checks, an alarm is generated.

Alarm basic information:

| Item | Content |
|------|---------|
| Alarm ID | 12039 |
| Alarm Name | OMS Database Primary-Standby Out of Sync |
| Alarm Severity | Critical (before MRS 3.3.1); Important (MRS 3.3.1 and later) |
| Alarm Type | Database synchronization alarm |
| Auto-Clearable | Yes |
| System Impact | Data on the primary database cannot be synchronized to the standby database normally. If the primary instance fails during the alarm period, user business data may be lost or the Manager page may display abnormal data |

## 2. Executable Operations

This section provides the operations that can be executed during alarm analysis.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information and determine the IP addresses of the primary and standby OMS database nodes.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameters:
- `<cluster_id>`: Cluster ID

### 2.2 Obtain OMS Key Directories

Execute the following command to obtain the OMS key directory information and determine the data directory path of the OMS database.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Alarm node name, obtained from alarm details

### 2.3 Check Standby Node Disk Space Usage

Execute the following command to check the disk space usage of the standby OMS database node and determine whether the disk is full.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Alarm node name (standby OMS database node), obtained from alarm details

## 3. Manual Operations

This section provides operations that cannot be executed automatically (i.e., commands that require logging into the node manually).

### 3.1 Check Primary-Standby Node Network Connectivity

Log in to the primary OMS database node as the root user and execute the ping command to check whether the standby OMS database heartbeat IP address is reachable.

```bash
ping <standby_OMS_database_heartbeat_IP>
```

- `<standby_OMS_database_heartbeat_IP>`: Heartbeat IP address of the standby OMS database node, obtained from alarm details

If the ping succeeds, the network is normal; proceed to step 3.2. If the ping fails, the network is abnormal; contact the network administrator to troubleshoot.

### 3.2 Check Standby OMS Database Status

Log in to the standby OMS database node as the root user and execute the following commands to check whether the standby OMS database resource status is normal.

```bash
su - omm
cd ${BIGDATA_HOME}/om-server/om/sbin/
./status-oms.sh
```

In the output, find the row where "ResName" is "gaussDB" and check whether the following information is displayed:

```
<standby_node_IP> gaussDB Standby_normal Normal Active_standby
```

- If `Standby_normal` is displayed and the status is `Normal`, the standby OMS database status is normal
- If other information is displayed, the standby OMS database status is abnormal

### 3.3 Check Whether Standby Node Disk Is Full

Log in to the standby OMS database node as the root user and execute the following commands to check disk space usage.

```bash
su - omm
echo ${BIGDATA_DATA_HOME}/dbdata_om
df -h
```

- `echo ${BIGDATA_DATA_HOME}/dbdata_om`: Obtains the OMS database data directory
- `df -h`: Views system disk partition usage

Check whether the disk where the OMS database data directory is mounted is full:
- If the disk is full, disk expansion is required
- If the disk is not full, collect fault information for further analysis

> **Note**: This check step is skipped in MRS 3.1.2 and later versions.

### 3.4 Collect Fault Information

When the above steps do not resolve the issue, collect fault log information.

1. On the FusionInsight Manager interface, navigate to "O&M > Logs > Download"
2. Select "OmmServer" under "Services" and click "OK"
3. Click the edit button in the upper right corner, set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm generation time, and click "Download"
4. Contact O&M personnel and send the collected fault log information

## 4. Common Fault Handling Solutions

### 4.1 Primary-Standby Network Instability

**Symptoms**:
- Cannot ping the standby OMS database heartbeat IP address
- High network latency or severe packet loss between primary and standby nodes

**Solution**:
1. Contact the network administrator to troubleshoot the network
2. After the network issue is fixed, wait for the system to automatically check and restore synchronization status
3. Check whether the alarm is cleared in the alarm list
4. If the alarm is not cleared, continue with the subsequent diagnosis steps

### 4.2 Standby OMS Database Abnormal

**Symptoms**:
- status-oms.sh output shows gaussDB not in Standby_normal status
- Standby OMS database resource status is abnormal

**Solution**:
1. Check whether the standby node disk is full
2. If the disk is full, expand the disk
3. If the disk is not full, collect fault logs and contact O&M personnel
4. After handling, wait for the alarm to auto-clear

### 4.3 Standby Node Disk Full

**Symptoms**:
- df -h shows the disk where the OMS database data directory is mounted at 100% usage
- Standby OMS database cannot write data normally

**Solution**:
1. Expand the disk on the standby node
2. After disk expansion, wait 2 minutes and check whether the alarm is cleared
3. If the alarm is cleared, the process is complete
4. If the alarm is not cleared, continue collecting fault information

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Chart

```
Start
  |
  v
Obtain standby OMS database node IP address from alarm details
  |
  v
Check primary-standby network connectivity (ping standby OMS database heartbeat IP)
  |
  +--- Network unreachable ---> Contact network administrator to troubleshoot
  |                               |
  |                               v
  |                        Fix network issue, check whether alarm is cleared
  |                               |
  |                               +--- Alarm cleared ---> Done
  |                               |
  |                               +--- Alarm not cleared ---> Continue with subsequent steps
  |
  +--- Network normal ---> Check standby OMS database status (status-oms.sh)
                            |
                            +--- Status normal ---> Collect fault information
                            |
                            +--- Status abnormal ---> Check standby node disk space (df -h)
                                                      |
                                                      +--- Disk full ---> Expand disk
                                                      |                     |
                                                      |                     v
                                                      |              Wait 2 minutes, check whether alarm is cleared
                                                      |                     |
                                                      |                     +--- Alarm cleared ---> Done
                                                      |                     |
                                                      |                     +--- Alarm not cleared ---> Collect fault information
                                                      |
                                                      +--- Disk not full ---> Collect fault information
  |
  v
Collect fault logs (OmmServer service logs, 10 minutes before and after the alarm)
  |
  v
Contact O&M personnel for handling
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following conclusions:

| Diagnosis Conclusion | Recommended Action |
|----------------------|---------------------|
| Primary-standby network fault | Fix network issue, wait for alarm to auto-clear |
| Standby OMS database abnormal | Check disk space, collect logs and contact O&M if necessary |
| Standby node disk full | Expand disk, wait for alarm to auto-clear |
| Cause not identified | Collect OmmServer logs and contact O&M personnel |
