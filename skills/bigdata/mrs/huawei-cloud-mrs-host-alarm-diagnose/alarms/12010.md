# `Manager Active/Standby Heartbeat Interruption` (12010) Alarm Diagnosis Skill

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **Manager Active/Standby Heartbeat Interruption (12010)** alarm. This alarm indicates that the active Manager node has not received a heartbeat signal from the standby Manager node within 7 seconds, indicating an abnormal heartbeat link between the active and standby Manager nodes, which may affect active/standby switchover functionality and basic O&M operations.

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12010 |
| Alarm Name | Manager Active/Standby Heartbeat Interruption |
| Alarm Severity | Important |
| Alarm Type | Communication Failure Alarm |
| Auto-cleared | Yes |
| System Impact | If the active Manager process resource is abnormal, active/standby switchover cannot be performed, affecting basic O&M operations |

---

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information and determine the active/standby OMS node names and IP addresses, as well as the IP address of the standby Manager (Peer Manager).

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Check Network Connectivity Between Active and Standby Manager Nodes

Execute the following command to check whether the active Manager node can ping the heartbeat IP address of the standby Manager node (i.e., Peer Manager). If the command executes successfully and returns a response, the network connectivity is normal; if the command fails or times out, the network is abnormal.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=network-connectivity-test' \
  -p 'env={"TARGET_IP":"<PEER_OMS_IP>"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred (active Manager node), obtained from the alarm information

### 2.3 Check Active/Standby Heartbeat Port Status

Execute the following command to check whether the heartbeat port (port 20012) between the active and standby Manager nodes is open. If the command output contains query results, the port is open; if there are no query results, the port is blocked by the firewall.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=port-check' \
  -p 'env={"PORT":"20012"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.4 Check Firewall Status

Execute the following command to check the firewall status of the alarm node and confirm whether there are rules blocking the heartbeat port.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/etc/sysconfig/iptables"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.5 Check hacom_local.xml Node Configuration

Execute the following command to view the hacom_local.xml configuration file content and confirm whether the local and peer node configurations are correct (local should be configured as the active node, peer as the standby node).

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-content' \
  -p 'env={"FILE_PATH":"/opt/soft/om/ha/local/hacom_local.xml"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred (active Manager node), obtained from the alarm information

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., commands that require manual login to the node).

### 3.1 Check Whether the Standby Manager Server Is Reachable

Log in to the active management node of the cluster as the root user and execute the following command to check whether the standby Manager server is reachable:

```bash
ping <standby_Manager_heartbeat_IP>
```

- The standby Manager heartbeat IP address is obtained from `2.1 Obtain Cluster OMS Active/Standby Node Information`
- If ping succeeds, the network connectivity is normal; proceed to `3.2` to check node name configuration
- If ping fails, contact the network administrator to check the network link

### 3.2 Find hacom_local.xml Configuration File

Log in to the active management node as the root user and execute the following command to find the configuration file directory for the active and standby nodes:

```bash
cd /opt
find -name hacom_local.xml
```

Navigate to the workspace directory:

```bash
cd ${BIGDATA_HOME}/om-server/OMS/workspace0/ha/local/hacom/conf/
```

### 3.3 Check and Modify hacom_local.xml Configuration

Open hacom_local.xml with vim and check whether the local and peer node configurations are correct:

```bash
vim hacom_local.xml
```

- local should be configured with the active node information
- peer should be configured with the standby node information

If the configuration is incorrect, modify the active/standby node configuration in hacom_local.xml. After modification, press Esc to return to command mode, then enter `:wq` to save and exit.

After modification, check whether this alarm has been automatically cleared.

### 3.4 Handle Firewall Blocked Port

When the heartbeat port is blocked by the firewall, log in to the alarm node as the root user and execute the following commands in order:

Prevent disconnection from the server:

```bash
iptables -P INPUT ACCEPT
```

Clear firewall rules:

```bash
iptables -F
```

After processing, check whether the alarm has been cleared in the alarm list.

### 3.5 Collect Fault Logs

If the above steps do not clear the alarm, collect fault log information:

1. In the FusionInsight Manager UI, select "Maintenance > Logs > Download"
2. In "Services", select the following node information, then click "OK":
   - OmmServer
   - Controller
   - NodeAgent
3. In the upper right corner, set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm generation time
4. Click "Download"
5. Contact operations personnel and send the collected fault log information

## 4. Common Fault Repair Solutions

### 4.1 Active/Standby Manager Node Link Abnormality

**Symptoms**:
- Active Manager node cannot ping the standby Manager node
- Alarm information shows heartbeat interruption between active and standby nodes

**Repair solution**:
1. Confirm the standby Manager (Peer Manager) IP address (refer to `2.1` to obtain cluster OMS active/standby node information)
2. Log in to the active Manager node and ping the standby Manager heartbeat IP address (refer to `3.1`)
3. If ping fails, contact the network administrator to troubleshoot the network link fault
4. After the network fault is repaired, check whether the alarm is automatically cleared
5. If not cleared, continue with subsequent inspection steps

### 4.2 Node Name Configuration Error

**Symptoms**:
- local and peer node configurations in hacom_local.xml are incorrect
- Active/standby node configurations are swapped or IP addresses are wrong
- Network connectivity is normal but the alarm persists

**Repair solution**:
1. Find the hacom_local.xml configuration file location (refer to `3.2`)
2. Check the local and peer node configurations in hacom_local.xml (refer to `2.5` or `3.3`)
3. Modify the configuration: local for the active node, peer for the standby node
4. After saving and exiting, check whether the alarm is automatically cleared
5. If not cleared, continue with the firewall check step

### 4.3 Firewall Blocking Heartbeat Port

**Symptoms**:
- `lsof -i :20012` returns no results, indicating the heartbeat port is blocked
- Firewall rules contain a policy blocking port 20012
- Network connectivity is normal and node configuration is correct, but the alarm persists

**Repair solution**:
1. Check the heartbeat port status (refer to `2.3`)
2. Check the firewall status (refer to `2.4`)
3. Execute `iptables -P INPUT ACCEPT` to prevent disconnection
4. Execute `iptables -F` to clear firewall rules
5. After processing, check whether the alarm is automatically cleared

### 4.4 Alarm Cannot Be Cleared

**Scenario**: After network checks, node configuration checks, and firewall checks, the alarm still persists

**Repair solution**:
1. Collect fault logs (refer to `3.5`)
2. Collect OmmServer, Controller, NodeAgent service logs
3. Log collection time range is 10 minutes before and after the alarm generation time
4. Contact operations personnel and send the fault log information

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Diagram

```

  |
  |  Determine active Manager node and standby Manager (Peer Manager) IP address
  |
  v

  |
  +--- Ping fails ---> Contact network administrator to check network link
  |                        |
  |                        v
  |               Repair network fault
  |                        |
  |                        v
  |               Check whether alarm is cleared
  |                        |
  |                        +--- Yes ---> End (alarm cleared)
  |                        |
  |                        +--- No ---> Check node name configuration
  |
  +--- Ping succeeds ---> Check hacom_local.xml node configuration (cat-hacom-local-xml)
                           |

                           |                        |
                           |                        v
                           |               Check whether alarm is automatically cleared
                           |                        |
                           |                        +--- Yes ---> End (alarm cleared)
                           |                        |
                           |                        +--- No ---> Check firewall port
                           |
                           +--- Configuration correct ---> Check heartbeat port status (lsof-port-20012)
                                                            |
                                                            +--- Port blocked ---> Check firewall status (iptables-list)
                                                            |                        |
                                                            |                        v
                                                            |               Handle firewall (iptables -P INPUT ACCEPT && iptables -F)
                                                            |                        |
                                                            |                        v
                                                            |               Check whether alarm is cleared
                                                            |                        |
                                                            |                        +--- Yes ---> End (alarm cleared)

                                                            |
                                                            +--- Port normal ---> Collect fault logs
  |
  v
Collect fault logs
  |
  |  Collect OmmServer, Controller, NodeAgent service logs
  |  Log time range: 10 minutes before and after alarm generation time
  |

  |

```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis conclusion | Recommended action |
|----------|----------|
| Active/standby Manager node link abnormality | Repair network link fault |
| Node name configuration error | Modify active/standby node configuration in hacom_local.xml |
| Firewall blocking heartbeat port | Clear firewall rules or allow port 20012 |
| Alarm still persists after processing | Collect fault logs, contact operations personnel |
