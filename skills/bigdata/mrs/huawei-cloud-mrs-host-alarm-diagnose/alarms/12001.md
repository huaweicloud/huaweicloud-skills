# `Audit Log Dump Failure` (12001) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Query dump configuration and status (MRS Manager REST API)
  │
  ├─ enableDump=OFF → Abnormal: switch off should not trigger this alarm, investigate whether it is a false alarm
  │
  └─ enableDump=ON → Step 2

Step 2: Query audit log accumulation (MRS Manager REST API)
  │
  ├─ totalCount < 100000 → Logs not accumulated, may be a historical transient failure alarm not cleared
  │
  └─ totalCount >= 100000 → Logs accumulated, dump not effective → Step 3

Step 3: Collect ACS logs + disk + network (lakewatch tool, can run in parallel)
  │
  ├─ No dump-related errors in ACS logs → Step 4 (dump may never have triggered or configuration issue)
  │
  └─ Dump-related errors in ACS logs → Match root cause by error keyword
       │
       ├─ write file failed → Root cause: dump directory disk full / insufficient permission
       ├─ exec commond failed → Root cause: database connection exception or script execution failure
       ├─ Sftp server public key is illegal → Root cause: SFTP public key mismatch
       ├─ connectFTP path exception → Root cause: SFTP target path invalid
       ├─ connectFTP exception + JSchException → Step 5 (refine SFTP connection/authentication issue)
       └─ SFTP transfer file.*failed → Root cause: SFTP upload failed (remote disk full or network interrupted)

Step 4: Dump never triggered or configuration issue
  │
  ├─ mode=0 (by count) and totalCount < 100000 → Dump condition not met, wait until accumulation reaches threshold to auto-trigger
  ├─ mode=1 (by time) and date not reached → Scheduled dump time not reached
  └─ Otherwise → Check whether the ACS process is running normally (manual path)

Step 5: Refine SFTP connection/authentication issue
  │
  ├─ Network unreachable (cannot ping ftpIp) → Root cause: SFTP server unreachable
  ├─ Network reachable but JSchException → Root cause: SFTP authentication failure (wrong username/password/public key) or port unreachable
  └─ Manual verification needed → Manual path (use sftp command to test authentication, port test)

> After locating the root cause, jump directly to "Common Root Causes and Repair Suggestions"; no need to continue subsequent steps.
```

## Diagnosis Steps

### Step 1: Query dump configuration and status

```bash
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/audits/config'
```

**Return field description** (`APIAuditConfig`, no nested wrapper, returned directly):

| Field | Type | Meaning | Key value |
|------|------|------|--------|
| `enableDump` | String | Dump switch | ON=enabled, OFF=disabled |
| `ftpIp` | String | SFTP server IP | — |
| `ipMode` | String | IP protocol | IPv4/IPv6 |
| `ftpPort` | String | SFTP port | default 22 |
| `ftpUserName` | String | SFTP username | — |
| `ftpPassword` | String | SFTP password | **always empty when queried** |
| `ftpServicePublicKey` | String | SFTP server public key | — |
| `savePath` | String | SFTP target path | — |
| `mode` | int | Dump mode | 0=by record count (full at 100000 records), 1=by time |
| `date` | String | Scheduled dump trigger time | ISO8601 format |

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| `enableDump=OFF` | Abnormal: switch off will not trigger this alarm | Investigate whether it is a false alarm |
| `enableDump=ON` | Dump enabled | Step 2 |

---

### Step 2: Query audit log accumulation

```bash
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/audits?limit=1'
```

> Returns `APIAuditItems`, where `totalCount` (int) is the total number of audit logs.
> The default value of oplogMax is 100000 (100 thousand records), used as the accumulation threshold.

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| `totalCount < 100000` | Logs not accumulated, may be a historical transient failure alarm not cleared | Step 4 |
| `totalCount >= 100000` | Logs accumulated, dump not effective | Step 3 |

---

### Step 3: Collect ACS logs + disk + network

> The following three collections can run in parallel to speed up diagnosis.

#### 3.1 Collect ACS logs (single collection, covers both CSV and SFTP stages)

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=30' \
  -p 'log_directory=/var/log/Bigdata/controller/acs' \
  -p 'log_file_name=acs*.log' \
  -p 'keywords=["exec commond failed","write file failed","ProcessDepositeTask","connectFTP","SFTP transfer file","public key is illegal","path exception","JSchException"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^\[([0-9]{4})-([0-9]{2})-([0-9]{2})T([0-9]{2}):([0-9]{2}):([0-9]{2})||ymdHMS'
```

**Log keyword analysis** (match by priority from high to low, stop on first hit):

| Log keyword | Failure stage | Conclusion | Next step |
|-----------|---------|------|--------|
| `write file failed` | CSV write | **Root cause located**: dump directory disk full or insufficient permission → Root cause 1 | — |
| `exec commond failed` | Script execution | **Root cause located**: database connection exception or dump script missing → Root cause 2/3 | — |
| `Sftp server public key is illegal` | SFTP public key | **Root cause located**: SFTP public key mismatch → Root cause 5 | — |
| `connectFTP path exception` + `SftpException` | SFTP path | **Root cause located**: SFTP target path invalid → Root cause 6 | — |
| `connectFTP exception` + `JSchException` | SFTP connection | SFTP connection failure (network/authentication/port) → Root cause 4 | Step 5 |
| `SFTP transfer file.*failed` | SFTP upload | SFTP upload failure → Root cause 4/6 | Step 5 |
| None of the above keywords | — | No explicit dump error in logs | Step 4 |

#### 3.2 Query disk space

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

> If disk usage is 100%, directly locate root cause 1 (dump directory disk full).

#### 3.3 Test SFTP server network connectivity

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=network-connectivity-test' \
  -p 'env={"TARGET_IP":"<ftpip>"}' \
  -p 'node_name=<node_name>'
```

> `ftpip` is obtained from the `ftpIp` returned in Step 1. Currently only IP reachability (ping) is tested; SFTP port and authentication need further judgment in Step 5 or manual verification.

**Analysis**:

| Network test result | Conclusion |
|-------------|------|
| ping unreachable | **Root cause located**: SFTP server unreachable → Root cause 4 |
| ping reachable | Network reachable, issue may be SFTP port/authentication/path → judge together with Step 3.1 logs |

---

### Step 4: Dump never triggered or configuration issue

> When there are no dump-related errors in the ACS logs of Step 3, check the dump trigger conditions.

| Condition | Analysis |
|------|------|
| `mode=0` (by count) and `totalCount < 100000` | Dump condition not met, log volume below threshold, dump will not trigger. Wait until logs accumulate to threshold to auto-trigger |
| `mode=1` (by time) and `date` not reached | Scheduled dump time not reached |
| None of the above but no dump records | ACS process may be abnormal, need to check ACS process status on the alarm node (manual path) |

---

### Step 5: Refine SFTP connection/authentication issue

> When Step 3.1 logs indicate SFTP connection failure (`connectFTP exception` + `JSchException`), refine judgment together with the Step 3.3 network test result.

**Comprehensive judgment**:

| Network test result | ACS log keyword | Conclusion | Next step |
|-------------|-------------|------|--------|
| ping unreachable | `connectFTP exception` | **Root cause located**: SFTP server unreachable → Root cause 4 | — |
| ping reachable | `connectFTP exception` + `JSchException` | SFTP port unreachable or authentication failure | Manual path: port test + sftp authentication test |
| ping reachable | `SFTP transfer file.*failed` | SFTP reachable but upload failed (remote disk full or path without write permission) | Manual path: check remote disk and path permission |

> **Note**: The current LakeWatch agent does not support the PUT method, so it cannot use the return codes (6400001/6400002/6400003) of `PUT /api/v2/audits/config` to automatically determine the specific SFTP failure cause. If the agent supports PUT in the future, the return codes can directly pinpoint the issue:
> - `6400001` → SFTP connection failure (network/port unreachable)
> - `6400002` → SFTP path does not exist
> - `6400003` → SFTP authentication failure (wrong username/password/public key)

## Manual Path

> When the LakeWatch tool or MRS Manager REST API is unavailable, use the following commands to execute directly on the **alarm node (OMS master node)**.

### Manual Step 1: Query dump configuration and status

```bash
gsql -d omm -p $OMS_GAUSS_PORT -U omm -c "SELECT ftpswitch, ftpflag, ftpdate, svreserved1, ftpip, ftpport, savepath, ftpusername FROM tbl_iam_oplog_saving_condition"
```

| Field | Meaning | Key value |
|------|------|--------|
| `ftpswitch` | Dump switch | ON=enabled, OFF=disabled |
| `ftpflag` | Dump mode | 0=by count, 1=by time |
| `ftpdate` | Scheduled dump date threshold | integer timestamp |
| `svreserved1` | Dump status | 0=success, 1=failure |
| `ftpip` | SFTP server IP | — |
| `ftpport` | SFTP port | — |
| `savepath` | SFTP target path | — |
| `ftpusername` | SFTP username | — |

### Manual Step 2: Query log count and threshold

```bash
# Query audit log count
gsql -d omm -p $OMS_GAUSS_PORT -U omm -c "SELECT count(*) FROM tbl_operate_log"

# Query dump threshold
cat $OMS_DATA_PATH/iam/config.properties | grep oplogMax
```

### Manual Step 3: Check CSV files and disk

```bash
# Check CSV directory
ls -lt ${GAUSSDATA}/../dumpData/iam/operatelog/

# Check disk space
df -h
```

### Manual Step 4: Check database connection and dump script

```bash
# Verify database connection
gsql -U omm -d omm -p $OMS_GAUSS_PORT -c "SELECT 1"

# Check dump scripts
ls -la $OMS_RUN_PATH/workspace0/bin/createCSV.sh
ls -la $OMS_RUN_PATH/workspace0/bin/createByBlogTimeCSV.sh
```

### Manual Step 5: Verify SFTP connectivity

```bash
# Test network
ping -c 3 <ftpip>

# Test SFTP port connectivity (3-second timeout)
python3 -c "import socket; s=socket.socket(); s.settimeout(3); s.connect(('<ftpip>',<ftpport>)); print('PORT OPEN'); s.close()" 2>&1 || echo "PORT CLOSED/TIMEOUT"

# Manual SFTP connection test (interactive, password required)
sftp -P <ftpport> <ftpusername>@<ftpip>
```

### Manual Step 6: Verify SFTP via MRS Manager UI

> Reconfigure the SFTP dump parameters in the MRS Manager UI (the same as current config is fine); after submission, the UI will display the specific error:
> - Connection failure → network or port unreachable
> - Authentication failure → wrong username/password/public key
> - Path does not exist → target path invalid

## Common Root Causes and Repair Suggestions

### 1. Dump directory issue

**Symptom**: ACS logs contain `write file failed`; disk usage 100%; CSV directory does not exist or has insufficient permission

**Repair suggestions**:
- Check and set the `$GAUSSDATA` environment variable
- Create directory and grant permission: `mkdir -p ${GAUSSDATA}/../dumpData/iam/operatelog/ && chmod 755 ${GAUSSDATA}/../dumpData/iam/operatelog/`
- Clean up disk space (refer to disk-space output)

### 2. Database connection exception

**Symptom**: ACS logs contain `exec commond failed`; gsql connection failed

**Repair suggestions**:
- Check whether GaussDB is running normally: `gsql -U omm -d omm -p $OMS_GAUSS_PORT -c "SELECT 1"`
- Check whether the `$OMS_GAUSS_PORT` environment variable is correct
- Investigate whether GaussDB has long transaction blocking: `SELECT * FROM pg_locks WHERE NOT granted`
- Restart GaussDB if necessary

### 3. Dump script missing

**Symptom**: ACS logs contain `exec commond failed`; `createCSV.sh` or `createByBlogTimeCSV.sh` does not exist or has no execute permission

**Repair suggestions**:
- Check whether the scripts exist under `$OMS_RUN_PATH/workspace0/bin/`
- Grant execute permission: `chmod +x $OMS_RUN_PATH/workspace0/bin/createCSV.sh $OMS_RUN_PATH/workspace0/bin/createByBlogTimeCSV.sh`
- If scripts are lost, copy from another normal node

### 4. SFTP connection failure

**Symptom**: ACS logs contain `connectFTP exception`, `JSchException`; network unreachable

**Repair suggestions**:
- Check whether the SFTP server IP/port is correct
- Check whether the firewall allows the SFTP port
- Test port connectivity on the alarm node: `python3 -c "import socket; s=socket.socket(); s.settimeout(3); s.connect(('<ftpip>',<ftpport>)); s.close()" 2>&1 || echo "PORT CLOSED"`
- Verify whether username/password is correct (manual `sftp` connection test or reconfigure in MRS Manager UI to trigger validation)
- Check whether the SFTP server disk is full

### 5. SFTP public key mismatch

**Symptom**: ACS logs contain `Sftp server public key is illegal`

**Repair suggestions**:
- The SFTP server may have changed its certificate; update the public key in the dump configuration
- Reconfigure SFTP dump parameters in the MRS Manager UI

### 6. SFTP target path invalid

**Symptom**: ACS logs contain `connectFTP path exception`

**Repair suggestions**:
- Confirm `savePath` exists on the SFTP server and has write permission
- Create the target directory on the SFTP server and grant permission
