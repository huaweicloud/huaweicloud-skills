# `OLdap Resource Abnormal` (12004) Alarm Diagnosis Skill

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **OLdap Resource Abnormal (12004)** alarm. The system detects the Ldap resource status at 60-second intervals. When the Ldap resource in Manager is detected as abnormal for 6 consecutive monitoring cycles, the system generates this alarm. When the Ldap resource in Manager recovers and the alarm handling is complete, the alarm is cleared. In MRS 3.3.1 and later versions, the alarm name was changed from "Oldap Resource Abnormal" to "Manager Oldap Resource Abnormal".

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12004 |
| Alarm Name | OLdap Resource Abnormal |
| Alarm Severity | Important |
| Alarm Type | Resource Abnormal Alarm |
| Auto-cleared | Yes |
| System Impact | May cause Manager active/standby switchover. Manager and component WebUI authentication services become unavailable, unable to provide security authentication and user management functions for web upper-layer services, which may prevent login to Manager and component WebUI |

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information and determine the active/standby OMS node names and IP addresses.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Check OMS Active/Standby Resource Status (View OLdap Resource Status)

Execute the following command to view the active/standby resource status of OMS nodes and determine whether the OLdap resource is normal. In the command output, check the "ResHAStatus" column of the "oldap" row:

- Single-node mode: OLdap resource should be in "Normal" status
- Dual-node mode: OLdap resource should be "Active_normal" on the active node and "Standby_normal" on the standby node
- If "ResHAStatus" is not one of the above normal states, the OLdap resource is abnormal

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred (the node where Manager is located), obtained from the alarm information

### 2.3 Check HA Resource Status

Execute the following command to view the current HA-managed resource status and confirm whether the OLdap resource is in a normal state.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

Example command output:
```
NodeName        ResName     ResStatus     ResHAStatus     ResType
xxx-oms-node1   oldap       Normal        Active_normal   Single_active
xxx-oms-node2   oldap       Stopped       Normal          Single_active
```

**Status description**:
- Single-node mode: OLdap resource is in Normal status
- Dual-node mode: OLdap resource is Normal on the active node and Stopped on the standby node
- If the OLdap resource status is abnormal (e.g., not Normal or not Stopped), the resource has failed

### 2.4 Check slapd Process Status

Execute the following command to check whether the slapd process is running normally. The configuration file is located under the "${BIGDATA_HOME}/om-server/om/" path. The LdapServer resource process should be running normally, with a slapd process listening on port 21750.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"slapd"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

How to determine:
- If the command output contains slapd process information and the process is listening on port 21750, the process is normal
- If the command output does not contain slapd process information, or the process port is not 21750, the process is abnormal

### 2.5 Check OLdap Listening Port Status

Execute the following command to check whether the OLdap service port (21750) is listening normally.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=port-check' \
  -p 'env={"PORT":"21750"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

How to determine:
- If port 21750 is listening normally, the OLdap service port is normal
- If port 21750 is not listening, the OLdap service has not started properly

### 2.6 Check Alarm Node System Resources

Execute the following command to check the system resources of the alarm node and determine whether insufficient system resources are causing the OLdap process to be abnormal.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=system-load' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.7 View OLdap HA Script Logs

Execute the following command to view the result logs of HA detecting the OLdap resource and analyze the direct cause of the OLdap resource abnormality.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/ha/scriptlog' \
  -p 'log_file_name=oldap*' \
  -p 'keywords=["ERROR","exception","Failed","Cannot find","Permission denied"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm occurrence time
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.8 View OmmServer Logs

Execute the following command to view OmmServer logs and analyze whether there is any abnormal information related to OLdap.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/server' \
  -p 'log_file_name=*.log*' \
  -p 'keywords=["ERROR","exception","ldap","slapd","OLdap"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm occurrence time
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., commands that require manual login to the node).

### 3.1 Log in to the Manager Node as omm User

Log in to the Manager node host in the cluster as the omm user and execute the following command to view the current Manager dual-node information:

```bash
sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh
```

Check the "ResHAStatus" column of the "oldap" row in the command output:
- If it is "Normal" (single-node mode) or "Active_normal"/"Standby_normal" (dual-node mode), the OLdap resource status is normal; proceed to step 3.3
- If it is not one of the above normal states, the OLdap resource is abnormal; proceed to step 3.2

### 3.2 Restart OLdap Process

When the OLdap resource is abnormal, log in to the alarm node as the omm user and execute the following command to terminate the abnormal ldap process. After waiting 20 seconds, HA will automatically start the OLdap process:

```bash
# Find the ldap process PID
ps -ef | grep slapd | grep -v grep

# Terminate the ldap process (<ldap_pid> is the process PID obtained in the previous step)
kill -2 <ldap_pid>
```

After waiting 20 seconds, re-execute `sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh` and observe whether the current OLdap resource status has recovered:
- If the OLdap resource status has recovered, the operation is complete
- If the OLdap resource status has not recovered, proceed to step 3.3

### 3.3 View slapd Process Details

Log in to the alarm node as the omm user and execute the following command to confirm whether the slapd process is normal and listening on port 21750:

```bash
ps -ef | grep slapd
```

How to determine:
- If a slapd process with its configuration file located under the "${BIGDATA_HOME}/om-server/om/" path exists and is listening on port 21750, the process is normal
- If the slapd process does not exist or the port is not 21750, the process is abnormal; proceed to step 3.2 to attempt a restart

### 3.4 Collect Fault Information

When the above steps do not resolve the issue, fault log information needs to be collected.

1. In the MRS cluster Manager UI, select "Maintenance > Logs > Download"
2. In "Services", select "OmsLdapServer" and "OmmServer", then click "OK"
3. In the upper right corner, set the log collection "Start Time" and "End Time" to 1 hour before and after the alarm generation time, then click "Download"
4. Contact operations personnel and send the collected fault log information

## 4. Common Fault Repair Solutions

### 4.1 LdapServer Process Failure

**Symptoms**:
- oldap's "ResHAStatus" in status-oms.sh output is not Normal/Active_normal/Standby_normal
- slapd process does not exist or terminated abnormally
- Port 21750 is not listening

**Repair solution**:
1. Log in to the Manager node as the omm user
2. Execute `kill -2 <ldap_pid>` to terminate the abnormal ldap process; after waiting 20 seconds, HA will automatically restart the OLdap process
3. Re-execute `status-oms.sh` to check whether the OLdap resource status has recovered
4. If recovered, wait for the next system detection cycle and check whether the alarm is automatically cleared
5. If not recovered, collect fault logs and contact operations personnel

### 4.2 System Resource Insufficiency Causing OLdap Abnormality

**Symptoms**:
- System load is too high or memory usage is near 100%
- Insufficient disk space prevents OLdap from running normally
- slapd process was killed by the system due to resource insufficiency (OOM)

**Repair solution**:
1. Check system resources (CPU load, memory usage, disk space)
2. Clean up unnecessary log files or temporary files to free disk space
3. If memory is insufficient, check whether other processes are consuming excessive memory and adjust process memory parameters if necessary
4. After resources are recovered, execute `kill -2 <ldap_pid>` to restart the OLdap process
5. Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 4.3 OLdap HA Resource Not Recovered

**Symptoms**:
- After executing kill -2 and waiting 20 seconds, HA did not automatically start the OLdap process
- oldap's "ResHAStatus" in status-oms.sh output is still abnormal
- Error messages exist in HA script logs

**Repair solution**:
1. View HA script logs (`/var/log/Bigdata/omm/oms/ha/scriptlog/oldap*`) to analyze the cause of resource startup failure
2. Check for file permission issues (`Permission denied`) or missing files (`Cannot find`)
3. If it is a permission issue, fix file permissions: `chown omm:omm <file_path>` and `chmod 755 <directory>`
4. If it is a configuration file issue, check the LdapServer configuration under the `${BIGDATA_HOME}/om-server/om/` path
5. After processing, re-execute kill -2 to restart the OLdap process
6. If still not recovered, collect fault logs and contact operations personnel

### 4.4 Alarm Cannot Be Cleared

**Scenario**: After OLdap process restart, system resource checks, and HA log investigation, the alarm still persists

**Repair solution**:
1. Collect fault logs (OmsLdapServer and OmmServer service logs)
2. Log collection time range is 1 hour before and after the alarm generation time
3. Contact operations personnel and send the collected fault log information

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Diagram

```
Start
  |
  v
Obtain Manager node hostname from alarm information
  |
  v
Obtain cluster OMS active/standby node information (query-management-node-info)
  |
  v
Check OMS active/standby resource status (status-oms), view oldap's ResHAStatus
  |
  +--- ResHAStatus abnormal ---> Check slapd process status (process-basic-info)
  |                                |
  |                                +--- slapd process exists ---> Restart OLdap process (kill -2)
  |                                |                                 |
  |                                |                                 v
  |                                |                         Wait 20s, check OLdap resource status
  |                                |                                 |
  |                                |                                 +--- Resource recovered ---> Check whether alarm is cleared
  |                                |                                 |
  |                                |                                 +--- Resource not recovered ---> Check system resources
  |                                |
  |                                +--- slapd process does not exist ---> Check system resources
  |                                                                   |
  |                                                                   v
  |                                                          Check OLdap listening port (port-check 21750)
  |                                                                   |
  |                                                                   +--- Port normal ---> Check HA script logs
  |                                                                   |
  |                                                                   +--- Port abnormal ---> Restart OLdap process (kill -2)
  |
  +--- ResHAStatus normal ---> Check OLdap listening port (port-check 21750)
                                |
                                +--- Port abnormal ---> Restart OLdap process (kill -2)
                                |                         |
                                |                         v
                                |                 Wait 20s, check OLdap resource status
                                |                         |
                                |                         +--- Resource recovered ---> Check whether alarm is cleared
                                |                         |
                                |                         +--- Resource not recovered ---> Check HA script logs
                                |
                                +--- Port normal ---> Check HA script logs
  |
  v
Check system resources (system-load, memory-usage, disk-space)
  |
  +--- Insufficient resources ---> Clean up resources/scale up ---> Restart OLdap process ---> Check whether alarm is cleared
  |                                                                        |
  |                                                                        +--- Alarm cleared ---> End
  |                                                                        |
  |                                                                        +--- Alarm not cleared ---> Check HA script logs
  |
  +--- Resources normal ---> Check HA script logs (oldap*)
                               |
                               +--- Errors found ---> Repair issue based on logs ---> Restart OLdap process ---> Check whether alarm is cleared
                               |                                                                                 |
                               |                                                                                 +--- Alarm cleared ---> End
                               |                                                                                 |
                               |                                                                                 +--- Alarm not cleared ---> Collect fault logs
                               |
                               +--- No obvious errors ---> Collect fault logs
  |
  v
Collect fault logs (OmsLdapServer and OmmServer, 1 hour before and after alarm)
  |
  v
Contact operations personnel and send fault log information
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis conclusion | Recommended action |
|----------|----------|
| LdapServer process failure | Restart OLdap process (kill -2), wait for alarm to be automatically cleared |
| System resource insufficiency causing OLdap abnormality | Clean up system resources and restart OLdap process, wait for alarm to be automatically cleared |
| OLdap HA resource not recovered | Check HA script logs, repair issue, and restart OLdap process, wait for alarm to be automatically cleared |
| Alarm still persists after processing | Collect OmsLdapServer and OmmServer logs, contact operations personnel |
