# Failed to Report Metrics to CES (12172) Alarm Diagnosis

## 1. Diagnosis Introduction

This document covers the diagnosis and handling of the **Failed to Report Metrics to CES (12172)** alarm. After MRS cluster metric sharing is enabled, the controller module periodically collects cluster metric information and reports it to the CES service. When the controller module fails to report metrics to the CES service, this alarm is generated. The alarm is automatically cleared when metric reporting returns to normal.

Alarm basic information:

| Item | Content |
|------|---------|
| Alarm ID | 12172 |
| Alarm Name | Failed to Report Metrics to CES |
| Alarm Severity | Important |
| Alarm Type | Service Fault Alarm |
| Auto-clearable | Yes |
| System Impact | Monitoring metric reporting to CES fails; MRS cloud service monitoring metrics cannot be viewed in CES |

## 2. Executable Operations

This section provides operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Obtain the cluster OMS active/standby node information to determine whether the alarm node is the OMS active node, and for subsequent login to the active management node to perform controller restart operations.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameters:
- `<cluster_id>`: Cluster ID

### 2.2 Obtain Controller Process Status

Execute the following command to obtain the running status of the Controller process on the alarm node and determine whether the controller process is running normally.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"controller"}' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.3 Collect Controller Logs

Execute the following command to collect the Controller module runtime log for analyzing the specific cause of the CES metric reporting failure (permission exception, network issue, or internal service error).

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/controller' \
  -p 'log_file_name=controller.log*' \
  -p 'keywords=["send metrics","CES","Permission exception","error code","Too many request"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm generation time
- `<node_name>`: Name of the node where the alarm occurred (OMS active node), obtained from alarm information or the active/standby node information from `2.1`

### 2.4 Obtain System Resource Usage

Execute the following command to obtain the system resource usage of the alarm node and determine whether a resource bottleneck is causing the controller module to fail in reporting metrics.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=system-load' \
  -p 'node_name=<node_name>'
```

Parameters:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the automation tool during the alarm analysis process (i.e., commands that require manual login to the node).

### 3.1 View Alarm Additional Information

View the alarm additional information on the FusionInsight Manager interface to determine the specific cause of the CES metric reporting failure:

1. Log in to the FusionInsight Manager page
2. Navigate to "O&M > Alarms > Alarms"
3. Find this alarm in the alarm list and expand the details
4. View the error description in the alarm additional information

Decision criteria:
- If the additional information shows "Call CES to send metrics fail. Permission exception", the resource tenant token has expired and the controller needs to be restarted to obtain a new token. Proceed to `3.2 Restart controller`
- If the additional information shows "Call CES to send metrics fail. Request CES error code xxx" or "CES internal error code xxx", a functional service exception exists. Proceed to `3.3 Collect Fault Information`
- If the additional information shows "Call CES to send metrics fail. Too many request", the service request has triggered rate limiting. Proceed to `3.3 Collect Fault Information`

### 3.2 Restart Controller

When the alarm additional information shows "Permission exception", the controller needs to be restarted to obtain a new token:

1. Log in to FusionInsight Manager, click the task center icon in the top-right corner, and confirm that no tasks are running in the task management center
2. Log in to the cluster active management node as the root user (the active management node can be obtained via `2.1 Obtain Cluster OMS Active/Standby Node Information`)
3. Execute the following command to switch to the omm user:
   ```bash
   su - omm
   ```
4. Execute the following command to restart the controller:
   ```bash
   sh ${BIGDATA_HOME}/om-server/om/sbin/restart-controller.sh
   ```
5. After restart is complete, wait five minutes and observe whether the alarm has recovered
   - If the alarm has recovered, the operation is complete
   - If the alarm has not recovered, proceed to `3.3 Collect Fault Information`

### 3.3 Collect Fault Information

When the above handling steps cannot clear the alarm, collect fault log information:

1. On the FusionInsight Manager interface, navigate to "O&M > Logs > Download"
2. Under "Service", select "OMS > Controller", select the active node under "Host", and click "OK"
3. Set the "Start Time" and "End Time" for log collection to 10 minutes before and after the alarm generation time respectively, then click "Download"
4. Contact O&M personnel and send the collected fault log information

## 4. Common Fault Handling Solutions

### 4.1 Resource Tenant Token Expired

**Symptoms**:
- Alarm additional information shows "Call CES to send metrics fail. Permission exception"
- Controller process is running normally but cannot report metrics to CES

**Solution**:
1. Obtain the cluster OMS active/standby node information via `2.1` to confirm the active management node
2. Confirm that no tasks are running in the task management center
3. Log in to the active management node as the root user, switch to the omm user
4. Execute `sh ${BIGDATA_HOME}/om-server/om/sbin/restart-controller.sh` to restart the controller
5. Wait five minutes and observe whether the alarm auto-clears

### 4.2 CES Service Exception

**Symptoms**:
- Alarm additional information shows "Call CES to send metrics fail. Request CES error code xxx"
- Alarm additional information shows "CES internal error code xxx"

**Solution**:
1. Collect Controller logs via `2.3` and analyze the specific error code returned by CES
2. Determine whether the CES server has an exception based on the error code
3. Contact O&M personnel to confirm the CES server status
4. Wait for CES service recovery, then observe whether the alarm auto-clears
5. If not cleared, collect fault information via `3.3` and contact O&M personnel

### 4.3 Request Triggered Rate Limiting

**Symptoms**:
- Alarm additional information shows "Call CES to send metrics fail. Too many request"
- Controller process is running normally but reporting requests are rejected by CES rate limiting

**Solution**:
1. Check the Controller process status via `2.2` to confirm whether the process is running normally
2. Obtain system resource usage via `2.4` to confirm whether the node has a resource bottleneck
3. Wait for a period of time and observe whether the alarm auto-recovers (rate limiting is typically a temporary restriction)
4. If rate limiting persists, collect fault information via `3.3` and contact O&M personnel

### 4.4 Controller Process Exception

**Symptoms**:
- Controller process not running or abnormal, as detected via `2.2`
- Controller logs contain exception errors

**Solution**:
1. Obtain the cluster OMS active/standby node information via `2.1` to confirm the active management node
2. Log in to the active management node as the root user, switch to the omm user
3. Execute `sh ${BIGDATA_HOME}/om-server/om/sbin/restart-controller.sh` to restart the controller
4. Wait five minutes and observe whether the alarm auto-clears
5. If not cleared, collect fault information via `3.3` and contact O&M personnel

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flowchart

```
Start
  │
  ▼
Obtain hostname and other locating information from alarm information
  │
  ▼
Obtain cluster OMS active/standby node information (confirm active management node)
  │
  ▼
Obtain Controller process status
  │
  ├─── Process abnormal ──→ Restart controller ──→ Wait 5 minutes ──→ Alarm cleared?
  │                                                        │
  │                                                        ├─── Yes ──→ Handling complete
  │                                                        │
  │                                                        └─── No ──→ Collect fault information
  │
  └─── Process normal ──→ View alarm additional information
                       │
                       ├─── "Permission exception" ──→ Restart controller
                       │                                  │
                       │                                  ▼
                       │                          Wait 5 minutes, alarm cleared?
                       │                                  │
                       │                                  ├─── Yes ──→ Handling complete
                       │                                  │
                       │                                  └─── No ──→ Collect fault information
                       │
                       ├─── "Request CES error code" or "CES internal error" ──→ Collect Controller logs
                       │                                                              │
                       │                                                              ▼
                       │                                                     Analyze CES error code, contact O&M
                       │
                       └─── "Too many request" ──→ Check system resource usage
                                                     │
                                                     ▼
                                            Wait and observe whether alarm recovers
                                                     │
                                                     ├─── Yes ──→ Handling complete
                                                     │
                                                     └─── No ──→ Collect fault information
  │
  ▼
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis Conclusion | Recommended Action |
|----------------------|---------------------|
| Resource tenant token expired | Restart controller to obtain a new token |
| CES service exception | Collect Controller logs, contact O&M personnel to confirm CES server status |
| Request triggered rate limiting | Wait for rate limiting to recover; if persistent, collect logs and contact O&M personnel |
| Controller process exception | Restart controller; if not recovered, collect fault logs and contact O&M personnel |
| Alarm persists after handling | Collect fault logs, contact O&M personnel |
