# System in Upgrade Observation Period Alarm Diagnosis

## 1. Diagnosis Introduction

This document mainly covers the diagnosis and handling of the **System in Upgrade Observation Period (12087)** alarm. The system checks at midnight daily whether the current system is in an upgrade observation period, and simultaneously checks whether the time since entering the upgrade observation period has exceeded the upgrade observation period time reserved for the customer (default is 10 days). When the system is in the upgrade observation period and the time since entering the upgrade observation period has exceeded the reserved upgrade observation period time, the system triggers this alarm. If the user performs a rollback or commit operation to exit the upgrade observation period, this alarm will be automatically cleared.

Alarm basic information:

| Item | Content |
|------|------|
| Alarm ID | 12087 |
| Alarm Name | System in upgrade observation period |
| Alarm Severity | Major |
| Alarm Type | System upgrade monitoring alarm |
| Auto-clearable | Yes |
| System Impact | During the upgrade observation period, adding or deleting operations on users, instances, roles, services, hosts, resource pools, and other entities that affect the management topology are prohibited |

## 2. Executable Operations

This section provides the related operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain cluster OMS active/standby node information, determine the primary management node, and use it for subsequent login to the primary management node for diagnostic operations.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Obtain OMS Key Directories

Execute the following command to obtain OMS key directory information, used to confirm OMS-related paths.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.3 Collect Controller Service Log

Execute the following command to collect Controller service logs for fault troubleshooting.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=30' \
  -p 'log_directory=/var/log/Bigdata/controller' \
  -p 'log_file_name=controller.log*' \
  -p 'keywords=["upgrade","UpdateTool","ERROR","WARN"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm trigger time
- `<node_name>`: OMS primary node name

## 3. Non-Executable Operations

This section provides the related operations that cannot be executed during the alarm analysis process (i.e., commands that need to be executed manually after logging into the node).

### 3.1 Check Whether the System Is in Upgrade Observation Period

Log in to the primary management node as the root user. The user password is customized by the user before installation. Please consult the system administrator. The active/standby status of the management node and corresponding IP addresses can be viewed in the FusionInsight Manager host management interface.

Execute the following command to switch to the omm user:

```bash
su - omm
```

Log in to the omm database:

```bash
gsql -U omm -W <omm_database_password> -p 20015
```

Parameter description:
- `<omm_database_password>`: omm database password, please consult the system administrator

Execute the following command to view cluster information:

```sql
select * from OM_CLUSTERS;
```

View the `upgradObservationPeriod isON` value in the query result:
- If it is `true`, the system is currently in the upgrade observation period. Please use the UpdateTool to commit this upgrade. Refer to the upgrade guide for the corresponding version for specific operations.
- If it is `false`, the system is currently not in the upgrade observation period. Proceed to `3.2 Collect Fault Information`.

### 3.2 Use UpdateTool to Commit the Upgrade

After confirming that the system is in the upgrade observation period, use the UpdateTool to commit the upgrade to exit the upgrade observation period.

Refer to the upgrade guide for the corresponding version for specific operations. Use the UpdateTool to perform an upgrade commit or rollback operation.

- **Upgrade commit**: Commits the current upgrade operation. The system exits the upgrade observation period and the alarm is automatically cleared.
- **Upgrade rollback**: Rolls back the current upgrade operation. The system exits the upgrade observation period and the alarm is automatically cleared.

After the operation is complete, wait until the next day's midnight to check whether the alarm is cleared.

### 3.3 Collect Fault Information

If the system is not in the upgrade observation period or the alarm is still not cleared after performing the upgrade commit, collect fault information.

1. In the FusionInsight Manager interface, select "O&M > Logs > Download".
2. In "Services", check "Controller" and click "OK".
3. In the upper right corner, set the log collection time range, generally 10 minutes before and after the alarm generation time, then click "Download".
4. Contact O&M personnel and send the collected fault log information.

## 4. Common Alarm Fault Handling Solutions

### 4.1 System Upgrade Timeout Without Commit

**Symptoms**:
- After system upgrade, the upgrade observation period time (default 10 days) has been exceeded without performing an upgrade commit
- The alarm parameter "Upgrade Observation Period (Days)" shows that the number of days since entering the upgrade observation period exceeds 10 days

**Handling solution**:
1. Log in to the primary management node, switch to omm user
2. Execute gsql query on OM_CLUSTERS table, confirm upgradObservationPeriod isON value is true
3. Use UpdateTool to perform upgrade commit operation, refer to the upgrade guide for the corresponding version
4. Wait until the next day's midnight to check whether the alarm is automatically cleared

### 4.2 System Not in Upgrade Observation Period but Alarm Not Cleared

**Symptoms**:
- Query of OM_CLUSTERS table shows upgradObservationPeriod isON value is false
- Alarm still exists

**Handling solution**:
1. Wait until the next day's midnight for the system scheduled check, check whether the alarm is cleared
2. If the alarm is still not cleared, collect Controller service logs
3. In the FusionInsight Manager interface, download Controller service logs with a time range of 10 minutes before and after the alarm generation time
4. Contact O&M personnel and send the collected fault log information

### 4.3 System Exception During Upgrade Observation Period

**Scenario**: During the upgrade observation period, adding or deleting operations on users, instances, roles, services, hosts, resource pools, and other entities that affect the management topology are prohibited, preventing normal O&M management.

**Handling solution**:
1. Confirm the system upgrade status, evaluate whether upgrade verification is complete
2. If upgrade verification passes, use UpdateTool to perform upgrade commit
3. If upgrade verification does not pass, use UpdateTool to perform upgrade rollback
4. After the system exits the upgrade observation period, normal O&M management operations are restored
5. Wait until the next day's midnight to check whether the alarm is automatically cleared

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Chart

```
Start
  |
  v
Obtain cluster ID and hostname from alarm information
  |
  v
Obtain cluster OMS active/standby node information, determine primary management node
  |
  v
Log in to primary management node, switch to omm user
  |
  v
Log in to omm database, query OM_CLUSTERS table
  |
  v
Check whether upgradObservationPeriod isON value is true
  |
  +--- Yes (true) ---> System is in upgrade observation period
  |                     |
  |                     v
  |              Use UpdateTool to commit upgrade
  |                     |
  |                     v
  |              Wait until next day's midnight, check whether alarm is cleared
  |                     |
  |                     +--- Alarm cleared ---> End
  |                     |
  |                     +--- Alarm not cleared ---> Collect Controller logs, contact O&M
  |
  +--- No (false) ---> System is not in upgrade observation period
                        |
                        v
                 Wait until next day's midnight, check whether alarm is cleared
                        |
                        +--- Alarm cleared ---> End
                        |
                        +--- Alarm not cleared ---> Collect Controller logs, contact O&M
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis Conclusion | Recommended Operation |
|----------|----------|
| System in upgrade observation period timeout without commit | Use UpdateTool to commit upgrade, exit upgrade observation period |
| System not in upgrade observation period but alarm not cleared | Wait for scheduled check, collect Controller logs and contact O&M |
| System exception during upgrade observation period affecting O&M | Use UpdateTool to commit or rollback upgrade, exit observation period |
| Alarm still occurs after handling | Collect fault logs, contact O&M personnel |

## 6. Notes on 12087 Alarm Diagnosis

Based on `2. Executable Operations` and `3. Non-Executable Operations` in the 12087 alarm diagnosis process, combined with `5. Alarm Diagnosis Flow`, generate the alarm troubleshooting method and common error handling solutions for the alarm node. The user should confirm the alarm cause based on the provided information.

**Notes**:
- During the upgrade observation period, adding or deleting operations on users, instances, roles, services, hosts, resource pools, and other entities that affect the management topology are prohibited.
- The default upgrade observation period is 10 days, which can be adjusted through cluster configuration.
- Before performing upgrade commit or rollback operations, confirm the upgrade status and refer to the upgrade guide for the corresponding version.
- The alarm is automatically cleared after the system exits the upgrade observation period, no manual clearing is required.
- If the system is not in the upgrade observation period but the alarm still exists, wait until the next day's midnight for the system scheduled check to confirm.
