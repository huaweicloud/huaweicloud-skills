# `Manager Active/Standby Data Sync Abnormal` (12011) Alarm Diagnosis Skill

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **Manager Active/Standby Data Sync Abnormal (12011)** alarm. The system checks the Manager active/standby node data synchronization status at 60-second intervals. When the standby Manager cannot synchronize files with the active Manager, this alarm is generated. When the standby Manager synchronizes files normally with the active Manager, the alarm is cleared.

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12011 |
| Alarm Name | Manager Active/Standby Data Sync Abnormal |
| Alarm Severity | Critical |
| Alarm Type | Active/Standby Sync Monitoring |
| Auto-cleared | Yes |
| System Impact | Standby Manager configuration files are not updated; configuration files with sync abnormalities may be lost during active/standby switchover, and Manager and some components may not run normally |

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Check Network Connectivity Between Active and Standby OMS Nodes

Execute the following command to check whether the active OMS node can ping the standby OMS node.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=network-connectivity-test' \
  -p 'env={"TARGET_IP":"<standby_oms_ip>"}' \
  -p 'node_name=<active_oms_node>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<standby_oms_ip>`: Standby OMS node IP address, obtained from alarm location information
- `<active_oms_node>`: Active OMS node name

### 2.3 Check LocalBackup Directory Disk Space

Execute the following command to check whether the disk space of the partition where the /srv/BigData/LocalBackup directory is located is full.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<standby_oms_node>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<standby_oms_node>`: Standby OMS node name (sync abnormalities are typically on the standby node)

### 2.4 Obtain OMS Key Directories

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<standby_oms_node>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<standby_oms_node>`: Standby OMS node name

### 2.5 Collect HA Runtime Logs

Execute the following command to collect HA runtime logs from the standby OMS node and search for sync abnormality keywords.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=30' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/ha/runlog' \
  -p 'log_file_name=ha.log*' \
  -p 'keywords=["sync","rsync","Permission denied","No space","error","fail","standby","active"]' \
  -p 'log_type=local' \
  -p 'node_name=<standby_oms_node>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm trigger time
- `<standby_oms_node>`: Standby OMS node name

### 2.6 Collect Controller Logs

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=30' \
  -p 'log_directory=/var/log/Bigdata/controller' \
  -p 'log_file_name=controller.log*' \
  -p 'keywords=["ERROR","exception","sync","rsync","standby","backup"]' \
  -p 'log_type=local' \
  -p 'node_name=<standby_oms_node>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm trigger time
- `<standby_oms_node>`: Standby OMS node name

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., commands that require manual login to the Manager UI or node).

### 3.1 Check LocalBackup Directory Disk Space

Log in to the standby OMS node as the root user and execute the following command to check whether the storage space of the /srv/BigData/LocalBackup directory is full:

```bash
df -hl /srv/BigData/LocalBackup
```

If the remaining space is insufficient, clean up unnecessary backup files:

```bash
# View backup directory
ls -lt /srv/BigData/LocalBackup/

# Clean up old backup directories
rm -rf /srv/BigData/LocalBackup/<old_backup_directory_path>
```

- `<old_backup_directory_path>`: The backup directory to be cleaned, e.g., `/srv/BigData/LocalBackup/0/default-oms_20191211143443`

### 3.2 Check Whether Sync Files Exist and Their Permissions

Log in to the standby OMS node as the root user and execute the following command to find whether sync files exist:

```bash
find /srv/BigData/ -name "sed*"
find /opt -name "sed*"
```

If the command returns no results, the sync files do not exist.

If sync files are found, view the file information and permissions:

```bash
ll <sync_file_path>
```

- If the file size is 0 and all permission columns are "-", it is a junk file; execute `rm -rf <file_path>` to delete it
- If the file size is not 0, check the HA runtime logs to investigate the specific cause

### 3.3 View HA Runtime Logs

Log in to the standby OMS node as the root user and navigate to the HA runtime log directory:

```bash
cd /var/log/Bigdata/omm/oms/ha/runlog/
```

Decompress and view the log files for the alarm time period:

```bash
gunzip ha.log.<date_time>.gz
vi ha.log.<date_time>
```

Check for error messages around the alarm time. For example, "Permission denied" indicates insufficient directory permissions; the corresponding directory permissions need to be modified to match those of a normal node.

### 3.4 Modify Maximum Backup Count

In the FusionInsight Manager UI, select "Maintenance > Backup & Restore > Backup Management", click "Configure" in the "Operation" column next to the backup task to be operated, and modify the "Maximum Backup Count" to reduce the number of backup file sets.

### 3.5 Collect Fault Information

In the FusionInsight Manager UI, select "Maintenance > Logs > Download", and in "Services", select the following node information:
- OmmServer
- Controller
- NodeAgent

Set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm generation time, then click "Download". Contact operations personnel and send the collected fault log information.

## 4. Common Fault Repair Solutions

### 4.1 Active/Standby Node Link Interruption

**Symptoms**:
- Active OMS node cannot ping the standby OMS node
- Connection timeout or unreachable errors appear in HA logs

**Repair solution**:
1. Check the network link between active and standby OMS nodes
2. Contact the network administrator to troubleshoot the network fault
3. After the network recovers, wait approximately 1 minute and check whether the alarm is cleared

### 4.2 LocalBackup Directory Storage Space Full

**Symptoms**:
- /srv/BigData/LocalBackup partition usage is 100%
- "No space left on device" appears in HA logs

**Repair solution**:
1. Check the LocalBackup directory disk space
2. Clean up unnecessary old backup files
3. Modify "Maximum Backup Count" in the Manager UI to reduce the number of backup files
4. Wait approximately 1 minute and check whether the alarm is cleared

### 4.3 Sync File Does Not Exist or Permission Abnormal

**Symptoms**:
- The find command did not find sync files
- Sync file size is 0 and all permissions are "-" (junk file)
- "Permission denied" appears in HA logs

**Repair solution**:
1. Check whether sync files exist
2. If it is a junk file (size 0, abnormal permissions), delete the file
3. If file permissions are insufficient, modify directory permissions to match those of a normal node
4. Wait a few minutes and observe whether the alarm is cleared

### 4.4 Emergency System Recovery

**Scenario**: Active/standby sync continues to be abnormal with active/standby switchover risk

**Repair solution**:
1. Log in to the standby OMS node as the omm user
2. Check the standby OMS core process status: `/opt/Bigdata/Manager/tools/check_process_status.sh`
3. If forced active/standby switchover is needed:
   - Log in to the active OMS node as the omm user
   - Execute: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=127.0.0.1 --port=20013 --switchover --name=product`
4. Collect OmmServer, Controller, NodeAgent logs and contact operations personnel

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Diagram

```
Start
  |
  v
Obtain standby OMS (Peer Manager) IP and active OMS node information from alarm information
  |
  v
Check network connectivity between active and standby OMS nodes (ping standby OMS IP)
  |
  +--- Ping fails ---> Contact network administrator ---> Repair network ---> Is alarm cleared?
  |                                                          |
  |                                                          +--- Yes ---> End
  |                                                          |
  |                                                          +--- No ---> Check disk space
  |
  +--- Ping succeeds ---> Check LocalBackup directory disk space (df -hl)
                           |
                           +--- Space full ---> Clean up old backup files ---> Modify maximum backup count
                           |                                      |
                           |                                      +---> Is alarm cleared?
                           |                                            |
                           |                                            +--- Yes ---> End
                           |                                            |
                           |                                            +--- No ---> Check sync files
                           |
                           +--- Space sufficient ---> Check whether sync files exist (find sed*)
                                                      |
                                                      +--- Does not exist ---> View HA logs
                                                      |
                                                      +--- Junk file ---> Delete file ---> Wait for alarm to clear
                                                      |
                                                      +--- File normal ---> View HA logs
                                                                          |
                                                                          +--- Has errors ---> Handle based on errors
                                                                          |                    |
                                                                          |                    +---> Wait 10 min for alarm to clear
                                                                          |
                                                                          +--- No errors ---> Collect logs
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis conclusion | Recommended action |
|----------|----------|
| Active/standby link interruption | Contact network administrator to repair network fault |
| LocalBackup directory space full | Clean up old backup files, modify maximum backup count |
| Sync file does not exist | View HA logs to investigate root cause |
| Sync file permission abnormal (junk file) | Delete junk file, wait for sync to recover |
| Insufficient directory permissions | Modify directory permissions to match normal node |
| Alarm still persists after processing | Collect OmmServer/Controller/NodeAgent logs, contact operations personnel |
