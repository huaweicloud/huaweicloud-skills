# CPU Usage Over Threshold (12016) Alarm Diagnosis Skill

## Diagnosis Flow

```
Step 1: Confirm CPU load (system-load)
  │
  ├─ iowait significantly high (>20%) → Step 5: disk-io
  │     │
  │     ├─ iowait high + disk await/util high → Root cause: disk IO bottleneck
  │     └─ No disk IO abnormality → Continue to Step 2 to investigate other causes
  │
  ├─ Load < core count (normal), alarm recovered → Alarm recovered branch
  │                                │
  │                                Step 1: Infer the process at that time from alarm info + messages
  │                                  │
  │                                  Step 2: Query GC logs by process name
  │                                    │
  │                                    ├─ Frequent Full GC → Root cause: GC
  │                                    ├─ OOM → Root cause: insufficient memory
  │                                    └─ No abnormality → Summarize current status, suggest observation
  │
  └─ Load ≥ core count (high load) → Step 2: high-CPU processes (high-cpu-processes)
                   │
                   │  Handle each high-CPU process separately:
                   │
                   ├─ Java process ──→ Step 3: jstack thread analysis (jstack-thread-dump)
                   │                 │
                   │                 ├─ GC-related threads exist (G1: "GC task#"/"G1 Conc#" etc; CMS: "Gang worker#" etc.)
                   │                 │     and the process CPU is high in Step 2 ──→ Step 4: GC logs → locate root cause
                   │                 ├─ Many BLOCKED threads ──→ Root cause: lock contention → End
                   │                 ├─ Same stack frame appears repeatedly ──→ Root cause: infinite loop → End
                   │                 └─ Many RUNNABLE threads and stack frame is business code ──→ Step 4: investigate GC
                   │                      └─ GC normal ──→ Root cause: business peak / inefficient task → End
                   │
                   ├─ Non-Java process ──→ Step 6: non-Java process analysis → locate root cause
                   │
                   └─ Root cause not located ──→ Step 5: supplementary investigation (as needed)

> After locating the root cause, jump directly to "Common Root Causes and Repair Suggestions"; no need to continue subsequent steps.
```

## Diagnosis Steps

### Step 1: Confirm CPU load

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=system-load' \
  -p 'node_name=<node_name>'
```

**Analysis**: View 1/5/15-minute average load. Core count is derived from the number of lines in the `mpstat -P ALL` output (one line per CPU number). Also pay attention to the `%iowait` value.

| Actual result | Conclusion | Next step |
|----------|------|--------|
| iowait > 20% | High CPU may be caused by disk IO bottleneck, but needs verification | Step 5 (disk-io); if IO is normal, continue to Step 2 |
| Load > core count (overloaded) | Alarm ongoing | Step 2 |
| Load ≈ core count (fully loaded) | Alarm ongoing | Step 2 |
| Load < core count (normal), alarm recovered | Need to investigate from historical traces | "Alarm recovered" branch below |

---

### Investigation Branch When Alarm Recovered

After the alarm is recovered, historical top cannot be traced back. Investigate in the following order:

#### Step 1: Obtain clues about the high-CPU process at that time

Determine the abnormal process at that time from the following sources (by priority):
1. Whether the **alarm details** contain process name, service name
2. OOM/killed process records in **messages logs**
3. **User confirmation** — directly ask the user which service may have been abnormal at that time

```bash
# Exception records during the alarm period in messages logs
# First try the rotated log with date suffix; if no result, use messages
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log' \
  -p 'log_file_name=messages-<YYYYMMDD>' \
  -p 'keywords=["oom","killed process","Out of memory","segfault"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=^([A-Za-z]{3}) +([0-9]{1,2}) ([0-9]{2}):([0-9]{2}):([0-9]{2})||bdHMS'
```

> If `messages-<YYYYMMDD>` does not exist (logs not rotated by date), retry with `log_file_name=messages`.

> **JDK11+ `-Xlog:gc*` format description**: The log line format is `[2026-07-13T14:52:24.801+0800][gc,start] GC(0) Pause Young (Normal)...`, the time part is similar to the JDK8 `-Xloggc` format, and can be matched with the `^\[([0-9]{4})-...` regex.
>
> **JDK8 `-Xloggc` format description**: The log line format is `2026-07-13T14:52:24.801+0800: GC pause (young)...`. With PrintGCDateStamps enabled, the default time_pattern can be used.
>
> **ACS has no GC logs**: If high CPU is located on the acs process, it cannot be investigated through GC logs; thread state must be analyzed directly via jstack.
>
> **messages log permission**: The omm user may not have permission to read `/var/log/messages`; sudo is required. If API collection fails, it is recommended that the user manually view it with sudo on the node.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \

  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=<gc_log_directory>' \
  -p 'log_file_name=<gc_log_file_name>' \
  -p 'keywords=<gc_keywords>' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=<gc_time_pattern>' \
  -p 'alarm_duration_minutes=60'
```

**Select GC keywords by format**:

| GC format | keywords | Description |
|--------|----------|------|
| JDK11+ `-Xlog:gc*` (G1) | `["Pause","Full","OutOfMemoryError","Metadata GC Threshold"]` | Both Young/Old GC of G1 contain the `Pause` keyword; `Full` marks a Full GC. Actual log format such as `[2026-07-13T14:52:24.801+0800][gc,start] GC(0) Pause Young (Normal)...` |
| JDK8 CMS `-Xloggc` | `["Full GC","Concurrent mode failure","OutOfMemoryError","Metadata GC Threshold"]` | CMS-specific `Concurrent mode failure` indicates concurrent collection failed and degenerated into Full GC |

> If the specific process cannot be determined, skip this step and summarize the available information to provide observation suggestions.

**Comprehensive analysis**:

| Phenomenon | Conclusion |
|------|------|
| Process info present in alarm details | Locate the process directly and query the corresponding GC logs |
| OOM/killed process in messages | Root cause: process killed due to insufficient memory |
| Frequent Full GC during alarm period in GC logs | Root cause: GC caused CPU spike; alarm recovery may be due to GC ending |
| GC logs normal / no GC logs | Issue has recovered; suggest continuous observation or immediately execute Steps 2-3 at the next alarm |

### Step 3: Java process thread analysis

For the high-CPU Java process confirmed in Step 2, obtain its PID and execute:

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=jstack-thread-dump' \
  -p 'env={"PID":"<java_pid>"}' \
  -p 'node_name=<node_name>'
```

> jstack-thread-dump returns thread state statistics and full jstack output. **First look at the thread state statistics line** (`java.lang.Thread.State` distribution); view the full jstack stack frames if you need to locate specific code.

**Analysis points**:

- jstack itself does not contain CPU usage information; it needs to be judged together with the CPU usage of the process in Step 2
- Search for GC-related thread names in the full jstack output:
  - **G1 GC** (JDK11+ default, tomcat/pms/controller/nodeagent/disaster etc.): `"GC task#"` or `"G1 Main Marker"` or `"G1 Conc#"`
  - **CMS GC** (JDK8, big data components hdfs/yarn/zk etc.): `"GC task#"` or `"Gang worker#"` or `"Concurrent Mark-Sweep GC Thread"`
  - Generic: `"GC Daemon"`

| jstack thread feature | Conclusion | Next step |
|----------------|------|--------|
| GC-related threads exist (G1: "GC task#"/"G1 Conc#" etc.; CMS: "Gang worker#" etc.) and the process CPU is high in Step 2 | Suspected GC causing high CPU | Step 4 (GC log confirmation) |
| Many BLOCKED threads | Thread lock contention | **Root cause located** → Common root cause item 2 |
| Same stack frame appears repeatedly | Infinite loop or busy waiting | **Root cause located** → Common root cause item 2 |
| Many RUNNABLE threads and stack frame is business code | High business load or GC issue | Step 4 (rule out GC first) |

> If Step 4 confirms GC is normal and RUNNABLE thread stack frames are business code, the root cause is business peak or inefficient task (e.g., data-skewed SQL); suggest investigating together with Yarn tasks.

### Step 4: GC log check

According to the Java process name confirmed in Step 2/3, query the corresponding GC logs based on the process name → path mapping (the mapping table is in "Alarm recovered" Step 2):

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=<gc_log_directory>' \
  -p 'log_file_name=<gc_log_file_name>' \
  -p 'keywords=<gc_keywords>' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>' \
  -p 'time_pattern=<gc_time_pattern>' \
  -p 'alarm_duration_minutes=60'
```

> Select GC keywords and time_pattern according to the GC format in the mapping table; see the description in "Alarm recovered" Step 2.

**Analysis**:

| GC log feature | Conclusion |
|-----------|------|
| **G1 format**: `Pause Full` or contains `Full` keyword and is time-consuming | **Root cause located**: G1 Full GC caused high CPU; root cause is usually insufficient memory or large object allocation |
| **G1 format**: `Pause Young` frequent but each not time-consuming | Frequent Young GC, may be due to too high allocation rate; not a serious issue, suggest observation |
| **CMS format**: `Full GC` frequent and time-consuming | **Root cause located**: CMS Full GC caused high CPU |
| **CMS format**: `Concurrent mode failure` | **Root cause located**: CMS concurrent collection failed and degenerated into Full GC; need to increase old generation or lower CMS trigger threshold |
| Generic: `OutOfMemoryError` | **Root cause located**: Out of memory caused repeated Full GC |
| Generic: `Metadata GC Threshold` | **Root cause located**: Metaspace insufficient triggering Full GC; need to increase `-XX:MaxMetaspaceSize` |
| GC normal | Not a GC issue; high CPU may be business peak or inefficient task; suggest investigating with Yarn tasks |

When Steps 2-4 do not locate a clear root cause, execute the following checks **as needed** (select based on symptoms):

```bash
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=d-state-process' \
  -p 'node_name=<node_name>'

# Memory usage (check when suspecting insufficient memory causing swap)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'

# Thread statistics (check when suspecting thread exhaustion)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=thread-statistics' \
  -p 'node_name=<node_name>'

# Disk IO (check when iowait is high or suspecting disk bottleneck)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-io' \
  -p 'node_name=<node_name>'

# File handles (check when suspecting handle exhaustion)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=file-handle' \
  -p 'node_name=<node_name>'

# Process file descriptors (check when suspecting fd leak in a process; PID required)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-file-descriptor' \
  -p 'env={"PID":"<pid>"}' \
  -p 'node_name=<node_name>'

# Process network connections (check when suspecting network storm / connection surge)
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-network-connection' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Phenomenon | Conclusion |
|------|------|
| Many zombie processes | Parent process did not reap child processes; need to restart the parent process |
| Many D-state processes | Processes waiting for IO not released; judge together with disk-io whether disk bottleneck |
| Thread usage close to 100% | Thread count exhausted; new requests cannot create threads |
| Insufficient memory + large swap usage | Insufficient memory causing frequent swap; CPU spent on paging |
| iowait high + disk await/util high | Disk IO bottleneck indirectly causing high CPU iowait |
| File handle usage close to 100% | Handle exhaustion; processes repeatedly retrying consuming CPU |
| Abnormally high fd count for a process | The process has an fd leak (e.g., unclosed connections), consuming CPU |
| Abnormally many network connections or many CLOSE_WAIT | Network storm or connection leak, consuming CPU |

## Common Root Causes and Repair Suggestions

> The following repair suggestions must be executed manually by the user; the automation tool is only responsible for diagnosis and locating.

### 1. Frequent Java Full GC

**Symptom**: Java process CPU high in Step 2 + GC threads exist in jstack + dense Full GC in GC logs

**Repair suggestions**:
- Check whether the JVM heap memory configuration is reasonable; consider increasing `-Xmx`
- Analyze whether there is a memory leak
- Optimize code to reduce large object allocation

**Notes**:
- **Increase `-Xmx`**: Need to SSH to the target node to modify the corresponding service's `application.properties` or startup script; service restart is required for it to take effect. Increasing heap memory will occupy more physical memory; ensure the node has sufficient remaining memory, otherwise other processes may trigger OOM
- **Analyze memory leak**: Can execute `jmap -histo:live <pid>` to view object distribution, but note: ① this command requires a JDK environment and is not available on nodes with only JRE installed; ② execution triggers a Full GC causing a brief STW; ③ the output may be large, suggest redirecting to a file. You can also execute `jcmd <pid> GC.heap_dump` to generate a heap dump file for analysis with MAT, but the dump file may be as large as the heap; ensure sufficient disk space
- **JVM parameter modification**: In MRS, JVM parameters modified via the Manager UI are automatically distributed; manual modification of the startup script will be overwritten on the next config distribution

### 2. Java thread leak / infinite loop

**Symptom**: Many BLOCKED threads or the same stack frame appears repeatedly in jstack

**Repair suggestions**:
- BLOCKED: investigate lock contention code, optimize synchronization logic
- Infinite loop: locate business code by thread stack, fix the logic

**Notes**:
- Need to combine the jstack output thread stack frames to locate the specific business class and method, then map to source code for analysis
- BLOCKED issues are usually synchronization design issues at the code level; fixing requires a release; for temporary relief, consider restarting the service

### 3. Disk IO bottleneck (high iowait)

**Symptom**: iowait > 20% in Step 1; disk-io shows high await/util

**Repair suggestions**:
- Investigate whether there is a large amount of log writing
- Investigate whether there is an abnormal disk read/write process
- Consider disk expansion or IO scheduling optimization

**Notes**:
- High iowait is not necessarily a disk issue; it may also be NFS or other network storage stalling; need to judge comprehensively together with D-state processes and mount type
- Before cleaning up large log files, confirm the file is not held by a process (otherwise disk space will not be released after deletion); suggest first `> file` to clear the content then delete
- Disk expansion involves MRS cluster O&M operations and must be performed according to the change process

### 4. Insufficient memory triggering swap

**Symptom**: memory-usage shows very low available memory and large swap usage; or kswapd0 process CPU high

**Repair suggestions**:
- Release unnecessary memory usage (restart leaking processes)
- Add physical memory or adjust swap strategy
- Adjust JVM heap memory quotas of each service

**Notes**:
- **Adjust JVM heap memory**: When multiple services share the same node, increasing `-Xmx` of a service needs to ensure it does not cause insufficient memory for other services. It is recommended to first understand the memory usage distribution of all services on the node through `omm-process-tree`, then adjust holistically
- **Disable swap**: `swapoff -a` can immediately disable swap, but before disabling, ensure physical memory is sufficient to accommodate the working sets of all processes, otherwise OOM Killer will be triggered. Disabling swap is a Hadoop community recommended practice (to avoid long-tail latency from accessing swap during GC), but it must be done under the premise of sufficient physical memory
- **Adjust swappiness**: `sysctl vm.swappiness=1` can reduce the kernel's tendency to use swap (value range 0-100, default 60); swap usage can be reduced without disabling swap, but `sysctl -p` is required for persistence

### 5. D-state process accumulation

**Symptom**: d-state-process shows D-state processes exist

**Repair suggestions**:
- Investigate whether the underlying IO device is faulty
- Check whether NFS or other network storage is stalling
- Restart the parent process of the D-state process if necessary

**Notes**:
- D-state (Uninterruptible Sleep) processes cannot be terminated with `kill`; they can only wait for IO to complete or restart the system
- If D-state processes persist, it usually means the underlying storage device is faulty or the NFS mount point is unreachable; the storage layer issue must be fixed first
- Restarting the parent process of the D-state process may cause service interruption; the impact needs to be evaluated

### 6. Thread / file handle exhaustion

**Symptom**: thread-statistics shows thread usage close to 100%; file-handle shows usage close to 100%

**Repair suggestions**:
- Increase system limits
- Investigate applications with thread/connection leaks
- Optimize connection pool configuration

**Notes**:
- **Increase thread limit**: `ulimit -u` modifies the current session limit; it must be written to `/etc/security/limits.conf` for persistence. Before increasing the limit, ensure sufficient system resources (memory, PID space); too many threads will exacerbate context switching overhead
- **Increase file handle limit**: `ulimit -n` similarly needs persistence. MRS services usually have the handle count already set in the startup script; manual modification needs to be synchronized with the startup script, otherwise it will be invalid after restart
- A fundamental solution requires locating the leak source (which process's threads/fd continuously grow and are not released); merely increasing the limit is a temporary measure

### 7. System process exception

**Symptom**: Non-Java system process occupies abnormally high CPU

**Repair suggestions**:
- collectd: check the collection plugin configuration, lower the collection frequency
- rsyslog: check whether there is a log storm, optimize log levels
- Scheduled scripts: investigate abnormal tasks in crontab

**Notes**:
- collectd/rsyslog are MRS O&M components; modifying their configuration must be done through the Manager or by modifying the corresponding config file and restarting the service; direct kill is not recommended
- Scheduled script investigation: `crontab -l` to view the omm user's scheduled tasks, confirm whether abnormal scripts are executing
- When python/shell script CPU is high, locate the actual script path and interpreter via `ls -la /proc/<pid>/cwd` and `ls -la /proc/<pid>/exe`

### 8. Business peak or inefficient task

**Symptom**: Java process CPU high + jstack shows RUNNABLE business threads + GC logs normal

**Repair suggestions**:
- Investigate whether there are data-skewed tasks on Yarn (a Container's CPU far exceeding other Containers of the same Job)
- Investigate whether there are inefficient SQL (full table scan, no partition filtering)
- Consider business rate limiting or off-peak execution

**Notes**:
- Investigating Yarn tasks requires the Yarn ResourceManager Web UI (default port 8088) or the `yarn application -list` command; internal cluster access permission is required
- Typical feature of data skew: in the same Stage, a few Tasks run much longer than other Tasks; can be viewed in the Task details page of Spark UI/MapReduce UI
- Inefficient SQL investigation needs to combine the execution plan of Hive/Spark SQL (`EXPLAIN`) and the historical records of task submissions for analysis
