# `OKerberos Resource Abnormal` (12005) Alarm Diagnosis Skill

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **OKerberos Resource Abnormal (12005)** alarm. The alarm module monitors the status of the Kerberos resource in Manager at 80-second intervals. When the Kerberos resource is detected as abnormal for 6 consecutive monitoring cycles, the system generates this alarm. When the Kerberos resource recovers and the alarm handling is complete, the alarm is cleared. In MRS 3.3.1 and later versions, the alarm name was changed from "OKerberos Resource Abnormal" to "Manager OKerberos Resource Abnormal".

OKerberos resource abnormalities are typically caused by abnormalities in the OLdap resource it depends on. OKerberos depends on OLdap for user authentication. When the OLdap resource is abnormal, Kerberos's WebUI authentication service becomes unavailable, unable to provide security authentication functions for web upper-layer services.

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12005 |
| Alarm Name | OKerberos Resource Abnormal |
| Alarm Severity | Important |
| Alarm Type | Resource Abnormal Alarm |
| Auto-cleared | Yes |
| System Impact | Kerberos resource abnormality in Manager causes component WebUI authentication services to become unavailable, unable to provide security authentication functions for web upper-layer services, which may prevent login to FusionInsight Manager and component WebUI |

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information and determine the active/standby OMS node names and IP addresses.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Check OMS Active/Standby Resource Status (View OKerberos Resource Status)

Execute the following command to view the active/standby resource status of OMS nodes and determine whether the OKerberos resource is normal. In the command output, check the "ResHAStatus" column of the "okerberos" row:

- Single-node mode: OKerberos resource should be in "Normal" status
- Dual-node mode: OKerberos resource should be "Active_normal" on the active node and "Standby_normal" on the standby node
- If "ResHAStatus" is not one of the above normal states, the OKerberos resource is abnormal

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred (the node where Manager is located), obtained from the alarm information

### 2.3 Check HA Resource Status

Execute the following command to view the current HA-managed resource status and confirm whether the OKerberos and its dependent OLdap resource are in a normal state.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

Example command output:
```
NodeName        ResName       ResStatus     ResHAStatus     ResType
xxx-oms-node1   okerberos     Normal        Active_normal   Single_active
xxx-oms-node1   oldap         Normal        Active_normal   Single_active
xxx-oms-node2   okerberos     Stopped       Normal          Single_active
xxx-oms-node2   oldap         Stopped       Normal          Single_active
```

**Status description**:
- Single-node mode: Both OKerberos and OLdap resources are in Normal status
- Dual-node mode: OKerberos and OLdap resources are Normal on the active node and Stopped on the standby node
- If the OKerberos resource status is abnormal (e.g., not Normal or not Stopped), the resource has failed
- If the OLdap resource status is abnormal, the OKerberos resource will also be affected

### 2.4 Check OLdap Resource Status (Dependency of OKerberos)

Execute the following command to view the "oldap" row in the OMS node resource status and confirm whether the OLdap resource that OKerberos depends on is abnormal. If the OLdap resource is abnormal, the OKerberos resource abnormality alarm is typically caused by the OLdap resource abnormality.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

How to determine:
- Check the "ResHAStatus" column of the "oldap" row in the command output
- If the OLdap resource status is normal, the OKerberos resource abnormality is not caused by OLdap; further investigation is needed
- If the OLdap resource status is abnormal, the OLdap resource abnormality must be handled first (refer to ALM-12004 OLdap Resource Abnormal handling steps)

### 2.5 Check slapd Process Status

Execute the following command to check whether the slapd process of the OLdap service (which OKerberos depends on) is running normally. A slapd process listening on port 21750 should exist.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"slapd"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

How to determine:
- If the command output contains slapd process information and the process is listening on port 21750, the process is normal
- If the command output does not contain slapd process information, or the process port is not 21750, the process is abnormal

### 2.6 Check OLdap Listening Port Status

Execute the following command to check whether the OLdap service port (21750) that OKerberos depends on is listening normally.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=port-check' \
  -p 'env={"PORT":"21750"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

How to determine:
- If port 21750 is listening normally, the OLdap service port is normal
- If port 21750 is not listening, the OLdap service has not started properly, and the OKerberos resource will be abnormal due to the dependency

### 2.7 Check Alarm Node System Resources

Execute the following command to check the system resources of the alarm node and determine whether insufficient system resources are causing OKerberos or OLdap process abnormalities.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=system-load' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.8 View OKerberos HA Script Logs

Execute the following command to view the result logs of HA detecting the OKerberos resource and analyze the direct cause of the OKerberos resource abnormality.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/ha/scriptlog' \
  -p 'log_file_name=okerberos*' \
  -p 'keywords=["ERROR","exception","Failed","Cannot find","Permission denied"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm occurrence time
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.9 View OLdap HA Script Logs

Execute the following command to view the result logs of HA detecting the OLdap resource and analyze whether the OLdap resource has abnormalities causing the OKerberos resource abnormality.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/ha/scriptlog' \
  -p 'log_file_name=oldap*' \
  -p 'keywords=["ERROR","exception","Failed","Cannot find","Permission denied"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm occurrence time
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.10 View OmmServer Logs

Execute the following command to view OmmServer logs and analyze whether there is any abnormal information related to OKerberos or OLdap.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/server' \
  -p 'log_file_name=*.log*' \
  -p 'keywords=["ERROR","exception","ldap","slapd","kerberos","OKerberos","OLdap"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm occurrence time
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., commands that require manual login to the node).

### 3.1 Log in to the Manager Node as omm User

Log in to the Manager node host in the cluster as the omm user and execute the following command to view the current Manager dual-node information:

```bash
sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh
```

Check the "ResHAStatus" column of the "okerberos" row in the command output:
- If it is "Normal" (single-node mode) or "Active_normal"/"Standby_normal" (dual-node mode), the OKerberos resource status is normal; further check the dependent OLdap resource status
- If it is not one of the above normal states, the OKerberos resource is abnormal; proceed to step 3.2

### 3.2 Check OLdap Resource Status

Execute the following command to query whether the current HA-managed OLdap resource status is normal:

```bash
sh ${BIGDATA_HOME}/om-server/OMS/workspace0/ha/module/hacom/script/status_ha.sh
```

Check the "ResHAStatus" column of the "oldap" row in the command output:
- In single-node mode, the OLdap resource should be in "Active_normal" status
- In dual-node mode, the OLdap resource should be "Active_normal" on the active node and "Standby_normal" on the standby node

How to determine:
- Yes (OLdap resource status is normal): proceed to step 3.4
- No (OLdap resource status is abnormal): proceed to step 3.3

### 3.3 Handle OLdap Resource Abnormality

Refer to ALM-12004 OLdap Resource Abnormal handling steps:

1. Find the abnormal slapd process:
```bash
ps -ef | grep slapd | grep -v grep
```

2. Terminate the abnormal ldap process (`<ldap_pid>` is the process PID obtained in the previous step); after waiting 20 seconds, HA will automatically start the OLdap process:
```bash
kill -2 <ldap_pid>
```

3. After waiting 20 seconds, re-execute `sh ${BIGDATA_HOME}/om-server/OMS/workspace0/ha/module/hacom/script/status_ha.sh` and observe whether the OLdap resource status has recovered
4. After the OLdap resource status recovers, observe whether the current OKerberos resource status has recovered
   - Yes: operation is complete
   - No: proceed to step 3.4

### 3.4 Restart OKerberos Process

When the OLdap resource is normal but the OKerberos resource is abnormal, log in to the alarm node as the omm user, find and restart Kerberos-related processes:

```bash
# Find kerberos process PID
ps -ef | grep -E "krb5|kadmind|kdc" | grep -v grep

# Terminate kerberos process (<kerberos_pid> is the process PID obtained in the previous step)
kill -2 <kerberos_pid>
```

After waiting 20 seconds, re-execute `sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh` and observe whether the OKerberos resource status has recovered:
- If the OKerberos resource status has recovered, wait for the next system detection cycle and check whether the alarm is automatically cleared
- If the OKerberos resource status has not recovered, proceed to step 3.5

### 3.5 Collect Fault Information

When the above steps do not resolve the issue, fault log information needs to be collected:

1. In the MRS cluster Manager UI, select "Maintenance > Logs > Download". For details on logging in to the cluster Manager, refer to Accessing MRS Cluster Manager.
2. In "Services", select "OmsKerberos" and "OmmServer", then click "OK".
3. In the upper right corner, set the log collection "Start Time" and "End Time" to 1 hour before and after the alarm generation time, then click "Download".
4. Contact operations personnel and send the collected fault log information.

## 4. Common Fault Repair Solutions

### 4.1 OLdap Resource Abnormality (Dependency of OKerberos)

**Symptoms**:
- okerberos's "ResHAStatus" in status-oms.sh output is not Normal/Active_normal/Standby_normal
- OLdap resource status is also abnormal (oldap's ResHAStatus is abnormal)
- slapd process does not exist or terminated abnormally
- Port 21750 is not listening

**Repair solution**:
1. Log in to the Manager node as the omm user
2. Execute `sh ${BIGDATA_HOME}/om-server/OMS/workspace0/ha/module/hacom/script/status_ha.sh` to confirm OLdap resource status is abnormal
3. Execute `kill -2 <ldap_pid>` to terminate the abnormal ldap process; after waiting 20 seconds, HA will automatically restart the OLdap process
4. Re-execute `status_ha.sh` to check whether the OLdap resource status has recovered
5. After the OLdap resource recovers, check whether the OKerberos resource status has recovered
6. If recovered, wait for the next system detection cycle and check whether the alarm is automatically cleared
7. If not recovered, collect fault logs and contact operations personnel

### 4.2 OKerberos Process Failure

**Symptoms**:
- OLdap resource status is normal, but OKerberos resource status is abnormal
- Kerberos-related processes (krb5, kadmind, kdc) do not exist or terminated abnormally
- Kerberos-related errors exist in HA script logs

**Repair solution**:
1. Log in to the Manager node as the omm user
2. Find Kerberos processes: `ps -ef | grep -E "krb5|kadmind|kdc" | grep -v grep`
3. Execute `kill -2 <kerberos_pid>` to terminate the abnormal Kerberos process; after waiting 20 seconds, HA will automatically restart the OKerberos process
4. Re-execute `status-oms.sh` to check whether the OKerberos resource status has recovered
5. If recovered, wait for the next system detection cycle and check whether the alarm is automatically cleared
6. If not recovered, check HA script logs to investigate the specific cause
7. If still not recovered, collect fault logs and contact operations personnel

### 4.3 System Resource Insufficiency Causing OKerberos Abnormality

**Symptoms**:
- System load is too high or memory usage is near 100%
- Insufficient disk space prevents OKerberos or OLdap processes from running normally
- Processes were killed by the system due to resource insufficiency (OOM)

**Repair solution**:
1. Check system resources (CPU load, memory usage, disk space)
2. Clean up unnecessary log files or temporary files to free disk space
3. If memory is insufficient, check whether other processes are consuming excessive memory and adjust process memory parameters if necessary
4. After resources are recovered, restart the OKerberos process or OLdap process (kill -2)
5. Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 4.4 Alarm Cannot Be Cleared

**Scenario**: After OLdap resource checks, OKerberos process restarts, system resource checks, and HA log investigation, the alarm still persists

**Repair solution**:
1. Collect fault logs (OmsKerberos and OmmServer service logs)
2. Log collection time range is 1 hour before and after the alarm generation time
3. Contact operations personnel and send the collected fault log information

Based on the diagnosis flow above, output one of the following diagnosis conclusions:
