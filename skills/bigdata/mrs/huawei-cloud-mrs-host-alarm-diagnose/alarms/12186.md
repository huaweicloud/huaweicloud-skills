## 2. Log Directory

### 2.1 Log Priority

> When analyzing CGroup task count exceptions, it is recommended to view logs in the following priority order:
>
> | Priority | Log Type | Description |
> |----------|----------|-------------|
> | 1 | System log | System-level log information |
> | 2 | Process thread information | Thread count statistics |
> | 3 | Java stack log | Java thread stack information |

### 2.2 Log Path

| Log File | Path | Purpose | Priority |
|----------|------|---------|----------|
| System log | `/var/log/messages` | System-level log information | 1 |
| Java stack log | `/tmp/jstack_*.log` | Java thread stack information | 2 |
| cgroup information | `/sys/fs/cgroup/pids/` | cgroup task count statistics | 3 |


| Keyword | Meaning | Severity |
|---------|---------|----------|
| `pids.max` | cgroup maximum task count limit | 🟢 P3 |
| `pids.current` | cgroup current task count | 🟢 P3 |
| `TasksMax` | systemd user task count limit | 🟢 P3 |
| `Resource temporarily unavailable` | Resource temporarily unavailable (task count exceeded) | 🔴 P0 |
| `fork` | Create process/thread | 🟢 P3 |
| `Cannot allocate memory` | Out of memory (possibly due to task count exceeded) | 🔴 P0 |
| `user-2000.slice` | systemd slice for omm user | 🟢 P3 |

| Keyword | Meaning | Severity |

## 7. Common Root Causes and Repair Suggestions

### CGroup Task Count Check

| Check Item | Command | Description |
|------------|---------|-------------|
| omm user task count limit | `systemctl status user-$(id -u).slice \| grep limit` | View TasksMax configuration value |
| System-level cgroup pids | `/sys/fs/cgroup/pids/pids.max` | System maximum task count |
| Current task count | `/sys/fs/cgroup/pids/pids.current` | System current task count |

### Root Cause Classification Table

| Root Cause | Characteristics | Repair Suggestion |
|------------|----------------|-------------------|
| TasksMax configured too low | omm user TasksMax<60000, task count exceeded | Execute `systemctl set-property user-2000.slice TasksMax=60000`, modify `UserTasksMax=60000` in `/etc/systemd/logind.conf` |
| Thread leak | A process's thread count keeps growing without releasing | Locate the leaking process, restart it, contact technical support to fix the code |
| Too many YARN containers | YARN NodeManager creates a large number of containers | Adjust YARN container concurrency configuration, limit the number of containers per node |
| Too many Flink TaskManager threads | Flink TM thread count exceeds expectations | Adjust Flink slot count configuration, optimize operator parallelism |
| Kafka thread bloat | Too many Kafka consumer/producer threads | Adjust Kafka thread pool configuration, optimize consumer group count |
| JVM thread bloat | Java process thread count keeps growing | Analyze thread status with jstack, locate BLOCKED/WAITING threads, fix the code |
| Zombie process buildup | Large number of Z-state processes | Locate the parent process, clean up zombie processes |
| Cron task buildup | Scheduled tasks create a large number of child processes | Check crontab configuration, optimize scheduled tasks |
| SSH session leak | Large number of sshd processes | Check SSH connection configuration, set `ClientAliveInterval` and `ClientAliveCountMax` |
| Python multiprocessing leak | Python multiprocessing not properly cleaned up | Check Python application process management logic |

### Temporary Solutions

| Operation | Command | Description |
|-----------|---------|-------------|
| Increase TasksMax | `systemctl set-property user-2000.slice TasksMax=60000` | Temporarily increase omm user task count limit |
| Permanent modification | Modify `UserTasksMax` in `/etc/systemd/logind.conf` | Takes effect after reboot |
| Kill leaking process | `kill -9 <PID>` | Terminate the leaking process to release task count |
