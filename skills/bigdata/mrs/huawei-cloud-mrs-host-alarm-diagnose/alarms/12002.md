# `HA Resource Abnormal` (12002) Alarm Diagnosis Skill

> **Note**: This alarm is a legacy alarm for MRS 2.x and earlier versions. In current versions (MRS 3.x+), this alarm has been split into independent alarms for each HA resource (e.g., 12004 OLdap Resource Abnormal, 12005 OKerberos Resource Abnormal, 12012 NTP Service Abnormal, etc.). The diagnosis logic is consistent with HA resource status checks.

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **HA Resource Abnormal (12002)** alarm. HA (High Availability) resources are core components of the Manager dual-node (active/standby) high-availability architecture, including OKerberos, OLdap, NTP, Controller, Tomcat, Httpd, PMS, and other resources. The system periodically monitors the status of each HA resource and generates this alarm when any HA resource is in an abnormal state (not a normal state). The alarm is cleared when all HA resources return to normal.

HA resource abnormalities are typically caused by:
- Process/service failure of the corresponding HA resource (process does not exist or terminates abnormally)
- Insufficient system resources (high CPU load, insufficient memory/disk space) causing processes to be killed by OOM
- File permission or configuration issues (Permission denied, missing configuration files)

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12002 |
| Alarm Name | HA Resource Abnormal (2.x and earlier versions) |
| Alarm Severity | Critical |
| Alarm Type | Resource Abnormal Alarm |
| Auto-cleared | Yes |
| System Impact | Services carried by the corresponding HA resource are unavailable, which may cause Manager and component functional abnormalities, active/standby switchover failures, etc. |

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Execute the following command to obtain the cluster OMS active/standby node information and determine the active/standby OMS node names and IP addresses.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Check OMS HA Resource Status

Execute the following command to view the active/standby resource status of OMS nodes and check each HA resource one by one to determine whether it is in a normal state.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=ha-resource-status' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred (the node where Manager is located), obtained from the alarm information

Example command output:
```
NodeName        ResName       ResStatus     ResHAStatus     ResType
8-5-235-6       okerberos     Normal        Active_normal   Active_standby
8-5-235-6       oldap         Normal        Active_normal   Active_standby
8-5-235-6       ntp           Normal        Active_normal   Active_standby
8-5-235-6       controller    Normal        Normal          Single_active
8-5-235-6       tomcat        Normal        Normal          Single_active
8-5-235-12      okerberos     Normal        Standby_normal  Active_standby
8-5-235-12      oldap         Normal        Standby_normal  Active_standby
8-5-235-12      ntp           Normal        Standby_normal  Active_standby
8-5-235-12      controller    Stopped       Normal          Single_active
8-5-235-12      tomcat        Stopped       Normal          Single_active
```

**Status description** (based on actual normal states observed in clusters):
- Dual-node mode (ACTIVE_STANDBY, e.g., okerberos/oldap/ntp/gaussDB): Active node is `Active_normal`, standby node is `Standby_normal` — this is normal
- Single-node mode (SINGLE_ACTIVE, e.g., controller/aos/tomcat/httpd/fms/disaster/acs/floatip/iam/pms): Active is `Normal`, standby is `Stopped` — this is normal
- If a resource's `ResHAStatus` is not one of the above normal states, the HA resource is abnormal

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Abnormal resource status exists (e.g., ResHAStatus is Abnormal/Fault/Initial) | **Root cause located**: Corresponding HA resource is abnormal | Step 2.3 |
| All resource statuses normal | HA status is normal | Step 2.5 (check system resources) |

### 2.3 Check Process Status of Abnormal HA Resource

Based on the abnormal resource name identified in Step 2.2, check whether the corresponding process exists and its running status. Common resource-to-process mappings:

| Resource name | Corresponding process |
|--------|----------|
| okerberos | krb5kdc, kadmind |
| oldap | slapd |
| ntp | chronyd / ntpd |
| controller | controller |
| tomcat | tomcat |
| httpd | httpd |

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=process-basic-info' \
  -p 'env={"process_name":"<process_name>"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<process_name>`: Process name corresponding to the abnormal resource (see table above)
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| Process does not exist or status is abnormal | **Root cause located**: HA resource process failure | Repair solution 4.1 |
| Process is normal | Continue investigation | Step 2.5 (check system resources) |

### 2.4 View HA Script Logs of Abnormal Resource

Execute the following command to view the result logs of HA detecting the abnormal resource and analyze the direct cause of the resource abnormality.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/omm/oms/ha/scriptlog' \
  -p 'log_file_name=<ha_log_file_name>' \
  -p 'keywords=["ERROR","exception","Failed","Cannot find","Permission denied","No space left"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm occurrence time
- `<ha_log_file_name>`: HA script log file name corresponding to the abnormal resource (see mapping table below)
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

**HA log file name to resource mapping** (in the /var/log/Bigdata/omm/oms/ha/scriptlog/ directory):

| Abnormal resource | log_file_name |
|----------|---------------|
| okerberos | okerberos* |
| oldap | oldap* |
| ntp | ha_ntp* |
| httpd | httpd* |
| tomcat | tomcat* |
| Others (general HA runtime log) | ha.log* (in /var/log/Bigdata/omm/oms/ha/runlog/ directory) |

**Log keyword analysis**:

| Log keyword | Conclusion |
|-----------|------|
| `Permission denied` | File permission issue |
| `Cannot find` / `No such file` | Missing configuration file |
| `No space left on device` | Insufficient disk space |
| `ERROR` / `Failed` | HA resource start/run failure |

### 2.5 Check Alarm Node System Resources

Execute the following command to check the system resources of the alarm node and determine whether insufficient system resources are causing HA resource process abnormalities (OOM kills, etc.).

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=system-load' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'

python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

**Analysis**:

| Actual result | Conclusion | Next step |
|----------|------|--------|
| High CPU load, memory near 100%, or insufficient disk space | **Root cause located**: System resource insufficiency causing HA resource abnormality | Repair solution 4.2 |
| Resources normal | Continue investigation | Step 2.4 (view HA script logs) |

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., commands that require manual login to the node).

### 3.1 Log in to the Manager Node as omm User

Log in to the Manager node host in the cluster as the omm user and execute the following command to view the current Manager dual-node information:

```bash
sh ${BIGDATA_HOME}/om-server/om/sbin/status-oms.sh
```

Check the "ResHAStatus" column of each resource in the command output:
- Dual-node mode (e.g., okerberos/oldap/ntp): Active node is `Active_normal`, standby node is `Standby_normal` — this is normal
- Single-node mode (e.g., controller/tomcat/httpd): Active is `Normal`, standby is `Stopped` — this is normal
- If not in the above normal states, the corresponding HA resource is abnormal

### 3.2 Check HA Resource Process Status

Log in to the alarm node as the omm user and execute the following command to check the process status of the abnormal resource:

```bash
ps -ef | grep <process_name> | grep -v grep
```

- If the process does not exist or its status is abnormal, it indicates an HA resource process failure

### 3.3 Restart Abnormal HA Resource

Log in to the alarm node as the omm user and execute `kill -2 <abnormal_process_pid>` to terminate the abnormal process. After waiting 20 seconds, HA will automatically restart the resource:

```bash
kill -2 <abnormal_process_pid>
```

> **Note**: `kill -2` is a graceful termination; HA will detect the resource abnormality and automatically restart it. Do not use `kill -9` directly.

### 3.4 View HA Script Logs

Log in to the alarm node as the root user and navigate to the HA script log directory:

```bash
cd /var/log/Bigdata/omm/oms/ha/scriptlog/
```

Check the corresponding resource logs (e.g., okerberos.log, oldap.log, ha_ntp.log) around the alarm time for error messages:
- `Permission denied`: File permission issue, execute `chown omm:omm <file_path>` and `chmod 755 <directory>` to fix
- `No space left on device`: Insufficient disk space, clean up logs or temporary files

### 3.5 Collect Fault Information

When the above steps do not resolve the issue, fault log information needs to be collected:

1. In the MRS cluster Manager UI, select "Maintenance > Logs > Download". For details on logging in to the cluster Manager, refer to Accessing MRS Cluster Manager.
2. In "Services", select "OmsKerberos", "OmsLdapServer", and "OmmServer", then click "OK".
3. In the upper right corner, set the log collection "Start Time" and "End Time" to 1 hour before and after the alarm generation time, then click "Download".
4. Contact operations personnel and send the collected fault log information.

## 4. Common Fault Repair Solutions

### 4.1 HA Resource Process/Service Failure

**Symptoms**:
- A resource's ResHAStatus is abnormal in ha-resource-status
- The corresponding process (krb5kdc/kadmind/slapd/chronyd/ntpd/controller, etc.) does not exist or terminated abnormally
- ERROR/Failed records exist in HA script logs

**Repair solution**:
1. Log in to the Manager node as the omm user
2. Check the process status of the abnormal resource: `ps -ef | grep <resource_process_name>`
3. Execute `kill -2 <abnormal_process_pid>` to terminate the abnormal process; after waiting 20 seconds, HA will automatically restart the resource
4. Re-execute `status-oms.sh` or `ha-resource-status` to check whether the resource status has recovered
5. If not recovered, check the corresponding HA script logs to investigate the specific cause

**Notes**:
- `kill -2` is a graceful termination; HA will detect the resource abnormality and automatically restart it. Do not use `kill -9` directly
- Some resources (e.g., oldap/okerberos) have dependencies; the dependent resource must be recovered first

### 4.2 System Resource Insufficiency Causing HA Resource Abnormality

**Symptoms**:
- High CPU load, memory usage near 100%, or insufficient disk space
- HA resource processes may have been killed by OOM
- `No space left on device` or abnormal process exit records appear in HA script logs

**Repair solution**:
1. Check system resources (CPU load, memory usage, disk space)
2. Clean up unnecessary log files or temporary files to free disk space
3. If memory is insufficient, check whether other processes are consuming excessive memory and adjust process memory parameters if necessary
4. After resources are recovered, execute `kill -2 <abnormal_process_pid>` to restart the corresponding HA resource
5. Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 4.3 File Permission or Configuration Issues

**Symptoms**:
- `Permission denied` or `Cannot find` / `No such file` appears in HA script logs
- Resource fails to start due to insufficient permissions or missing configuration

**Repair solution**:
1. Fix file permissions: `chown omm:omm <file_path>` and `chmod 755 <directory>`
2. Check whether the configuration files of the corresponding resource are complete
3. After processing, re-execute `kill -2` to restart the corresponding HA resource
4. Wait for the next system detection cycle and check whether the alarm is automatically cleared

### 4.4 Alarm Cannot Be Cleared

**Scenario**: After HA resource status checks, process restarts, system resource checks, and HA log investigation, the alarm still persists

**Repair solution**:
1. Collect fault logs (OmsKerberos, OmsLdapServer, and OmmServer service logs)
2. Log collection time range is 1 hour before and after the alarm generation time
3. Contact operations personnel and send the collected fault log information

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Diagram

```
Start
  |
  v
Obtain Manager node hostname from alarm information
  |
  v
Obtain cluster OMS active/standby node information (query-management-node-info)
  |
  v
Check OMS HA resource status (ha-resource-status, check each ResHAStatus)
  |
  +--- Abnormal resource status exists ---> Locate abnormal resource
  |                                          |
  |                                          v
  |                                  Check abnormal resource process status (process-basic-info)
  |                                          |
  |                                          +--- Process abnormal ---> Restart abnormal HA resource (kill -2, wait 20s for HA auto-restart)
  |                                          |                               |
  |                                          |                               v
  |                                          |                       Check whether resource status is recovered
  |                                          |                               |
  |                                          |                               +--- Recovered ---> Check whether alarm is cleared
  |                                          |                               |
  |                                          |                               +--- Not recovered ---> View HA script logs
  |                                          |
  |                                          +--- Process normal ---> View abnormal resource HA script logs (scriptlog)
  |                                                                  |
  |                                                                  +--- Errors found ---> Repair based on logs (permission/config/disk)
  |                                                                  |                      |
  |                                                                  |                      +---> Restart resource and check alarm
  |                                                                  |
  |                                                                  +--- No obvious errors ---> Check system resources
  |
  +--- All resource statuses normal ---> Check system resources (system-load, memory-usage, disk-space)
                                          |
                                          +--- Insufficient resources ---> Clean up resources/scale up ---> Restart corresponding HA resource ---> Check whether alarm is cleared
                                          |                                                                                     |
                                          |                                                                                     +--- Cleared ---> End
                                          |                                                                                     |
                                          |                                                                                     +--- Not cleared ---> View HA script logs
                                          |
                                          +--- Resources normal ---> View HA script logs (scriptlog)
                                                                       |
                                                                       +--- Errors found ---> Repair issue based on logs ---> Check whether alarm is cleared
                                                                       |
                                                                       +--- No obvious errors ---> Collect fault logs
  |
  v
Collect fault logs (OmsKerberos, OmsLdapServer, and OmmServer, 1 hour before and after alarm)
  |
  v
Contact operations personnel and send fault log information
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis conclusion | Recommended action |
|----------|----------|
| HA resource process/service failure | Restart the corresponding HA resource (kill -2), wait for HA auto-restart and check whether the alarm is cleared |
| System resource insufficiency causing HA resource abnormality | Clean up system resources and restart the corresponding HA resource, wait for the alarm to be automatically cleared |
| File permission or configuration issues | Fix file permissions/restore configuration and restart the corresponding HA resource, wait for the alarm to be automatically cleared |
| Alarm still persists after processing | Collect OmsKerberos, OmsLdapServer, and OmmServer logs, contact operations personnel |
