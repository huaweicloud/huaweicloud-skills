# OMS Parameter Configuration Mismatch with Cluster Scale Alarm Diagnosis

## 1. Diagnosis Introduction

This document mainly covers the diagnosis and handling of the **OMS Parameter Configuration Mismatch with Cluster Scale (12062)** alarm. The system checks once every hour at the top of the hour whether the OMS parameter configuration matches the cluster scale. When the check finds that the OMS configured parameters are insufficient to support the current cluster scale, this alarm is triggered. After the user modifies the OMS parameter configuration, this alarm is automatically cleared.

Alarm basic information:

| Item | Content |
|------|------|
| Alarm ID | 12062 |
| Alarm Name | OMS parameter configuration mismatch with cluster scale |
| Alarm Severity | Major |
| Alarm Type | Configuration mismatch alarm |
| Auto-clearable | Yes |
| System Impact | May cause user job execution delays and slow service page response; in severe cases, may cause cluster node Agent or OMS process to run abnormally, leading to component job submission failures and OMS data synchronization failures |

## 2. Executable Operations

This section provides the related operations that can be executed during the alarm analysis process.

### 2.1 Determine Whether the Alarm Cluster is a Virtual Machine

Execute the following command. If the result is `none`, it is a physical machine. If the output is `kvm`, `vmware`, `oracle` or other virtualization platform names, it is a virtual machine environment.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=systemd-detect-virt' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.2 Obtain Cluster OMS Active/Standby Node Information

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.3 Obtain OMS Key Directories

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.4 Check Whether the modify_manager_param.log Contains Alarm Keywords

Execute the following command. If the command result contains "Current oms configurations can not support xx nodes" (where xx is the current cluster node count), it indicates that the OMS configuration is insufficient to support the current cluster scale, confirming the alarm cause.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'alarm_duration_minutes=60' \
  -p 'log_directory=/var/log/Bigdata/controller/scriptlog' \
  -p 'log_file_name=modify_manager_param.log*' \
  -p 'keywords=["Current oms configurations can not support","ERROR","WARN"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm trigger time
- `<node_name>`: OMS primary node name

## 3. Non-Executable Operations

This section provides the related operations that cannot be executed during the alarm analysis process (i.e., commands that need to be executed manually after logging into the node).

### 3.1 Log In to the MRS Cluster Primary Management Node and Switch to omm User

Log in to the MRS cluster primary management node as the root user, then execute the following command to switch to the omm user.

```bash
su - omm
```

### 3.2 View Manager Parameter Modification Log

Execute the following command to open the corresponding Manager log file, search for "Current oms configurations can not support xx nodes" (where xx is the current cluster node count), and confirm whether the OMS configuration matches the cluster scale.

```bash
vi $BIGDATA_LOG_HOME/controller/scriptlog/modify_manager_param.log
```

- In the vi editor, enter `/Current oms configurations can not support` to search for the keyword
- If matching content is found, the OMS configuration is insufficient to support the current cluster scale. Proceed to `3.3` and `3.4` for configuration optimization
- If no matching content is found, analyze other anomalies in the log

### 3.3 View Current Cluster Manager Configuration

Execute the following command to view the current cluster Manager configuration and confirm whether the current configuration parameters match the cluster scale.

```bash
cd ${BIGDATA_HOME}/om-server/om/sbin
sh oms_config_info.sh -q
```

The output will show the current Manager configuration parameters, including Controller Xmx, Xms, heartbeat timeout threshold, and Pms memory configuration. Compare the current configuration with the configuration standard required by the cluster node scale to determine whether optimization is needed.

### 3.4 Optimize Manager Configuration Based on Cluster Node Count

Execute the following command to specify the current cluster node count and optimize the Manager configuration.

```bash
sh oms_config_info.sh -s <node_count>
```

- `<node_count>`: Current cluster node count, for example `1000`

For example:
```bash
sh oms_config_info.sh -s 1000
```

Follow the on-screen prompt, enter "y" to confirm the configuration modification:

```
The following configurations will be modified:
     Module       Parameter         Current               Target 
     Controller   controller.Xmx    4096m             =>  16384m
     Controller   controller.Xms    1024m             =>  8192m
     Controller   controller.node.heartbeat.error.threshold     30000  =>   60000                   
     Pms          pms.mem           8192m             =>  10240m 
Do you really want to do this operation? (y/n):
```

The following message indicates the configuration update is successful:

```
Operation has been completed. Now restarting OMS server.                  [done]
Restarted oms server successfully.
```

Notes:
- During the configuration update process, OMS will automatically restart
- Manager configurations are shared across similar cluster node scales. For example, changing from 100 nodes to 101 nodes does not require refreshing any new configuration items

### 3.5 Collect Fault Information

If the alarm is not cleared after waiting 1 hour following the configuration optimization, collect the fault log information.

- In the FusionInsight Manager interface, select "O&M > Logs > Download"
- In "Services", check "Controller" and click "OK"
- In the upper right corner, set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm generation time, then click "Download"
- Contact O&M personnel and send the collected fault log information

## 4. Common Alarm Fault Handling Solutions

### 4.1 OMS Configuration Insufficient to Support Current Cluster Scale

**Symptoms**:
- modify_manager_param.log shows "Current oms configurations can not support xx nodes"
- Job execution delays, slow service page response
- In severe cases, cluster node Agent or OMS process runs abnormally

**Handling solution**:
1. Log in to the MRS cluster primary management node as the root user
2. Switch to omm user: `su - omm`
3. View current Manager configuration: `cd ${BIGDATA_HOME}/om-server/om/sbin && sh oms_config_info.sh -q`
4. Execute configuration optimization based on actual cluster node count: `sh oms_config_info.sh -s <node_count>`
5. Confirm that OMS restarts successfully
6. Wait 1 hour and check whether the alarm is cleared
7. If the alarm is not cleared, collect logs per `3.5 Collect Fault Information` and contact O&M personnel

### 4.2 Alarm Not Cleared After Configuration Optimization

**Symptoms**:
- oms_config_info.sh configuration optimization has been executed
- OMS has restarted successfully
- Alarm still exists after waiting 1 hour

**Handling solution**:
1. Re-check modify_manager_param.log to confirm whether there are other anomalies
2. Confirm whether the cluster node count was set correctly (whether the actual node count matches the configured node count)
3. Confirm whether OMS restart was successful: check OMS process status
4. Collect Controller service logs (10 minutes before and after the alarm generation time)
5. Contact O&M personnel and send the collected fault log information

### 4.3 OMS Restart Failure

**Symptoms**:
- After executing oms_config_info.sh -s, OMS restart fails
- Interface shows restart unsuccessful

**Handling solution**:
1. Check OMS active/standby node status to confirm whether the primary node is faulty
2. If the primary node OMS restart fails, try executing configuration optimization on the standby node
3. Check whether OMS key directory disk space is sufficient
4. View OMS startup logs to identify the restart failure cause
5. Contact O&M personnel for handling

## 5. Alarm Diagnosis Flow

### 5.1 Diagnosis Flow Chart

```
Start
  |
  v
Obtain hostname from alarm information
  |
  v
Obtain cluster OMS active/standby node information (query-management-node-info)
  |
  v
Log in to MRS cluster primary management node, switch to omm user
  |
  v
View modify_manager_param.log
Search for "Current oms configurations can not support xx nodes"
  |
  +--- Match found ---> Confirm OMS configuration insufficient for current cluster scale
  |                        |
  |                        v
  |                View current Manager configuration (oms_config_info.sh -q)
  |                        |
  |                        v
  |                Optimize configuration based on cluster node count (oms_config_info.sh -s)
  |                        |
  |                        v
  |                Confirm OMS automatic restart successful
  |                        |
  |                        +--- Restart successful ---> Wait 1 hour to check whether alarm is cleared
  |                        |                        |
  |                        |                        +--- Alarm cleared ---> Processing complete
  |                        |                        |
  |                        |                        +--- Alarm not cleared ---> Collect fault logs, contact O&M personnel
  |                        |
  |                        +--- Restart failed ---> Check OMS active/standby status and disk space, identify restart failure cause
  |
  +--- No match found ---> Analyze other anomalies in the log
                            |
                            v
                    Collect Controller service logs, contact O&M personnel
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis Conclusion | Recommended Operation |
|----------|----------|
| OMS configuration insufficient for cluster scale | Execute oms_config_info.sh -s to optimize configuration based on cluster node count |
| Alarm not cleared after configuration optimization | Check whether configuration is correct, collect fault logs and contact O&M personnel |
| OMS restart failure | Check active/standby status and disk space, identify restart failure cause |
| No matching keyword in log | Analyze other log anomalies, collect Controller logs and contact O&M personnel |
