# TCP Temporary Port Usage Rate Exceeds Threshold (12052) Log Information Description

## I. Alarm Type

| Item | Content |
|------|------|
| Alarm Name | TCP temporary port usage rate exceeds the threshold |
| Alarm ID | 12052 |
| Alarm Type | System resource monitoring |
| Alarm Severity | Major (default threshold 70%), Critical (default threshold 85%) |
| Monitor Metric | `dev_temp_port_usage` (TCP temporary port usage rate) |

---

## II. Log Directory

### 2.1 Log Priority

> When analyzing TCP temporary port exhaustion, it is recommended to view logs in the following priority order:
>
> | Priority | Log Type | Description |
> |--------|----------|------|
> | 1 | System logs | System-level port/connection related log information (`/var/log/messages`) |
> | 2 | OMS/Controller logs | MRS management plane runtime logs |
> | 3 | Component logs | Business component logs (HDFS/Yarn/DBService etc.) that report `Address already in use` |

### 2.2 Log Paths

| Log File | Path | Purpose | Priority |
|----------|------|------|--------|
| System logs | `/var/log/messages*` | System-level port/connection errors | 1 |
| OMS logs | `/var/log/Bigdata/omm/` | OMS runtime logs | 2 |
| Controller logs | `/var/log/Bigdata/controller/` | Controller runtime logs | 2 |
| Component logs | `/var/log/Bigdata/<service_name>/` | Component logs that report connection/port errors | 3 |

## III. Log Time Format

### 3.1 System Log Format

```
Dec 20 10:30:15 hostname process_name[pid]: message
```

| Field | Description | Example |
|------|------|------|
| Date and time | Month Day Hour:Minute:Second | `Dec 20 10:30:15` |
| Hostname | Host name | `hostname` |
| Process info | Process name and PID | `process_name[pid]` |
| Message content | Log body | `message` |

### 3.2 Component Log Format

```
2026-07-07 20:54:25,171 WARN [thread] component: message
```

| Field | Description | Example |
|------|------|------|
| Date and time | Year-Month-Day Hour:Minute:Second,Millisecond | `2026-07-07 20:54:25,171` |
| Level | Log level | `WARN` / `ERROR` |
| Thread | Thread name | `[Thread-1]` |
| Message content | Log body | `message` |

## IV. Abnormal Error Keywords

### 4.1 Port Exhaustion Related Keywords

| Keyword | Meaning | Severity |
|--------|------|----------|
| `Cannot assign requested address` | No available local port, port exhaustion | 🔴 P0 |
| `Address already in use` | Port already occupied | 🔴 P0 |
| `No buffer space available` | No buffer space available (port backlog) | 🟠 P1 |
| `Connection refused` | Connection refused (backlog full or service down) | 🟠 P1 |
| `Too many open files` | File descriptor exhaustion (may accompany port exhaustion) | 🔴 P0 |

### 4.2 Connection State Related Keywords

| Keyword | Meaning | Severity |
|--------|------|----------|
| `TIME_WAIT` | Connection in TIME_WAIT state, waiting to be recycled | 🟡 P2 |
| `CLOSE_WAIT` | Connection not closed by the application | 🟠 P1 |
| `ESTABLISHED` | Established connection | 🟢 P3 |
| `net.ipv4.ip_local_port_range` | Local temporary port range | 🟢 P3 |

## VII. Analysis Steps and Root Cause Determination

### Step 1: Confirm the alarm and node status

- Collect `network-io`, `process-network-connection` and, when available, `port-check` to confirm the current connection and port state of the alarm node.
- Check whether the node also has the `12053` file-handle alarm or `12027` PID alarm; handle companion alarms first.

### Step 2: Judge the cause type

| Symptom | Possible Cause | Priority |
|--------|----------------|----------|
| TIME_WAIT count > 5000 | Too many short connections / TIME_WAIT reuse not enabled | High |
| ESTABLISHED count approaches the port range | Normal business growth / connection not released | Medium |
| Port range too small (e.g. 32768-60999 default) | Improper configuration | High |
| Specific IP connection count abnormally high | Possible attack/anomaly | High |
| CLOSE_WAIT continuously growing | Application not closing connections (connection leak) | High |
| `No buffer space available` in logs | Kernel buffer/socket backlog exhaustion | High |

### Step 3: Verify against logs

- Confirm the root cause with the log search commands in section V:
  - `Cannot assign requested address` / `Address already in use` → port exhaustion confirmed
  - `No buffer space available` → kernel socket buffer exhaustion
  - None found → the alarm may have recovered; suggest continuous observation

## VIII. Common Root Causes and Repair Suggestions

### 8.1 TIME_WAIT accumulation

**Symptom:** TIME_WAIT state connection count is very high (>1000); temporary port range is small

**Repair suggestions (must be executed manually after user confirmation):**

```bash
# Increase temporary port range
sysctl -w net.ipv4.ip_local_port_range="1024 65535"

# Enable TIME_WAIT reuse
sysctl -w net.ipv4.tcp_tw_reuse=1

# Shorten TIME_WAIT duration
sysctl -w net.ipv4.tcp_fin_timeout=30
```

> Persist the parameters with `sysctl -p` after confirmation, and evaluate the impact of the port range on the firewall/security group.

### 8.2 Connection count too high (normal business growth)

**Symptom:** ESTABLISHED connection count is very high; business indeed has a large number of clients

**Repair suggestions:**
- Expand temporary port range
- Load balancing to disperse connections
- Add servers

### 8.3 Short connections frequently created

**Symptom:** Large number of short connections; both TIME_WAIT and CLOSE_WAIT are numerous

**Repair suggestions:**
- Use connection pool / long connections
- Adjust TCP parameters
- Optimize application connection logic

### 8.4 Port exhaustion (most severe)

**Symptom:** Unable to establish new connections; errors `Cannot assign requested address` or `Address already in use`

**Repair suggestions:**
- Immediately increase port range
- Check for port leaks (use `process-network-detail` with a PID, or `ss -tan | wc -l` on the node)
- Restart the problematic process

### 8.5 File handle exhaustion accompanying the port alarm

**Symptom:** Logs contain `Too many open files`

**Repair suggestions:**
- Manually execute `ulimit -n` on the alarm node to view the handle upper limit
- Increase the `nofile` limit appropriately; investigate the handle usage of abnormal processes
- Refer to the 12053 Host File Handle alarm diagnosis for details

## X. Alarm Recovery Description

After the repair is completed, the system will automatically check the TCP temporary port usage rate in the next monitoring period to confirm whether the alarm is recovered. If the business keeps creating short connections, active observation is required after recovery to avoid a recurring alarm.
