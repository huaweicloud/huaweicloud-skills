# Process Failure (12007) Alarm Diagnosis Skill

## Alarm Mechanism Description

Alarm location info format: `service name;role name;host name;`, e.g. `HDFS;NameNode;host1;`

## Diagnosis Flow

```
Step 1: Confirm alarm location info and current process status
  |
  +-- Alarm recovered (process status GOOD) -> Check for ALM-12006 accompanying alarm
  |     |
  |     +-- ALM-12006 present -> Handle 12006 first (NodeAgent process exception)
  |     +-- No ALM-12006 -> Check process logs to locate the historical fault cause
  |
  +-- Alarm ongoing (process status BAD/CONCERNING)
        |
        +-- Many 12007 alarms in the same period -> Step 2: Batch alarm troubleshooting
        |     |
        |     +-- Host fault / ALM-12006 -> Handle host/NodeAgent first
        |     +-- Host normal -> Directory permission / deleted files -> Repair and wait for recovery
        |
        +-- Single/few alarms -> Step 3: Single instance fault troubleshooting
              |
              +-- Directory permission abnormal -> Repair permission -> Wait for recovery
              +-- Disk space insufficient -> Step 4: Disk troubleshooting
              +-- Process abnormal -> Step 5: Component process fault handling
              +-- Not located -> Step 6: Health check interface/script troubleshooting
```

## Diagnosis Steps

### Step 1: Confirm Alarm Location Info and Current Process Status

Get the location info (service name, role name, host name) from the alarm details and confirm the current process status:

```bash
# View the omm process tree on the node
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=omm-process-tree' \
  -p 'node_name=<node_name>'

# View instance running status (Manager API proxy, returns runningStatus/haStatus)
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/clusters/<cluster_id>/services/<service_name>/instances'

# View process status (Manager API proxy, returns processStatus/processId)
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/clusters/<cluster_id>/hosts/<node_name>/processes'
```

**Analysis**:

| Actual result | Conclusion | Next step |
|---------------|------------|-----------|
| Target process has recovered | Alarm recovered, investigate historical cause | Check accompanying alarms and process logs |
| Target process missing or status abnormal | Alarm ongoing | Judge by alarm count |
| Many 12007 alarms in the same period | Possibly directory/file deleted or permission modified | Step 2 |
| Single/few alarms | Single instance fault | Step 3 |

---

### Step 2: Batch Alarm Troubleshooting

Many 12007 alarms in the same period, possible causes and troubleshooting order:

#### 2.1 Check Whether It Is a Host Issue

When many 12007 alarms are concentrated on the same host, check the host itself first:

```bash
# Query host status (Manager API proxy)
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/clusters/<cluster_id>/hosts'

# Query alarms on this host, check for ALM-12006 NodeAgent process exception (Manager API proxy)
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/clusters/<cluster_id>/alarms'

# Check node connectivity
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=omm-process-tree' \
  -p 'node_name=<node_name>'
```

| Phenomenon | Conclusion |
|------------|------------|
| Host status abnormal (e.g. critical/unknown) | Host fault causes all processes on the host unavailable, handle host issue first |
| ALM-12006 alarm present | NodeAgent exception causes all process health checks to fail, handle 12006 first |
| Node reachable but process tree empty | Processes fully unavailable, possibly directory/file deleted or permission modified |

#### 2.2 Check Installation Directory Permission and File Integrity

After excluding host issues, check whether files in the installation directory were deleted or permissions modified. Normal state should be `omm:ficommon 750`.

---

### Step 3: Single Instance Fault Troubleshooting

#### 3.1 Check for ALM-12006 NodeAgent Process Exception Accompanying Alarm

```bash
# Query current alarm list (Manager API proxy)
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/clusters/<cluster_id>/alarms'
```

Check whether an `ALM-12006 NodeAgent process exception` alarm exists in the returned results:
- **Yes**: Handle the 12006 alarm first; 12007 is usually a side effect of 12006.
- **No**: Continue to 3.2.

#### 3.2 Check Instance Process Directory Permission (SSH to the target node required)

Check whether the user, user group, and permission of the alarm role installation directory are normal. Normal state should be `omm:ficommon 750`.

**Installation directory reference per role**:

| Service | Role | Installation directory (under `$BIGDATA_HOME`) |
|---------|------|------------------------------------------------|
| HDFS | NameNode | `FusionInsight_Current/1_8_NameNode/etc` |
| Others | — | `FusionInsight_Current/1_8_<role name>/etc` |

> The `1_8` in the directory is the instance number, which may differ between clusters; use the actual value.

**Analysis**:

| Actual result | Conclusion | Next step |
|---------------|------------|-----------|
| Permission abnormal (not omm:ficommon 750) | Permission modified, process cannot work | Repair permission and wait 5 minutes |
| Permission normal | Continue troubleshooting | Step 4 |

---

### Step 4: Disk Space Troubleshooting

```bash
# Query current alarm list, confirm whether ALM-12017 is present (Manager API proxy)
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/clusters/<cluster_id>/alarms'

# View node disk IO
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-io' \
  -p 'node_name=<node_name>'
```

**Analysis**:

| Phenomenon | Conclusion | Next step |
|------------|------------|-----------|
| ALM-12017 alarm present | Disk space insufficient causes process fault | Handle 12017 first, wait 5 minutes after clearing |
| Disk usage > 85% | Disk space about to be insufficient | Clean up disk space |
| Disk normal | Not a disk issue | Step 5 |

---

### Step 5: Component Process Fault Handling

Based on the service name and role name in the alarm location info, refer to the corresponding component process fault handling document:

| Component | Handling document |
|-----------|-------------------|
| DBService | [12007/DBService.md](12007/DBService.md) |
| KrbServer | [12007/KrbServer.md](12007/KrbServer.md) |
| LdapServer | [12007/LdapServer.md](12007/LdapServer.md) |

After handling, wait 5 minutes to check whether the alarm is cleared.

---

### Step 6: Health Check Interface/Script Troubleshooting

If Steps 3-5 do not locate the issue, check the instance health check configuration and interface/script.

#### 6.1 View Instance Health Check Status via Manager API

```bash
# Query instance health check result (Manager API proxy)
python3 lakewatch_api_client.py -a access_manager_get \
  -p 'cluster_id=<cluster_id>' \
  -p 'target_url=api/v2/clusters/<cluster_id>/services/<service_name>/instances/<instance_name>/healthcheck'
```

#### 6.2 View Health Check Configuration (SSH to the target node required)

Health check configuration is in the `healthMonitor.properties` section of `$BIGDATA_HOME/components/current/<service name>/configurations.xml`. Key fields:

| Config item | Description | Example |
|-------------|-------------|---------|
| `monitor.type` | Monitor type (PID/HTTP/HTTPS/JMX/SCRIPT, comma-combinable) | `PID,HTTPS` |
| `monitor.info` | Health check URL or script path | `https://host:port/dfshealth.html` |
| `monitor.pidFileLocation` | PID file path | `/opt/huawei/Bigdata/tmp/hadoop-omm-namenode.pid` |

#### 6.3 Troubleshoot by Monitor Type (SSH to the target node required)

Troubleshoot according to `monitor.type`:

**PID type**: Check whether the PID file exists and the process is alive:
```bash
cat <monitor.pidFileLocation>
ps -p <PID> -o pid,comm
```

| Phenomenon | Conclusion |
|------------|------------|
| PID file missing | Process not started or PID file deleted |
| PID file exists but process missing | Process crashed, check process logs |
| PID file exists and process alive | False positive, check other monitor types |

**HTTP/HTTPS type**: Manually request the health check URL to confirm reachability:
```bash
curl -k <monitor.info>
```

| Phenomenon | Conclusion |
|------------|------------|
| Returns 200 OK | Interface normal, possibly transient network jitter |
| Connection timeout | Process hung or port not listening, check process status |
| Connection refused | Process not started or crashed |
| Non-200 status code | Internal exception, check process logs |

**SCRIPT type**: Manually execute the health check script, observe output and exit code:
```bash
bash <monitor.info>
echo $?
```

| Phenomenon | Conclusion |
|------------|------------|
| Exit code 0 | Script normal, possibly transient fault |
| Exit code non-zero | Check script output to locate the specific fault cause |

## Common Root Causes and Repair Suggestions

### 1. Instance Process Abnormal

**Features**: Single process fault, directory permission and disk space normal

**Repair suggestions**:
- View process running logs to locate the crash cause
- Check process GC logs for OOM (GC log path: see the process name -> GC log mapping table in 12016.md)
- Check whether the process PID file was deleted
- Manually restart the process (via Manager UI or command line)

**Notes**:
- After a process fault, NodeAgent automatically attempts to restart; if the auto-restart succeeds, the alarm clears automatically
- Check logs before manual restart to locate the cause and avoid repeated restarts
- Restarting a service briefly affects business availability

### 2. Directory Permission Abnormal

**Features**: User/user group/permission of the process installation directory is not `omm:ficommon 750`; or many 12007 alarms in the same period

**Repair suggestions**:
- Run `chmod 750 <folder_name>` and `chown omm:ficommon <folder_name>` to repair permission
- Investigate whether an O&M operation accidentally modified directory permission

**Notes**:
- Do not use recursive modification (`-R`) for batch permission repair; it may affect special permissions of subdirectories
- Wait 5 minutes after repair for the health check to re-detect

### 3. Disk Space Insufficient

**Features**: ALM-12017 accompanying alarm; or disk usage > 85%

**Repair suggestions**:
- Clean up disk space (log files, temporary files, etc.)
- Expand the disk

**Notes**:
- Before cleaning large log files, confirm the file is not held by a process; recommended to empty with `> file` first, then delete
- After disk space recovers, the process may auto-restart; wait 5 minutes and observe

### 4. Health Check Interface/Script Abnormal

**Features**: Process actually running normally but health check keeps reporting fault

**Repair suggestions**:
- Check whether the health check URL is reachable (HTTPS type)
- Check health check script execution permission and content (SCRIPT type)
- Check whether the PID file path is correct (PID type)
- Check whether the JMX port is reachable (JMX type)

**Notes**:
- Health check interface unreachable does not necessarily mean process fault; it may be a network issue or firewall rule change
- `monitor.timeout` default is 60000ms; if the process starts slowly and times out, increase it appropriately

### 5. Installation Directory File Deleted

**Features**: Many 12007 alarms in the same period; `No such file or directory` in logs

**Repair suggestions**:
- Restore deleted files (from backup or copy from a normal node)
- Reinstall the faulty component instance

**Notes**:
- Confirm permission and ownership after file restoration
- If files cannot be restored, uninstall and reinstall the instance via Manager UI
