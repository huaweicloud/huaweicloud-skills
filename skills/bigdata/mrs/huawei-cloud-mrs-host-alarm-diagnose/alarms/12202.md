# Process Memory Usage Exceeds Threshold Alarm Diagnosis

## 1. Diagnosis Overview

This document covers the diagnosis and handling of the **Process Memory Usage Exceeds Threshold (12202)** alarm. This alarm indicates that the memory usage of the OMS main process exceeds 90% of the maximum memory (default threshold), which may affect OMS process performance or even cause out-of-memory errors that make the process unavailable.

This alarm is applicable only to MRS 3.3.1-LTS and later versions.

Alarm basic information:

| Item | Content |
|------|---------|
| Alarm ID | 12202 |
| Alarm Name | Process Memory Usage Exceeds Threshold |
| Alarm Severity | Important |
| Alarm Type | System resource alarm |
| Auto-clearable | Yes |
| System Impact | Excessive memory usage of OMS main processes affects their performance, and may even cause out-of-memory errors that make OMS main processes unavailable, resulting in slow or failed OMS task execution |

Alarm parameter description:

| Parameter Name | Description |
|----------------|-------------|
| Source | Name of the cluster where the alarm was generated |
| Service Name | Name of the service where the alarm was generated |
| Role Name | Name of the role where the alarm was generated |
| Host Name | Host name where the alarm was generated |
| Additional Information | Trigger Condition: the current system metric value meets the custom alarm setting condition |

## 2. Executable Operations

This section provides the operations that can be executed during alarm analysis.

### 2.1 Check Whether the Alarm Cluster Is a Virtual Machine

Execute the following command. If the result is `none`, it indicates a physical machine; if the output is `kvm`, `vmware`, `oracle`, or other virtualization platform names, it indicates a virtual machine environment.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=systemd-detect-virt' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.2 Obtain Cluster OMS Active/Standby Node Information

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.3 Obtain OMS Key Directories

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.4 View System Memory Usage

Execute the following command to view the system memory usage on the alarm node, including total memory, used memory, available memory, and other information.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=memory-usage' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.5 View Process Memory Usage

Execute the following command to view the memory usage of each process on the alarm node, focusing on processes with high memory usage.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=high-cpu-processes' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.6 View Process Detailed Information

Execute the following command to view detailed process information on the alarm node, including process PID, CPU usage, memory usage, etc.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=high-memory-process' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

## 3. Non-Executable Operations

This section provides the operations that cannot be executed through the API during alarm analysis (i.e., commands that require logging into the node for manual execution).

### 3.1 View Memory Usage Details of the Alarm Process

Based on the process name recorded in the alarm information, log in to the alarm host and execute the following command to view the memory usage details of that process:

```bash
ps -p <PID> -o pid,vsz,rss,pcpu,pmem,cmd
```

Parameter description:
- `<PID>`: PID of the alarm process, which can be obtained via `ps aux | grep <process_name>`

Check the RSS (physical memory actually used) and VSZ (virtual memory) values in the command result:
- If the RSS value is close to or exceeds the maximum memory configured for the process, it confirms that the process memory usage is indeed too high
- If the RSS value is much smaller than the maximum memory configured for the process, it may indicate a monitoring metric anomaly or unreasonable threshold configuration

### 3.2 Check Process Memory Configuration

Review the OMS process memory configuration file to confirm whether the maximum memory configuration is reasonable. The OMS process memory configuration is typically located in the process startup configuration file, such as JVM parameter settings.

- Log in to the alarm host
- Find the OMS process configuration file, for example:
  ```bash
  # Find OMS process configuration directory
  ls -la ${OMS_RUN_PATH}/workspace/
  # View process startup configuration
  cat ${OMS_RUN_PATH}/workspace/oms/launcher/start_oms_agent.sh | grep -i "Xmx\|MaxMetaspaceSize"
  ```
- Check the values of the `-Xmx` (maximum heap memory) and `-XX:MaxMetaspaceSize` (maximum metaspace size) parameters

Determine whether the memory configuration is reasonable:
- If the `-Xmx` value is too small, it may cause high memory usage during normal process operation
- If the `-Xmx` value is too large, it may cause the process to consume excessive system memory

### 3.3 Modify Process Memory Configuration

If the process memory configuration is confirmed to be unreasonable, contact O&M personnel to modify the memory configuration of the corresponding process:

- Edit the process startup configuration file to adjust the `-Xmx` and `-XX:MaxMetaspaceSize` parameters
- For example:
  ```bash
  # Back up the configuration file before modification
  cp ${OMS_RUN_PATH}/workspace/oms/launcher/start_oms_agent.sh ${OMS_RUN_PATH}/workspace/oms/launcher/start_oms_agent.sh.bak
  # Edit the configuration file to adjust JVM memory parameters
  vi ${OMS_RUN_PATH}/workspace/oms/launcher/start_oms_agent.sh
  ```
- After modification, restart the process for the configuration to take effect

### 3.4 Restart the Process Reporting the Alarm

After modifying the memory configuration or when you need to restore normal process operation, restart the process that reported the alarm:

```bash
# Log in to the alarm host as the omm user
su - omm

# Restart the OMS process (adjust according to the actual process name)
${OMS_RUN_PATH}/workspace/oms/launcher/restart_oms_agent.sh
```

Parameter description:
- `${OMS_RUN_PATH}`: OMS runtime path, default is `/opt`

After restarting, wait 10 minutes and observe whether the alarm is cleared.

### 3.5 Collect Fault Log Information

If the alarm is not automatically cleared or further analysis is needed, collect fault log information:

- On the FusionInsight Manager page, navigate to "Operation and Maintenance > Log > Download"
- Check "OmmServer" for the target cluster in "Services"
- Click the edit button in the upper right corner to set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm occurrence time
- Click "Download"
- Contact O&M personnel and send the collected fault log information

## 4. Common Fault Handling Solutions

### 4.1 Unreasonable Process Memory Configuration

**Symptoms:**
- OMS process memory usage consistently exceeds 90%
- The `-Xmx` configuration value is too small, causing high memory usage during normal operation
- System physical memory is sufficient, and there is room to adjust the maximum process memory configuration

**Solution:**
1. Log in to the alarm host and check the process memory configuration (refer to `3.2 Check Process Memory Configuration`)
2. Contact O&M personnel to modify the process memory configuration and appropriately increase the `-Xmx` parameter value (refer to `3.3 Modify Process Memory Configuration`)
3. Restart the process that reported the alarm (refer to `3.4 Restart the Process Reporting the Alarm`)
4. Wait 10 minutes and observe whether the alarm is cleared on the UI
5. If the alarm is cleared, the handling is complete; otherwise, execute `3.5 Collect Fault Log Information`

### 4.2 Process Memory Leak

**Symptoms:**
- OMS process memory usage keeps increasing without automatic recovery
- After restarting the process, memory usage returns to normal but exceeds the threshold again after running for a period
- The process RSS value keeps rising with no downward trend

**Solution:**
1. Collect process memory usage information, including RSS value change trends from multiple samples
2. Restart the process that reported the alarm (refer to `3.4 Restart the Process Reporting the Alarm`)
3. Wait 10 minutes and observe whether the alarm is cleared on the UI
4. If the alarm is cleared but recurs later, collect fault logs (refer to `3.5 Collect Fault Log Information`)
5. Send the log information and memory usage trends to O&M personnel to analyze the memory leak cause

### 4.3 Process Running Abnormally

**Symptoms:**
- OMS process memory usage suddenly spikes far above normal levels
- The process may also have abnormal CPU usage
- OMS task execution slows down or fails

**Solution:**
1. View the process memory usage details (refer to `3.1 View Memory Usage Details of the Alarm Process`) to confirm the memory usage anomaly
2. Restart the process that reported the alarm (refer to `3.4 Restart the Process Reporting the Alarm`)
3. Wait 10 minutes and observe whether the alarm is cleared on the UI
4. If the alarm is not cleared, collect fault logs (refer to `3.5 Collect Fault Log Information`)
5. Contact O&M personnel and send the collected fault log information

### 4.4 Insufficient System Memory Resources

**Symptoms:**
- Total system physical memory is insufficient, with multiple processes competing for memory resources
- System available memory (free) remains persistently low
- Swap usage indicates system memory pressure

**Solution:**
1. View system memory usage (refer to `2.4 View System Memory Usage`) to confirm whether system memory is sufficient
2. View process memory usage (refer to `2.5 View Process Memory Usage`) to analyze memory consumption of each process
3. If system memory is insufficient, consider scaling up node memory or migrating some services to other nodes
4. If an individual process has abnormal memory consumption, refer to `4.2 Process Memory Leak` or `4.3 Process Running Abnormally` for handling

## 5. Alarm Diagnosis Process

### 5.1 Diagnosis Flowchart

```
Start
  |
  v
Obtain host name and process name from alarm information
  |
  v
Check whether the alarm cluster is a virtual machine (systemd-detect-virt)
  |
  +--- Virtual machine ---> View system memory usage
  |                            |
  |                            v
  |                      View process memory usage
  |
  +--- Physical machine ---> Obtain cluster OMS active/standby node information
                              |
                              v
                       View system memory usage
                              |
                              v
                       View process memory usage
  |
  v
View memory usage details of the alarm process
  |
  +--- Memory usage exceeds threshold ---> Check process memory configuration
  |                                          |
  |                                          +--- Configuration unreasonable ---> Modify process memory configuration
  |                                          |                                         |
  |                                          |                                         v
  |                                          |                                 Restart alarm process
  |                                          |
  |                                          +--- Configuration reasonable ---> Determine whether it is a memory leak
  |                                                                              |
  |                                                                              +--- Is memory leak ---> Restart process + Collect logs
  |                                                                              |
  |                                                                              +--- Not memory leak ---> Restart process
  |
  +--- Memory usage does not exceed threshold ---> Collect fault logs, contact O&M personnel
  |
  v
Wait 10 minutes, observe whether alarm is cleared
  |
  +--- Alarm cleared ---> Handling complete (end)
  |
  +--- Alarm not cleared ---> Collect fault logs, contact O&M personnel
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the above diagnosis process, output one of the following conclusions:

| Diagnosis Conclusion | Recommended Action |
|----------------------|---------------------|
| Unreasonable process memory configuration | Modify memory configuration and restart process |
| Process memory leak | Restart process and collect logs for analysis |
| Process running abnormally | Restart process and collect logs for analysis |
| Insufficient system memory resources | Scale up node memory or migrate services |
| Alarm persists after handling | Collect fault logs and contact O&M personnel |
