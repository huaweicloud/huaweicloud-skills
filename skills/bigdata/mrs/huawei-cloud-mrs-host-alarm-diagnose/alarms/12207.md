# Slow Disk Handling Timeout Alarm Diagnosis

## 1. Diagnosis Overview

This document covers the diagnosis and handling of the **Slow Disk Handling Timeout (12207)** alarm. When the slow disk detection switch is enabled, the system checks the slow disk handling status every 10 minutes by default. If a disk or node remains in any of the following states for more than 10 hours without a status change, it is considered a handling timeout and this alarm is reported.

- Disk: Auto-isolation aborted, isolated, isolation failed, de-isolation failed.
- Node: Isolated, isolation failed, de-isolation failed, node startup failed, de-isolated.

When the status of the timed-out node or disk changes, the alarm is automatically cleared. This section is applicable only to MRS 3.3.1-LTS and later versions.

Alarm basic information:

| Item | Content |
|------|---------|
| Alarm ID | 12207 |
| Alarm Name | Slow Disk Handling Timeout |
| Alarm Severity | Important |
| Alarm Type | Service fault alarm |
| Auto-clearable | Yes |
| System Impact | Disks or nodes in isolation state that cannot be restored in a timely manner may affect the operation of big data components, thereby impacting user business usage |

## 2. Executable Operations

This section provides the operations that can be executed during alarm analysis.

### 2.1 Obtain Cluster OMS Active/Standby Node Information

Obtain the cluster OMS active/standby node information to determine whether the alarm node is the OMS active node and for subsequently logging in to the active OMS node to view controller logs.

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.2 Obtain Node IP

Obtain the IP addresses of the alarm reporting node and the OMS active node for subsequent connectivity checks.

```bash
python3 lakewatch_api_client.py -a query-node-ip \
  -p 'cluster_id=<cluster_id>' \
  -p 'nodeName=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.3 Alarm Node Connectivity Check

Check the network connectivity of the alarm node to confirm whether the node is reachable.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=network-connectivity-test' \
  -p 'env={"TARGET_IP":"<alarm_node_ip>"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_node_ip>`: Alarm node IP, obtained from the `2.2 Obtain Node IP` section
- `<node_name>`: Cluster OMS active node, obtained from the `2.1 Obtain Cluster OMS Active/Standby Node Information` section

### 2.4 View Controller Logs (Check Slow Disk Handling Timeout Cause)

View the controller logs on the active OMS node to analyze the slow disk handling timeout cause and check for obvious error messages.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/controller/' \
  -p 'log_file_name=controller.log*' \
  -p 'keywords=["ERROR","Exception","timeout","isolate","isolation","fence","unfence"]' \
  -p 'log_type=local' \
  -p 'node_name=<oms_master_node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm occurrence time
- `<oms_master_node_name>`: OMS active node name, obtained from `2.1 Obtain Cluster OMS Active/Standby Node Information`

### 2.5 View NodeAgent Logs (Check Slow Disk Handling Timeout Cause)

View the agent logs on the alarm reporting node to analyze the slow disk handling timeout cause and check for obvious error messages.

```bash
python3 lakewatch_api_client.py -a collect_alarm_log_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'alarm_time=<alarm_time>' \
  -p 'log_directory=/var/log/Bigdata/nodeagent/agentlog/' \
  -p 'log_file_name=agent*' \
  -p 'keywords=["ERROR","Exception","timeout","isolate","isolation","fence","unfence"]' \
  -p 'log_type=local' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<alarm_time>`: Alarm occurrence time
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

### 2.6 Check Whether the Alarm Disk Name Exists in `df -h` Output

Execute the following command. If the command result contains the alarm disk name, the alarm disk exists; otherwise, it does not.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from alarm information

## 3. Non-Executable Operations

This section provides the operations that cannot be executed through the API during alarm analysis (i.e., commands that require logging into the node for manual execution).

### 3.1 View Alarm Detailed Information

View the alarm detailed information on the FusionInsight Manager page:

1. Log in to the FusionInsight Manager interface
2. Navigate to "Operation and Maintenance > Alarm > Alarm" and expand the detailed information of this alarm in the alarm list
3. View and record the hostname, disk name, and slow disk isolation description reported by the alarm
4. Record the source, service name, and role name from the location information

Judgment criteria:
- Record the hostname, disk name, and slow disk isolation description from the detailed information for subsequent log analysis
- Based on the disk name, determine whether the alarm involves disk isolation timeout or node isolation timeout

### 3.2 Manually Execute Slow Disk or Node Isolation/De-isolation Operations

When the Controller logs or Agent logs contain obvious error messages, contact O&M personnel to handle the fault and manually execute slow disk or node operation commands.

**Disk Isolation/De-isolation:**

Log in to the alarm reporting node as the root user and execute the slow disk isolation or de-isolation command (the specific command depends on the MRS version and disk status). After the command completes, wait 5 minutes and check whether the alarm is cleared.

- If the disk status is "Isolated", execute the de-isolation operation
- If the disk status is "Isolation Failed" or "Auto-isolation Aborted", re-execute the isolation operation
- If the disk status is "De-isolation Failed", re-execute the de-isolation operation

**Node Isolation/De-isolation:**

Log in to the active OMS node as the root user and execute the node isolation or de-isolation command (the specific command depends on the MRS version and node status). After the command completes, wait 5 minutes and check whether the alarm is cleared.

- If the node status is "Isolated", execute the de-isolation operation
- If the node status is "Isolation Failed", re-execute the isolation operation
- If the node status is "De-isolation Failed", re-execute the de-isolation operation
- If the node status is "Node Startup Failed", re-execute the node startup operation
- If the node status is "De-isolated", confirm whether the node status has returned to normal

### 3.3 Collect Fault Information

When the above handling steps cannot clear the alarm, collect fault log information:

1. On the FusionInsight Manager page, navigate to "Operation and Maintenance > Log > Download"
2. Check "Controller" and "NodeAgent" in "Services"
3. In "Hosts", check the active and standby OMS nodes and the alarm reporting node host, then click "OK"
4. Click the edit button in the upper right corner to set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm occurrence time
5. Click "Download"
6. Contact O&M personnel and send the collected fault log information

## 4. Common Fault Handling Solutions

### 4.1 Disk Isolation Operation Timeout

**Symptoms:**
- The alarm detailed information shows the disk status as "Isolated", "Isolation Failed", or "Auto-isolation Aborted"
- Controller logs show disk isolation-related operations timing out or failing
- The disk remains in isolation state for an extended period without recovery

**Solution:**
1. View the Controller logs to confirm the specific cause of the disk isolation timeout
2. View the `df -h` output to confirm whether the alarm disk exists
3. Based on the current disk status, manually execute the corresponding isolation or de-isolation operation
4. Wait 5 minutes after the command completes and check whether the alarm is cleared
5. If not cleared, collect fault log information and contact O&M personnel

### 4.2 Node Isolation Operation Timeout

**Symptoms:**
- The alarm detailed information shows the node status as "Isolated", "Isolation Failed", "De-isolation Failed", "Node Startup Failed", or "De-isolated"
- Controller logs show node isolation-related operations timing out or failing
- The node remains in isolation state for an extended period without recovery

**Solution:**
1. View the Controller logs to confirm the specific cause of the node isolation timeout
2. View the NodeAgent logs to confirm whether there are errors on the node side
3. Based on the current node status, manually execute the corresponding isolation or de-isolation operation
4. Wait 5 minutes after the command completes and check whether the alarm is cleared
5. If not cleared, collect fault log information and contact O&M personnel

### 4.3 Disk/Node De-isolation Failed

**Symptoms:**
- The alarm detailed information shows the disk or node status as "De-isolation Failed" or "De-isolation Failed"
- Controller logs or Agent logs show the de-isolation operation failed
- The disk or node cannot recover from the isolation state

**Solution:**
1. View the Controller logs and NodeAgent logs to confirm the specific cause of the de-isolation failure
2. Check the alarm node connectivity to confirm whether the node is reachable
3. Re-execute the de-isolation operation
4. Wait 5 minutes after the command completes and check whether the alarm is cleared
5. If not cleared, collect fault log information and contact O&M personnel

### 4.4 Alarm Not Automatically Cleared

**Symptoms:**
- After handling, the disk or node status has changed
- The alarm still exists and has not been cleared

**Solution:**
1. Confirm whether the current disk or node status has returned to normal
2. Wait for the next system detection cycle (10 minutes) and confirm whether the alarm is automatically cleared
3. If still not cleared, collect fault log information and contact O&M personnel

## 5. Alarm Diagnosis Process

### 5.1 Diagnosis Flowchart

```
Start
  |
  v
Obtain hostname, disk name, and slow disk isolation description from alarm information
  |
  v
Obtain cluster OMS active/standby node information, identify the OMS active node
  |
  v
Check alarm node connectivity (ping)
  |
  +--- Ping failed ---> Contact network/hardware administrator to investigate node fault
  |                            |
  |                            v
  |                     Provide diagnosis conclusion and handling solution
  |                            |
  v                            v
Ping successful               End
  |
  v
View Controller logs (active OMS node), check slow disk handling timeout cause
  |
  +--- Obvious errors ---> Contact O&M personnel, manually execute slow disk/node operation commands
  |                                |
  |                                v
  |                       Wait 5 minutes, observe whether alarm is cleared
  |                                |
  |                                +--- Cleared ---> Handling complete
  |                                |
  |                                +--- Not cleared ---> Collect fault logs, contact O&M personnel
  |
  +--- No obvious errors ---> View NodeAgent logs (alarm node), check slow disk handling timeout cause
                                    |
                                    +--- Obvious errors ---> Contact O&M personnel, manually execute slow disk/node operation commands
                                    |                                |
                                    |                                v
                                    |                       Wait 5 minutes, observe whether alarm is cleared
                                    |                                |
                                    |                                +--- Cleared ---> Handling complete
                                    |                                |
                                    |                                +--- Not cleared ---> Collect fault logs, contact O&M personnel
                                    |
                                    +--- No obvious errors ---> Collect fault logs, contact O&M personnel
  |
  v
End (alarm cleared)
```

### 5.2 Diagnosis Conclusion Output

Based on the above diagnosis process, output one of the following conclusions:

| Diagnosis Conclusion | Recommended Action |
|----------------------|---------------------|
| Disk isolation operation timeout | Manually execute disk isolation/de-isolation operation, wait for alarm to clear |
| Node isolation operation timeout | Manually execute node isolation/de-isolation operation, wait for alarm to clear |
| Disk/node de-isolation failed | Check node connectivity, re-execute de-isolation operation |
| Alarm node unreachable | Contact network/hardware administrator to investigate node fault |
| Alarm persists after handling | Collect fault logs, contact O&M personnel |
