# `Device Partition Lost` (12014) Alarm Diagnosis Skill

## 1. Diagnosis Overview

This document primarily covers the diagnosis and handling of the **Device Partition Lost (12014)** alarm. Device partition loss typically refers to the partition of a device that mounts service directories being lost due to device removal, device going offline, partition deletion, or other reasons, which may cause data loss, business failure, or even system crash.

Alarm basic information:

| Item | Description |
|------|------|
| Alarm ID | 12014 |
| Alarm Name | Device Partition Lost |
| Alarm Severity | Important |
| Alarm Type | Hardware Fault Alarm |
| Auto-cleared | Yes: MRS 3.3.0 and later versions, MRS 3.1.0.0.10/3.1.5.0.3 and later patch versions; No: versions before MRS 3.3.0 |
| System Impact | Data loss (data on the partition may be lost), system crash (system disk loss causes node abnormality), business failure (business read/write operations fail), business latency, security risk |

## 2. Executable Operations

This section provides the relevant operations that can be executed during the alarm analysis process.

### 2.1 Determine Whether the Alarm Cluster Is a Virtual Machine

Execute the following command. If the result is "none", the cluster is on a physical machine; if the output is a virtualization platform name such as kvm, vmware, or oracle, the cluster is on a virtual machine.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=systemd-detect-virt' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.2 Confirm Whether the Device Partition Is Lost

Execute the following command. If the command output does not contain the alarm device partition name, the device partition has been lost; if the output contains the alarm device partition name, the device partition still exists.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-health-check' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.3 Determine Whether the `df -h` Output Contains the Device Partition Name

Execute the following command. If the command output contains the alarm device partition name, the device partition name exists; otherwise, it does not.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=disk-space' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.4 Determine Whether the Device Partition-to-Disk Mapping Can Be Viewed

Execute the following command. If the command output contains the alarm device partition information, the device partition-to-disk mapping exists; otherwise, it does not.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=lsblk' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.5 Determine Whether the Alarm Disk Has RAID

Execute the following command. If the third column of the command output for the alarm disk shows ATA, SATA, or SAS, the disk does not have RAID; if it shows other information, the disk may have RAID.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=lsscsi' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

### 2.6 Determine Whether Non-RAID Hardware Supports SMART

Execute the following command. If the command output contains "SMART support is: Enabled", the disk supports SMART; if the output contains "Device does not support SMART" or other messages, the disk does not support SMART.

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=smartctl_-i' \
  -p 'env={"DISK_NAME":"<DISK_NAME>"}' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information
- `<DISK_NAME>`: Alarm disk name (obtain the corresponding disk name from the device partition name; e.g., if the device partition name is `/dev/sda1`, the disk name is `/dev/sda`)

### 2.7 Obtain Cluster OMS Active/Standby Node Information

```bash
python3 lakewatch_api_client.py -a query-management-node-info \
  -p 'cluster_id=<cluster_id>'
```

Parameter description:
- `<cluster_id>`: Cluster ID

### 2.8 Obtain OMS Key Directories

```bash
python3 lakewatch_api_client.py -a collect_alarm_node_res_data \
  -p 'cluster_id=<cluster_id>' \
  -p 'strategy_name=oms_core_dir' \
  -p 'node_name=<node_name>'
```

Parameter description:
- `<cluster_id>`: Cluster ID
- `<node_name>`: Name of the node where the alarm occurred, obtained from the alarm information

## 3. Non-Executable Operations

This section provides operations that cannot be executed through the tool during the alarm analysis process (i.e., commands that require manual login to the node).

### 3.1 Check Whether /etc/fstab Contains the Alarm Mount Directory Name

Log in to the alarm node as the root user and check whether the "/etc/fstab" file contains a line with the "mount directory name". The user password is customized before installation; consult the system administrator.

```bash
cat /etc/fstab
```

- If the fstab file contains a line with the "mount directory name", the system has auto-mount configured; this line needs to be deleted (refer to 3.2)
- If the fstab file does not contain a line with the "mount directory name", the system has not configured auto-mount; a new disk can be inserted directly (refer to 3.3)

### 3.2 Delete the Line Containing the Alarm Mount Directory Name from /etc/fstab

If the "/etc/fstab" file contains a line with the "mount directory name", execute the following command to edit the file and delete the line containing the "mount directory name".

```bash
vi /etc/fstab
```

After deleting the line containing the "mount directory name", save and exit.

### 3.3 Insert a New Disk and Configure RAID

Contact a hardware engineer to insert a new disk. For specific operations, refer to the hardware product documentation for the corresponding model.

- If the original failed disk was RAID, configure RAID according to the corresponding RAID card configuration method.

### 3.4 Check Whether the Disk Has Been Mounted to the Mount Directory

After waiting 20-30 minutes (the specific time depends on the disk size), execute the mount command to check whether the disk has been mounted to the "mount directory name" directory.

```bash
mount
```

- If the disk has been mounted to the mount directory name, the disk replacement was successful:
  - For MRS 3.3.0 and later versions, MRS 3.1.0.0.10/3.1.5.0.3 and later patch versions: wait 2 minutes and check whether the alarm has automatically recovered
  - For versions before MRS 3.3.0: manually clear the alarm; the operation is complete
- If the disk has not been mounted to the mount directory name, the disk replacement may have issues; proceed to 3.5 to collect fault information

### 3.5 Collect Fault Information

If the above steps do not clear the alarm, collect fault log information:

1. In the FusionInsight Manager UI, select "Maintenance > Logs > Download"
2. In "Services", select "OmmServer", then click "OK"
3. In the upper right corner, set the log collection "Start Time" and "End Time" to 10 minutes before and after the alarm generation time, then click "Download"
4. Contact operations personnel and send the collected fault log information

## 4. Common Fault Repair Solutions

### 4.1 Disk Removed

**Symptoms**:
- Device partition lost; mount command output does not contain the alarm device partition name
- The corresponding disk on the server is not in the slot
- The disk corresponding to the "device partition name" in the alarm parameters does not exist

**Repair solution**:
1. Confirm whether the node with the failed disk is the OMS active node; if so, perform an active/standby switchover before replacing the disk
2. Check whether the failed disk is mounted on OMS key directories; if involved, data migration is needed first
3. Check whether the "/etc/fstab" file contains a line with the "mount directory name"; if so, delete that line
4. Contact a hardware engineer to insert a new disk; if the original failed disk was RAID, configure RAID according to the corresponding RAID card configuration method
5. Wait 20-30 minutes and check whether the disk has been mounted to the mount directory
6. Verify whether the alarm is automatically cleared (MRS 3.3.0 and later versions) or manually clear the alarm (versions before MRS 3.3.0)

### 4.2 Disk Offline Failure

**Symptoms**:
- Device partition lost; mount command output does not contain the alarm device partition name
- The corresponding disk on the server is still in the slot
- The disk may have hardware failure (bad sectors, circuit board failure, etc.)

**Repair solution**:
1. Confirm whether the node with the failed disk is the OMS active node; if so, perform an active/standby switchover before replacing the disk
2. Check whether the failed disk is mounted on OMS key directories; if involved, data migration is needed first
3. Contact a hardware engineer to confirm the disk hardware failure and online-remove the failed disk
4. Check whether the "/etc/fstab" file contains a line with the "mount directory name"; if so, delete that line
5. Contact a hardware engineer to insert a new disk; if the original failed disk was RAID, configure RAID according to the corresponding RAID card configuration method
6. Wait 20-30 minutes and check whether the disk has been mounted to the mount directory
7. Verify whether the alarm is automatically cleared (MRS 3.3.0 and later versions) or manually clear the alarm (versions before MRS 3.3.0)

### 4.3 Disk Has Bad Sectors

**Symptoms**:
- SMART information shows "Reallocated_Sector_Ct" or "Elements in grown defect list" count greater than 100
- GLIST list shows "READ SECTOR(S)" or "WRITE SECTOR(S)" errors
- Device partition lost due to disk bad sectors

**Repair solution**:
1. Confirm whether the node with the failed disk is the OMS active node; if so, perform an active/standby switchover before replacing the disk
2. Check whether the failed disk is mounted on OMS key directories; if involved, data migration is needed first
3. Contact a hardware engineer to confirm the disk hardware failure and online-remove the failed disk
4. Check whether the "/etc/fstab" file contains a line with the "mount directory name"; if so, delete that line
5. Contact a hardware engineer to insert a new disk; if the original failed disk was RAID, configure RAID according to the corresponding RAID card configuration method
6. Wait 20-30 minutes and check whether the disk has been mounted to the mount directory
7. Verify whether the alarm is automatically cleared (MRS 3.3.0 and later versions) or manually clear the alarm (versions before MRS 3.3.0)

### 4.4 Disk Circuit Board Failure

**Symptoms**:
- GLIST list shows non-read/write-related errors
- Disk cannot be properly identified or responds
- Device partition lost due to disk circuit board failure

**Repair solution**:
1. Confirm whether the node with the failed disk is the OMS active node; if so, perform an active/standby switchover before replacing the disk
2. Check whether the failed disk is mounted on OMS key directories; if involved, data migration is needed first
3. Contact a hardware engineer to confirm the disk hardware failure and online-remove the failed disk
4. Check whether the "/etc/fstab" file contains a line with the "mount directory name"; if so, delete that line
5. Contact a hardware engineer to insert a new disk; if the original failed disk was RAID, configure RAID according to the corresponding RAID card configuration method
6. Wait 20-30 minutes and check whether the disk has been mounted to the mount directory
7. Verify whether the alarm is automatically cleared (MRS 3.3.0 and later versions) or manually clear the alarm (versions before MRS 3.3.0)

### 4.5 Disk SMART Self-Test Failed

**Symptoms**:
- SMART overall-health self-assessment test result shows "FAILED"
- Device partition lost due to disk SMART self-test failure

**Repair solution**:
1. Immediately back up important data
2. Confirm whether the node with the failed disk is the OMS active node; if so, perform an active/standby switchover before replacing the disk
3. Contact a hardware engineer to confirm the disk hardware failure and online-remove the failed disk
4. Check whether the "/etc/fstab" file contains a line with the "mount directory name"; if so, delete that line
5. Contact a hardware engineer to insert a new disk; if the original failed disk was RAID, configure RAID according to the corresponding RAID card configuration method
6. Wait 20-30 minutes and check whether the disk has been mounted to the mount directory
7. Verify whether the alarm is automatically cleared (MRS 3.3.0 and later versions) or manually clear the alarm (versions before MRS 3.3.0)

### 4.6 Emergency System Recovery

**Scenario**: Device partition loss causes system running lag, delayed page refresh, or slow API response, preventing O&M operations

**Repair solution**:
- **Active OMS node**:
  1. Log in to the active OMS node as the omm user
  2. Execute the active/standby switchover command:
     - IPv4 mode: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=127.0.0.1 --port=20013 --switchover --name=product`
     - IPv6 mode: `${OMS_RUN_PATH}/workspace/ha/module/hacom/tools/ha_client_tool --ip=::1 --port=20013 --switchover --name=product`
  3. After the active/standby switchover succeeds, the system returns to normal operation
  4. Check whether the "/etc/fstab" file contains a line with the "mount directory name"; if so, delete that line
  5. Contact a hardware engineer to insert a new disk; if the original failed disk was RAID, configure RAID according to the corresponding RAID card configuration method
  6. Wait 20-30 minutes and check whether the disk has been mounted to the mount directory
  7. Verify whether the alarm is automatically cleared

- **Active node of active/standby mode instances**:
  1. Log in to FusionInsight Manager
  2. Select "Cluster > Services > <service_name>"
  3. On the service details page, click "More" and select "Perform xxx Switchover"
  4. Enter the current login user password to confirm identity, then click "OK"
  5. On the popup page, click "OK" to perform the role instance active/standby switchover
  6. After the active/standby switchover succeeds, the system returns to normal operation
  7. Check whether the "/etc/fstab" file contains a line with the "mount directory name"; if so, delete that line
  8. Contact a hardware engineer to insert a new disk; if the original failed disk was RAID, configure RAID according to the corresponding RAID card configuration method
  9. Wait 20-30 minutes and check whether the disk has been mounted to the mount directory
  10. Verify whether the alarm is automatically cleared

### 5.2 Diagnosis Conclusion Output

Based on the diagnosis flow above, output one of the following diagnosis conclusions:

| Diagnosis conclusion | Recommended action |
|----------|----------|
| Disk removed | Check fstab, insert new disk, configure RAID (if needed), wait for mount |
| Disk offline failure | Online-remove failed disk, check fstab, insert new disk, wait for mount |
| Disk failure - bad sectors | Online-remove failed disk, check fstab, insert new disk, wait for mount |
| Disk failure - circuit board issue | Online-remove failed disk, check fstab, insert new disk, wait for mount |
| Disk SMART self-test failed | Online-remove failed disk, check fstab, insert new disk, wait for mount |
| Hardware does not support SMART | Use RAID card vendor tools for inspection |
| Alarm still persists after processing | Collect fault logs, contact operations personnel |

## 6 Notes for 12014 Alarm Diagnosis

Based on the `2. Executable Operations` and `3. Non-Executable Operations` in the 12014 alarm diagnosis process, combined with `5. Alarm Diagnosis Flow`, generate the alarm troubleshooting methods and common fault repair solutions for the alarm node. The user should confirm the alarm cause based on the provided information.

**Special notes**:
- The 12014 alarm is auto-clearable in MRS 3.3.0 and later versions, MRS 3.1.0.0.10/3.1.5.0.3 and later patch versions. When the device partition recovers, the system will automatically clear this alarm; versions before MRS 3.3.0 require manual alarm clearing.
- The "device partition name" in the alarm parameters is the lost partition (e.g., `/dev/sda1`). When executing smartctl checks, the corresponding disk name (e.g., `/dev/sda`) must be used. The partition-to-disk mapping can be determined using the lsblk command.
- When handling the 12014 alarm, first check whether the "/etc/fstab" file contains a line with the "mount directory name"; if so, delete it to prevent mount failure during system startup after inserting a new disk due to fstab configuration.
- After inserting a new disk, wait 20-30 minutes (the specific time depends on the disk size); do not force operations during this period.
- If the lost disk is the system disk, it may cause node system abnormality or even crash; it should be handled with priority.
