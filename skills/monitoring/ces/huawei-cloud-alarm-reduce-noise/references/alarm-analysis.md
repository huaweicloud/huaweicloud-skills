# Alarm Noise Reduction Analysis Methodology

## Overview

This document describes the analysis methodology and dimensions of the Huawei Cloud CES+AOM alarm noise reduction analysis skill.

AOM provides alarm noise reduction functionality: before sending alarm notifications, alarms are processed through a rule chain, and notifications are sent only after processing is complete. The noise reduction rules are divided into four stages: **route grouping, deduplication, suppression, and silencing**. The CES platform does not have this functionality; events generated by CES alarm rules do not go through the AOM noise reduction chain.

> **Constraint**: AOM noise reduction only applies to notification delivery — all triggered alarms are still visible in the "Alarm List" page. Rule orchestration only supports Prometheus monitoring and log monitoring alarms; it does not support events generated by CES alarm rules.

## Analysis Dimensions

### 1. Alarm Governance

Based on the four stages of AOM alarm noise reduction, this dimension analyzes alarm data and generates noise reduction rule suggestions that can be directly created in the AOM console.

#### 1.1 Route Grouping

**AOM mechanism**: Grouping rules filter a subset of alarms that meet specific conditions and merge notifications by merge method. Alarms in the same group are merged into a single email, reducing notification volume. Rules must be manually created, with a limit of 100.

**Analysis contents**:
- Identify high-frequency alarm sources (same `service` triggering large numbers of alarms) → suggest grouping by alarm source
- Identify alarm storms (same resource, same metric, >30 triggers) → suggest grouping + merge by alarm source + severity
- Identify batch alarms for the same resource type (e.g., multiple ECS instances alarming on CPU simultaneously) → suggest grouping by resource type

**Suggested parameters**:
- Grouping conditions: alarm level, resource type, alarm source, labels, etc. (supports and/or combinations)
- Merge method: by alarm source / by alarm source + severity / by alarm source + all labels
- First wait: how long to wait after first creating the merge set before sending notification (recommended 15s, range 0s-10min)
- Change wait: how long to wait after an alarm change within the merge set before sending notification (recommended 60s, range 5s-30min)
- Repeat wait: how long to wait after an alarm repeat within the merge set before sending notification (range 5s-30min)

#### 1.2 Deduplication Analysis

**AOM mechanism**: Deduplication is a built-in strategy — the service backend automatically checks whether alarm content is identical and deduplicates if so. Users do not need to manually create rules.

**Analysis contents**:
- Count completely identical alarms (same resource + same metric + same threshold + same level) to confirm built-in deduplication effectiveness
- Identify duplicate rules with same threshold but different levels → these rules produce similar alarm content, increasing notification burden
- Identify CES alarm proportion → CES alarms do not go through the AOM noise reduction chain; migrating to AOM Prometheus monitoring alarm rules is recommended

**Constraint notes**:
- Deduplication only applies to AOM alarms; CES alarms do not go through this stage
- Deduplication is automatic and requires no manual configuration; the analysis focus is confirming deduplication coverage

#### 1.3 Suppression Rules

**AOM mechanism**: Suppression rules suppress related alarm notifications when a root alarm triggers. Suppression is lifted when the root alarm recovers. Rules must be manually created, with a limit of 100.

**Analysis contents**:

**Severity suppression**:
- Count the proportion of CRITICAL / MAJOR / MINOR / Info alarms at each level
- If CRITICAL proportion is too high → suggest creating a suppression rule: when critical alarms trigger, suppress minor/info level alarms
- Suggested parameters: root alarm condition = alarm level equals critical, suppressed alarm condition = alarm level equals minor

**Root cause suppression**:
- Identify multi-metric alarms on the same resource, sort by trigger frequency to identify the root cause metric
- Suggest creating a suppression rule: when the root cause metric triggers, suppress derived metric alarms
- Suggested parameters: root alarm condition = alarm rule equals {root cause rule}, suppressed alarm condition = alarm rule equals {derived rule}

**Dependency suppression**:
- Infer dependency relationships based on resource type: host down → suppress process/container alarms on that host
- Base service abnormal → suppress application service alarms
- Suggested parameters: root alarm condition = resource type equals {host} AND alarm level equals critical, suppressed alarm condition = alarm source equals {container/process}

**Constraint notes**:
- If the root alarm recovers before the notification is sent, the suppression rule becomes ineffective and the suppressed alarm is sent normally
- Suppression only applies to notifications; suppressed alarms are still visible in the alarm list

#### 1.4 Silence Rules

**AOM mechanism**: Silence rules suppress alarm notifications during a specified time period. Rules take effect immediately upon creation. Must be manually created, with a limit of 100.

**Analysis contents**:

**Test environment silencing**:
- Detect alarms where the resource name contains keywords like test / dev / demo
- Suggest creating a silence rule: filter condition = resource name regex match `test*|dev*|demo*`, silence time = all day

**Low-priority silencing**:
- Count the proportion of MINOR / Info level alarms
- If proportion is too high → suggest creating a silence rule: filter condition = alarm level equals minor, silence time = non-working hours

**Maintenance window silencing**:
- Identify high-frequency alarm patterns during non-working hours
- Suggest creating a silence rule: filter condition = alarm source equals {service name}, silence time = maintenance window (e.g., 00:00-06:00)

**Suggested parameters**:
- Filter conditions: alarm level, resource type, alarm source, labels, etc. (supports and/or combinations)
- Silence time: specified time period (e.g., daily 00:00-08:00, or one-time maintenance window)

### 2. Alarm Convergence

Analysis contents:
- Alarm storm identification (same resource, same metric, high-frequency trigger: >30 times = high risk, >100 times = severe)
- Alarm temporal correlation analysis (time-window-based co-occurrence analysis, identify correlation groups)

> Note: The noise reduction action for alarm storms is route grouping (see 1.1); this section only performs identification and statistics.

### 3. Alarm Correlation

Analysis contents:
- Root cause analysis (same resource, multiple metrics, sorted by frequency to identify root cause)
- Derived alarm identification (silence derived alarms when root cause triggers)

> Note: The noise reduction action for root cause analysis is suppression rules (see 1.3); this section only performs analysis and identification.

### 4. Long-Unresolved Alarms

Analysis contents:
- Filter alarms with alarm_status = active
- Tier by duration: >7 days (info), >14 days (info), >30 days (warning), >90 days (danger)
- Unresolved alarm detail list

## Data Format

### Input Data Format

```json
{
  "alarm": {
    "customerId": "xxx",
    "alarm_history": [
      {
        "id": 123456789,
        "alarm_level": "MAJOR",
        "metric_name": "mem_usedPercent",
        "metric_expression": "{metric=#mem_usedPercent:value.last(0)}>88.00",
        "alarm_start_value": "95.54%",
        "alarm_trigger_time": 73429,
        "service": "ECS",
        "region": "cn-north-4",
        "alarm_resource": {
          "resourceType": "ECS",
          "resourceId": "xxx",
          "resourceName": "server-name",
          "privateIP": "10.0.0.1"
        }
      }
    ]
  }
}
```

### Key Field Descriptions

| Field | Description |
|-------|-------------|
| alarm_level | Alarm level: CRITICAL, MAJOR, MINOR |
| metric_name | Metric name |
| metric_expression | Alarm expression |
| alarm_trigger_time | Alarm trigger count (milliseconds) |
| service | Service type: ECS, DCS, RDS, CDN, etc. |
| alarm_resource | Alarm resource information |

## Output Report Structure

The generated HTML report contains the following sections:

1. **Alarm Overview**
   - Total alarm count
   - Number of affected resources
   - Distribution by level
   - Distribution by service type

2. **Alarm Governance Recommendations**
   - Route grouping suggestions (high-frequency alarm source grouping, alarm storm grouping)
   - Deduplication analysis (built-in deduplication description, duplicate alarm statistics, CES migration suggestions)
   - Suppression rule suggestions (severity suppression, root cause suppression, dependency suppression)
   - Silence rule suggestions (test environment silencing, low-priority silencing, maintenance window silencing)

3. **Long-Unresolved Alarms**
   - Tiered statistics by duration
   - Unresolved alarm detail list
