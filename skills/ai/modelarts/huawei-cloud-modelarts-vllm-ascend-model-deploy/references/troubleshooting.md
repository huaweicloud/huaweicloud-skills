# 常见问题排查

本文件支撑 SKILL.md"常见问题排查"章节,按现象定位根因并给出排查动作。

| 现象 | 可能原因 | 排查动作 |
|------|----------|----------|
| 服务反复重启(最常见) | **健康检查启动延迟过短** — vLLM V1 引擎首次启动需编译 IR + 捕获 CUDAGraph,耗时 5~10 分钟;探针过早探测超时 → 实例被杀 → 重启 → 重新编译 → 死循环。特征: 日志每次从零开始、无 Error/Traceback、pid 递增、间隔约数分钟 | ① 确认健康检查启动延迟 600s 及以上(超时 60s、周期 60s)与**失败次数 300**(部署配置已自动设置,18000s/300 分钟容忍窗口);② 确认探针路径/端口与启动脚本一致;③ 仍重启则检查实例日志定位真实原因 |
| 启动即退出,日志报 `Value error, Total number of attention heads (24) must be divisible by tensor parallel size (16)` | **TP 不是模型注意力头数的约数** — vLLM 启动硬校验: 头数必须能被 TP 整除(实测 Qwen3.8-27B 头数 24 + TP=16 → 24%16≠0,master/slave 全部崩溃)。**注意**: 该 TP 与 flavor 卡数无关,flavor 给多少卡都不能绕过架构约束;多节点场景"每节点卡数 ≠ TP"时最易踩坑(16 卡节点想全量 TP=16,但 24 头数不可被 16 整除) | ① 从模型 config.json 取 `num_attention_heads`(如 Qwen3.8-27B=24);② TP 必须取头数的约数(24 → 2/4/6/8/12/24)且 ≤ 单节点卡数;③ 改 `start_vllm.sh` 的 `TENSOR_PARALLEL_SIZE`/`TP_SIZE` 为合法值,重跑 `check_artifacts.py`(H12 传 `--num-attention-heads` 可自动拦截),重新上传 OBS 并重建服务 |
| 启动即退出 | 镜像与 NPU 驱动/CANN 不匹配 | 确认 SWR 镜像 tag 与资源池昇腾版本兼容 |
| 启动即退出,日志报 `Value error, The checkpoint ... has model type \`xxx\` but Transformers does not recognize this architecture` | **镜像内 transformers 版本过旧,不识别实验性模型新架构**(如 GLM-5.3-Flash 的 `glm5_next`)——镜像 tag 与模型文档要求的版本不配套(文档基于 v0.30.0RC,却用了稳定版 v0.23.0) | ① 核对模型页面标注的文档版本 vs 镜像版本;② 用 `docker run --rm <镜像> python -c 'import transformers; print(transformers.__version__)'` 确认镜像内 transformers;③ 换团队/内部构建的新版镜像(如 tag 直接叫模型名),或换稳定版本模型;④ 见 SKILL.md 步骤 1.0"镜像版本要求"与 2.1"镜像类型识别" |
| 启动即退出,容器初始化阶段日志报 `libcontainer: container start initialization failed ... exec user process caused "exec format error"` | ① **镜像架构与资源池不匹配**(docker inspect 镜像 `Architecture` 非 arm64);② **非标准镜像(MindIE/ATB 专用)带自定义 Entrypoint**,与 ModelArts 平台 `cmd` 组合冲突;③ 镜像内部混入 x86 二进制(架构声明正确但实际 exec 失败) | ① 确认镜像 `docker inspect <镜像> \| grep Architecture` 为 arm64,且 SWR 中镜像架构与本地一致(查 SWR 实际存储架构,勿只看本地缓存);② 确认镜像是否标准 vllm-ascend 镜像(环境变量含 `ATB_*`/`LCCL_*`/`SOC_VERSION`/CANN 版本异常 → 非标准,需按其自带入口启动,见 2.1);③ 在 ARM 节点 `docker run` 验证镜像可启动;④ 架构与 docker run 均正常仍报此错 → 平台调度节点/驱动与镜像 CANN 不兼容,需反馈团队或换资源池 |
| 创建服务返回 `400 ModelArts.8118 Insufficient NPU resources ... Requested: 16.0 Cards, Available: 0.0 Cards` | **失败/部署中的旧服务仍占用资源池全部卡数**,新服务无法调度 | ① 查旧服务状态: RUNNING/DEPLOYING/FAILED 均可能占资源;② 用 `POST /v2/{project_id}/services/{sid}/stop` 停止旧服务(FAILED 状态不可 stop 时,其实例已终止不占资源,直接创建新服务);③ 等待旧服务 STOPPED 后再创建新服务 |
| 部署到实验性模型专用镜像,容器反复 exec format error 无法定位 | 专用镜像可能基于 **MindIE/ATB 推理链路**(环境变量 `ATB_*`/`LCCL_*`、`SOC_VERSION=ascend910b1`、WorkingDir=/workspace、自定义 Entrypoint),**不是标准 vllm-ascend 镜像**,本 skill 的标准 `start_vllm.sh`/cmd 不适用 | ① 部署前在 2.1 完成镜像类型识别,确认镜像用途与启动方式;② 若为非标准镜像,询问用户镜像自带部署脚本或团队既有部署方式;③ 无法适配则换标准 vllm-ascend 镜像或稳定版模型 |
| multinode/pd_colocate slave 节点日志报 `RuntimeError: Remote engine N must use --headless unless in external or hybrid dp lb mode` | **vLLM 0.23.0 默认 DP LB 模式下 slave 必须追加 `--headless`,但脚本未加**(模板 `DP_LB_MODE` 逻辑被错误改为按 `DATA_PARALLEL_SIZE_LOCAL=1` 判断为 external LB→不加 → 崩溃)。`check_artifacts.py` H14 旧版误判 `dp_local=1` ⇒ external LB,已修正为按 `DP_LB_MODE` 判断 | ① 恢复 `start_vllm.sh` slave 分支为模板原始 `DP_LB_MODE` 判断: 默认/未设置→`SLAVE_OPTS="--headless"` + `nohup python -m http.server 8080`;`DP_LB_MODE=external\|hybrid`→不加;② 重跑 `check_artifacts.py` H14 应 PASS;③ 覆盖上传 OBS 后重新部署 |
| 启动即退出,日志报 `error: argument --speculative-config/-sc: Value '{"method": cannot be converted to ...` 或同类 JSON 参数解析失败 | **JSON 参数用字符串变量传递,引号丢失** — 启动脚本把 `--speculative-config`/`--compilation-config`/`--additional-config` 等 JSON 参数放进 `EXTRA_ARGS` 字符串变量,`${EXTRA_ARGS}` 展开时单引号失效,argparse 收到 `{"method":` 截断值 | ① 模型特有参数(尤其 JSON)一律加入模板内置的 `MODEL_ARGS` bash 数组(每项一个元素,JSON 单引号包裹);② 普通无 JSON 参数才可走 `EXTRA_ARGS` 环境变量;③ 见 SKILL.md 步骤 3.2 说明 |
| 启动即退出,日志报 `Syntax error: "(" unexpected` | **脚本被 `sh` 执行** — 启动脚本使用 bash 数组(`MODEL_ARGS=(...)`),但 ModelArts 启动命令写成 `sh .../start_vllm.sh`,`sh`(dash)不识别数组语法 | 启动命令改为 `bash /home/ma-user/code/start_vllm.sh`(code 目录挂载到容器后,见 SKILL.md 步骤 3.2) |
| 启动即退出,日志报 `OSError: Repo id must be in the form 'repo_name' or 'namespace/repo_name': '<路径>'` | **模型权重未挂载** — `${MODEL_PATH}` 下无 `config.json`(ModelArts 模型存储地址填错层级、挂载路径与 MODEL_PATH 不一致、OBS 挂载认证凭据缺失导致挂载为空),vllm 把本地路径当 HuggingFace repo 处理 | ① 启动脚本必须内置 config.json 存在性自检(见 SKILL.md 步骤 3.2);② 检查模型配置: 存储地址精确到模型目录(如 `obs://bucket/models/<模型名>`)、挂载路径与 MODEL_PATH 一致;③ 用 OBS 对象桶挂载时确认认证凭据(临时委托凭证或 DEW AK/SK)已配置;④ 容器内 `ls -la ${MODEL_PATH}` 核对 |
| 健康检查失败,日志报 `python3: can't open file '/code/xxx.py': No such file or directory` | 探针脚本引用了**硬编码的绝对路径**(如 `/code/get_master_ip.py`),或该脚本未上传/挂载路径与预期不符 | ① 脚本内引用同目录文件一律用 `$(dirname "$0")` 相对定位(见 SKILL.md 步骤 3.3);② 核对 `CODE_OBS_PATH` 目录文件齐全并已挂载到探针引用的目录;③ 核对文件存储挂载的存储地址精确到 code 目录、挂载路径与探针配置一致 |
| OOM / 显存不足 | max-model-len 或并发过大 | 调小 `--max-model-len`,调低 `--gpu-memory-utilization`,减少 TP 卡数需求需配小模型 |
| 模型过大单节点放不下/启动 OOM | 模型权重+KV Cache 超出单节点显存 | 回到 SKILL.md 步骤 1.1 重新确定部署形式: 扩大 TP 卡数或改**多节点部署**;若为量化权重可改用 W8A8 等降低显存 |
| 多节点/PD 部署卡住或启动失败 | **节点间网络不通(HCCL/DP)**、master/slave 角色判定失败(rank table 未 completed / `POD_IP` 不匹配)、`--tensor-parallel-size` 与单节点卡数不一致 | ① 确认节点间网络互通、安全组放通 HCCL/DP 通信端口(`--data-parallel-rpc-port`);② 核对平台注入 `GLOBAL_RANK_TABLE_FILE_PATH`/`POD_IP` 与 `get_master_ip.py` 角色判定(rank table 是否 completed、POD_IP 是否匹配);③ TP_SIZE = 每台推理单元 NPU 卡数;④ 查 vllm-ascend 多机部署示例核对环境变量 |
| PD 分离请求失败/ConnectError | pd(双角色)双角色端口未打通或角色判定失败;多节点/pd_colocate(单引擎): DP 通信或 master/slave 判定失败 | **pd(PD 分离)**: ① 核对 Prefill/Decode 双角色 `VLLM_ROLE`/`PORT` 注入正确;② 核对节点角色判定(经 `get_master_ip.py` 读 rank table)与端口网络可达。**multinode/pd_colocate(单引擎)**: ③ 放通 `--data-parallel-rpc-port`(13389);④ 核对 `get_master_ip.py` 读 rank table 角色判定正确 |
| 模型不支持 | 不在 vllm-ascend 支持列表 | 换支持列表内模型,或告知用户需自行适配 |
| 访问 docs.vllm.ai / quay.io 等第三方站点报 `SSL certificate problem: self-signed certificate in certificate chain`,或 curl 000(非代理真拦截) | **企业/云上代理对目标站点做 TLS 中间人(MITM)证书替换**,本机不信任其 CA;`getent`/直连 DNS 可能不通,但 curl 走代理不受影响 | ① 先按"安全编码规范"校验 URL 主机在白名单内(docs.vllm.ai 等),再重新用 `curl -sk <url>`(跳过证书校验)访问——多数场景实际可达;② `-k` 仅跳过证书校验,不影响"以官方文档为准"的 tag 决策;③ 若 `-k` 后仍 000/超时,才是代理白名单真拦截(如部分环境 github.com / modelscope.cn),再走降级机制 |
| 拉取镜像失败 | Quay.io 网络受限 | 配置代理;或找镜像站/自行构建后推送 SWR |
| 多机部署卡住 | HCCL 网络不通 | 检查节点间网络互通、安全组放通 |
| 跨节点 TP 部署(multinode/pd_colocate)报业务错误 | **超节点亲和组实例数未配置或不等于 N** | ModelArts 部署配置"超节点亲和组实例数"=N(副本内节点数),确保多机调度到同一超节点(参见 ModelArts 故障排除 inference2.0-modelarts-0042) |
| 多副本实例间 DP 端口冲突 | 多副本实例 `--data-parallel-rpc-port` 相同 | 各副本 `DATA_PARALLEL_RPC_PORT` 环境变量按副本注入不同值;副本间由 ModelArts 流量分发,无需跨副本通信 |
| 多机 PD(pd_colocate)实例间 ConnectError | DP 通信端口未放通或 master/slave 角色判定失败 | 核对 `--data-parallel-rpc-port`(13389)网络放通、`get_master_ip.py` 读 rank table 角色判定正确、超节点亲和组=N |
| 多机 PD 请求 502/504 | 前置 LB 或流量权重配置错误 | 核对 ModelArts 流量权重配置、前置 LB 健康检查;多机 PD(pd_colocate 单引擎)核对 master 节点 API 端口正常对外 |
| 调用 CreateInferService API 返回 401/403 | IAM Token 失效(24h 有效)或权限不足(缺 modelarts:service:create);token 复制截断(含非标准字符 `-`/不以 `==` 结尾)→ `APIGW.0301 decrypt token fail`;**获取 token 本身 401**: IAM 域名未确认用错 / `scope.project.name` 误用 region 原值(含 `.beta` 后缀,须去掉)/ 账号名·用户名·密码三要素错配 | ① 重新获取 Token(推荐 IAM API 获取,Python 正则完整提取,禁 shell 管道);② **获取前确认 IAM 域名与 `project_name`**(见 SKILL.md 4.3 token 获取第 ③ 条: 默认 `iam.<region>.myhuaweicloud.com`;project name 默认 region 去 `.beta` 等后缀,如 region=`cn-southwest-301.beta` → `cn-southwest-301`);③ 确认账号有 ModelArts 服务创建权限与资源池使用权限;④ 见 SKILL.md 4.3 token 获取与提取 |
| 查工作空间/资源池列表为空,但配额显示有资源 | **ModelArts 域名用错 / GET 接口未带 workspace 双查询参数 / 当前 IAM 用户缺 `modelarts:pool:list` 权限**: `X-Workspace-Id` 头不起过滤作用,只带头或只带单参数返回 default 工作空间的服务,误判无服务 | ① **先确认环境域名**(统一 `modelarts.<region>.myhuaweicloud.com`,不存在 dev 域名,须与资源池同区域);② **所有 GET 接口(除工作空间列表接口 `GET /v1/{project_id}/workspaces` 外)统一在 URL 上携带 `?workspaceId={}&workspace_id={}` 双查询参数** + `X-Workspace-Id` 头;工作空间列表接口不带 workspace 查询参数、不带该头,仅带 `Authorization: Bearer <token>`,全局查询用于获取 WORKSPACE_ID 本身;③ 用正确域名 + 双查询参数重新查工作空间(`GET /v1/{project_id}/workspaces`)→ 按工作空间名取 workspace-id;④ 若列表仍空但配额非零(`GET /v1/{project_id}/quotas` 中 `type=pool` used>0),多为权限不足,直接向用户确认资源池 ID/名称(见 SKILL.md 4.3 步骤 0) |
| 调用 CreateInferService API 返回 400 `name/type/group_configs/runtime_config` 缺失 | **请求体用了旧骨架 `service.deployment.roles[]`**——新版 API 要求**顶层平铺结构** | 用 SKILL.md 4.3 的平铺结构: `name`/`type`/`group_configs[]`/`runtime_config` 直接放顶层;查询已部署服务 `show` 反推正确结构 |
| 创建 API 返回 400 `ModelArts.8162` OBS 挂载认证凭据为空 | 缺 `secret_type` 或取值错误(`dew`/`obspool`/`obs` 均不被接受) | `group_configs[].secret_type: "agency"`(委托方式,与控制台默认一致) |
| 创建返回 400 `ModelArts.6404` Flavor not found | `unit_configs[].flavor` 用了资源池节点池 flavor(如 `modelarts.bm.npu.arm.ssd`) | 改用推理实例规格 `modelarts.bm.arm.{CPU}u.{RAM}g.npu.{N}d910b`,查同工作空间已有服务的 `version.instance_groups[].unit_configs[].flavor` 反推(见 SKILL.md 4.3) |
| 创建返回 400 `ModelArts.8003 Cannot find a specific flavor` | **`unit_configs[].flavor` 字段缺失或值为空**(与 6404 区分: 8003=字段缺失,6404=值不是合法 flavor id)。根因: 绕过 `create_infer_service.py` 手写请求体直接 POST,跳过脚本的 `validate_request_body()`(已含 flavor 必填校验) | ① 在 `unit_configs[]` 补 `flavor` 字段,值从 ShowInferServiceCluster `flavors[]` 按 `ascend.npu` 取 id(见 SKILL.md 步骤 0 第 ⑦ 条);② 强制走 `create_infer_service.py create --raw-json` 提交,`validate_request_body()` 本地拦住缺失字段;禁止手写 `tmp_*.py` 绕过脚本直接 POST |
| 创建 API 返回 `400 ModelArts.8084 No available resource for the specified flavor`(实际根因是请求体必填字段缺失) | **平台对结构不完整的请求不报 400 field missing,而是报 8084 误导为 flavor 资源问题**——必填字段缺失: `group_configs[].pool_id` / `model.host_cache`(true) / `unit_configs[].image.source`("SWR") / `unit_configs[].files[].host_cache`(true) / `unit_configs[].recovery`("Instance") / `runtime_config.service_invoke.internet_access_enable`(true) / `runtime_config.service_secret`(即使禁用必填对象) | ① 按 `references/modelarts-console-guide.md` 第三节 3.1 完整示例**一次构造全部必填字段**;② 构造后用 assert 校验 `pool_id`/`host_cache`/`image.source`/`files[].host_cache`/`recovery`/`internet_access_enable`/`service_secret` 全部存在;③ 仍 8084 再查 `show` 反推正确结构(见 SKILL.md API 部署前置校验第 12 条) |
| 创建 API 返回 400 `ModelArts.8037` RateLimit must not be null | `runtime_config.service_limit.rate_limit` 缺失 | 补 `"rate_limit": {"num": 200, "unit": "SECONDS"}` |
| 调用服务返回 504/408,`error_msg` 含 `request timeout: 30s`(错误码 `ModelArts.8909`) | **`runtime_config.service_limit.request_timeout` 未显式设置,平台默认 30s** — PD 分离首请求需 prefill+decode 协作、大模型首请求含权重加载/CUDAGraph 编译,>30s 被平台掐断(模型预热后短请求可通过,掩盖问题) | ① 请求体 `service_limit` 补 `"request_timeout": 300`(秒),`request_size_limit`: 20;② 已部署服务用 PUT UpdateService 更新 `runtime_config.service_limit.request_timeout=300`(更新后经 UPGRADING 回 RUNNING,用 `show` 确认 `version.runtime_config.service_limit.request_timeout=300` 生效);③ 排查方向: 更新后仍超时 → 查实例日志(模型加载慢/首个请求 prefill 排队) |
| 创建 API 返回 400 `group_configs[0].weight`/`image`/`auth_type` 校验失败 | 平铺结构已对,字段内容不全 | 补 `group_configs[].weight`(100)、`unit_configs[].image`(SWR 镜像)、`runtime_config.service_invoke.auth_type`(NONE/TOKEN/API_KEY) |
| 部署后 Pod 健康检查失败(Unhealthy 事件) | **pd(PD 分离)双角色端口未分离**(Decode 缺 `PORT` env)+ **failure_threshold 过小**(30 < vLLM V1 首启 10~20 分钟) | ① pd 各角色 `unit_configs[].envs` 显式设不同 `PORT`(pd_colocate 单引擎形态单一 PORT 无此问题);② 健康检查 `failure_threshold=300`/`initial_delay_seconds=300`/`period_seconds=60` |
| 容器端口与启动脚本不一致 | `runtime_config.service_invoke.port` 误填非 8080 | `service_invoke.port` 必须与启动脚本 `PORT` 一致(8080),否则探针探测端口错位 |
| API 401/403 | 推理请求认证未配置 | 在在线服务配置推理请求认证,或获取对应 token |
