# Execution Workflow

## Overview

This document describes the complete execution workflow of the ECS shutdown fault injection experiment: `start → monitor → report`.

## Workflow overview

```
Load experiment.json
    ↓
Pre-check (instance status must be ACTIVE)
    ↓
Execute shutdown (BatchStopServers)
    ↓
Monitor polling (ACTIVE → STOPPING → SHUTOFF)
    ↓
Wait for duration (duration_seconds)
    ↓
Execute rollback (BatchStartServers)
    ↓
Verify recovery (confirm all instances back to ACTIVE)
    ↓
Generate execution report (Markdown)
```

## Step details

### Step 1: Load configuration

**Input**: `experiment.json` file path (generated by the `experiment-prepare` skill)

**Action**: parse JSON and extract:
- `targets.instance_ids` - list of target ECS instance IDs
- `actions.shutdown.duration_seconds` - experiment duration
- `actions.shutdown.parameters.os_stop` - shutdown mode (SOFT/HARD)
- `region` - region
- `safety.auto_rollback_on_failure` - whether to auto-rollback

**Output**: in-memory experiment configuration object

**Exception handling**: file missing → error and exit; JSON malformed → error and exit; required field missing → error and exit

### Step 2: Pre-check

**Input**: instance ID list + region

**Action**: call `hcloud ECS ListServersDetails` to query the current status of each instance

**Validation rules**:
- All instances must be `ACTIVE`
- If any instance is not ACTIVE, refuse to execute

**Output**: pre-check result (pass/fail + detailed status)

**Exception handling**: instance not found → mark error; query timeout → retry 3 times; API error → error and exit

### Step 3: Execute shutdown (fault injection)

**Input**: instance ID list + shutdown mode

**Action**: call `hcloud ECS BatchStopServers` with `os_stop: SOFT`

**Output**: API response + shutdown start timestamp

**Exception handling**:
- API returns error → rollback immediately if `--auto-rollback`, otherwise error and exit
- Partial shutdown failure → record the failed instances and keep monitoring the stopped ones
- `--abort-on-failure` mode → terminate immediately on any failure

### Step 4: Monitor polling

**Input**: instance ID list + monitoring interval (default 10 seconds)

**Action**: periodically call `hcloud ECS ListServersDetails` to query instance status

**State machine**:
```
ACTIVE → STOPPING → SHUTOFF    (shutdown process)
SHUTOFF → STARTING → ACTIVE    (start process)
```

**Pre-execution confirmation gate**: real execution (non `--dry-run`) requires the `--yes` flag; default is refuse; on refusal the script prints the affected instance list and exits with code 1

**Stop conditions**:
- All instances reach `SHUTOFF` → monitoring complete
- Monitor timeout exceeded (default 300 seconds) → mark timeout warning
- CES alarm triggered (if stop_conditions are configured) → terminate early (the wait phase also checks each poll; on trigger, skip the remaining duration and roll back directly)

**Output**: state change timeline (each transition records timestamp + old status + new status)

### Step 5: Wait for duration

**Input**: `duration_seconds` configuration value

**Action**: `sleep` in chunks of the polling interval; each chunk checks instance status and stop conditions (CES alarms); when the duration elapses → proceed to rollback. If a stop condition triggers → interrupt the remaining wait and roll back immediately

**Output**: state records within the duration; on early termination record `waited_seconds` and the triggering condition

**Exception handling**:
- Stop condition triggered (during wait) → end the wait early, `wait.result = "stopped_early"`, enter rollback
- User interrupt (Ctrl+C) → enter rollback immediately

### Step 6: Execute rollback

**Input**: instance ID list

**Action**: call `hcloud ECS BatchStartServers` to start all instances

**Output**: API response + rollback start timestamp

**Exception handling**: API error → record error and continue verification; partial start failure → mark the failed instances

### Step 7: Verify recovery

**Input**: instance ID list + verification timeout (default 300 seconds)

**Action**: poll instance status until all instances are back to `ACTIVE`

**Validation rules**:
- All instances are `ACTIVE` → verification passed
- Timeout without recovery → mark verification failure and output the failed instance list

**Output**: verification result (pass/fail + detailed status)

### Step 8: Generate execution report

**Input**: execution log (timestamps and state records of all steps)

**Action**: call `generate_report.py` to build the Markdown report

**Report content**:
- Experiment overview (name, region, target count, duration)
- Target instance list
- Execution timeline (shutdown time/duration/rollback time/total duration)
- State change records
- Success/failure statistics
- Conclusions and recommendations

**Output**: `execution-report.md` file

## Exception handling overview

| Exception scenario | Handling |
|---|---|
| Instance not ACTIVE | Refuse to execute |
| Shutdown API failure | Rollback with --auto-rollback, otherwise exit |
| Monitor timeout | Mark warning, continue |
| Rollback failure | Mark error, output failed instances |
| User interrupt | Rollback immediately |
| CES alarm triggered | Terminate early, enter rollback |
