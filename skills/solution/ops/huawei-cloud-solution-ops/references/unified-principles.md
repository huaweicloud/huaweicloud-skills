# 跨服务共享原则

## 定位

本文件提供跨服务、跨轮次任务可以共同使用的少量原则。它帮助 Agent 保留目标、区分事实和推断、诚实描述完成程度，但不替 Agent 决定服务、工具、参数或操作次序。

以下场景优先读取本文件：

- 一个用户目标需要多个云服务共同完成；
- 用户会在多轮对话中追加或修改要求；
- 任务包含真实变更、异步等待、失败恢复或业务验收；
- 任务可能被中断，之后需要从 workspace 恢复。

简单、一次性的只读查询不必为了套用本文件而增加额外记录。

## 1. 目标优先于初始方案

- 持续保留用户当前有效目标、关键约束和期望结果。
- 初始服务选择和执行方案只是候选。遇到新要求、工具能力变化、region 差异或 API 不可用时，Agent 可以调整服务、工具、参数和先后关系。
- 如果新信息使旧方案失效，记录变化原因和影响，不要为了维持原计划而偏离用户目标。

## 2. 区分信息来源

重要判断应能区分以下来源：

| 类型 | 含义 | 使用要求 |
| --- | --- | --- |
| 用户声明 | 用户明确给出的目标、约束、授权或事实 | 保留原意；后续明确修改时以新要求为准 |
| Agent 推断 | Agent 根据上下文得到的判断 | 标明为推断；高影响场景应验证或请用户确认 |
| 工具观测 | 工具、API、CLI 或文件读取获得的结果 | 保留必要的查询范围、时间和结果依据 |
| 文档资料 | Skill、本地资料或官方文档描述的通用能力 | 不自动当成当前租户、region 或资源的实时事实 |

对于会改变架构、费用、安全范围或完成结论的信息，可按需记录：

- `source`：信息来自用户、工具、文档或 Agent 推断；
- `observed_at`：观测或确认时间；
- `scope`：适用的账号、region、project、资源或任务范围；
- `evidence`：必要时指向摘要、命令结果或 artifact，而不是复制全部输出。

这些字段是共享语义，不要求每条普通笔记都填写。

## 3. 处理新旧信息冲突

- 用户最新的明确目标或约束，优先于旧方案和旧偏好。
- 相同 `scope` 下，较新的工具观测通常优先于旧快照；但先确认两次查询的范围和过滤条件一致。
- 文档能力描述不能覆盖当前环境的工具观测。
- 两个来源冲突且会显著影响结果时，应明确冲突、补充查询或向用户澄清，不要静默选一个。
- workspace 中的历史观测可能过期；恢复任务时按影响判断是否重新查询。

## 4. 使用共同的完成语义

以下词用于跨服务一致地描述进展，不构成必须逐级经过的状态流程：

| 语义 | 说明 |
| --- | --- |
| `planned` | 已形成方案或执行计划，尚未提交真实操作 |
| `submitted` | 请求已提交，但不代表云侧完成或业务可用 |
| `resource_ready` | 资源达到所需云侧状态，业务路径可能仍未验证 |
| `business_verified` | 已按任务目标验证关键用户路径或验收条件 |
| `partially_succeeded` | 只有部分目标完成；需列明成功、失败和未验证部分 |
| `outcome_unknown` | 缺少可靠终态证据，不能判断成功或失败 |
| `blocked` | 当前缺少必要信息、权限、工具、授权或外部条件 |

API 返回成功、获得 `job_id` 或资源状态正常，都不应自动写成 `business_verified`。Agent 可以根据具体服务补充更合适的阶段描述。

## 5. 重要结论要有依据

- 只声明已经真实发生并获得证据的操作和结果。
- 对“已经上线”“可公网访问”“数据已恢复”等重要结论，记录对应的查询、探测、artifact 或用户验收。
- 证据只保留恢复和复核所需的摘要与位置；大输出遵循 `references/output-and-query.md`。
- 无法取得终态或业务证据时，使用 `outcome_unknown`、`partially_succeeded` 或明确缺口，不编造闭环。

## 6. 安全、授权和失败处理沿用现有权威规则

本文件不复制另一套安全或错误规则。执行时以以下资料为准：

- 认证与上下文：`references/auth-and-context.md`
- 真实变更、授权、凭据和公网边界：`references/runtime-safety-boundaries.md`
- 错误分类、重试和恢复：`references/error-playbook.md`
- 输出收敛和大结果处理：`references/output-and-query.md`
- 默认发现、计划、执行和验证流程：`references/workflow.md`

尤其注意：

- 高影响操作仍需遵守现有确认和安全边界，task 文件不能代替用户授权；
- 未确认幂等性和当前真实状态时，不因“可能失败”而机械重试；
- 凭据和敏感值不进入任务记录、日志或 artifact；
- 共享原则只改善信息连续性，不能把 Skill 变成执行控制器，也不能替 Agent 应对未知情况。
