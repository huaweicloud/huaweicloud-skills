# DWS And Database Diagnostic Method

## 目标

把 DWS、数据库、SQL 性能和资源异常排障拆成“指标 -> 假设 -> 证据 -> 结论”的诊断树。这个 playbook 只吸收诊断方法论，不引入外部执行面，不自动连接数据库，不读取业务数据。

## 适用场景

- 用户说 DWS 慢查询、CPU 高、IO 高、内存压力、SQL 执行慢。
- 用户需要数据库类根因分析报告。
- 用户要区分客户侧配置/SQL 问题和系统侧资源/平台问题。
- 用户只有云侧指标，还没有数据库内部执行计划或日志。

## 总体诊断顺序

1. 先确定时间窗口、集群、节点范围和业务影响，不从单个 Top 值直接定因。
2. 区分全节点、部分节点、单节点，以及节点上的单磁盘/多磁盘分布。
3. 在同一采样窗口关联云侧指标、数据库会话/SQL、OS 进程、告警和业务变更。
4. 每个假设写明支持证据、反证、缺口和下一步；区分“已证实”“高概率”“待验证”“已排除”。
5. 客户侧、系统侧和混合原因都保留。并发与单条重 SQL、数据倾斜与存储异常可以同时存在，不强制二选一。

## CPU 诊断

### 范围优先

- 全部节点同时升高：优先检查并发、批任务窗口、全局 SQL 和规格容量。
- 部分节点升高：优先检查数据/计算分布、节点角色、SQL 落点和局部进程。
- 单节点升高：同时核对该节点的 SQL、OS 进程、故障/维护事件，不能只凭集群平均值解释。

### 采样语义

- `ctime` 表示采样快照时间，不是 SQL 开始时间；只有同时有 `duration_ms` 时，才能估算 `start_time = ctime - duration_ms`。
- `cpu_rate` 已是实例级百分比时直接按其语义使用，不再除以核数或重新归一化。
- 数据库用户与 OS 进程用户是两个身份域，不能用同名/不同名直接归责。
- `gaussdb-dn` / `gaussdb-cn` 主进程的 CPU 需要继续归到同窗口 SQL/工作负载；`gaussdb` fenced UDF 进程可能承载真实业务计算，不能因名称不同而过滤。

只有并发、SQL、进程与业务时间窗能够相互解释时才提高置信度。禁止用固定节点比例、固定单 SQL 占比、Top N 截断或用户名直接判定责任。

## 内存诊断

按“节点范围 → CN/DN 角色 → dynamic/process/memory pool/session”逐层定位：

- CN 压力：检查连接偏斜、无法下推、解析/计划和会话集中。
- DN 压力：检查数据/计算倾斜、sort/hash spill 和节点局部负载。
- dynamic memory 上升：关联同窗口 SQL 和 `work_mem` 使用假设。
- process memory 上升：关联连接数、进程生命周期和可能的进程泄漏。

当前活跃用户/会话只用于解释当前贡献；idle session 持有大量内存应作为长事务、连接池或泄漏线索单列，不能混入 active 排名。内存持续单调增长且没有对应工作负载变化时，只能标记“疑似泄漏”，还需要多窗口趋势、会话/进程和版本事件证据。

不要使用固定百分比、固定节点偏差、固定长事务时长自动定因，也不要自动修改 `work_mem` 或 kill session。

## I/O 诊断

先把四类信号分开：

- throughput：单位时间读写数据量；
- IOPS：单位时间 I/O 操作次数；
- latency/await：请求完成等待；
- queue/iowait：排队和 CPU 等待存储的程度。

判断时使用当前资源规格和实际存储能力：

- throughput/IOPS 接近当前规格上限并伴随延迟/队列升高，才支持“容量饱和”。
- throughput/IOPS 不高但延迟或队列持续升高，更像路径、磁盘或存储侧异常线索，不能用“业务流量大”解释。
- 单节点单盘、单节点多盘、多节点同盘位和全节点同时异常，对应不同假设；系统盘与数据盘也要分开。

SQL 关联必须使用高 I/O 的同一采样窗口。若 per-SQL `io_read` / `io_write` 为 0 或缺失，CPU Top 只能作为调查线索，不能写成“I/O Top SQL”。节点间偏差只能说明可能存在倾斜；要证明表分布、spill 或全表扫描，还需要执行计划、wait event、表/分布和 I/O 证据。

不要复制固定 SSD/HDD 能力、固定延迟/偏差阈值、固定 Top N，也不要用 SQL 文本正则直接定因。

## 标准报告结构

- 现象摘要：用户影响、时间窗口、对象范围。
- 证据摘要：云侧指标、数据库侧指标、日志或 SQL 证据。
- 根因分类：客户侧、系统侧、混合、证据不足。
- 假设列表：每条假设对应证据和状态。
- 修复建议：P0/P1/P2，先低风险读写分离、限流、索引/统计信息、SQL 改写，再考虑规格和架构。
- 验收方式：指标恢复、慢 SQL 降低、错误率下降、业务探测通过。
- 置信度和缺口：说明结论基于哪些同窗口证据，以及哪些数据缺失会改变判断。

## 安全边界

- 不默认连接数据库或执行 SQL。
- 不输出表中业务数据、用户数据、SQL 参数里的隐私字段或连接串密码。
- 不自动执行 `VACUUM`、`ANALYZE`、建索引、kill session、扩容、重启、升级或参数修改。
- SQL 静态检查可以输出规则命中和建议，但不能替代真实执行计划和业务压测。
- 若只有云侧指标，没有数据库内部证据，不要把结论写成“SQL 一定有问题”或“平台一定异常”。
