# Resource Idempotency Reconcile Playbook

## 目标

把任务中的逻辑角色和用户给出的资源名共同作为幂等线索，避免失败重试时创建一批名称相同或名称不同、但用途重复的资源。

## 适用场景

- 用户要求创建或修复命名资源
- 上一次执行可能中断、超时或部分完成
- 查询发现同名 ECS、EIP、ELB、安全组、RDS、OBS 桶等资源
- 创建、删除、替换或绑定操作仍在进行、结果未知，或恢复后无法确认上次动作结果

## 默认流程

### 1. 先确定逻辑角色和预期数量

逻辑角色表示资源在当前任务目标中的用途，例如“个人站点主机”“站点公网入口”“生产数据库”。即使名称不同，只要候选资源承担同一用途，也属于同一逻辑角色。先从用户目标和已确认方案确定预期数量，再查询当前资源和待决操作。

### 2. 查询资源和待决动作

创建或替换前先调用对应 `List*` / `Show*`，并检查 task 记录、job 或 action receipt 中是否存在待决 create/delete：

- ECS: `ListServers`
- EIP: `ListPublicips`
- ELB: `ListLoadBalancers`
- Security Group: `ListSecurityGroups`
- RDS: `ListInstances`
- VPC/Subnet: `ListVpcs` / `ListSubnets`

查询结果必须记录资源 ID、名称、状态、创建时间、region/project、关键绑定关系，以及仍未确认终态的 job/动作。待决或结果未知时，优先通过 job、列表和详情回读；在状态收敛前不要提交第二个同角色副作用操作。

### 3. 选择 canonical resource

若没有同名或同角色候选、没有待决动作，并且实时查询仍支持原方案，才继续创建。

若只有一个同名或同角色候选：

- 规格、状态、网络接近目标：修复它
- 明显不属于目标或状态不可恢复：说明原因，除非用户授权删除，否则不要直接释放

若有多个同名或同角色候选，不要继续创建新资源。选择 canonical resource 的顺序：

1. 状态健康或最接近健康终态
2. 规格、镜像、端口、VPC、子网最接近用户要求
3. 已绑定更多目标依赖，例如 EIP、ELB member、磁盘
4. 创建时间最新

其他候选资源只做只读记录，不要自动删除。

### 4. 修复而不是重建

对 canonical resource 执行缺口修复：

- 缺安全组规则：补规则
- 缺 EIP 绑定：绑定 EIP
- 缺 listener/member：补 ELB 依赖
- ECS `ACTIVE` 但应用不可达：优先排查 cloud-init、服务端口、安全组和协议探测

ECS 登录或应用失败不直接证明实例需要重建。根据现场可用证据检查创建 job/实例状态、EIP 与网络、安全组、凭据/登录方式、cloud-init、服务和日志；Agent 可以自主决定检查深度与次序。

### 5. 受控替换

- 默认是一换一：先确认删除终态，并通过列表或详情确认旧资源已不存在，再创建替代资源。
- 只有用户明确批准迁移、高可用或其他临时并存方案时，才允许在受控时间窗内超过预期数量。
- 原确认已经披露一次有界替换，且数量、费用、安全暴露和破坏范围不变时，可继续该次替换；连续替换、并行保留、扩大费用或暴露面必须重新说明并确认。
- 替代资源创建后，把它设为 canonical resource，更新 task 记录并验证预期数量；不要让旧候选静默失联。

### 6. 最终输出

最终必须说明：

- 选定的 canonical resource ID
- 发现了多少同名资源
- 同一逻辑角色的预期数量、实际候选数和待决动作
- 已修复哪些差异
- 哪些重复资源需要人工清理

## 不要做的事

- 不要在同名资源已存在时继续创建同名资源。
- 不要通过改名绕过逻辑角色幂等，也不要在待决 create/delete 或结果未知时继续创建。
- 不要为了幂等直接删除旧资源，除非用户明确授权。
- 不要把“可重建”理解为连续替换或同角色资源可以无限并存。
- 不要只按名称模糊匹配后宣布成功，必须核对状态和关键配置。
