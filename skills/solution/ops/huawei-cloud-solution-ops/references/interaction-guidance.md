# 任务状态与用户表达指南

本指南帮助 Agent 从同一份 task 记忆中按需组织用户可理解的状态。它统一的是信息来源、完成口径
和表达维度，不是固定回复模板、五个必须落盘的文件或不可偏离的状态机。Agent 可以根据任务、用户
关注点和现场变化选择所需视图，调整服务、工具、参数、顺序和表达形式。

## 1. 信息基础和边界

形成状态表达前，优先使用以下信息：

1. 用户当前有效的目标、约束、授权和最新修改；
2. task 入口中的当前方案、重要变化、待决操作、证据引用和未知项；
3. 已核验的 artifact、工具结果和云侧实时事实；
4. Skill、playbook 和官方资料提供的方法与知识。

task 文件是可恢复的工作记忆，不是实时云状态、可信授权账本或不可篡改审计记录。恢复任务、继续
副作用操作或形成最终完成结论前，Agent 应自主判断哪些易变事实需要重新查询。用户改变目标后，
旧证据可能仍然真实，但未必继续支持新目标，不能直接沿用旧完成结论。

## 2. 五种按需视图

| 视图 | 适用时机 | 最少表达内容 | 避免的问题 |
| --- | --- | --- | --- |
| Goal | 对齐目标、收到重要变化、恢复任务 | 当前目标、关键约束、授权边界 | 重复全部历史或继续使用失效目标 |
| Option | 需要用户选择或方案发生变化 | 当前候选、主要权衡、关键未知、需要决定的事项 | 把候选写成唯一方案或假装未知已经解决 |
| Progress | 多阶段任务、等待、受阻或用户询问进度 | 已完成阶段、当前状态、阻塞、下一步 | 按工具调用逐条播报或用动作数量冒充进展 |
| Recovery | 失败、部分成功、pending/unknown 或恢复对话 | 已知事实、未知副作用、失效证据、安全继续条件 | 原样重试副作用、掩盖结果未知或重新猜测状态 |
| Completion | 阶段交付、部分完成或最终交付 | 完成条件、支持证据、未完成项、遗留费用和责任 | 把 API 受理、资源存在或模型推测写成目标完成 |

简单一次性任务通常只需要一个紧凑结论。复杂任务也不要求每轮同时输出五种视图；只选择能帮助
用户理解、决策或安全继续的部分。

## 3. Goal：当前真正目标

Goal 视图用于回答“现在要达成什么”，应优先表达：

- 当前目标和用户真正关心的结果；
- 会改变方案的关键约束；
- 当前授权边界，例如仅规划、只读分析或已确认的具体变更范围；
- 最近用户修改对旧方案和旧证据的影响。

同一 task 中用户追加操作或改变要求时，更新现有目标，不为每轮对话创建新任务。目标已经改变时，
不要为了延续原计划而保留失效假设；也不要把单次授权扩大为后续高影响动作的长期授权。

## 4. Option：候选和选择

Option 视图用于回答“有哪些选择，为什么当前倾向某个方向”。按需说明：

- 一个或多个可行候选及其适用前提；
- 成本、可用性、安全、运维、可逆性和迁移影响中的主要权衡；
- 仍需要实时查询、实验或用户补充的未知；
- 当前可以由 Agent 自主决定的技术细节，以及必须由用户决定的影响边界。

目标指南和 playbook 只提供候选信息。Agent 可以采用未列出的合理方案，也可以在新事实出现后
改变选择。不要为了保持表格或模板完整而编造精确价格、库存、配额或可用性。

## 5. Progress：有意义的进展

Progress 视图用于回答“进行到哪里”，建议围绕用户目标而不是工具轨迹组织：

- 已经完成的阶段及其关键依据；
- 当前正在处理的目标层问题；
- 阻塞、等待或需要用户决定的事项；
- 下一步及其前置条件；
- 若有必要，说明对预算、时间、可用性或现有资源的影响。

普通只读调用、重复查询和中间思考不需要逐条播报。异步 job 已提交只能写成“已受理/等待收敛”，
不能写成资源或业务目标已经完成。

## 6. Recovery：失败和结果未知

Recovery 视图用于回答“发生了什么，如何安全继续”。至少区分：

- 已确认成功、已确认失败、部分成功和结果未知；
- 最近一次可靠证据的来源、作用域和时间；
- 是否存在待决 job、可能已开始的副作用或 canonical 资源候选；
- 哪些旧证据因目标变化、超时或外部状态变化而失效；
- 安全继续前需要回读、等待、补充证据或重新确认的条件。

结果未知时，优先查询真实状态并收敛现有动作。不能把重新提交创建、删除、替换或付费调用当作
普通重试。需要改变资源数量、费用、公网暴露、数据或破坏范围时，向用户说明新增影响并重新确认。
具体调查方法和调用顺序仍由 Agent 根据现场决定。

## 7. Completion：完成、部分完成和遗留事项

Completion 视图用于回答“真正完成了什么”。一个结论应能关联：

- 当前仍有效的目标和完成条件；
- 支持每项关键结论的证据或 artifact；
- 证据的状态、来源、观测时间和作用域中与判断有关的部分；
- 未验证、失败、结果未知或用户接受的剩余缺口；
- 临时资源、持续费用、安全暴露、外部依赖和用户后续责任。

完成状态不要求使用固定枚举，但语义必须明确：全部完成、部分完成、阻塞、等待收敛或结果未知
不能混为一谈。资源创建成功通常只证明资源就绪；网站、迁移、治理或故障恢复还需要与用户目标
对应的业务证据。用户明确接受剩余缺口时，可以说明“在约定范围内完成”，同时保留缺口内容。

## 8. 证据的轻量表达

task 或 artifact 中的证据只需要保留后续判断会使用的信息。可按需记录：

- 它支持哪个结论或完成条件；
- 当前状态，例如已核验、部分、失败、过期或未知；
- 来源和 artifact 相对路径；
- 观测时间和适用作用域；
- 重要限制或需要重查的条件。

字段名、Markdown 表格或 JSON 形式均可调整，不要求固定 `EvidenceRecord`。未经处理的大输出继续
保存在独立 artifact；用户回复只引用必要摘要和路径，不复制完整响应或秘密。

## 9. 从 task 记忆生成表达

需要对齐、汇报、恢复或交付时，Agent 可以采用以下轻量方法：

1. 读取当前 task 入口和必要的最近进展；
2. 合并用户本轮变化，识别已经失效的目标、方案和证据；
3. 根据本轮沟通目的选择一到数个视图；
4. 把事实、推断、未知和待确认事项分开；
5. 重要状态发生变化时先更新 task 记忆，再给出紧凑的用户表达；
6. 继续高影响动作前重新核验易变事实和授权边界。

该方法不要求固定调用顺序。紧急故障、安全事件或用户明确要求直接行动时，Agent 可以先处理最
关键的风险，再补齐必要记录和表达，但不能省略真实授权、结果未知和副作用边界。

## 10. 避免机械化和过度记录

- 不在每轮重复完整目标、方案和历史；只表达本轮需要用户理解或决定的变化。
- 不为了填满模板创建空字段、空文件或没有后续用途的证据记录。
- 不把 Agent 的完整思考、普通聊天或每次工具调用写入 task。
- 不把“遵循指南”本身当作任务进展；进展必须对应用户目标。
- 不因指南没有覆盖现场情况而拒绝合理替代方案。
- 不在 task、artifact 或回复中保存 AK/SK、私钥、完整 token 或其他秘密。

本指南与 `references/task-workspace-guide.md`、`references/unified-principles.md` 和具体场景
playbook 配合使用。任务记忆负责连续性，统一原则负责事实和完成语义，本指南负责面向用户的按需
投影；三者都不替代 Agent 判断和可信运行时的权限、安全与授权控制。
